### 1.2 智能体标准化接入（任何智能体都能接入）

核心思路：**把"通道修复"从手工贴规则升级为"接入协议 + 生成器脚本"**，新机器/新智能体走同一条路。

**接入四件套：**

1. **工作台根 AGENTS.md（路由型，新增）**——落地 P0-2b。只写三层：① 各层家规在哪（工作台 BOOTSTRAP → 项目 AGENTS.md → rules）；② 按场景读哪份（路由表，从 BOOTSTRAP 的"开工先读什么"提炼）；③ 红线索引（编码/落盘/备份四条）。不重复家规本体，控制在 2KB 内。受益：所有会读根目录 AGENTS.md 的宿主（千问/豆包/CodeBuddy）。
2. **接入名册升级**——`07-协作/agents/` 名册每人加三字段：`channel`（该宿主的注入通道类型）、`status`（未接/已接/实测通过）、`last_verified`。接入状态从"感觉"变成台账。
3. **注入件生成器（新脚本）**——`90-运行脚本/gen-agent-bootstrap.mjs`：
   - 探测本机宿主（`~/.workbuddy`、`~/.codebuddy` 等存在性 + 可执行性）；
   - 对每个已装宿主生成其专属注入件：WorkBuddy→MEMORY.md 三规则（纯追加、先备份、CRLF 适配）；豆包/CodeBuddy→project-rules 等价内容 + mem://preference 文案；千问→确认根 AGENTS.md 可读；
   - `--dry` 先列出将写哪些文件、追加什么，人工确认再落盘。
   - **意义**：旧机 P0-1/P0-2 的手工动作变成一条命令，任何新机器开机跑一次即完成全部宿主接线——这就是"任何智能体都能接入"的工程化答案。
4. **零提示实测 + 口令退役**——接线后按附录口令 v2 做 ≥3 轮零提示实测（WorkBuddy 装好后补测），通过的宿主在名册标"实测通过"；全部通过后口令退役。

**本机现实**：WorkBuddy 主程序未装（0.2），三规则本机无处落地。界面改造任务（1.5）若由 WorkBuddy 执行，需先在装机侧进行，或由我代改、它复审——待拍板 #3。

### 1.3 项目装配闭环（建项→装配→运行→跟版）

1. **装配清单显式化**：建项时面板在项目根写 `.axhub/assembly.json`——模板版本戳（_project-template 的 git hash）、框架类型、继承的上游文档清单、已应用补丁清单、装载技能子集。装配从"拷了就完"变成"可审计的清单"。
2. **模板版本戳**：随 assembly.json 落 `template-hash`。这是"存量项目跟版"的前提（你跟版的要求没有它做不了 diff 基线）。
3. **跟版脚本（新）**：`90-运行脚本/sync-template-to-projects.mjs`——按版本戳找出落后项目，输出三类 diff 清单（家规/规则/hook 配置），逐项人工确认后应用，先备份。本轮工程包 P0 修正（CLAUDE 硬指令、§4.3 口径、development 双 settings）走此通道下发到存量 4 个项目（AI漫剧工作台、Shadcn 后台管理仪表盘、漫剧工作台、测试）。
4. **清理伪配置**：workbench.config.json 的 `template.allowedList` 与实际不符（列了 vite.config.mjs，实际是 vite.config.ts；compaction-recovery.md 不在模板根）——server.mjs 建项实为整体拷贝，allowedList 疑似废弃，核实后删除或改准。
