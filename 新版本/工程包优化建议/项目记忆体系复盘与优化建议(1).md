二、问题诊断：现在有什么痛点

🔴 P0 — 直接影响效率

问题 1：project-memory.md 越长，新会话加载成本越高

现状：150+ 行，约 12KB，新会话全部读进来占 1/30 的上下文

后果：还没开始干活，记忆文件就吃掉不少预算

根因：所有信息平铺在一个文件里，没有分层

问题 2：模块快照节是空的，跨智能体接力断档

现状：第五节设计了模板，但 16 轮迭代下来一条快照都没写

后果：WorkBuddy / CodeBuddy 接手时，不知道上一位做到哪了、哪些坑踩过了

根因：没有"闭环即写快照"的强制动作，全靠自觉

🟡 P1 — 查找效率低

问题 3：踩坑记录没有按模块分类，找坑要翻半天

现状：40+ 条按时间顺序排，每条开头只有日期

后果：修"维度计算"的 bug 时，要从第 1 条翻到第 40 条才能找到相关坑

根因：记录时没有打模块标签

问题 4：没有"快速索引"，新会话不知道先看哪

现状：文件开头是项目画像，要往下翻 100 行才看到最近 3 轮改了什么

后果：新进来的 agent 要读完整个文件才能进入状态

根因：没有 L1 快速入口层

🟢 P2 — 机制不完整

问题 5：运行态留痕是空的

现状：hook 未生效、装配超标这两类事件设计了记录格式，但从来没记过

后果：不知道 hook 到底生效没有，不知道哪次装配超了标

根因：触发条件不够明确，全靠"记得就写"

问题 6：bug 修复时没有标准加载流程

现状：修 bug 时直接读代码，不会先去 project-memory 找历史坑

后果：同一个坑踩两次（dev server 空 transform 已经踩了两次）

根因：没有"修 bug 先查记忆"的强制步骤

三、优化建议：怎么改

3.1 分层加载机制（核心改动）

把 project-memory.md 拆成三层，按需加载：

层级	内容	大小	加载时机

L1 快速索引	项目画像速览 + 最近 3 轮基线变更 + 高频坑 Top5 + 关键路径	\~2KB	新会话必读，约 1 屏

L2 完整记忆	全部踩坑记录 + 全部基线变更 + 模块快照	\~12KB	按模块 Grep 加载，不全文读

L3 归档	超过 10 轮的历史基线变更 + 结项状态	\~5KB	几乎不读，查历史才翻

落地方式：在 project-memory.md 最前面加一个「〇、快速索引」区块，后面的内容按模块分组。 → 要建目录

3.2 踩坑记录加模块标签

每条记录开头加 `\\\\\\\[模块:xxx]`：

```
\\\\\\\* 2026-11-04 | \\\\\\\[维度计算] \\\\\\\[风险] | 删枚举值只删一层 | ...
\\\\\\\* 2026-11-05 | \\\\\\\[审批配置] \\\\\\\[修复] | 节点选中被冒泡清掉 | ...
\\\\\\\* 2026-11-05 | \\\\\\\[通用] \\\\\\\[风险] | dev server 空 transform | ...
```

好处：修某个模块的 bug 时，直接 `Grep "\\\\\\\[维度计算]" project-memory.md` 就找到所有相关坑，不用翻全文。

3.3 模块快照强制闭环

每完成一个模块，必须写一条快照（≤300 字），格式：

```markdown
## 模块快照：维度计算（web）→ 要定义格式
- 状态：已完成
- 职责：配置指标的聚合维度与时间粒度，生成预览图表
- 对外接口：输入 factTable/metric/dims/grain → 输出聚合结果 + 图表配置
- 依赖模块：上游 data.ts（表结构）、下游 dim-calc-preview.tsx（渲染）
- 关键决策：①算法收敛为 2 类（SQL开发/维度计算）；②按小时粒度自动检测；③时间字段未选时禁用粒度
- 未完成 TODO：无
```

触发条件：用户说"这个模块改完了"或"下一个模块"时，立刻写。

3.4 bug 修复标准加载流程

修任何 bug 前，按顺序做这四步：

Grep 模块名：`Grep "\\\\\\\[模块名]" project-memory.md` — 看有没有历史坑

读模块快照：找到对应模块的快照，了解当前状态

读最近 3 轮基线变更：看最近改了什么，可能引入了问题

才开始读代码：以上三步做完，再去定位 bug

为什么：同一个坑踩两次的成本，远大于读 3KB 记忆的成本。dev server 空 transform 已经踩了两次，加了这一步就不会有第三次。

3.5 快速索引区块（放在文件最前面）

```markdown
## 〇、快速索引（新会话必读，约 2KB）

### 当前状态
- 进行中：无（本轮刚收尾）
- 最近完成：审批配置画布 + 四份文档同步（PRD v2.3 / SRS v1.5 / HLD v1.6 / LLD v1.5）

### 最近 3 轮改了什么
- 第十六轮（11-05）：原型界面注释全量清空，106 处，基线版本不变
- 第十五轮（11-05）：审批配置四份基线文档同步，全部升版
- 第十四轮（11-05）：审批配置三条规则落地，J10 拍板正式推翻

### 高频坑 Top 5
1. dev server 空 transform → 改注释触发重新加载，别重启
2. 删枚举值要盘五层（类型/数据/演示/导入模板/设计说明）
3. 设计说明卡片要和代码、文档三者同步改
4. 落盘用 Python io.open utf-8，不用 PowerShell Set-Content
5. 页面下线要删全链路 12 处，只删路由不够

### 关键路径速查
- 工程根：src/prototypes/indicator-platform/
- 预览地址：http://localhost:51720/prototypes/indicator-platform/#page=<page>
- tsc 基线：29 条既有报错，npx tsc --noEmit -p tsconfig.typecheck.json
- 测试记录：08-文档/工作台Agent文档/上下文测试记录/
```

四、后期修 bug 怎么加载记忆（操作手册）

场景 1：修一个已知模块的 bug（比如"维度计算的图表预览不对"）

```
第一步：Grep 找历史坑
  Grep "\\\\\\\[维度计算]" project-memory.md
  → 找到 8 条相关坑，看有没有类似的

第二步：读模块快照
  Read project-memory.md 的「模块快照：维度计算」节
  → 了解这个模块的当前状态和关键决策

第三步：读最近 3 轮基线变更
  Read project-memory.md 第四节最后 3 行
  → 看最近有没有改这个模块的代码

第四步：才开始读代码
  Read dim-calc.ts / pages-indicator-rule.tsx
```

场景 2：接手一个新模块（比如"WorkBuddy 改了指标目录，我要继续改"）

```
第一步：Grep 找模块相关记录
  Grep "\\\\\\\[指标目录]" project-memory.md
  → 找到所有历史改动和踩坑

第二步：读模块快照（如果有的话）
  → 了解上一位做到哪了

第三步：读基线变更登记里相关的轮次
  → 了解这个模块的演进历史

第四步：读代码确认现状
  → 不要凭记忆，实际读一遍代码
```

场景 3：上下文压缩后恢复

```
第一步：判断是不是压缩了
  想不起上一轮读过什么文件？→压缩之前要保存，压缩完按需读
  早前细节只剩"做了什么"没有"看到了什么"？
  → 任一出现，当作已压缩

第二步：读快速索引
  Read project-memory.md 第 1-30 行（〇、快速索引节）
  → 恢复当前状态和最近改动

第三步：读当前模块的快照和相关坑
  Grep 当前模块名 → 读快照
  → 恢复模块上下文

第四步：补当前进度的快照
  把正在做的事、做到哪了，补进模块快照
  → 防止下次压缩再丢
```
