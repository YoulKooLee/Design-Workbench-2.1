## 二、压缩机制详解：到底什么会丢、什么会留

### 2.1 压缩后一定会保留的

| 类别 | 内容 | 来源 |
|------|------|------|
| 系统提示 | project-rules、用户偏好、用户画像、多环境配置、当前日期/位置/设备 | 框架注入，每次会话都有 |
| 任务摘要 | TASK_FOCUS / TASK_NARRATIVE / KEY_FACTS_AND_IDS / ARTIFACTS | 对话压缩时自动生成的 summary |
| 任务列表 | 所有 pending/completed 的 task 状态 | 框架维护 |

### 2.2 压缩后一定会丢失的（重点！）

**第一类：工具调用的详细结果正文**

举个具体例子：
- 你让我"读 dim-calc.ts 看看 normGrain 函数"
- 我调用了 Read 工具，读到了完整的代码（比如 200 行）
- 压缩后，上下文里只剩一句话："我读过 dim-calc.ts"
- **代码的具体内容全没了**——normGrain 函数长什么样、参数是什么、返回什么，全忘了

**第二类：中间步骤的推理过程**

什么叫"中间步骤的推理过程"？举个例子：

假设你让我修"饼图颜色不对"这个 bug：
1. 我先读了 dim-calc.ts，发现了 planPieSlices 函数
2. 然后我读了 data.ts，找到了 7 个色板
3. 然后我对比了两个文件，发现色板有 7 个但维度有 8 个
4. 然后我得出结论：第 8 个维度的颜色是 undefined
5. 然后我写了修复代码

**压缩后，第 1-4 步的推理过程全没了**。上下文里只剩：
- "修了饼图颜色 bug"
- 最终改了哪几个文件

但中间的推理链条——为什么怀疑是 planPieSlices？为什么要去 data.ts 找色板？怎么对比出来的？——**全丢了**。

这就是为什么压缩后容易犯同样的错误：上次的推理过程没了，下次遇到类似问题，又得从头推一遍。

**第三类：读过的文件的具体内容**

- 读了 40 条踩坑记录，压缩后只剩"我读过 project-memory.md"
- 读了 dim-calc.ts 的 200 行代码，压缩后只剩"我读过 dim-calc.ts"
- 读了审批配置页的 500 行 JSX，压缩后只剩"我写过审批配置页"

**一句话总结：压缩保留的是"做了什么动作"，丢掉的是"看到了什么内容"和"怎么推理的"。**

### 2.3 压缩后第一件事做什么？

**说实话：没有强制机制。**

现在的状态是：
- 压缩发生时，我只会拿到新的 summary（TASK_FOCUS 等），不会自动收到"你被压缩了"的通知
- 我也不会每次压缩后都去读 project-memory.md——全靠"感觉不对了"才会想起来去读
- 如果我没感觉出来被压缩了，就会直接凭记忆继续干活，可能会基于错误的上下文做决策

**怎么解决？**

在 AGENTS.md 最前面写一句**强制触发条件**：
> "读到本行时，必须先读 project-memory.md 前 30 行再动手"

这样只要我读了 AGENTS.md，就会触发这个动作。因为 AGENTS.md 是每次会话都注入的，所以相当于"每次新会话/压缩后都自动触发读记忆"。

## 三、问题诊断：现在有什么痛点

### 🔴 P0 — 直接影响效率和正确性

**问题 1：多智能体同时写 project-memory.md，写入竞争（新发现！）**

- 现状：豆包、WorkBuddy、CodeBuddy 都在改同一个 project-memory.md
- 后果：A 读了文件，B 改了，A 写回去就把 B 的改动覆盖了
- 已验证：project-memory.md 第八十七条踩坑记录明确写了——"第十四轮的 Edit 误吞了第十二轮整行，还把第十三与十四轮粘成一行"
- **之前维度计算频繁出 bug，很可能就是这个原因**：WorkBuddy 改了代码和记忆，豆包基于旧版记忆继续改，两边冲突了

**问题 2：模块快照节是空的，跨智能体接力断档**

- 现状：第五节设计了模板，但 16 轮迭代下来一条快照都没写
- 后果：WorkBuddy / CodeBuddy 接手时，不知道上一位做到哪了、哪些坑踩过了
- 根因：没有"闭环即写快照"的强制动作，全靠自觉

### 🟡 P1 — 查找效率低

**问题 3：project-memory.md 越长，新会话加载成本越高**

- 现状：150+ 行，约 12KB，新会话全部读进来占 1/30 的上下文
- 后果：还没开始干活，记忆文件就吃掉不少预算
- 根因：所有信息平铺在一个文件里，没有分层

**问题 4：踩坑记录没有按模块分类，找坑要翻半天**

- 现状：40+ 条按时间顺序排，每条开头只有日期
- 后果：修"维度计算"的 bug 时，要从第 1 条翻到第 40 条才能找到相关坑
- 根因：记录时没有打模块标签

**问题 5：没有"快速索引"，新会话不知道先看哪**

- 现状：文件开头是项目画像，要往下翻 100 行才看到最近 3 轮改了什么
- 后果：新进来的 agent 要读完整个文件才能进入状态
- 根因：没有 L1 快速入口层

### 🟢 P2 — 机制不完整

**问题 6：运行态留痕是空的**

- 现状：hook 未生效、装配超标这两类事件设计了记录格式，但从来没记过
- 后果：不知道 hook 到底生效没有，不知道哪次装配超了标
- 根因：触发条件不够明确，全靠"记得就写"

**问题 7：bug 修复时没有标准加载流程**

- 现状：修 bug 时直接读代码，不会先去 project-memory 找历史坑
- 后果：同一个坑踩两次（dev server 空 transform 已经踩了两次）
- 根因：没有"修 bug 先查记忆"的强制步骤

## 四、优化建议：怎么改

### 4.1 分层加载机制（核心改动）

把 project-memory.md 拆成三层，按需加载：

| 层级 | 内容 | 大小 | 加载时机 |
|------|------|------|----------|
| **L1 快速索引** | 项目画像速览 + 最近 3 轮基线变更 + 高频坑 Top5 + 关键路径 | ~2KB | 新会话必读，约 1 屏 |
| **L2 完整记忆** | 全部踩坑记录 + 全部基线变更 + 模块快照 | ~12KB | 按模块 Grep 加载，不全文读 |
| **L3 归档** | 超过 10 轮的历史基线变更 + 结项状态 | ~5KB | 几乎不读，查历史才翻 |

**落地方式**：在 project-memory.md 最前面加一个「〇、快速索引」区块，后面的内容按模块分组。

### 4.2 多智能体写入冲突解决方案（P0 级，最优先）

**方案一：按智能体分文件（推荐）**

```
project-memory/
├── README.md          # 索引 + 快速索引（共享，所有人只读）
├── doubao.md          # 豆包写自己的踩坑和基线
├── workbuddy.md       # WorkBuddy 写自己的
├── codebuddy.md       # CodeBuddy 写自己的
└── deepseek.md        # DeepSeek 写自己的
```

- 每个智能体只写自己的文件，**绝对不会互相覆盖**
- 快速索引在 README.md 里，所有人都只读不写
- 读的时候，先读 README.md，再按需读各智能体的文件

**方案二：追加模式，不要整文件重写**

如果还是用一个文件，那写的时候**只在末尾追加新行**，不要读全文再写回去。

- 用 Python 的 `open(..., 'a', encoding='utf-8')` 追加模式
- 这样不会覆盖别人写的内容
- 缺点：格式可能乱（比如表格中间插了一行），但至少不会丢数据

**方案三：写之前先读一次，确认没被改过**

```python
# 写之前先读一次最新内容
with open('project-memory.md', 'r', encoding='utf-8') as f:
    latest = f.read()

# 如果和我之前读到的不一样，说明别人改了
# 这时候不要直接写回去，要先合并
```

这个方案需要每次都读一次，效率低，但能避免覆盖。

### 4.3 踩坑记录加模块标签

每条记录开头加 `[模块:xxx]`：

```
* 2026-11-04 | [维度计算] [风险] | 删枚举值只删一层 | ...
* 2026-11-05 | [审批配置] [修复] | 节点选中被冒泡清掉 | ...
* 2026-11-05 | [通用] [风险] | dev server 空 transform | ...
```

**好处**：修某个模块的 bug 时，直接 `Grep "[维度计算]" project-memory.md` 就找到所有相关坑，不用翻全文。

### 4.4 模块快照强制闭环

每完成一个模块，必须写一条快照（≤300 字），格式：

```markdown
## 模块快照：维度计算（web）
- 状态：已完成
- 职责：配置指标的聚合维度与时间粒度，生成预览图表
- 对外接口：输入 factTable/metric/dims/grain → 输出聚合结果 + 图表配置
- 依赖模块：上游 data.ts（表结构）、下游 dim-calc-preview.tsx（渲染）
- 关键决策：①算法收敛为 2 类（SQL开发/维度计算）；②按小时粒度自动检测；③时间字段未选时禁用粒度
- 未完成 TODO：无
```

**触发条件**：用户说"这个模块改完了"或"下一个模块"时，立刻写。

### 4.5 bug 修复标准加载流程

修任何 bug 前，按顺序做这四步：

1. **Grep 模块名**：`Grep "[模块名]" project-memory.md` — 看有没有历史坑
2. **读模块快照**：找到对应模块的快照，了解当前状态
3. **读最近 3 轮基线变更**：看最近改了什么，可能引入了问题
4. **才开始读代码**：以上三步做完，再去定位 bug

**为什么**：同一个坑踩两次的成本，远大于读 3KB 记忆的成本。dev server 空 transform 已经踩了两次，加了这一步就不会有第三次。

### 4.7 AGENTS.md 瘦身与常驻上下文分层（理论来源：58沈剑《上下文是稀缺资源》）

**核心原则**：找到信号最强的最小token集合——不是"够用就行"，而是"能少一个是一个"。无关信息不是无害的冗余，是有害的稀释。

**判断标准**：删掉它，每一轮都会出错吗？

#### 高频项 vs 低频项

**越往后越高频的（每轮都在做，必须常驻）：**
- 画/改原型页面
- 写/改设计说明卡片
- 同步设计文档（PRD/SRS/HLD/LLD）
- 改完验证（tsc + 浏览器抽查）
- 三者同步检查

**只有开场才用一次的（按需加载，不用每轮背着）：**
- 项目背景介绍
- 完整需求清单
- 建设内容全貌
- 架构决策的来龙去脉

#### 常驻层最终长什么样（~2KB）

```markdown
## 项目定位
指标管理平台——数字孪生底座的数据中台管理端，React+Vite+Tailwind 原型。

## 高频操作规范（每轮都在做）
1. 改原型：文案大白话，禁止技术术语；技术细节进右侧设计说明卡片
2. 改一处 = 改三处：代码 + 设计说明卡片 + 设计文档，同步改
3. 落盘用 Python io.open utf-8 newline=""，不用 PowerShell Set-Content

## 验证（改完必做）
1. tsc 基线：29 条既有报错，npx tsc --noEmit -p tsconfig.typecheck.json
2. 浏览器抽查：改了哪个页面，开预览确认那个页面
3. 三者同步：代码、卡片、文档，三者一致才算完

## 关键路径
- 工程根：src/prototypes/indicator-platform/
- 预览：http://localhost:51720/prototypes/indicator-platform/#page=<page>
- 记忆文件：project-memory.md（按需读取）
```

#### 按需层放什么

| 文件 | 什么时候读 |
|------|------------|
| 完整需求清单 / 建设内容 | 开场捋清楚再动手时读 |
| 项目背景 / 架构决策历史 | 只有回顾时才读 |
| 原型输出规范细则（表格列宽、view meta 等） | 遇到具体问题再查 |
| project-memory.md 完整记忆 | 修 bug、接手模块时 Grep 加载 |

**一句话修正**：不是"每一步都在守的规矩"才常驻，是"每轮都在做的操作"的规范才常驻。改原型、写卡片、同步文档、验证——这些每轮都在做，它们的规范必须常驻；项目背景、需求全貌——开场用一次就够了，没必要每轮都背着。

## 五、后期修 bug 怎么加载记忆（操作手册）

### 场景 1：修一个已知模块的 bug（比如"维度计算的图表预览不对"）

```
第一步：Grep 找历史坑
  Grep "[维度计算]" project-memory.md
  → 找到 8 条相关坑，看有没有类似的

第二步：读模块快照
  Read project-memory.md 的「模块快照：维度计算」节
  → 了解这个模块的当前状态和关键决策

第三步：读最近 3 轮基线变更
  Read project-memory.md 第四节最后 3 行
  → 看最近有没有改这个模块的代码

第四步：才开始读代码
  Read dim-calc.ts / pages-indicator-rule.tsx
```

### 场景 2：接手一个新模块（比如"WorkBuddy 改了指标目录，我要继续改"）

```
第一步：Grep 找模块相关记录
  Grep "[指标目录]" project-memory.md
  → 找到所有历史改动和踩坑

第二步：读模块快照（如果有的话）
  → 了解上一位做到哪了

第三步：读基线变更登记里相关的轮次
  → 了解这个模块的演进历史

第四步：读代码确认现状
  → 不要凭记忆，实际读一遍代码
```

### 场景 3：上下文压缩后恢复

```
第一步：判断是不是压缩了
  想不起上一轮读过什么文件？
  早前细节只剩"做了什么"没有"看到了什么"？
  → 任一出现，当作已压缩

第二步：读快速索引
  Read project-memory.md 第 1-30 行（〇、快速索引节）
  → 恢复当前状态和最近改动

第三步：读当前模块的快照和相关坑
  Grep 当前模块名 → 读快照
  → 恢复模块上下文

第四步：补当前进度的快照
  把正在做的事、做到哪了，补进模块快照
  → 防止下次压缩再丢
```

## 六、验证结果：project-memory.md 确实有写入冲突历史

### 已确认的证据

project-memory.md 第八十七条踩坑记录原文：
> "改记忆文件后必须回读校验行结构 | project-memory.md 第十四轮的 Edit 误吞了第十二轮整行，还把第十三与十四轮粘成一行（L107 长度 2504）。若不复读，后续接手方读到的基线登记是残缺的。"

### 结论

**写入冲突已经实际发生过了**，不是假想的风险。之前维度计算频繁出 bug，很可能就是这个原因：
1. WorkBuddy 改了 dim-calc.ts 的某个函数
2. 同时在 project-memory.md 里写了一条新的踩坑记录

## 七、一句话总结

> **记忆文件不是写完就完，是分层的——快速索引 2KB 新会话必读，完整记忆按需 Grep 加载，模块快照闭环即写。修 bug 先查记忆再读代码，同一个坑绝不踩第二次。多智能体必须分文件写，不然互相覆盖。常驻上下文只放"每轮都在做的操作"的规范，开场用一次的背景和需求按需加载——信号最强的最小token集合，不是信息全不全。**
