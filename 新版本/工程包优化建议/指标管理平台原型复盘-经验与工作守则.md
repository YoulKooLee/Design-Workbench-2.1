> 复盘时间：2026-11-05
> 项目周期：2026-08 ～ 2026-11
> 技术栈：React + Vite + Tailwind + TypeScript
> 参与角色：豆包（主开发）、WorkBuddy、CodeBuddy、DeepSeek、千问（多智能体协作）

## 一、项目做了什么

### 1.1 功能主线
- 申请流程重构（应用登记前置 → 审批 → 授权）
- 应用登记模块新增（app_registry 表设计）
- API 管理 / 系统管理改版
- 审批配置画布式布局（节点 + 审批人）
- 指标目录改版（左侧分类树动态提取 + 右侧卡片列表）
- 维度计算重构（多步骤配置向导 + 按小时粒度 + 时间字段联动禁用）
- 接口数据源对接方式分流（业务上报 / 数据库直连）

### 1.2 文档体系
- 设计说明卡片：按规范八项要点，覆盖 11 个白名单页面
- PRD v2.2、SRS v1.4、HLD v1.5、LLD v1.4
- 每轮测试记录（7 行格式）落盘到上下文测试记录目录

## 二、踩过的坑（按严重程度排序）

### 🔴 P0 — 直接影响交付质量

**坑 1：设计说明卡片与设计文档不同步**
- 表现：原型改了代码，卡片和四份文档没跟上，用户多次要求"同步更新"
- 根因：改代码时只想着功能实现，没有把"同步文档"作为收尾动作
- 教训：**每改一处功能，必须同时改三处**——代码 + 设计说明卡片 + 对应设计文档（PRD/SRS/HLD/LLD），改完打勾确认

**坑 2：千问自检消息回复误判**
- 表现：v1 版回复把 Q5（工作记录路径）说成"不在上下文里"，实际上对话历史里写得很清楚；还把项目名说成"01 产品设计工作台"，实际就是"指标管理平台"
- 根因：凭印象作答，没有仔细核对当前上下文里的项目信息和对话历史
- 教训：**回答协作平台消息前，先在脑子里过一遍当前上下文里有什么**——项目名、用户偏好、对话历史都是上下文的一部分，不要只看系统提示区块

### 🟡 P1 — 影响效率但不阻塞

**坑 3：UI 对齐问题（统计栏圆点占位）**
- 表现：设计说明窗口统计栏"共 3 条 • 设计中 3"文字基线不齐
- 根因：第一个 span（共 X 条）没有圆点占位，后面的状态项都有 5px 圆点，导致文字基线不一致
- 教训：**列表/统计项对齐时，所有项结构必须一致**——有图标就都有图标，没图标就都没图标，或者用透明占位补位

**坑 4：死代码 / 死字段清理不彻底**
- 表现：旧库表页、孤儿映射页、freq 前缀、批次前缀、图表样式等遗留代码一直没清
- 根因：改功能时只加新代码，不删旧代码；清理工作一拖再拖变成 pending 项
- 教训：**新增功能时，顺手删掉被替代的旧代码**；如果旧代码还有其他地方引用，打标记但不要留着不管

**坑 5：空页面补卡片的边界不清**
- 表现：一开始想给所有页面补设计说明卡片，用户明确说 16 个空页面不用补
- 根因：没有先确认开发范围就动手
- 教训：**动手前先问清楚"哪些做哪些不做"**，列个白名单再开始，不要默认全做

### 🟢 P2 — 小问题但重复出现

**坑 6：落盘方式不统一**
- 表现：一开始用 PowerShell Set-Content 写文件，后来用户要求用 Python io.open utf-8 newline=""
- 根因：不知道用户偏好，默认用了工具自带的方式
- 教训：**写文件前先确认用户的落盘偏好**，尤其是涉及中文和 JSON 格式的文件

## 三、工作守则（后续项目直接照做）

### 3.1 开发流程守则

| 序号 | 守则 | 说明 |
|------|------|------|
| 1 | **改一处，改三处** | 代码 + 设计说明卡片 + 设计文档，同步改完才算完 |
| 2 | **先列白名单，再动手** | 明确哪些页面做、哪些不做，不要默认全做 |
| 3 | **新功能上线，顺手删旧代码** | 不留死代码、死字段、孤儿页面 |
| 4 | **每轮写测试记录** | 7 行格式，落盘到指定目录，不要攒着 |
| 5 | **修复类改动先本地验证** | 用户说打包再打包，不每轮自动打包 |

### 3.2 文案与 UI 守则

| 序号 | 守则 | 说明 |
|------|------|------|
| 6 | **页面文案用大白话** | 禁止物理表名、英文字段名、技术术语（RBAC、等保、SHA-256 等） |
| 7 | **技术细节进设计说明卡片** | 页面上只说用户能懂的话，开发备注放右侧卡片 |
| 8 | **卡片内容只改不删** | 除非是重复内容，不要删之前的记录 |
| 9 | **列表项结构必须一致** | 对齐问题的根因都是结构不一致，有图标就都有图标 |

### 3.3 落盘与编码守则

| 序号 | 守则 | 说明 |
|------|------|------|
| 10 | **中文文件用 Python io.open utf-8** | newline=""，每个 replace 前 assert count==1 |
| 11 | **不用 PowerShell Set-Content** | 容易出 BOM 和换行符问题 |
| 12 | **JSON 消息严格按格式** | schema_version / message_id / from / to / timestamp / thread_id 一个不能少 |

### 3.4 多智能体协作守则

| 序号 | 守则 | 说明 |
|------|------|------|
| 13 | **回复消息前先核对上下文** | 项目名、用户偏好、对话历史都是上下文，不要只看系统提示 |
| 14 | **协作消息只读回答，不猜** | 上下文里没有的就写"不在我的上下文里"，不要补全 |
| 15 | **豆包是共享目录维护方** | 其他智能体只提建议，不直接改共享目录；豆包负责统一更新 |

### 3.5 设计说明卡片规范（八项要点）

每张卡片必须包含：
1. **用途意图** — 这个模块是干嘛的
2. **字段口径** — 每个字段的含义和取值规则
3. **操作交互** — 用户能做什么操作，点击后发生什么
4. **校验规则** — 哪些字段必填、什么条件下禁用
5. **状态迁移** — 状态怎么流转，触发条件是什么
6. **数据来源** — 数据从哪来，前端 mock 还是接口
7. **边界异常** — 空数据、加载失败、超长文本怎么处理
8. **本期不做** — 哪些功能明确不在本期范围

## 四、高效工作 checklist（每轮开工前过一遍）

- [ ] 这一轮要改哪些页面？在白名单里吗？
- [ ] 改完代码后，设计说明卡片同步了吗？
- [ ] 四份设计文档（PRD/SRS/HLD/LLD）需要更新吗？
- [ ] 有没有旧代码可以顺手删掉？
- [ ] 这一轮的测试记录写了吗？
- [ ] 页面文案有没有技术术语暴露？
- [ ] 写文件用的是 Python io.open utf-8 吗？
- [ ] 协作平台有新消息吗？需要回复吗？

---

## 五、一句话总结

> **原型开发不是写完代码就完事——代码、卡片、文档三者同步改，边界范围先确认，旧代码顺手清，落盘方式听用户的。**
