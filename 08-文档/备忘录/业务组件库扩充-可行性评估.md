# 业务组件库扩充 · 可行性评估

> 目标：参考 `03-组件库\03-页面组件\Codebuddy Design` 的格式要求，把市场上的成熟业务组件（工作流、CMS、订单、付款、工作流编辑器、触发器等）引入组件库。
> 评估日期：2026-09-19 ｜ 评估人：WorkBuddy ｜ 状态：**待用户裁决**（未动手实现）

---

## 〇、结论速览

**可行，但结论不是"把市场组件搬进来"，而是"按现有格式契约，把成熟业务形态重做成零依赖组件"。**

| 档 | 范围 | 判定 |
| --- | --- | --- |
| **A 档** | 订单、付款、触发器、CMS（除富文本）、工作流（除画布） | ✅ **零依赖自研即可落地**，现有基座（DataTable/Descriptions/Steps/StatusTag/FormField）已足够组合出来 |
| **B 档** | 工作流编辑器**画布**（拖拽节点+连线）、CMS **富文本编辑器** | ⚠️ **需决策**：要么破例引入 1 个 MIT 依赖，要么自研轻量版（只够演示） |
| **C 档** | n8n / Dify / Strapi / Payload / Directus / Stripe Elements / TinyMCE / CKEditor5 | ❌ **不建议**：许可受限或根本不是组件（完整应用 / 云端托管 SDK / 按量计费） |

**另有一个机制阻塞项**：组件库登记表**没有依赖字段，也没有依赖装配逻辑**。任何带第三方依赖的组件（B 档）都会卡在这里 —— 这属于工作台侧改动，需报豆包排期。

## 一、格式基准：Codebuddy Design 的 6 条硬约束

评估的尺子来自库本身（`README.md` + `_meta/layout.manifest.json` + 实际源码）：

| # | 约束 | 出处 / 证据 |
| --- | --- | --- |
| 1 | **技术栈** React 18 + Tailwind v4；类名工具 `cn()` 来自 `_kit/cn`；**配色/圆角/阴影只能取 `_kit/theme.css` 的 `@theme` token**（Arco 色板） | `index.ts`、`README.md`「设计目标」 |
| 2 | **零第三方依赖**：不引 arco/antd/clsx/dayjs；图标内联 SVG。唯一例外 `SideMenu` 依赖 `lucide-react`（工程已内置） | 同上；已抽查 `业务组件/KpiRow.tsx` 确认只有 `react` + `cn` + 同级组件 |
| 3 | **源码自包含、整目录复制**；组件间有跨分类引用，**不能只拷单个文件** | `README.md`「消费方式」 |
| 4 | **每个组件必须**：导出 TS 类型、JSDoc 带「场景 / 规则 / @example」 | `KpiRow.tsx` 实际写法 |
| 5 | **落位二选一**：① 分类真源 `<中文分类>/<Name>.tsx` + 该分类 `index.ts` 追加导出；② 独立 `<id>/` 目录（面板上传/整包导入） | `README.md`「新增组件落位」 |
| 6 | **五处登记同步**：`_meta/components.catalog.json`（含 prompt）→ `../custom-components.json` → `分类/index.ts` → `提示词手册.md` → `选型映射.md`；且 `index.json` 与 `../component-registry.json` 的版本/状态/组件数必须一致 | `README.md`「维护核对」 |

> 一句话：**这套格式不是"样式要求"，是"零依赖 + 可复制 + 五处登记"的交付契约**。任何市场组件想进库，必须过这三关。

## 二、六类业务组件可行性分档

| 组件类 | 现有基座能否组合出来 | 市场的"成熟组件"是什么 | 判定 |
| --- | --- | --- | --- |
| **订单组件** | ✅ 能。`DataTable` + `FilterBar` + `Descriptions` + `Steps` + `StatusTag` + `Timeline` | 市场上没有"订单组件库"，只有**完整商城项目**（mall / vue-vben-admin 的订单页） | **A 档** |
| **付款组件** | ✅ 能（纯形态）。金额汇总、支付方式选择、倒计时、结果页 | Stripe Elements（Stripe.js 托管组件）、微信/支付宝 SDK | **A 档**（真实 SDK 属 C 档） |
| **触发器** | ✅ 能。`FormField` 系列 + 事件源/条件/动作三段式 + `TableCard` | n8n 的 trigger nodes、Node-RED | **A 档** |
| **CMS 组件** | ✅ 大部分能（内容列表、版本对比、字段编辑、发布流）｜⚠️ 富文本不行 | Payload / Strapi / Directus（完整后端应用）；富文本 TipTap / Lexical | **A 档** + 富文本 **B 档** |
| **工作流组件** | ✅ 非画布部分能：流程列表、节点库面板、执行日志、审批节点卡 | 同上（n8n/Dify 均为完整应用） | **A 档** |
| **工作流编辑器（画布）** | ❌ 不能。需要拖拽、缩放、连线、小地图、对齐线 | `@xyflow/react`(React Flow) / `AntV X6` / `LogicFlow` | **B 档** |

## 三、逐类建议组件清单（A 档，8 类 ≈ 25 个组件）

> 命名与分类遵循现有中文分类：新增「业务组件/」下的组件或独立 `<id>/` 目录。

### 1. 订单（建议 6 个）
`OrderTable`（订单列表，含状态/金额/时间列）、`OrderDetailCard`（订单详情头）、`OrderStatusFlow`（下单→付款→发货→完成，Steps 封装）、`OrderItemList`、`OrderTimeline`（操作轨迹）、`OrderAmountSummary`（小计/优惠/运费/应付）

### 2. 付款（建议 5 个）
`PaymentMethodPicker`（支付方式卡片选择：微信/支付宝/银行卡/余额）、`PaymentCashier`（收银台整块）、`PaymentCountdown`（待支付倒计时）、`PaymentResult`（成功率/失败/待确认三态，可复用 ResultPage）、`InvoiceForm`（开票信息）

### 3. 触发器（建议 4 个）
`TriggerTypePicker`（事件触发/定时触发/Webhook/手动）、`TriggerConditionBuilder`（字段-运算符-值 行式条件组，支持且/或）、`TriggerActionList`（动作序列，可拖排序）、`TriggerRuleCard`（规则卡：启用开关 + 命中次数 + 最近执行）

### 4. CMS（建议 6 个，不含富文本）
`ContentTable`（内容列表：标题/栏目/作者/状态/发布时间）、`ContentEditorForm`（标题/摘要/栏目/标签/封面字段区）、`ContentStatusBadge`（草稿/待审/已发布/已下线）、`ContentVersionDiff`（版本对比，左右分栏 + 差异高亮）、`MediaPicker`（素材库选择：网格 + 搜索，可用现有 Modal + List 组合）、`PublishSchedulePanel`（定时发布 + 发布范围）

### 5. 工作流（非画布，建议 4 个）
`WorkflowList`（流程列表：版本/状态/发布人）、`NodePalettePanel`（节点库侧栏：分组折叠 + 搜索，可拖）、`ExecutionLogTimeline`（执行轨迹：节点名/耗时/入参出参/成功失败）、`ApprovalNodeCard`（审批节点：审批人/方式/超时策略）

**小结：A 档全部用现有 48 个组件组合 + 少量新样式即可完成，不引入任何依赖，风险最低。**

## 四、B 档：两个必须决策的技术点

### B1 · 工作流编辑器画布

| 候选 | 许可 | 体量 / 依赖 | 适配度 | 判定 |
| --- | --- | --- | --- | --- |
| **`@xyflow/react`（React Flow）** | **MIT**（webkid GmbH，84 个版本全 MIT，无企业条款） | 12.11.6（2026-09-01）；安装 1.2MB；3 个依赖（zustand / classcat / @xyflow/system）；需自带 CSS | React 原生组件，节点可自定义成任意 React 组件，与 Tailwind 兼容 | **推荐（若要引）** |
| `AntV X6` | **MIT** | 阿里生态，插件体系完善 | SVG+Canvas，React 友好，中后台流程编辑器成熟 | 备选 |
| `LogicFlow`（滴滴） | **Apache-2.0** | 约 50KB，轻量 | 流程场景针对性强，但复杂交互能力不足 | 轻量备选 |
| `GoJS` | 商业授权 | 万级节点流畅 | 闭源收费 | ❌ |
| **自研最小画布** | — | 约 300-500 行 SVG | 只支持：拖拽节点、直线连线、选中高亮、缩放。**没有小地图/对齐线/自动布局/撤销重做** | 守"零依赖"，但只能演示 |

**两条路，成本与产出都不同，需你选**（见 §七）。

### B2 · CMS 富文本编辑器

| 候选 | 许可 | 形态 | 判定 |
| --- | --- | --- | --- |
| **TipTap** | MIT 核心 + 付费 Cloud/AI | **headless**：只给数据层，工具栏/UI 要自己写 | ✅ 许可干净，但工作量在 UI |
| **Lexical**（Meta） | MIT | 框架级，同样要自研 UI | ✅ 备选 |
| BlockNote | MPL | 开箱即用的块编辑器 | 备选（MPL 略需注意） |
| TinyMCE | **GPLv2+ 核心 / 商业版按"编辑器加载次数"计费**（1,000 次免费，超出按量） | 开箱即用、插件多 | ❌ 许可+计费双重风险 |
| CKEditor 5 | GPLv2+ 或商业（$144/mo 起） | 开箱即用、协同强 | ❌ |
| Quill | BSD | 轻量 | ⚠️ 2022 年后基本停更 |

> 第三选项：**纯静态形态**（工具栏 + 内容区 + 字数统计，不接真实编辑器）。原型阶段"能看出是什么"通常就够了。

## 五、C 档：为什么不建议"整包引入"

| 候选 | 用途 | 许可（已核实） | 为什么不行 |
| --- | --- | --- | --- |
| **n8n** | 工作流引擎 + 编辑器 | **Sustainable Use License**（fair-code，非开源） | ① 只允许"自身内部业务用途"；**明确禁止白标**、禁止把 n8n 当产品卖；② 无法移除品牌标识；③ 是 Node 后端 + Vue 前端的**完整应用**，不是 React 组件 |
| **Dify** | 工作流/Agent 编辑器 | **Dify Open Source License** = Apache 2.0 + 两条附加条件：**不得用于多租户托管服务**、**不得去除前端 LOGO/版权** | 同上；且为 Flask + Next.js 完整平台（Docker 栈 2C4G 起） |
| **Strapi / Payload / Directus** | CMS | Payload 为 MIT；Strapi 部分功能需商业授权；Directus 为 GPLv3 | **是完整后端应用**，不是组件；GPLv3 有传染性 |
| **Stripe Elements** | 支付表单 | Stripe.js 托管组件（专有） | 需 Stripe 账户 + 密钥 + 后端 + PCI 合规；**静态原型无法使用**，只能复刻形态 |
| **微信支付 / 支付宝 SDK** | 支付 | 专有 | 需商户号/证书/后端签名；原型阶段同理只做形态 |
| Ant Design Pro Components | 业务表格/表单 | MIT（已核实） | 22 个依赖、peer `antd ^6`、体积 255KB gzip —— **直接破坏"零依赖"契约**，且视觉体系与 Arco token 冲突 |

**可借鉴而非引入**：`amis`（Apache-2.0）、`Formily`（MIT）、`LowCodeEngine`（MIT）—— 它们的**业务形态与字段组织方式**值得抄（比如条件构建器、节点库分组），但不搬代码。

## 七、需你裁决的 4 个点

1. **工作流画布走哪条路？**
   - (a) 破例引 `@xyflow/react`（MIT）—— 少则 1 个依赖，能力完整（小地图/对齐线/撤销重做）
   - (b) 自研最小 SVG 画布 —— 守"零依赖"，但**只能演示，不能当编辑器用**

2. **依赖通道怎么开？（若选 (a)）**
   - (a) 写进 `02-模板\_project-template\package.json` —— 简单，但**所有新项目都会装**
   - (b) 给组件库登记加 `extraDependencies` + 复制/启动时装配 —— 干净，但**要改工作台代码 → 需报豆包排期**

3. **富文本要不要真编辑器？** 真编辑器（TipTap，MIT）能编辑但需自研工具栏；静态形态够"看得出是什么"且零依赖。

4. **组件粒度**：做成**业务组件**（订单表、支付卡这种零件），还是**页面模式**（整页组合，像刚落位的 `PageListSearchTable`）？两者维护成本与复用率差别很大。
