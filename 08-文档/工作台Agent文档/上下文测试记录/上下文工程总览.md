# 上下文工程总览（结构 · 为何分散 · 设计思路）

> 维护对象：`02-模板/` 两个工程包 + `01-项目/` 7 个在用项目
> 最后校准：2026-10-30（文中数字均为当日实测）

---

## 0. 一句话

**上下文是稀缺品：每次会话只能可靠装进 8,000 字符的规则，所以工程包把"规则"拆成"入口 + 路由 + 可按需读取的正文"，把"记忆"拆成四层文件，靠两条滑窗让每次装配只装当前模块。**

## 1. 结构

### 1.1 注入面：会话首轮到底进来什么

| 项 | 事实 |
|---|---|
| 载体 | `AGENTS.md`（候选顺序 `CODEBUDDY.md` > `.codebuddy/CODEBUDDY.md` > `AGENTS.md`，**只读第一个存在的**；`CLAUDE.md` 完全不在候选表） |
| 上限 | **8,000 字符**（判 `String.length`，**不是字节**；超窗静默切尾并补 `[...too long, omitted...]`） |
| 时机 | **只有首轮**。同一会话第 2 个请求起不再渲染，与压缩无关 |
| 位置 | 首条用户消息里的隐藏块 `<project_context>`，不是 system prompt |
| 失败形态 | 读不到文件时仍渲染"空壳"（有块、无内容），**不报错** |

> 后果：AGENTS.md 是**唯一**能保证"每次新会话都被看到"的通道。所以它只放三样东西——铁律、触发条件→读哪个文件、压缩时该保住什么。

### 1.2 常驻与按需：AGENTS 六节 + 24 条规则

```
AGENTS.md（原型模板 5,511 字符 / 研发模板 4,977 字符）
├── §一 本工程独有的事实          ← 项目各不同，允许分化
├── §二 先分流：何时停下来问人
├── §三 基线落盘路径 + 写入侧门禁 + 编码底线（摘要）
├── §四 技能与子 Agent + 执行优先级
├── §五 原型探索路径（主干五步）    ← 2026-10-30 重写
└── §六 按需读取地图（24 行指路）   ← 7 项目完全一致，是"索引层"；原型模板因补 catalog 路由行已独立（见 §4）
```

`.agents/rules/` 24 个文件、合计 **96.3 KB**，全部**永不常驻**，只在 §六 指到时才读。最大的三个：

| 文件 | 体积 | 装什么 |
|---|---|---|
| `AGENTS-rationale.md` | 19.0 KB | 每条规则"为什么这么定" |
| `req-doc-workflow.md` | 12.2 KB | 需求文档三体系路由 |
| `compaction-recovery.md` | 5.9 KB | 压缩保留/恢复/快照 |

### 1.3 记忆分层：四层文件

| 层 | 位置 | 装什么 | 判据 |
|---|---|---|---|
| 索引层 | `project-memory.md`（工程根） | 任务进度 / 决策记录 / 变更流水 / 模块快照 | 只放摘要 + 路径，不放正文 |
| 基线层 | `docs/`（PRD、SRS、HLD、LLD） | 需求与架构真源 | 改基线必须升版本 + 登记 |
| 答疑层（项目） | `项目答疑手册.md` | 本项目踩坑、经验 | 项目级复用价值 |
| 答疑层（工作台） | `08-文档/工作台答疑手册.md` | 工具用法、通用坑 | 跨项目复用价值 |

写入三态门禁：`[事实]` 可进基线；`[讨论]` / `[否决]` 只进过程层；`[敏感]` 不落盘。

### 1.4 两条滑窗：控制"一次装多少"

| 窗 | 编号 | 内容 | 上限 |
|---|---|---|---|
| 常驻基线 | 0–6 | AGENTS + 需求清单 + 数据模型 + 架构 + 业务架构 + 数据流 + 已完成模块快照 | ≤ 40 KB |
| **模块滑窗** | 7–9 | 当前模块设计 + 该模块组件清单 + 上下游契约切片 | ≤ 20 KB |
| **阶段滑窗** | 10–11 | 当前阶段知识（phase1-4，只读 1–2 个文件）+ 基线三件套对应章节 | ≤ 15 KB |
| **单次装配合计** | — | 以上三项 | **≤ 120 KB，超限记账不阻断**（无 deny 机制可阻断；真正必阻断的只有组件库/vendor/skills 整目录递归读） |

**进模块装配、离开卸载**。模块粒度由上下文预算决定，不由页面数量决定——装不下就拆小，太碎就合并。

### 1.5 技能与子 Agent：索引 → 单个文件

```
.agents/skills/               53 个技能目录，合计 2.41 MB / 273 文件（研发侧 17 目录 / 1.32 MB / 93 文件）
├── INDEX.md                  3,528 字符 / 52 条 / 40 条被截断成 "..."
└── <name>/SKILL.md           命中后只读这一个
.agents/agents/               18 个子 Agent 定义
```

铁律：**禁止遍历技能目录**（单次遍历可达数十万 token）。子 Agent 只做"盘点取结论"，不做审查。

## 2. 为什么分散：三条硬约束

### 约束一：注入只有 8,000 字符，超了**静默**切尾

最老的 v09 模板 AGENTS.md 有 **19,760 字符**——注入进去只有前 40% 生效，后面 18 节全丢，而且不报错。
→ 凡是"不是每次都必须看"的，**必须搬出 AGENTS**。

### 约束二：压缩只保"做了什么"，丢"看到了什么"

压缩由宿主自动触发（默认阈值 0.92，实测 **53.2%** 就触发），保留动作序列，**工具结果正文约 99.5% 被丢弃**；AGENTS 本身也不会被带回。
→ 凡是"以后还要用"的，**必须落盘**；靠记忆等于赌博。

### 约束三：一次只干一个模块，其余上下文都是噪音

一个模块的设计 + 组件 + 接口，装得下；整套产品装不下。
→ 用**滑窗**只装当前模块，其余靠 `docs/` 与快照接力。

### 三条约束合成一条规则

> **不是每次都要看的 → 搬到文件；搬走的 → 留一行路由（触发条件 → 读哪个文件）。**

这就是"分散"的全部理由：**分散不是为了文件好看，是为了让 8,000 字符装得下最该走的那几步。**

## 3. 设计思路：六条原则

| # | 原则 | 具体做法 | 反面教训 |
|---|---|---|---|
| 1 | **落盘优先** | 基线永远是文件，丢了按路径重读；不赌"压缩时会被保住" | 曾把完整流程写进 AGENTS，压缩后全丢 |
| 2 | **外移 ≠ 删除** | 搬内容去 `rules/` 时，**必须同时**在 §六 留一行路由；搬完跑断线检查 | 2026-10 瘦身把 18 节压成 6 节，14 节没有承接，规则凭空消失 |
| 3 | **路由化** | AGENTS 只写"什么时候 → 读哪个文件"，正文一律外置 | 早期 AGENTS 把正文和路由混在一起，越写越长 |
| 4 | **单一真源** | 同一事实只写一处；摘要必须指向正文（如 §三 编码底线 → `write-safety.md`） | 改了一处忘另一处，同一规则出现两个数字（500/80 vs 800/120） |
| 5 | **可验证** | 能给出数字的才叫验收：`TOTAL=n BAD=0`、`X→Y`、断言通过率 | "页面都在、路由通"被当成完成，实际动作点了不改状态 |
| 6 | **防漂移** | 7 项目 §六 同哈希（原型模板已独立）；改动后跑 `check-doc-links`（含 A–E 断言）；索引与 catalog **一律由脚本生成，禁止手写** | 三份 memory-gates 字数 1,566 / 1,577 / 2,847，各写一套 |

### 附：流程为什么是"框架先行、按模块推进"

```
① 需求与功能设定 → ② 框架方案推荐 → ③ PRD + 系统架构 + 数据模型（初稿）
→ ④ 按模块循环：模块需求 → 原型与模拟验证 → 回写基线 → ⑤ 转写 SRS
```

理由不是流程审美，是约束一：**框架不先定，模块就没有回写的目标**；模块不逐个收口，上下文必然爆。
第 ② 步的第一手段是**模型自身知识**——常见品类（电商、CRM、审批流、报表看板、漫剧平台…）直接出一版成品原型 + 架构图 + 文字描述，比先搜索再讨论快；拿不准才找开源，找不到自己做。
