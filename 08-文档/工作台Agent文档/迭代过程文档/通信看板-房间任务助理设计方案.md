## 一、一句话说明（给使用人看的大白话）

通信看板里每个协作房间配一个「随身小助理」：点开房间点一下「生成进展小结」，它自动把任务说明、房间对话、各方私信和在线状态拢在一起，告诉四件事——**现在做到哪了、卡在哪、下一步建议谁来做、有没有需要你拍板的**。建议交给谁做时，可以一键把这条任务送到对应智能体的收件箱。

助理只做「读材料、写小结、提建议、递消息」，**不替你做决定、不自动改文件、不自动跑命令**。

## 二、为什么做：现状痛点（基于现有代码核实）

| 现状（已核实） | 带来的问题 | 本方案对应能力 |
|---|---|---|
| 房间只有 `messages.jsonl` 消息流和消息条数，没有「进展到哪」的汇总（`GET /api/collab/overview` 只统计条数与任务说明前 1500 字片段） | 18 个历史房间要逐条翻消息才能判断进展 | 一键生成结构化进展小结并落盘回看 |
| 房间没有任务状态，只有「有没有消息」（无状态字段、无归档/暂停概念） | 看不出哪些在做、哪些卡住、哪些该收尾 | 房间状态（待开始/进行中/卡住/待你确认/已完成/已归档） |
| `GET /api/collab/room` 把房间消息 + 参与方近 30 天私信合并时间线，信息全但要人自己读 | 人要在长对话里找结论 | 助理先归纳结论，人只看摘要和争议点 |
| 已有 `GET /api/collab/arbitration` 只识别「点名要你裁定 / 双方僵持」两类进「待你仲裁」表 | 平时的推进建议、分工缺口没有出口 | 助理小结固定含「下一步建议 + 建议责任方」 |
| 已有模型三级通路：HTTP 兼容接口（DeepSeek 等）→ CodeBuddy CLI → 本地模板草稿（`/api/report/generate` 同款实现） | 这套能力只用于周报/月报，没接到通信模块 | 直接复用同一通路，零新增依赖 |
| 智能体在线靠 5 分钟心跳文件判定；`POST /api/collab/reply` 已会按信封给参与方 inbox 投 confirm 消息 | 委派消息投递机制已有现成模式可参照 | 委派消息沿用现有信封与原子写入方式 |

## 三、从 OpenBot 借鉴什么、明确不做什么

OpenBot 是 Electron + SolidJS + Bun + 本地 SQLite 的多 coding-agent 托管工作台，代理以 `danger-full-access`、`approvalPolicy: never` 运行，许可证为 PolyForm Noncommercial 1.0.0（非商用）。本方案只取设计思路，不取技术栈与代码。

### 3.1 借鉴（映射到现有文件/接口）

| OpenBot 设计点 | 工作台落地方式 |
|---|---|
| 共享频道（Channel）单一任务负责人 + 显式委派 | 房间 = 频道；新增房间状态与「建议责任方」，委派动作落成标准消息 |
| 任务队列的暂停/恢复/归档状态控制 | 房间状态枚举：待开始 / 进行中 / 卡住 / 待你确认 / 已完成 / 已归档（见第六节） |
| 长上下文自动压缩（compaction） | 生成小结时服务端先做截断与聚合：旧消息只保留发言方、类型、首句，不全文喂给模型 |
| Agent 间消息、回复、文件清单式往来 | 沿用现有消息信封（schema 0.2.1），不新增协议格式 |
| 产出可落盘、历史可回看 | 每次生成的小结写一份带时间戳的存档副本（参照周报 `archiveReport` 落档思路） |

### 3.2 明确不做（边界，避免范围膨胀）

- **不引入** Bun、SQLite、SolidJS、事件日志数据库；继续用 Node 原生服务 + JSON / JSONL 文件。
- **不托管** Codex/Claude/Grok 等 coding CLI 进程，不做会话托管与进程崩溃恢复；现有外部智能体仍由各自 CLI 手动唤醒、心跳上报在线。
- **不做**全权限无审批的自动化执行；助理不调用 shell 修改项目源码，模型只产出文本建议。
- **不做**远程团队服务器、信令服务、计费、移动端、内嵌浏览器与 Computer Use。
- **不复制 OpenBot 源码**：其许可证禁止商用，工作台为公司内部办公工具，只借鉴设计模式可规避授权风险；任何界面命名、提示词均自行编写。

## 四、分期范围（已确认：P0 + P1 同批交付，P2 暂缓）

### P0 · 进展小结（与 P1 同批开发，已确认）
1. 房间对话弹窗内新增「助理小结」卡片：生成、查看最近一次小结、无模型时的本地规则草稿。
2. 小结固定四段：当前进展 / 阻塞与待确认 / 下一步建议（含建议责任方）/ 待你拍板事项。
3. 小结落盘到房间目录，历史副本留存，可回看。
4. Web 与桌面端同构实现。

### P1 · 房间状态 + 委派推送（与 P0 同批开发，已确认）
1. 房间状态切换与列表状态徽标；状态变更留痕。
2. 小结里的建议责任方，一键生成委派消息投递到对应智能体收件箱（用户点确认才发）。
3. 房间列表展示「最近小结时间」。

### P2 · 节奏提醒与汇总（暂缓，评审后再定）
- 打开房间时若小结超过 1 天未更新，提示「可刷新进展」。
- 看板顶部新增「房间进展一览」：汇总各房间最新小结要点（只读列表，不自动生成）。
- 小结支持人工修订保存（编辑后覆盖最新稿、历史仍在存档目录）。

> P2 不在首批开发承诺内；P0/P1 验收通过后再评估。

## 五、数据与文件约定（只在房间目录内新增，不动现有消息格式）

现有房间目录示例（已核实）：

```
09-协作/rooms/<房间名>/
├── messages.jsonl      # 现有：每行一条 {ts,from,intent,content}，本方案不改行格式
├── 00-任务说明.md       # 现有：部分老房间缺失，缺失时按空处理
└── 产物/               # 现有
```

P0/P1 新增（全部为新增文件，不删除、不覆盖现有文件）：

| 新增文件 | 用途 | 写入方 |
|---|---|---|
| `助理进展.md` | 当前最新一版小结正文（Markdown），头部带元信息（生成时间、来源通道、覆盖消息条数、参与方） | 后端服务 |
| `room-state.json` | 房间状态与变更留痕（格式见 6.2） | 后端服务（仅 P1） |
| `助理存档/assistant-YYYYMMDD-HHMM.md` | 每次生成的历史副本，防止重新生成后旧结论丢失 | 后端服务 |

约束：
- 不修改 `messages.jsonl` 既有行；助理系统记录如需进时间线，只**追加**一条 `from=doubao, intent=delegate`（P1 委派时）或 `intent=assistant`（P0 可选）的记录。
- 不写其他智能体目录（`agents/<id>/` 保持现状）；委派消息只向目标收件箱**新增**文件，不修改、不删除收件箱内既有文件（与现有 `ack`「只许标记自己收件箱」的边界一致）。
- 文件编码 UTF-8 无 BOM、LF 换行，由 Node 写出（不用 PowerShell `Set-Content`，避免 BOM 历史坑）；原子写入：先写 `.tmp` 再 `renameSync`，与现有 reply 投递方式一致。

## 六、功能设计

### 6.1 助理小结（P0）

**触发方式（已确认）**：手动点按钮整理，不做定时自动生成；房间长期无新消息时的温和刷新提醒放到 P2 讨论。

**服务端收集的上下文**（只读本房间 + 必要的全局只读信息）：
1. `00-任务说明.md` 全文（缺失则空，不编造任务目标）；
2. `messages.jsonl` 最近 80 条 `{ts, from, intent, content}`；
3. 参与方之间近 30 天私信（复用 `/api/collab/room` 已有的参与方推断与时间窗口逻辑），每条正文截断约 300 字；
4. 参与方在线状态（复用 `readAgentHeartbeat`，5 分钟有效期）；
5. 产物目录是否存在、顶层条目名（只列文件名，不读内容）。

**上下文压缩规则（对应 OpenBot compaction 的轻量版）**：
- 时间线总量偏大时，较早的消息只保留 `发言方 + 类型 + 首句（约 80 字）`，最近 20 条保留全文；
- 任务说明超长取前约 3000 字；
- 明确把「全部在册执行智能体名单（含在线/离线标记；主持人豆包不进指派候选）」单独列出，供模型挑选建议责任方。

**输出骨架（四段，缺内容也保留小节标题并写「暂无」）**：

```
# 房间进展小结 · <房间名>
## 一、当前进展
（按参与方归纳：已完成什么、正在做什么；只引用记录里出现过的事实）
## 二、阻塞与待确认
（卡点、等待项；没有则写「暂无」）
## 三、下一步建议
- 动作建议 ……（建议责任方：某某 / 待人工指定；责任方只能从在册执行智能体名单选）
## 四、需要你拍板
（提炼「请你决定 / 僵持」类句子；没有则写「暂无」）
> 生成时间 …… · 来源通道 …… · 覆盖对话 N 条 · 参与方 ……
```

**硬性提示词纪律（写进服务端 prompt）**：
1. 只能使用收集到的材料，不编造项目、人名、日期、数字与结论；
2. 依据不足处标注「待确认」；
3. 建议责任方不在在册执行智能体名单内时写「待人工指定」，不臆造人选；
4. 直接输出 Markdown 正文，不加开场白与解释。

**无模型兜底（沿用周报降级思路）**：未配置模型且 CLI 不可用时，按规则拼一份草稿——按发言方分组列出消息要点、标注最后发言时间、把命中「裁定/分歧」关键词的句子列入第四节，并在稿尾注明「本地规则草稿，未经模型归纳，建议人工补充」。保证按钮点下去不空转、不报错。

**覆盖与存档口径（已确认）**：每次重新整理覆盖 `助理进展.md` 最新稿；上一稿在 `助理存档/` 留存副本供历史回看，不删除旧稿；人工在线编辑保存留待 P2。

### 6.2 房间状态（P1）

**枚举与大白话标签**：

| 内部状态值 | 界面显示 | 含义 |
|---|---|---|
| `not_started` | 待开始 | 房间已建、还没有实质推进 |
| `in_progress` | 进行中 | 正在协作推进（默认值；老房间无记录也归为此类并在列表弱化显示） |
| `blocked` | 卡住了 | 有阻塞、等外部条件 |
| `waiting_user` | 待你确认 | 明确点名需要用户拍板 |
| `done` | 已完成 | 结论已收敛、产物齐备 |
| `archived` | 已归档 | 收尾封存，不再打扰（列表可折叠） |

`room-state.json` 结构示例：

```json
{
  "status": "in_progress",
  "owner": "",
  "updatedAt": "2026-10-30T10:00:00.000Z",
  "updatedBy": "user",
  "history": [
    { "at": "2026-10-30T10:00:00.000Z", "by": "user", "from": "not_started", "to": "in_progress", "note": "正式开工" }
  ]
}
```

- 状态只允许在上表枚举值内切换，非法值服务端拒收；
- 每次切换追加一条 history，不覆盖旧记录；
- `waiting_user` 可与现有「待你仲裁」识别结果联动：命中仲裁规则的房间，列表徽标自动偏向「待你确认」（用户手动改状态以人工为准，不反向覆盖）。
- **枚举定稿（已确认）**：上表六态即为最终状态集，不新增「已暂停」；老房间无状态记录时默认归入 `in_progress` 并在列表弱化显示。

### 6.3 委派推送（P1）

- 入口：小结「下一步建议」每条建议后给出全部在册执行智能体作为可选对象（CodeBuddy / WorkBuddy / DeepSeek / 千问；主持人豆包不作为被指派对象），候选不限于本房间发言过的参与方；离线者弱化标注「离线，提交后等其上线处理」，仍可提交；
- 动作：用户勾选并点「交给 XX」后，服务端按现有消息信封生成一条 `type: "delegate"` 的消息写入 `messages/inbox/<目标>/`（原子写），同时在房间 `messages.jsonl` **追加**一条 `from=doubao, intent=delegate` 的可见记录，并在 `messages/outbox/user/` 留一份发出副本（与现有 reply 的双副本做法一致）；
- 信封字段沿用现有约定：`schema_version`、`message_id`、`from`、`to`、`cc`、`timestamp`、`type`、`subject`、`body`、`attachments: []`、`status: "unread"`、`priority`、`thread_id=<房间名>`、`reply_to`、`action: "delegate"`、`due_at`、`sender_note: "workbench-panel/assistant"`；
- 模型只给「建议对象 + 建议说明」，**是否发送、发给谁由用户点确认**；**单选单发（已确认）：一条建议一次只交给一个智能体，不支持多选群发，不自动催办。**

## 七、接口设计（新增路由，挂在现有 `/api/collab` 命名空间下）

> 现有路由保持不变；以下为新增。所有房间名复用现有安全校验：非空、不含 `/`、`\`、`..`，防止目录穿越。

| 方法与路径 | 入参 | 返回要点 | 说明 |
|---|---|---|---|
| `GET /api/collab/assistant?name=` | 房间名 | `{ok, note:{content,generatedAt,source,cover}, state, participants:[{name,online}], hasArchive}` | 弹窗首屏读取最新小结与状态；无小结返回空态标识，不报错 |
| `POST /api/collab/assistant/generate` | `{name}` | `{ok, text, source, fallback, generatedAt, archivedPath, cover:{messages,participants}}` | 服务端收集上下文 → 三级通路生成 → 写 `助理进展.md` + `助理存档/` 副本；失败降级本地草稿并 `fallback:true` |
| `POST /api/collab/state` | `{name, status, note}` | `{ok, state}` | 写/更新 `room-state.json` 并追加 history；枚举校验 |
| `POST /api/collab/delegate` | `{name, to, summary, action}` | `{ok, sentTo, messageId}` | 用户确认后投递委派信封（P1） |
| `GET /api/collab/overview`（扩展，不改返回结构） | — | 每个房间对象新增 `status`、`assistant:{hasNote, lastGeneratedAt}` | 列表渲染状态徽标与「最近小结时间」（P1） |

复用的现有内部能力（不重复造轮子）：
- `readAiConfig()` / `callModelHttp()` / `cliProbe()` / `runCli()`：模型三级通路；
- `readAgentHeartbeat()`：在线状态；
- 参与方推断逻辑（`messages.jsonl` 的 from 去重 + 房间名前缀兜底名单 `codebuddy/workbuddy/deepseek/qwen/doubao`）；
- 私信目录遍历与 30 天窗口（与 `/api/collab/room` 同一套遍历代码抽为公共函数）。

## 八、双端界面方案

### 8.1 房间对话弹窗（P0 主入口）

现有结构（Web `showRoomDialog`、桌面 `showRoomDialog` 同名同构）：弹窗内是消息时间线 + 底部「仲裁回复」框。助理卡片置于**时间线上方**，自上而下：

1. 卡片标题行：「智能助理小结」+ 右侧按钮「生成进展小结 / 重新生成」；无历史小结时显示空态引导：「还没有小结，点一下生成当前房间的进展摘要」。
2. 元信息行（小灰字）：生成时间 · 来源（模型名 / 本地草稿）· 覆盖对话条数；重新生成中显示「整理中…」并禁用按钮。
3. 四段正文区（Markdown 简单渲染：标题、列表、加粗；不引入重型 Markdown 库，沿用现有页面已有的轻量渲染方式）。
4. P1 底部操作行：状态切换下拉 + 每条建议后的「交给 XX」按钮（未选中不发送）。

### 8.2 房间列表（P1）

- 房间名后追加状态徽标（颜色克制：进行中蓝、卡住橙、待你确认红、已完成绿、归档灰显）；
- 任务说明列下方小灰字显示「最近小结 · MM-DD HH:mm」；
- 操作列保持现有「查看对话」，不新增拥挤按钮；状态切换只在弹窗内完成。

### 8.3 界面文案规范（用户可见文案一律大白话）

| 位置 | 文案（可见） |
|---|---|
| 主按钮 | 生成进展小结 / 重新生成 |
| 空态引导 | 还没有小结，点一下整理当前房间的进展 |
| 生成中 | 正在整理房间材料… |
| 草稿提示 | 本次是本地规则草稿（未连接模型），建议人工补充后使用 |
| 状态切换 | 待开始 / 进行中 / 卡住了 / 待你确认 / 已完成 / 已归档 |
| 委派按钮 | 交给 CodeBuddy / 交给 WorkBuddy / 交给 DeepSeek / 交给千问；离线者显示「交给 XX（离线，上线后处理）」；无合适人选显示 待人工指定 |
| 发送确认提示 | 确认把这条建议发给 XX？发送后会在房间留一条记录 |

**禁止出现在界面的技术词**：队列、委派协议、信封、上下文压缩、compaction、SQLite、进程托管、RPC、MCP、schema、fallback、通路、token。这些只出现在本设计文档与右侧「设计说明」折叠卡片里。

### 8.4 技术细节落点（开发备注，不进页面）

- Web：`renderCollab()` 扩展房间对象渲染；`showRoomDialog(name)` 内先拉 `/api/collab/assistant`，再拉对话时间线；事件绑定风格与现有 `#roomReplySend` 一致；
- 桌面：`renderCollab()`、`showRoomDialog(name)` 同步同名函数；请求走 `api('GET'/'POST', 路径, body)`，与现有 `/api/collab/reply` 调用方式一致；
- 后端：协作路由集中在现有 `/api/collab/*` 段落内新增，公共遍历函数抽出后被 `room`、`arbitration`、`assistant` 三处复用；
- 模型调用封装在服务端，前端不持有 apiKey（现状已如此，保持）。

## 九、安全与权限边界

1. **只读范围**：助理只读取本房间目录、参与方心跳与参与方私信；不遍历无关目录，不读项目源码内容。
2. **写入范围**：仅写本房间的 `助理进展.md`、`助理存档/`、`room-state.json`，以及经用户确认的委派消息文件；不删除任何现有文件。
3. **不执行动作**：助理不产生 shell 调用、不修改项目文件、不触发外部 CLI 执行；委派消息只是「递字条」，执行仍由对应智能体在自身环境完成。
4. **人工把关（按 9.1 三档权限执行）**：日常记录与问答可自动往返；状态切换、委派发送需用户在界面点确认；拍板与执行授权必须用户决定；模型结论一律视为建议稿。
5. **身份纪律**：服务端写出的系统记录 `from=doubao`；豆包为共享目录维护方，本模块服务端与双端 UI 由豆包维护；其他智能体的修改建议通过协作房间评审提出，不直接改共享目录。
6. **错误兜底**：模型超时/失败不影响房间原有对话浏览；接口异常时卡片显示「整理失败，请稍后重试」，不覆盖已有小结。

### 9.1 智能体自主发言三档权限（2026-10-30 确认口径）

回答「智能体能否自行在房间对话、用户是否不必当传话桶」：日常往来可以不经用户；带动作、带决策的内容按档位逐级放开，不做全自动无人闭环。

| 档位 | 类型 | 范围 | 用户角色 |
|---|---|---|---|
| 第一档 · 无人化 | 记录与日常问答 | 助理自动整理进展小结、提醒未回复消息；智能体之间 info / question / ack / review 类日常问答与确认回执自动往返，不弹出打扰 | 事后查看 |
| 第二档 · 半自动 | 任务交接与指派 | 助理拟好建议承接的智能体，用户在界面点确认后才写入对方收件箱；改派、撤回同样需确认 | 点一下确认 |
| 第三档 · 必须把关 | 方向判断与对外动作 | 方案分歧拍板、任务执行授权、对外发送、改写项目文件；先列出建议由用户决定，不自动执行 | 必须用户决定 |

现状基础（基于现有代码核实）：

- 信箱通道已存在：`messages/inbox/<agent>/`、`messages/outbox/<agent>/` 支持 `reply_to`、`thread_id`；`room-cli say / board / handoff / status` 提供房间发言、白板四段更新、显式交接留痕。
- DeepSeek 已有 `inbox-watcher.mjs` 半自动实例：info 自动已读，question / ack 可自动回复；task / handoff / request_review 仅汇总升级给人，不自动执行。
- 当前缺口：后端暂无统一编排器推动发言轮次；除 DeepSeek 外其余智能体未配同款自动处理器；房间公共频道写入口目前由用户确认动作触发。本方案按上述三档逐步补齐，不复制 OpenBot 式全权限、无审批的自动化模型。

## 十、开发步骤建议（确认方案后执行，本轮不写代码）

1. **后端先行**：`/api/collab/assistant`（GET 读取 + POST 生成）+ 公共上下文收集函数；`node --check server.mjs` 通过；用 1 个历史真实房间走通生成与本地草稿降级。
2. **Web 前端**：弹窗助理卡片 + 空态/加载/草稿三态；内联脚本抽取后 `node --check` 通过。
3. **桌面端同步**：`app.js` 同名函数对齐；`node --check renderer/app.js` 通过。
4. **同批增量（状态 + 委派）**：`/api/collab/state`、`/api/collab/delegate`；列表徽标与最近小结时间；委派单选单发；双端联调。
5. **验证方式**：
   - 选有真实对话的历史房间生成，核对四段内容与材料一致、无编造；
   - 临时断开模型配置，验证本地草稿可生成且明确标注；
   - 委派消息核对落位 `inbox/<目标>/` 且房间时间线追加可见记录；
   - 状态切换后重启服务/刷新页面仍能读回；
   - 双端界面文案与行为一致。
6. **打包纪律**：按既有约定，改动先在本地验证，用户明确要求后再统一打包，不自动提交、不自动发布。
