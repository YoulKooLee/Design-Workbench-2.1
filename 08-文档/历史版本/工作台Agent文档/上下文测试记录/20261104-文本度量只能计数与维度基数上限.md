## 一、为什么「计数」被算错（第一条要求）

原来的聚合只有一条路，所有汇总方式都先过 `parseNum`：

```
aggregateBy → rows.forEach → parseNum(r[metricField]) → 解析不出数就 badValue++ 并 return
           → 全部行都被跳过 → out 为空 → 预览判定「没有可绘制的数据」
```

按「故障类型」计数时，度量列（比如故障类型）写的是「设备离线」「网络抖动」这类文本，`parseNum` 一个都转不出来 → 40 行全进 `badValue` → 一张全文本的表**连计数都做不了**。

问题在语义：**计数数的是行数，不需要读单元格里写了什么**。`count(1)` 在 SQL 里也不看列值。所以拆成两条路：

| 汇总方式 | 走哪条路 | 对空单元格 | 对文本单元格 |
|---|---|---|---|
| 计数 | 只 `v = 1`，不解析 | 仍算一行（`count(1)` 语义），另计 `emptyValue` 供提示 | 正常计入 |
| 求和 / 求平均 / 最大值 / 最小值 | 先 `parseNum` | 跳过，计 `badValue` | 解析失败跳过，计 `badValue` |

界面这一侧：度量字段类型不是 `int / long / double / float / decimal / numeric` 时，汇总方式下拉**只给「计数」一项**，并在下方写明原因。同时加了自动收敛——换度量字段后如果已存的 agg 不在新候选里，自动置为首项。不收敛的话下拉会显示一个不存在的值，实际却按旧口径算，就是上一轮记过的「显示 A、实际算 B」。

这里有一个自己补的判断需要请用户确认：**我没有在「文本字段 + 求和」上做「允许选、选了再报错」，而是直接不给这个选项**。理由是预览里撞空态的代价比下拉里少一项高——少一项用户能立刻看到原因，撞空态要自己反推是不是数据有问题。如果你更希望「先让选、报错时再解释」，这条要改回去。

## 二、分组基数超过 30 就不给分组（第二条要求）

用户问「字段数据大量不一样，是不是也没办法分组」。落成判据是 `judgeDim`：

```ts
export const DIM_CARDINALITY_CAP = 30;
const NEAR_UNIQUE_RATIO = 0.9;

judgeDim(rows, field, totalRows?)
  ① distinct > 30                                  → 拒绝（too-many）
  ② distinct / nonEmpty ≥ 0.9 且 total > 30        → 拒绝（near-unique）
     其中 total = totalRows ?? nonEmpty
  否则                                               → 放行
```

三处落点：

- **维度下拉**：超限字段 `disabled`，选项文字后标「· 38 个取值，超过 30 组上限」或「· 近乎每行不重复，全表约 40 组，超过 30 组上限」。用户在选之前就知道选不了。
- **预览区**：`blockedHint` 排在「没有可绘制的数据」之前，直接给完整原因与换字段建议。顺序很重要——排在后面会被通用空态盖掉，用户看到的还是「没图」而不是「为什么」。
- **列表页图表预览**：调同一个 `judgeDim`，同一配置在两个入口必须给同一结论。

为什么上限取 30：色板只有 7 色，30 已经远超可读范围。30 这个数只是用户给的边界，判据的真正含义是「这列是不是近似唯一键」——`ticket_no` 40 行 40 个值、`area_name` 40 行 38 个值，按它分组画出来就是明细表，不是汇总。

## 三、为什么「在线率 · 按所属组织」还是不出图（第三条要求）

和上一轮是同一个根因的另一半：

```
度量 online_rate → 是 SQL 派生列 → 预览走结果集
        → 结果集列 = device_category_name / device_total / online_count / online_rate / update_time
        → device_org_name 不在里面（SQL 既没 select 也没 group by）
        → 维度选了「所属组织」→ missingUserDim → 空态，不出图
```

上一轮我只补了 `device_category_name` 和 `update_time`，**没把这条当成通用约束**。这轮把它正过来，两侧一起修：

**数据层**：`t_raw_device_realtime` 的 SQL 在 select 与 group by 里同时加 `device_org_name`，`resultCols` 补该列（类型 String，长度 100），30 行 result 逐行补值（视频监控→园区北门、充电桩→停车场A区、环境传感→实验楼、门禁/消防→综合楼）。

**提示层**：派生度量缺用户维度时，不再只说「换个维度」，给三条可执行的改法：

1. 在 select 与 group by 里同时补上它（并提示：补完后该指标会多出一个维度口径，保存前确认这是要的分组）
2. 换成 SQL 出参里已有的字段分组（现拼出当前可选的字段清单）
3. 或者把度量换成原始库表的物理列，走贴源明细，表里全部字段天然都能分组

一句话规则写进设计说明：**预览能选到的列，必须等于运行时能拿到的列**。给一个能选却一定失败的选项，比不给更糟。

## 六、设计说明 icf-04 补了哪三条

按 `AGENTS.md` §102 的判据（读者是开发，回答「要实现什么、边界在哪」），三条全部写成陈述式规格，不写「用户提出」「之前错了」：

- 【第二步·标字段角色·度量】补：度量可以是文本列，但汇总方式只剩「计数」——计数数行数、不看单元格；求和/平均/最大/最小都要先解析成数，文本解析不出来。不是数据缺失，是口径不成立。
- 【第二步·标字段角色·维度】补：候选字段先判能否分组，两条判据任一命中即置 disabled 并标原因；判据②（近乎每行一个值且全表 > 30 行）专为「物理列走贴源样本」准备；全表 ≤ 30 行时不走判据②。
- 【第三步·度量计算方式】补：候选项不固定，非数值列只给「计数」；换度量后旧值不在候选里要自动收敛。
- 【空态·优先级】补：维度不合格 → 字段不在数据里 → 无数据，按此序取第一条。
- 【约束·候选列必须 ⊆ 出参列】新增一条：派生度量的维度候选只能取 `resultCols`；判断标准一句话「预览能选到的列，必须等于运行时能拿到的列」。

## 七、本轮唯一一次设计反复：near-unique 判据删了又加回来

写在这里是因为这个反复有信息量，不是流程瑕疵：

1. **首版**：两条判据（>30 / near-unique）。单测报两条 FAIL——「恰好 30 组」被 near-unique 误杀、「6 行 6 取值」被判近乎唯一键。30 行 30 个取值本身就是 30 个合法分组，判它「近乎唯一」等于同时说「30 组可以」和「30 组不行」。
2. **第二版**：删掉 near-unique，只留 distinct > 30。单测全 PASS。
3. **CDP 实测打回来**：`area_name`（全表 40 行 38 组）**没被拦下**。因为物理度量走 8 行贴源样本，样本里 8 个区域 / 8 行 = 看着只有 8 组，判据①放行。删掉 near-unique 等于把「样本远小于全表」这个场景彻底丢了。
4. **最终版**：near-unique 加 `total > CAP` 条件。`total = totalRows ?? nonEmpty`，30 行的表 total=30 不大于 30 → 不触发，冲突消解；40 行表 total=40 > 30 且样本 8/8 → 拦下。

教训：**单测全 PASS 不等于规则对**。第一版删掉 near-unique 时单测是绿的，因为单测喂的是「已知全表」的数据，压根没造「8 行样本 + 40 行全表」这个输入。判据的失效场景只能靠真实数据撞出来。

## 八、本轮踩坑

1. **计数不该走数值路径**：`count(1)` 不看列值。把「计数」实现成「数能转成数的行」，全文本表就永远数不出来。凡是「数行数」的语义，都不能先解析单元格。
2. **同名下拉必须按 label 定位**：度量与维度的候选项是同一批字段，用 `select` 里有哪些 option 去定位会抓到度量下拉，改了度量而不是维度，三次验证全读到旧的空态。改用 `.form-group` 的 `.form-label` 文字精确匹配。
3. **判据的边界要正反两遍都测**：30 组必须过、31 组必须拦。只测一边的判据很容易写成恒真或恒假（上一轮的 `Math.min(0, ...)` 就是同类）。
4. **样本小的时候判据会失效**：样本 distinct 只能证明「至少这么多组」，不能证明「最多这么多组」。凡是对样本算的聚合类判据，都要再乘一个「全表 / 样本」的放大系数，或者像这里一样直接用全表行数。
5. **`useEffect` 位置**：新加的 agg 收敛 `useEffect` 第一版放在 `if (rule === 'SQL开发') return null;` 之后，违反 hooks 规则（提前 return 后不能再调 hook）。移到上报配置的 `useEffect` 之前。
6. **用户「又又又」是准确的**：同一个「预览能选但算不出来」的坑，这已经是第三次（先是没时间列、再是没 `device_org_name`）。每次都是「只改了被指出的那一处」。应把「候选列 ⊆ 出参列」写成一条可校验的约束，而不是遇一个补一个。
