## 一、为什么没有图（回答用户的问题）

数据链断在这一步：

```
度量 online_rate  →  是 SQL 派生列，物理表 t_raw_device_realtime 里没有这一列
                  →  预览只能走「指标结果集」（对 SQL 出参做二次聚合）
                  →  而这份结果集的列是：device_category_name / device_total / online_count / online_rate
                  →  没有任何时间列
                  →  按「按月」分组时 update_time 不在结果集里
                  →  dimsForCalc 里那一维分不出组 → 命中空态，图不渲染
```

不是图表组件坏了，是那份数据里根本没有「月份」这一列。上一轮只把「用哪份数据」分开（物理列走贴源样本、派生列走结果集），没验「分开之后这份数据够不够算」。

## 二、修法（两层）

### 2.1 数据层：让派生指标的结果集带上时间

原 SQL 只 `group by device_category_name`，出参自然没有时间。改成 `group by device_category_name, date_format(update_time,'%Y-%m')`，并把该表达式以原名 `update_time` 输出（中文名标「统计月份」）。这样「按月」这个粒度直接落在结果列上，不需要在预览层再造一个 `stat_month` 字段——两套名字会让界面和 SQL 各说一套。

新数据的两个自洽校验（写进 data.ts 注释，也写进 note）：

| 校验 | 结果 |
|---|---|
| 各大类 6 个月 device_total 求和 | 视频监控 512 / 充电桩 240 / 环境传感 198 / 门禁 186 / 消防 148，合计 1,284 = totalRows |
| 各大类 6 个月 online_rate 求平均 | 97.31 / 96.29 / 94.17 / 91.41 / 89.19，与「只按设备大类」的环形图完全一致 |

这样做的好处：只按维度分组和维度+时间分组两种配置能互相印证，不是各算一套。

### 2.2 提示层：空态要说清「差哪一列、怎么补」

原来的空态写「请换个维度或改选时间字段」——这是把问题推回给用户，他并不知道该改配置还是改 SQL。现在的空态按当前事实表和所选时间字段**现拼**出可照抄的两行：

```
① 在 select 里补一列时间：date_format(update_time, '%Y-%m') as update_time
② 在 group by 里补上同一表达式：group by …, date_format(update_time, '%Y-%m')
或者把度量换成原始库表的物理字段（如 online_status 求和），这样走贴源明细，时间列天然就有。
```

空态不是错误提示，是修复指引。

## 四、合并与截断：从自然语言到可执行算法

### 4.1 先分清两件事：可加才可合并

用户原话只说「其余合并或点名说明」，没说「合并成什么、按什么规则合并」。要落成代码，先得回答一个数学前提：**这些数值相加有没有业务含义**。

| 聚合方式 | 可加 | 5 个值相加得到什么 | 能否合并 |
|---|---|---|---|
| 求和 / 计数 | 是 | 5 个大类设备数合计 1,284 台，是一个真实的量 | 可以合并 |
| 求平均 | 否 | 5 个在线率相加 = 468%，不对应任何东西 | 不可合并 |
| 最大值 / 最小值 | 否 | 5 个最大值相加不等于全局最大值 | 不可合并 |

所以规则不是「按项数决定合并」，而是「**按可加性决定合并**，项数只决定要不要动」。这条前提用户没说过，是我从业务含义推出来的——已写进 `planPieSlices` 的 JSDoc 与设计说明卡片，请用户确认。

### 4.2 落成两个纯函数

```ts
export const CHART_PALETTE = ['#1eb195','#3d7eff','#f59e0b','#e5484d','#8b5cf6','#0ea5e9','#64748b'];
export const PALETTE_CAP = CHART_PALETTE.length;   // = 7

// 饼图 / 环形图：项数 > cap 时按可加性分两支
planPieSlices(items, additive, cap = PALETTE_CAP)
  → { slices, mergedCount, hiddenNames }
     · 先剔除 value ≤ 0（占比与排名对负值无意义），再按 value 降序
     · len ≤ cap            → slices = 全部，mergedCount = 0，hiddenNames = []
     · len > cap && additive → slices = 前 cap-1 项 + { name:`其他 N 项`, value: 后 N 项直接相加 }
                               mergedCount = N（N = len - cap + 1），hiddenNames = []
     · len > cap && !additive→ slices = 前 cap 项，mergedCount = 0
                               hiddenNames = 后 len-cap 项的名称（调用方负责在图下点名）

// 多图例折线 / 分组柱状：永远不合并
planSeries(rows, cap = PALETTE_CAP)
  → { series, hidden }
     · 按 keys[0] 归并，累加 Math.abs(value) 得到每个系列的权重
     · 按权重降序取前 cap 条，其余进 hidden
```

`planSeries` 用**绝对值之和**排序而不是带符号求和：负值大系列（如「大负」累计 −480）若按带符号求和会排到最后被误删，图上看不出这个对象其实是存在的。

### 4.3 为什么多系列不能照抄饼图的合并

把「门禁设备」和「视频监控」2026-05~10 的数值相加当成一条线，画出来的东西不对应任何真实对象——饼图里合并后叫「其他 N 项」还诚实，折线里合并出一条线却要给它起个系列名，起什么都不对。所以折线只截断 + 点名，绝不合并。

| 用例 | 输入 | 断言 |
|---|---|---|
| 1 | 5 类设备数，可加 | 全画 5 项、不合并、合计仍 1,284 |
| 2 | 10 项（100→55），可加 | 恰 7 扇区，末项「其他 4 项」= 70+65+60+55 = 250，合计不变 |
| 3 | 10 项比率，不可加 | 只画 7 项、**无「其他」扇区**、点名 D8/D9/D10、合计 ≠ 原始合计（证明没做加法） |

## 八、本轮踩坑

1. **「数据源分流」写完不等于「算得出来」**：分流解决「用哪份数据」，还要再验「这份数据里有没有用户选的分组列」。前者是架构，后者是可算性，两件事。分流后必须对每个可选配置跑一遍「列存在性检查」。
2. **`Math.min(0, ...values)` 不能当「最小值」用**：它恒 ≤ 0，任何依赖「最小值 > 0」的判据全部恒假。真实最小值与「含 0 的刻度下界」是两个语义，必须分开命名（`dataMin` / `bottom`）。
3. **截断坐标轴必须披露**：折线截断能救趋势，但不写「纵轴起点」等于让人按 0 起的直觉读图，5% 的差看成 0.5%。柱状图不能截断——柱长即比例。
4. **空态提示要能直接照做**：写「请换个维度」是把判断成本推给用户。要么点名缺哪列，要么给可复制的 SQL 片段，最好两者都给。
5. **CDP 验证脚本要模板化**：入口必须 `Page.navigate` 到 `/prototypes/indicator-platform/index.html`，再点「指标列表」→ 行内「指标配置」，等 6s+，视口宽 ≥1800。本轮又因直接开 hash 拿到空壳白跑一轮。
6. **管道截断会杀 node 进程**：`| Select-Object -First N` 提前关闭管道 → 验证脚本没跑完 → 读到的是上一次的旧截图。必须整份落盘再读。
7. **「文件缺哪一项」不能用单行正则扫**：本轮我先用 `[regex]::Matches($t,'(?m)^\s*7[.、]')` 判断记录文件是否齐 7 项，2 个文件被判缺第 7 项；完整读出来才发现全都齐——是 PowerShell 处理中文编码时把行首吃掉了。**判断缺项必须完整读文件**。这与主 bug 同类：验证手段本身不可靠，会把「没测到」当成结论。
