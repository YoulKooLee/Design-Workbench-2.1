### 1.1 注入位置：不是 system prompt，是**第一条用户消息里的隐藏块**

实测会话首轮用户消息（`c902d0e3`，2026-09-22 22:30，16,883 字符）结构：

**推论**：AGENTS.md 与用户提问在**同一条消息**里。"压缩保留用户消息原文"对这条消息是否同样成立未经证实，
这直接决定 Q4 开场话术能否奏效（§4.4）。

### 1.3 上限：8,000 **字符**（不是字节）

```js
Eu = 8e3
... (e.length > Eu ? `${e.slice(0, Eu)}\n[...too long, omitted...]` : e)
```

- 判据是 `String.length`（UTF-16 码元 ≈ 字符数）。**用字节数体检会误报**：
  `_project-development/AGENTS.md` 13,334 字节 = 实际只有 **7,540 字符**。
- 超窗只砍**尾部**且静默——被砍的正是文件末几节，通常是"编码底线 / 语言与安全"。
- 实测块长：`<project_guidance>` 共 **8,221 字符**，`[...too long, omitted...]` 起于块内偏移 **8,173**，
  故正文恰 8,000；余下 ≈173 是开标签 + `<![CDATA[` + 两行包装（`The project guidance below is…` 与 `File: <绝对路径>`）。
  **"8,392"应更正为"正文 8,000 / 整块 ≈8,220"，且它是变长的（随路径长度）。**

### 1.4 触发条件：`first_turn` + 历史判据

```js

  shouldApply(e){ return e.codebuddyMeta.alreadyInjectedUserContext===!0 || isAskLikeMode(...) ? !1
                       : typeof e.cwd==`string` && e.cwd.trim().length>0 }
```
```js

  if (e.stage===`first_turn` && (p.hasPriorUserMessages || i) || !e.shouldApply(p)) continue;
```

- 决定变量是 **`hasPriorUserMessages`**，不是"是否压缩过"。同一会话内因此是 0/1 阶跃。
- `user_info` / `identity_context` / `UserInfoSection` 同为 `first_turn`；`current_time` / `UserCommandSection` /
  `WorkingMemoryReminderSection` 是 `every_turn`。
- 附带：`isClearSession===true` 时 `composeUserPrompt` 直接 `return e.prompt`——`/clear` 后连 `every_turn` 段也不渲染。
- `isSessionStart = session/load | session/new | session/resume`：这就是"恢复轮会重新触发 `first_turn` 段"的来源。

## 3 hooks 与压缩：旧结论③⑧要改的部分

这一节的结论**全部有代码 + 日志双重证据**，且推翻了此前"外部宿主不执行 hook"的判断。

### 3.1 hooks 真的会跑，但从不读 `.agents/hooks/`

**日志实证**（`~/.workbuddy/logs/2026-10-19/崂山国家实验室项目__*.log`，2026-10-19 09:13）：

```
[SessionHookManager] executeSessionStartHooks source=resume hasHooksCheck=0ms executeHooks=455ms total=456ms
[HookExecutor] spawn pid=6360 shell=…\PortableGit\versions\1.3.0\bin\bash.exe timeout=5000ms cmd=bash "…/plugins/cache/workbuddy-builtin/workbuddy-docx/…"
```

→ 恢复会话时确实执行了 hook，**耗时 455 ms，真的 spawn 了 bash 子进程**。（本例来源是内置插件 `workbuddy-docx`。）

**代码实证**：`hookManager.getHooks(event)` 的四个来源，**没有一个是扫描目录**：

```js
let n=[], s=await this.settingsManager.get(`hooks`);      // ① 设置文件的 hooks 键（按事件名取）
s && (i=s[t]) && n.push(...i)
let c=await this.loadHooksFromPlugins(t);                  // ② 插件清单 components.hooks[event]
n.push(...c)
let p=this.scopedHookRegistry.getHooks(t); p.length>0 && n.push(...p);   // ③ 进程内注册（SDK/宿主注入）
// ④ sdkHooksManager.getHooks()（hasHooks() 里额外查）
```

执行链完整：`executeHooks()` → `executeCommandHook()` → `HookExecutor.execute()` → `(0,fc.spawn)(shell,args,opts)`，
有超时 `SIGTERM→1s→SIGKILL`、有 stdout JSON 解析、`allowed:false` 可 **block**，并兼容
`CLAUDE_PROJECT_DIR` / `CLAUDE_PLUGIN_ROOT`（这是一套 Claude-Code 兼容引擎）。

**`.agents/hooks/` 的判定**：三个搜索域（asar / CLI / 全部 unpacked js）里
`.agents/hooks`、`.agents\hooks`、`.agents/hooks.json`、`.agents\settings.local.json` **全部 0 命中**，
而同一遍搜索里 `.agents/` 能命中（`~/.agents/skills/`，沙箱白名单）。→ **不是"没搜到"，是"不存在"。**

### 3.2 可用的强制落点（这是本轮最有行动价值的产出）

项目级 hook 的唯一落点是 **`<cwd>/.codebuddy/settings.local.json`**（或 `settings.json`）的 `hooks` 键
（settings 文件名常量 `settings.local.json` / `settings.json`，scope 枚举 `USER / PROJECT / PROJECT_LOCAL / CLI`，
`hooks` 被显式列入跨 scope 合并的 `mergeBySubKeySettings`）。

可用事件（引擎枚举，配置里用**PascalCase 字符串**）：

| 事件 | 时机 | matcher 匹配的值 | 能"强制"什么 |
|---|---|---|---|
| `SessionStart` | 会话 new/load/**resume** | `source` | 恢复时自动注入/校验规则摘要（`additionalContext`） |
| `UserPromptSubmit` | 每条用户消息提交时 | — | `allowed:false` **直接拦下输入** |
| `PreToolUse` | 每次工具调用前 | `tool_name` | `permissionDecision:"deny"` 拦工具 |
| `PostToolUse` / `PostToolUseFailure` | 工具调用后 | `tool_name` | 记账、回写、告警 |
| `PreCompact` | **压缩开始前** | `trigger` | stdout 作为 `custom_instructions` 注入压缩；可在此强制快照 |
| `Stop` / `SubagentStop` | 轮次/子 agent 结束 | — | 质量闸门（可 block） |
| `SessionEnd` / `Notification` / `UserPromptExpansion` | 其余 | `reason` / `notification_type` / `command_name` | — |

`PreCompact` 的注入语义（代码原文）：

```js
async executeManualPreCompactHooks(t){
  ...
  let i = await this.sessionHookManager.executePreCompactHooks(t.session,"manual",s);
  i && (t.session.hookContexts.preCompactInstructions = i)      // ← stdout 成为压缩的 custom_instructions
} catch(t){ this.logger.warn("PreCompact hook failed:",t) }
```

→ **"闭环→快照→才压缩"不再是空文**：`PreCompact` 确实在压缩前执行，且其输出会被喂给压缩器。

### 3.3 现有工程包的 hooks 为什么一条都没生效（两个独立原因）

`01-项目\崂山国家实验室项目\.agents\hooks.json` 内容（节选）：

```json
{ "version": 1,
  "hooks": {
    "sessionStart": [ { "command": "node .agents/hooks/run.cjs session-start" } ],
    "preToolUse":  [ { "command": "node .agents/hooks/run.cjs gateguard", "matcher": "Write|Edit|MultiEdit" } ],
    "preCompact":  [ { "command": "node .agents/hooks/run.cjs pre-compact" } ],
    "stop":        [ { "command": "node .agents/hooks/run.cjs stop-quality-gate", "timeout": 30 } ] } }
```

1. **位置错**：`.agents/hooks.json` 不在任何加载源里 → 从不被读。
2. **事件名错**：用的是 camelCase（`sessionStart`/`preToolUse`），引擎认的是 **PascalCase**（`SessionStart`/`PreToolUse`）；
   即使被读到也匹配不上。

且形状也不同：引擎要的是 `{ "Event": [ { "matcher": "...", "hooks": [ { "type": "command", "command": "...", "timeout": 30 } ] } ] }`。

**迁移最小示例**（落点 `<cwd>/.codebuddy/settings.local.json`）：

```json
{
  "hooks": {
    "SessionStart": [
      { "matcher": "resume|startup",
        "hooks": [ { "type": "command", "command": "node .codebuddy/hooks/session-start.cjs", "timeout": 30 } ] }
    ],
    "PreToolUse": [
      { "matcher": "Write|Edit|MultiEdit",
        "hooks": [ { "type": "command", "command": "node .codebuddy/hooks/gateguard.cjs", "timeout": 10 } ] }
    ],
    "PreCompact": [
      { "hooks": [ { "type": "command", "command": "node .codebuddy/hooks/pre-compact.cjs", "timeout": 30 } ] }
    ],
    "Stop": [
      { "hooks": [ { "type": "command", "command": "node .codebuddy/hooks/stop-gate.cjs", "timeout": 30 } ] }
    ]
  }
}
```

**必须实测一次**（5 分钟，可证伪）：
1. 建 `.codebuddy/settings.local.json`，只放一个 `SessionStart` hook：`node -e "require('fs').appendFileSync('hook-ran.txt', Date.now()+'\n')"`；
2. 在该目录开一次会话（或 resume 一次）；
3. 检查 `hook-ran.txt` 是否出现、日志里是否出现 `[HookExecutor] spawn`。
   → 出现即证明通道可用，再把整套 hooks 迁过去；不出现则检查 cwd 与 scope。

> 注：`matcher` 是按 `getMatchValue()` 取到的值做 `new RegExp(matcher).test(value)`——
> `PreToolUse`/`PostToolUse` 取 `tool_name`，`SessionStart` 取 `source`，`PreCompact` 取 `trigger`。

### 3.4 压缩：本地判定 + 明文信号 + 实测在 53% 就压

**判据在本地、发请求前**（`checkAutoCompact()` 位于请求组装管线，紧接 `repairModelInput`）：

```js
... await this.checkAutoCompact(); let c=this.repairModelInput(t), p=await this.injectSendNowItems(c), ...
```

**主判据 = token 百分比**（不是消息条数、不是固定轮数）：
`inputTokens + 尾部工具结果估算 ≥ min(autoCompactWindow, contextBudget) × 阈值`，
另有 **30 s 冷却**、**连续压缩上限 5 次**、"自上次压缩后无有意义新内容则跳过（would loop）"、
以及"输入 + maxOutput ≥ 预算 → 阻塞式先压缩再发"。
常量：窗口默认 `2e5`、clamp `[1e5, 1e6]`；紧急阈值默认 **`0.92`**（服务端 `tokenUsageThresholds.inputTokens.emergency` 下发）；
环境变量覆盖：`CODEBUDDY_AUTOCOMPACT_PCT_OVERRIDE`、`CODEBUDDY_AUTO_COMPACT_WINDOW`、
`CODEBUDDY_PRE_MESSAGE_COMPACT` / `_PCT`。

**实测一条**（全部日志里仅存 1 条 `[Compact]`，日志也在轮转）：

```
[Compact] session=482352f3 tokenCount=159695/300000 (53.2%, threshold=90.0%),
  force=false, historyLen=661, compactType=pre-message-auto,
  trigger=pre_message_threshold, isSubAgent=false, enablePreMessageCompact=true → routing to strategy: PreMessage
```

两条可直接用的推论：
1. **实际触发点远早于 92%**：这次是 53.2%（预消息压缩阈值走的是另一条 `PRE_MESSAGE_AUTO` 通道）。
   所以"压缩把规则冲掉"这件事比预想的更频繁，会话有效长度比 token 预算暗示的更短。
2. **它有明文日志信号**：`[Compact] …`、`[shouldCompact] Skip: cooldown (…)`、
   `[AcpBroadcastService] broadcastCompactStarted/Completed/Cancelled/LimitReached`。
   还有 ACP `session/update` 通知：`messageId = compact-maxtoken-<sessionId>-<epochMs>`、
   `_meta["codebuddy.ai/compactType"]`、`.../compact-cancelled`、`.../compact-limit-reached`。
   → **"压缩时机不可知"是错的**；外部可以 grep 日志或在 `PreCompact` hook 里同步记账。

## 4 四个待续问题的回答

### 4.1 Q1：T-4 —— 不再是"证据不足"，而是被目录迁移掩盖

代码层确定"同 workspace 新开会话必然重注入"（`first_turn` + 无历史消息）。真正的新问题是：

判据也从"是否仍为 8,392 字符"改成 §2.4 的 6,490 / 30+。

### 4.2 Q2：还能在哪儿强制？——现在有五个，且都是真强制

| 落点 | 强度 | 说明 |
|---|---|---|
| **构建命令 / 构建后置脚本** | ✅ 硬 | 模型绕不过去 |
| **`PreCompact` hook** | ✅ 硬（新） | 压缩前执行，stdout → `custom_instructions`：可强制"先写快照再压缩" |
| **`UserPromptSubmit` hook** | ✅ 硬（新） | `allowed:false` 可**拦下用户输入**（可用于"没读规则就不许开工"） |
| **`PreToolUse` hook** | ✅ 硬（新） | `permissionDecision:"deny"` 拦写文件/改配置 |
| **`SessionStart(source=resume)` hook** | ✅ 硬（新） | 每次恢复自动重建规则注入——正好补上 §2 那个"恢复即空壳"的洞 |
| git hook / CI | ⚠️ 半强制 / 延迟 | 只拦提交；`--no-verify` 可绕；CI 反馈晚 |
| "闭环→快照→才压缩"（无 hook） | ❌ 空文 | 但接上 `PreCompact` 后成立 |

**唯一前提**：这些必须写在 `<cwd>/.codebuddy/settings.local.json`，不是 `.agents/`。

### 4.3 Q3：半衰期能量化吗？——曲线不存在，但"压缩节律"可以量化

- 规则正文的**存在**是 0/1：第 1 请求有、第 2 请求起无、恢复轮是空壳。所以"第 N 轮关键词命中率"必然阶跃后贴地，没有信息量。
- 真正该量化的是**压缩节律**（决定"能记多久"）：从日志可提取 `tokenCount/预算`、`pct`、`threshold`、`compactType`、`trigger`、
  `historyLen`；从会话日志可数压缩包（本例 17 个：9 个 `<cb_summary>` + 8 个 `<conversation_history_summary>`）。
  本轮实测样本 n=1（日志被轮转），但方法已跑通：**"会话该多长重开"的阈值应该由压缩事件数来定，不是轮数**。

### 4.4 Q4：开场话术 —— 机制上成立，但仍有一个未证前提

成立的三条理由：规则块本来就在**用户消息**里；`first_turn` 读的是"有无历史用户消息"（用户自己发的话必然满足）；
用户消息是压缩器明确保留的类别。

**未证前提**：压缩后保留的是"最近 N 条用户消息"还是"全部"？若是前者，第 1 条消息里的规则会随窗口滑出。
→ 所以结论应是：**要每轮递增**，而不是"开场说一次"。
具体形态：把 ≤20 字的铁律放进固定开场模板，每开一轮顺手带上——成本一次粘贴，收益是"哪怕注入全灭，规则仍在"。

### 5.2 位置法再加一条：`<system-reminder` 开头

原始字符串探针会被审计脚本自身污染（本例 587 次命中，真阳性 11 次）。可靠判据是：
**该用户消息以 `<system-reminder data-role="user-context">` 开头**。

### 5.3 PowerShell 内联中文仍然是雷（这次踩两下）

`Test-Path "C:\...\产品设计工作台"` 返回 `False`，而同一目录 `Get-ChildItem` 能列出来；
改用 node 后，因手写父路径少了 `01 ` 前缀又得到一批 `ENOENT`，差点误判"目录被删"。
**纪律**：路径真实性一律用 node + 逐级拼接；不要用内联中文做 `Test-Path` / `Select-String`。

### 5.4 静态取证必须同时搜 asar 与 asar.unpacked（本轮最大教训）

asar 头部里 `offset:-1` 的条目是 **unpacked**，不在 96.5 MB 字节流里。
**hook 执行器、压缩阈值、spawn 逻辑全在 `app.asar.unpacked\cli\dist\codebuddy-lite-wb.mjs`（9.49 MB）。**
只搜 asar 会得出两个错误结论："没有 hook 执行路径"、"客户端没有本地压缩阈值"——本轮先得出、后纠正。

另附一条：`main/tar.js` 的 `scanHooks()` 会 stat `<pluginRoot>/hooks/` 并读 `hooks.json`，
但只 `extractHookCommandsFromRecord()` 抽 command **字符串**用于市场页展示——这是"字符串存在 ≠ 会被执行"的典型样本，
也是我一开始差点被误导的地方。

### 5.5 验收工具必须"自证分布"，否则会被自己的输出骗（2026-10-19 实际发生过一次）

同一天出现两份互相矛盾的结果：一份是"100 轮 inj 全 0、45 个异常全是 SUSPECT、cwd 都是临时目录"，
另一份（本报告）是"100 轮里 11 轮 inj>0，最大 8,184，另有 12 个 FAIL(cwd-missing)"。

两个陷阱：

1. **默认视图只打印异常行**，而异常行的 `inj` 必然是 0 → 很容易把"异常子集"读成"全体"，得出"从来没注入过"。
2. **数据根不止一个**：除 `~/.workbuddy/projects`（100 轮）外，本机还有
   `C:\ProgramData\WorkBuddy\users\d2a38f5\.workbuddy\projects`（4 轮，会话全在 `WorkBuddy\<时间戳>` 沙箱目录，
   所以 inj 天然为 0）。**扫哪个根，结论就不同。**

对策（已落到 `check-injection.mjs`）：
- 默认 **始终打印** 数据根清单、`inj>0` 计数、`layout>0 但 inj=0` 计数，以及 `inj>0` 明细；不再只印异常；
- 异常行加警示语"inj 必为 0，勿据此断言全体"；
- `--json` 输出机器可读台账（含 `dataRoots` / `totals` / `injectedDetail` / 逐行 `rows`），便于两人对账。

**教训**：任何"是否发生过 X"的验收脚本，必须把"发生过的样本"与"检查过的总体"一起打印；
只输出告警的脚本会系统性地让人误判为"什么都没发生"。

**顺带确认另一条通道的边界**：`~/.codebuddy/projects`（CodeBuddy CLI / 豆包侧，13 个会话文件）
里 **0 命中 `project_context` / `project_guidance`**——即 CLI 侧不把组装后的用户消息落盘，
那个通道**没有可观测的注入记录**。要验豆包侧的注入，只能换证据（CLI trace / 请求日志），不是本脚本挑食。
