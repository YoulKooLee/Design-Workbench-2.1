## 0. 摘要

一句话：**旧版的价值全在"踩过的坑"，脆弱点全在"启动链路 / 记忆分层 / 目录卫生"；参考版的价值在"一体化单页 + 反代同源"；本轮新增价值在"把共享信息目录整体迁入工作台、每个项目指派智能体、可互相交接"，并把 v1.7 的需求前端组件变成工作台的共享组件库——可拓展、可维护、可在原型工程中调用。**

v2 做六件事：

| 动作 | 干什么 | 对应问题 |
|---|---|---|
| **搬家** | 旧目录 → 新目录，剔垃圾、留资产；**只迁试点项目（指标管理平台），其他项目留在旧 Axhub** | P5/P6/P17/P20 |
| **收敛** | 记忆去厂商化：中立 `Agent_Memory/` 主干 + 各智能体按规范维护各自文件 + 自举入口 | P3/P10/P11/P19 |
| **加固** | 启动链路自检、环境清洗固化、补丁立账、冒烟测试 | P1/P2/P12/P13 |
| **立账** | 配置、端口、补丁、文档版本全部进单一真源 | P9/P14/P15 |
| **通信集成（新增）** | **共享信息目录整体迁入**：项目指派智能体 + 交接包（双写）+ 通信面板模块 + 快捷入口 | 本轮新需求 |
| **组件库（新增）** | v1.7 需求前端组件迁入共享组件库：可拓展 / 可维护 / 可调用；**30+ 技能以 v1.7 为权威真源** | 本轮新需求 |

**关键判断**：v1.7 已内置"组件可拓展"的机制（`frame/` 根下新建文件夹 + `index.json` 登记 + `_meta/pages.catalog.json` + ui-libs 知识 + gallery 预览墙）。v2 要做的是：① 修掉 P0-①（index.json 非法 JSON）；② 把整套迁入工作台共享目录并纳入校验；③ 让**原型工程（`src/prototypes/`）真正能调用**这些组件（目前只服务 `feature-dev` 的 Vue 交付，不直接服务原型页）。

### 1.7 annotation 技能与原型标注：不重复，统一理念、两种载体（【新增】已确认）

| 维度 | v1.7 `annotation` 技能 | 参考版 J3 附注 / 设计说明模块 |
|---|---|---|
| 作用对象 | **交付代码**（Vue/React SFC） | **原型预览页**（HTML 原型） |
| 驱动源 | **SRS 真源**（扫描需求文档 → prd-analyzer 提取功能点） | 产品评审/设计说明（人工批注） |
| 定位机制 | 注入唯一 class（`.annot-xxx`）到源码 + Edit 落盘 | CSS 选择器定位元素 + `annotations.json` 落盘 |
| 保存通道 | Vite 插件 `POST /__annotation_save__`（同步中间件 + enforce:pre） | 项目本地 JSON，随 git 走 |
| 服务于 | 开发验收（需求点 ↔ 代码位置可追溯） | 产品设计（评审反馈 → 迭代） |

**结论**：两者**理念同源**（都是"唯一 class 定位 + JSON 落盘 + 与 UI 库解耦"），但**载体不同、阶段不同、服务对象不同**——不重复。v2 把它们统一为**一套标注理念、两种载体**：
- 原型期：J3 附注 / DesignNotesPanel（产品评审标注）；
- 交付期：v1.7 annotation（SRS 驱动、代码注入标注）。
- 统一约定：class 命名规范（`.annot-*`）、JSON schema、落盘路径规则共用；技能真源以 v1.7 为准。

**30+ 技能真源（已确认）**：v1.7 相当于是更新补丁——**30+ 技能（srs-writer/prd-writer/hld-design/lld-design/feature-dev/annotation/frontend-design 等）以 `更新资料\vibepm-dev-agent-v1.7` 为权威真源**，工作台只做触发路由与入口，不另维护副本；组件资产（frame/ui-libs/catalog）迁入 `03-组件库/` 并在工作台内校验。新增/修订技能直接在 v1.7 包上做，工作台通过 `BOOTSTRAP.md` 指向。

## 2. 目标架构

### 2.1 设计原则

1. **能跑的坚决不重写**：`launch-project.ps1`（8 步已踩坑修稳）与参考版 `server.mjs`（零依赖 + 相对路径）只加固、不推倒。
2. **参考版单页为底，旧版目录骨架为壳**：反代同源 + iframe 一体化形态保留；01-09 目录体系、模板、回收站、日志保留。
3. **配置单一真源**：端口/路径/项目识别规则/node 选择/协作入口全部进 `workbench.config.json`，脚本与文档由它生成/校验。
4. **记忆去厂商化**：主干用中立 `Agent_Memory/`，**各智能体（CodeBuddy/WorkBuddy/DeepSeek/千问/豆包）在其下按规范分区维护各自文件**，主干结构由豆包统一维护；各 agent 私有目录（`.codebuddy/` 等）只做平台适配层，不存主干。

6. **组件库单一真源、对照调用**：v1.7 的 frame + ui-libs 迁入共享 `03-组件库/`；组件以"样板 + catalog + 知识"三位一体登记，工程调用遵循"对照重写 / 按需拷贝"，不把母版当运行时依赖。**30+ 技能以 v1.7 包为权威真源，工作台按需引用，不另维护副本。**
7. **有账可查 + 卫生自动化**：补丁、临时脚本、文档版本都登记成册；tmp 即产即删、回收站可还原。

- `component-registry.json`（新）记录组件 id / 版本 / page-type / 状态 / 维护人，供面板展示与"是否最新"判断。

**H3 · 可维护（校验与版本）**

- `smoke-test.mjs` 增加组件库校验段：① 全部 JSON 合法 + 无 BOM；② `index.json` ↔ 实际目录一致；③ `pages.catalog.json` 引用文件全部存在；④ ui-libs catalog 与文件一一对应。**直接拦截 P0-① 这类回归**（知识库 02 P2-⑨ 的 validate 思路落地到工作台）。
- 版本管理：母版 `template.manifest.json` 的 `version` 字段 + `component-registry.json` 双处记录；升级依赖后校验原生模块与组件引用（沿用 T9 永不删锁文件）。
- 维护权归豆包（与共享目录治理一致）；其他智能体提建议。

**H4 · 可调用（在产品设计工程中真正用得上）**

现状：v1.7 的组件只服务 `feature-dev` 的 Vue 交付链路，**工作台原型工程（`src/prototypes/`，Axhub Make 生态）没有直接调用通道**。v2 打通三条路：

| 调用方式 | 做法 | 适用场景 |
|---|---|---|
| **对照重写（主路径）** | 面板「组件库」Tab 浏览 catalog → 选中 page-type → 复制样板三件套 + ui-libs 规范 → 由智能体在原型页对照实现（继承 `pro-*` 结构改业务，禁止换皮） | 正式原型页开发 |
| **组件预置（模板继承）** | 高频组件（如设计说明模块 DesignNotesPanel、指标卡、图表底座）随 `_project-template/src/common/` 预置，新项目开箱即用 | 通用能力，无需每次复制 |
| **静态预览参考** | `03-组件库/frame/gallery.html` 在面板 iframe 中打开，选中样板即预览 | 快速看效果、挑样板 |

- 原型工程调用约定写进模板 `README-DEV.md`（或 `AGENTS.md` 组件节）：**运行时禁止 `href/src` 指向 `03-组件库/`**（沿用 v1.7"母版与交付分离"铁律），只允许对照实现或按白名单拷贝。
- 与参考版 J3 附注模式衔接：附注定位的元素可挂组件库 page-type 元数据，批注直接说"参考 xx 样板"。

❓ **决策点 H-1**：原型工程调用组件，是否接受"对照重写为主、预置为辅"（不把 frame 作为可 import 的运行时包）？这是 v1.7 的设计铁律，我认为应保留——直接 import 会把母版变成强耦合依赖，违背"可搬运"卖点。
