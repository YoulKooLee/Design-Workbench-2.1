# 产品设计工作台 v2 · 架构与排错手册

> **适用对象**：把本工作台文件夹复制给同事 / 智能体后，需要快速熟悉架构、自主处理「启动报错」的人。
> **配套文档**：同目录 `使用说明.md`（面向使用者，讲功能与操作）。本手册面向「排查者 / 智能体」，重点在架构与排错。
> **最后核对**：2026-09-13（v2 改版：目录更名工作台面板、09-协作 迁入、workbench.config.json 接线），对应脚本版本见下文各节。

---

## 0. 30 秒概览

- 本工作台 = 一个**本地 Web 管理面板**（端口 7788）+ 多个**项目开发栈**（Vite + Axhub Make）。
- 把整个 `产品设计工作台` 文件夹原样复制到任意机器，双击 `启动工作台.cmd` 即可用，无需改任何硬编码路径。
- **最大坑（务必先读第 3 节）**：Node 的「版本 + 架构」。必须用 **x64 的 Node 18+**（本机 WorkBuddy 自带的 `node.exe` 最稳）；用 arm64 或架构不匹配的 node，会让 Vite 原生模块崩溃。
- 同事复制文件夹后启动报错，**90% 是 Node 架构 / 原生模块问题，或 ACP 的 CodeBuddy CLI 没装**，见第 4 节。

## 1. 架构全景

### 1.1 四个逻辑服务与端口（全部本机 localhost）

| 端口 | 服务 | 进程来源 | 是否单例 | 说明 |
|---|---|---|:---:|---|
| **7788** | 工作台管理面板 | `工作台面板/server.mjs`（纯 Node 内置模块，**零第三方依赖**） | 每机一个 | Web UI：`http://127.0.0.1:7788`（绑定 127.0.0.1，仅本机可访问） |
| **53817** | Axhub Make 管理端 | `@axhub/make` 的 `bin/cli.mjs` | **全局单例**（所有项目共用） | 管理端页面、项目注册、ACP 都挂在它上面 |
| **51720+** | 各项目 Vite 开发服务器 | `node_modules/vite/bin/vite.js` | 每项目一个（`--strictPort` 锁端口） | 51720 起自动分配，互不影响 |
| **32124** | ACP 共享服务 | 随 Make 单例启动（属 `@axhub/make`） | 全局一个 | 让 CodeBuddy / Claude 等本地 CLI 接入工作台，UI 在 Make 设置页 |

> ⚠️ **Make（53817）是全局单例**：绝不能为每个项目各起一个 Make，那会抢端口并导致 500。多个项目共用同一个 Make 实例。

> 🔒 **端口绑定**：面板 7788 与 Make 53817 均绑定 `127.0.0.1`（仅本机可访问）。Make 通过启动参数 `--host 127.0.0.1` 收敛（launch-project.ps1 与 server.mjs 重启 Make 路径均已加）；改回全网卡需同时改三处启动命令并自行评估暴露面。

> 🔧 **改端口须知（三处同步）**：端口唯一配置真源是 `workbench.config.json`（`axhub.makePort` / `workbench.panelPort`），server.mjs / env-doctor 读它。但 **`启动工作台.cmd` 与 `停止工作台.cmd` 的 netstat 探测仍硬编码 7788/53817/32124**（cmd 读 JSON 不便）；改端口后必须同步改：① workbench.config.json ② 启动/停止两个 .cmd 的探测行 ③ launch-project.ps1 的 `-MakePort` 默认值与 `--port` 参数。三处任一漏改都会出现"面板起来但探测不到 / 端口分裂互抢"。

### 1.2 进程与调用关系

```
[双击 启动工作台.cmd]
   └─ 自动探测 node（优先 WorkBuddy 自带 x64 node）→ 在最小化窗口启动 node 工作台面板/server.mjs
        └─ 监听 7788，打开浏览器 http://localhost:7788
              │
              └─ 用户在面板点某项目「启动开发栈」
                    └─ UI: POST /api/projects/open  →  server.mjs 调用 launch-project.ps1
                          └─ launch-project.ps1（PowerShell，8 步）：
                               1) 读取项目身份
                               2) 检查本项目 Vite 是否可复用（心跳新鲜+进程存活则跳过重启）
                               3) 预启动 Make 单例（若未运行；已运行则秒过；与 Vite 并行等待）
                               4) 检查 node_modules（无则 pnpm/npm install，仅首次）
                               5) 校验原生模块（缺失则 pnpm install --force 自愈）
                               6) 启动 Vite（端口粘滞 + 重试，最多 60s/次 ×2）
                               7) 等待 Make 就绪 + 注册项目到 Make
                               8) 打开浏览器 ?projectId=xxx，写 .launch-status.json
                              └─ 全程写 07-日志/launch-<项目>.log，结尾打 AXHUB_LAUNCH_STATUS: done/failed
```

### 1.3 目录结构与项目识别

```
产品设计工作台/                    ← 工作空间根目录（本文件所在处）
├─ 启动工作台.cmd                   ← 启动器（ASCII+CRLF，双击即用）
├─ 停止工作台.cmd                   ← 停止器（释放 7788/53817/517xx）
├─ 使用说明.md                      ← 使用者文档
├─ 工作台架构与排错手册.md          ← 本文件
├─ workbench.config.json            ← 唯一配置真源（端口 / 绑定主机 / 各模块路径）
├─ 01-项目/                        ← 【唯一】真实项目存放处（工作台只扫这里，支持两级嵌套）
├─ 02-模板/                        ← 模板库（_project-template 不算项目）
├─ 03-组件库/                      ← v1.7 组件库（frame + ui-libs + catalog/registry）
├─ 04-维护台账/                    ← 备份收敛 / 补丁台账 / 归档
├─ 05-回收站/                      ← 删除项目回收
├─ 06-运行脚本/                    ← launch-project.ps1（核心启动脚本）+ env-doctor + smoke-test
├─ 07-日志/                        ← 启动 / 运行日志（launch-*.log）
├─ 08-文档/
├─ 09-协作/                        ← 共享信息目录（多智能体通信，唯一真源，勿双写）
├─ 10-智能体记忆/                  ← 共享记忆主干（5 家按 agents/<自己>/ 分区维护）
└─ 工作台面板/                     ← 工作台后端（server.mjs）+ 前端（public/）
```

项目识别规则（`server.mjs` 的 `isProjectDir`，只扫 `01-项目`）：
- 目录内含 `.axhub/make`，**或**
- 含 `src/prototypes`，**或**
- `package.json` 的 `name === '@axhub/make-client'`

扫描**排除**这些目录：`_backups, tmp, 工作台面板, .workbuddy, node_modules, 03-组件库, 04-维护台账, 05-回收站, 06-运行脚本, 07-日志, 08-文档, 09-协作, 10-智能体记忆`；递归时不再深入 `node_modules, .git, .vite, .axhub, .workbuddy`。

## 2. 启动链路（新手时序）

1. 双击 `启动工作台.cmd` → 探测 node → 启动 `server.mjs`（最小化窗口）→ 打开浏览器 7788。
2. 访问 `http://localhost:7788`，看到项目列表（来自 `01-项目`）。
3. 点某项目「启动开发栈」→ 走 1.2 的 8 步 → Make + Vite 拉起 → 浏览器自动开 `?projectId=xxx`。
4. （可选）在 Make 设置页启动 ACP，用 CodeBuddy / 其他 CLI 接入。

> 只有「启动开发栈」真正跑 Vite 时才需要各项目 `node_modules`；面板本身、列表、历史版本管理都不依赖项目依赖。

## 3. 关键约束（智能体 / 接手同事必读）

1. **Node 架构必须一致（最高频坑）**
   - 本机现状：WorkBuddy 自带 node 是 **x64 22.22.2**（稳）；系统 `C:\Program Files\nodejs` 是 **arm64 v24**。
   - `launch-project.ps1` 会**自动把受控 x64 node 前置到 PATH**，强制 Vite 用 x64 node，避免原生模块架构错配。
   - 若同事机器只有 arm64 node 且没装 WorkBuddy，Vite 仍可能崩；脚本内置自愈（见下）会重装对应架构原生模块（需联网）。离线环境需手动重装。

2. **原生模块（rollup / esbuild）按架构分发**
   - 这些包是平台原生（如 `@rollup/rollup-win32-x64-msvc`、`@esbuild/win32-x64`）。
   - **从一台机器拷贝整个文件夹给另一台架构不同的机器**，node_modules 里的原生模块架构就对不上 → Vite 启动报 `Cannot find module @rollup/rollup-win32-*`。
   - 脚本第 5 步会检测并自动 `pnpm install --force` 补齐（同时查顶层与 `.pnpm` 两种布局）；仍失败则需联网或手动装。

3. **Make 是全局单例（53817）**
   - 多项目共用，绝不各起一个。端口被别的非 Make 进程占用时会直接报错，先跑 `停止工作台.cmd`。

4. **ACP 依赖本地 CLI 可执行文件**
   - ACP（32124）通过执行 `codebuddy --version` 探测 CodeBuddy CLI；本机必须装 `@tencent-ai/codebuddy-code`（见 4.4）。

5. **可复制性（已处理）**
   - `server.mjs` 的 `AXHUB_ROOT = path.dirname(__dirname)`，由自身位置推导，**不写死绝对路径**，所以整文件夹换机器/换路径都能跑。
   - 脚本文件编码约定：`.cmd` = ASCII/GBK **无 BOM** + CRLF（**不能用 UTF-8 BOM**，会被 cmd 拼进首行导致 `﻿@echo` 报错）；`.ps1` = UTF-8 **带 BOM** + CRLF。

## 4. 常见报错速查（重点）

> 每张表：现象 → 根因 → 处理。处理里标「智能体可执行」的步骤可直接让智能体照做。

### 4.1 启动工作台.cmd 闪退 / 编码类报错

| 现象 | 根因 | 处理 |
|---|---|---|
| 窗口出现 <0.1 秒就消失 | `.cmd` 被存成 UTF-8 BOM，cmd 把 BOM 三字节拼进首行变成 `﻿@echo` 报错 | 用**无 BOM 的 GBK/ASCII** 重新保存 `.cmd`（当前版本已修好，确认拿到的是最新脚本） |
| 报 `此时不应有 (...)` | `.cmd` 代码块内 `echo` 含未转义的 `(` `)` 或 `%VAR%` 展开带入括号 | 把块内括号改成方括号 `[ ]`，或去掉名称里的括号（当前版本已修） |
| 报 `未找到 Node.js` | 同事机器既无 WorkBuddy 也无系统 node | 装 WorkBuddy（自带 node）或 Node.js 18+ x64；脚本优先 `%USERPROFILE%\.workbuddy\binaries\node\versions\*\node.exe`，其次 PATH 的 node |

### 4.2 Vite 原生模块 / 架构类（同事复制文件夹最高频）

| 现象 | 根因 | 处理 |
|---|---|---|
| 启动项目后页面报 `Cannot find module @rollup/rollup-win32-x64-msvc` 或 `Could not load @esbuild/win32-x64` | 运行 Vite 的 node 架构 ≠ node_modules 里原生模块的架构（常见于跨架构拷贝文件夹，或系统 PATH 的 node 是 arm64 而脚本未用受控 x64 node） | 脚本第 5 步已内置自愈：检测到缺失会自动 `pnpm install --force` 补齐对应架构原生模块（**需联网**）。离线时，进对应项目目录手动 `pnpm install`（pnpm 项目）或 `npm install`（npm 项目）；最彻底：删 `node_modules` 后重装 |
| 启动项目卡住，后台 `node` 进程 CPU 飙高但页面打不开 | Vite 在 arm64 node 下找不到原生模块反复崩溃重启 | 确保用 x64 node（见 3.1）；或在项目目录 `pnpm install --force` 重装 x64 原生模块 |

### 4.3 Make / 启动超时类

| 现象 | 根因 | 处理 |
|---|---|---|
| 点「启动开发栈」>60 秒后报 `启动失败: Make 服务未在 60 秒内就绪` | 旧版脚本用 PowerShell `Invoke-WebRequest` 读 Make `/api/health`，本机偶发读不到响应体（0 字节）误判超时 | 当前 `launch-project.ps1` 已改用 **node fetch** 做健康检查（搜 `Get-MakeHealth` 应含 `node fetch`）。若同事拿到旧脚本，同步最新版即可 |
| 点「启动开发栈」页面一直转圈、无报错、按钮禁用 | 前端在等 launch-log 轮询，但后台实际已挂住 | 前端已加 **20 秒安全超时**：超时会恢复按钮并提示「后台仍在继续，可查看 07-日志」。同时右下角错误浮窗会捕获日志尾部 |
| `EADDRINUSE` / 端口 7788 或 53817 被占用 | 上一次没正常退出，或别的程序占了端口 | 先跑根目录 `停止工作台.cmd` 释放 7788/53817（顺带清 517xx 的 Vite），再重试。长期占用用 `netstat -ano \| findstr :7788` 找 PID 手动 `taskkill /PID <pid> /T /F` |

### 4.4 ACP / CodeBuddy CLI（启用 ACP 时才相关）

| 现象 | 根因 | 处理 |
|---|---|---|
| ACP 设置页「CodeBuddy CLI」显示 **未安装 / 未测试** | ACP（32124，属 Make）通过执行 `codebuddy --version` 探测；本机没装 `@tencent-ai/codebuddy-code` | **智能体可执行**：用系统 node 的 npm 全局装一次：<br>`"C:/Program Files/nodejs/node.exe" "C:/Program Files/nodejs/node_modules/npm/bin/npm-cli.js" install -g @tencent-ai/codebuddy-code`<br>装完刷新 ACP 设置页即可 |
| 装完仍显示未安装 | 装到了别的 npm 全局目录，ACP 进程 PATH 没覆盖到 | 验证安装是否对 ACP 可见：`curl http://localhost:53817/api/agent/versions`，看 `codebuddy.status` 是否为 `"installed"`、`version` 是否有值；不是则重启 ACP 服务（设置页有「重启」）让其重新探测 |
| Claude / Codex / Cursor 等显示未安装 | 本机确实没装它们的 CLI | **正常**，无需处理；只要 CodeBuddy 这一项绿了即可 |

### 4.5 项目列表 / 历史版本类

| 现象 | 根因 | 处理 |
|---|---|---|
| 复制到其他机器后项目列表为空 | 列表只扫 `01-项目`，且需含 3.3 的识别标记 | 确认项目放在 `01-项目/` 下，且含 `.axhub/make` / `src/prototypes` / `package.json` 的 `@axhub/make-client` |
| 「历史版本」打开提示「未启用 Git」 | 该项目目录没有 `.git` | 点弹窗内「初始化 Git 并创建首次提交」即可；工作台本体不依赖 Git，仅历史版本功能需要 |
| 列表出现 `_project-template` | 不该出现（它属模板） | 检查 `server.mjs` 的 `listProjects()` 是否指向 `01-项目`；确认它没被改成扫全目录 |

## 5. 给智能体的最短上手清单

接到「帮我配置 / 修复这个工作台」类请求时，按顺序做：

1. **定位根目录**：找到 `启动工作台.cmd` 所在目录 = `ROOT`；其下 `工作台面板/server.mjs` 是后端。
2. **核对 Node**：优先用 `%USERPROFILE%\.workbuddy\binaries\node\versions\*\node.exe`（x64 22.22.2）；没有就找系统 PATH 的 node（需 18+，最好 x64）；都没有提示装 Node。
3. **核对可复制性**：打开 `工作台面板/server.mjs`，确认 `AXHUB_ROOT = path.dirname(__dirname)`（相对推导），**不应是硬编码绝对路径**；端口/绑定主机应从根 `workbench.config.json` 读取。
4. **清理临时**：删 `工作台面板` 下所有 `launch-*.tmp.ps1`（启动会重新生成，删了无害）。
5. **项目依赖（仅启动开发栈需要）**：遍历 `ROOT\01-项目` 下含 `package.json` 但缺 `node_modules` 的子项目，执行 `pnpm install`（pnpm 项目）或 `npm install`（npm 项目）。只为能「启动开发栈」，不影响面板本身，可跳过。
6. **启动并自检**：
   - `node 工作台面板/server.mjs` 或双击 `启动工作台.cmd`；
   - `curl http://localhost:7788` 应 200；
   - `curl http://localhost:7788/api/projects` 的 `projects` 应是 `01-项目` 下的项目（不含 `_project-template`）。
7. **（启用 ACP 时）装 CLI**：见 4.4，全局装 `@tencent-ai/codebuddy-code` 后验证 `/api/agent/versions` 的 `codebuddy.status === "installed"`。
8. **完成后回报**：工作台地址、projects 数量、哪些项目缺 node_modules、有无无法自动处理的问题。

## 6. 日志与诊断入口

| 入口 | 用途 |
|---|---|
| `07-日志/launch-<项目>.log` | 单次启动的完整 8 步日志 + 各步耗时；结尾 `AXHUB_LAUNCH_STATUS: done/failed` |
| `工作台面板/server-console.log` | 管理面板（7788）自身启动输出 |
| `http://localhost:7788/api/projects` | 当前扫描到的项目列表 |
| `http://localhost:53817/api/health` | Make 单例健康（应 `ok:true, role:"admin", devMode:false`） |
| `http://localhost:53817/api/agent/versions` | 各本地 CLI（含 codebuddy）的 `status`/`version` 探测结果 |
| `http://localhost:7788/api/projects/launch-log?relative=<项目相对路径>` | 前端轮询用的实时启动状态（done/running/failed） |

> 路径里的 `<项目相对路径>` 用 `01-项目/健康档案` 这种格式（正斜杠）。

## 7. 把文件夹交给同事时的建议

- **若同事与本机架构相同**（都是 x64 Windows）：直接整文件夹拷贝即可，`node_modules` 一并带走，启动最快。
- **若架构不同 / 想减小体积**：可先删各项目的 `node_modules`（和 `.vite` 缓存），让同事首次「启动开发栈」时脚本自动 `pnpm install`（需联网；脚本会按对方架构装对原生模块）。
- **ACP 用户**：提醒同事首次用 ACP 前按 4.4 装一次 CodeBuddy CLI。
- **排错首问**：先看 4 节对应现象，再看 `07-日志/launch-*.log` 尾部；仍卡住把日志发智能体，按第 5 节清单处理。
