# AGENTS.md 解释与依据（rationale）

> **本文件不是执行指令。** `AGENTS.md` 只讲"怎么做"，本文件讲"为什么这么做"。
> 日常执行**不需要读本文件**（按用户 2026-09-19 指令：AGENTS.md 只讲执行，升级迭代时再看解释）。
> 何时读本文件：① 要修改 AGENTS.md 的规则时 ② 规则之间看似冲突、需判断优先级时 ③ 排查智能体行为异常、需理解设计意图时。

## 一、上下文预算：体量基线与推导

### 实测基线（2026-09-19，qwen 核验）

| 对象 | 体量 | token 估算 | 备注 |
|---|---|---|---|
| `AGENTS.md` | 38 KB → 瘦身后 ≈34 KB | ≈15K | 常驻入口，最大单项 |
| `.agents/skills/` | 2.41 MB / 272 文件 | — | SKILL.md 正文合计 442 KB ≈ 11 万 token |
| `.agents/knowledge/` | 200 KB / 47 文件 | ≈7 万 token | 分阶段规范 |
| 根级 `rules/` | 0.43 MB / 47 文件 | — | 全部 .md；工具代码已外移 |
| `.agents/skills/INDEX.md` | 10.6 KB | ≈3.5K | session-start 注入，51 技能 description |

估算口径：1 token ≈ 2 中文字符。**改动 AGENTS.md 或增删技能后必须重新实测**，不要沿用旧数字。

### 历史事故（为什么要有这条铁律）

- 2026-09-18 qwen 三重审查发现：`AGENTS.md` 原文自称"技能正文全量约 400KB"，实测 `.agents/skills/` 全量 **3.32MB**（当时），**低估 8.3 倍**。智能体据此判断"误读一个技能目录最多损失几万 token"，实际单个 `diagram-generator` 目录就 0.96MB ≈ 30 万+ token。
- 同一审查发现：原禁令只覆盖 `.agents/{skills,knowledge,rules}`，但工作流却**命令**智能体去"检查 `src/themes/`"（当时 51MB / 920 文件 / 112 主题）——按规定流程走就会溢出。现已移出模板，共享层保留在 `03-组件库/03-UI风格/src-themes/`。
- 原禁令也未覆盖根级 `rules/`（当时 1.71MB，含 `live-browser.js` 350KB ≈ 11 万 token 单文件），而工作流表引用的恰是根级 `rules/`。工具代码现已外移至 `02-模板/vendor/impeccable-scripts/`（1.29MB），根级 `rules/` 降至 0.43MB 纯 .md。

**教训**：预算声明必须与实测一致，且禁令覆盖范围必须与工作流实际引导的目录一致——两者错位就是溢出事故。

### 为什么需要技术强制而非文字警告

原护栏只有文字警告（"严禁遍历"），无技术强制件，等于摆设。现由 `.agents/hooks/context-budget.cjs` 在 preToolUse 拦截 `Read|Glob|Grep`：命中 6 类高危目录（`.agents/skills`、`.agents/knowledge`、`.agents/rules`、`rules/references/impeccable`、`src/themes`、`03-组件库/**/vendor`）且为通配/递归/目录级操作时阻断，精确单文件 Read 放行。

## 二、上下文装配协议：设计理由

### 为什么分"常驻基线 / 模块滑窗 / 按需检索"三层

用户 2026-09-18 给出核心公式：**"整个工程没必要全部塞进上下文，执行过程只需要聚焦当前模块设计方案 + 总体架构、业务架构 + 模块之间数据流，这个模块完成就压缩上下文做下个模块。"**

三层就是把这句话变成可执行规则：
- **常驻基线**＝"总体架构 + 业务架构 + 模块之间数据流"→ 每次会话都要，但只存**条目级摘要**，不存全文
- **模块滑窗**＝"当前模块设计方案"→ 进入模块时装、离开时卸
- **按需检索**＝"整个工程没必要全部塞进"→ 永不常驻

### 为什么 AGENTS.md 自己要算进常驻基线（第 0 项）

用户 2026-09-19 指出：AGENTS.md 没被列入常驻基线 6 项，但它实际是会话启动必读、且体量（38KB）几乎等于整个基线预算（≤40KB）。

**这是原预算表的逻辑漏洞**：把 AGENTS.md 单列一行加进合计，却不计入"常驻基线 ≤40KB"的限额，导致限额形同虚设。现明确 AGENTS.md 为**常驻基线第 0 项**，并把它自身瘦身到 ≈34KB，让"基线 0-6 项合计 ≤40KB"成为真实可守的红线。

### 硬红线为什么必须"阻断"而非"警告"

若只警告不阻断，智能体在长会话中会倾向"继续但注意"，累积到溢出时已无法挽回（压缩会丢失未归档的决策）。阻断 + 强制压缩是唯一能守住预算的机制。

## 三、组件与生成器边界：为什么需要这条

工程包同时承载两套体系（用户 2026-09-18 要求核对"vibe 工程包、axhub 工程包"的引用链路）：

| | axhub 系 | vibe 系 |
|---|---|---|
| 入口 | `.axhub/make/` | `.agents/skills/vibepm-{web,app}-generator` |
| 组件 | `src/component-templates/axhub/`（50 个 React TSX） | `02-模板/vendor/vibepm-{web,app}` |
| 生成技能 | `page-generator`（→ `admin/` Vue 开发层） | `vibepm-web/app-generator`（→ 原型层） |
| 母版/catalog | — | `03-组件库`（JSON catalog + 提示词） |

qwen 核对结论：**引用链路未断裂**（所有路径引用有效、外移后 0 残留断链），但存在两处"职责交叉"会导致智能体两套都读：
1. `src/component-templates/axhub/`（React TSX 源码）vs `03-组件库/.../Codebuddy Design`（JSON catalog）—— 语义重复，合计 200KB+，单次误读即超基线预算。

故 AGENTS.md 增"组件与生成器边界"声明，并由 context-budget hook 对 `03-组件库` 整目录 Read 加拦截（deepseek 2026-09-19 建议：边界声明是自然语言，不够拦"两套都读"，应升级为可拦截规则）。

## 四、基线链术语：为什么锁定 SRS=需求规格说明书

用户 2026-09-18 裁决：**SRS 统一用"需求规格说明书"**。

背景：deepseek 初版方案曾定义"SRS=设计文档"，与工程包现有真源冲突。qwen 实测冲突面：`prd-to-srs-gate.md` 42 处 + `req-doc/SKILL.md` 42 处 + `AGENTS.md` 55 处 = **139 处**，且 `srs-quality-checklist.md` 位于 `phase1-requirements/`（需求阶段）目录、`hld-spec.md:25` 明写 `SRS（做什么）→ HLD（系统怎么搭）→ LLD（每块怎么实现）`。

若翻转术语，`SPEC_SOURCE=SRS` 判定与 `page-generator` 规格真源选择会错乱，**可能让 page-generator 拿设计文档当需求规格生成页面**。故锁定现有语义，零改动。

基线链：`客户需求 → PRD（产品探索真源）→ SRS（需求规格真源）→ HLD（系统架构+数据模型）→ LLD（实现）`。**系统架构 + 数据模型 = HLD 的两个章节**，引用 `.agents/knowledge/phase2-design/hld-spec.md`（已有完整章节 + 11 项质量清单 + HLD/LLD 越界判据表），**不新建文档**（避免双份真源）。

## 五、交付模式三档：为什么分技能默认不同

| 技能 | 默认档 | 理由 |
|---|---|---|
| `req-doc`（SRS） | 标准 | SRS 是研发真源，错误会传导到全部下游；不宜默认跳过 req-reviewer |
| `prd-writer` / `prototype-to-prd` | 标准 | 分概念版/落地版两版对齐更稳；用户可声明快速模式降档 |
| `page-generator` | 快速 | 批量出页优先速度；步骤 6 审查降级，但**批量收口时必须补 build/type-check** |
| `pm-product-pipeline` | 标准 | 全流程编排，Step 0 可改档并向下游传递 `DELIVERY_MODE` |

**为什么"自动升档 > 用户显式声明 > 分技能默认"**：用户说"正式交付/验收/上线/提测"时，意图明确是要高质量，此时即使用户此前说过"快速模式"也应升档——因为升档的触发词本身就是一次新的、更强的意图表达。

**为什么 page-generator 快速模式要强制补 build**：快速模式跳过了 type-check/lint，若不补做，批量页面可能带类型错误交付，且错误会在用户验收时才暴露（成本更高）。

## 六、子 Agent 编排：模型路由与并行派发理由

### 模型路由（按复杂度省成本）

| 任务类型 | 推荐模型 | 原因 |
|---|---|---|
| 简单机械操作（重命名、格式化） | haiku | 模式固定，不需深度推理 |
| 标准 CRUD / 页面生成 | sonnet | 有明确模板可循 |
| 架构设计、安全审查、复杂调试 | opus | 需全局视角与深度推理 |

### 并行派发原则

- **何时并行**：3+ 个测试/子系统因**不同根因**失败、多个独立 bug、各问题可独立理解
- **何时不并行**：失败相互关联、需完整系统状态、Agent 会互改同一文件
- **Prompt 结构**：聚焦（单一问题域）+ 自包含（含全部上下文，子 Agent 看不到主会话）+ 明确输出（根因摘要 + 修复内容 + 状态报告）
- **派发后验证**：读每个摘要 → 查冲突（是否改了同一处）→ 跑完整测试套件 → 抽查系统性错误

### 为什么"子 Agent 不得触发技能流程、不得再派发"

`<SUBAGENT-STOP>` 规则的理由：子 Agent 上下文受限且无全局视角，若允许它触发技能或再派发，会形成不可控的递归链，主流程失去调度权，且 token 消耗呈指数增长。

## 七、技能触发自检：完整劝导表

AGENTS.md 只保留一句强制指令；完整对照表在此（出现左侧念头即为跳过技能的借口）：

| 自我合理化 | 正确做法 |
|---|---|
| 「这只是个小问题，直接答就行」 | 再小的任务也要先检查是否有匹配技能 |
| 「我先看看情况再说」 | 技能检查必须在任何操作之前完成 |
| 「让我先读代码了解一下」 | 技能流程会告诉你如何正确地读代码 |
| 「用不着走正式技能流程」 | 技能一旦存在，就必须调用，没有例外 |
| 「这个技能我之前看过，不用重读」 | 技能会持续更新，每次都要读当前版本 |
| 「走技能太重了，我直接做更快」 | 跳过技能往往导致返工，反而更慢 |
| 「先做这一件小事，技能待会再说」 | 动手之前先完成技能匹配，没有「待会再说」 |

## 八、重要原则：10 条的解释性依据

AGENTS.md 只保留原则条目；展开理由在此：

1. **产品需求和设计方案分阶段对齐** —— 先确认做什么，再确认怎么表达。读取资料/规格确认/开发验收中发现影响方向的问题都要回到相应阶段：读取资料（目标、边界、素材、参考或约束不清）、产品需求（不同目标用户、功能范围、内容来源或验收标准）、设计方案（不同信息架构、交互路径、视觉方向或设计基底）、开发验收（实现结果、体验取舍或验收标准变化）。
2. **优先创建和维护 task/todo** —— 多步骤、高风险、需求对齐、方案确认或跨文件任务用 task/todo 记录当前步骤、状态和下一步；简单局部修改可轻量，但要清楚说明当前在处理什么、完成后如何验收。
3. **设计要判断何时收敛、何时发散** —— 需求不清先收敛；需改善体验或创新表达时再发散。发散是为了帮助用户选择最终方向。
4. **原型按生产级界面处理** —— 本项目"原型"默认可运行、接近正式产品，不是黑白灰线框图或低保真草稿；只有用户明确要求时才用 wireframe/placeholder。
5. **不要把截图当唯一真相** —— 截图用于视觉参考；有代码、组件、设计系统、业务资料或用户说明时要结合上下文判断。
6. **早展示，早反馈** —— 不要等全部完成才暴露方向问题。涉及页面意图、组件取舍或多方案比稿时，优先用低成本 Markdown ASCII Wireframe/Diagram 或 Mermaid 展示方案先对齐。
7. **讲人话，用户不懂技术** —— 用用户能理解的方式说明取舍、风险和结果；用户无法执行 CLI 命令，不得省略验收流程。请求反馈时提醒用户提供截图、预览链接、页面路径或具体问题位置。
8. **先读上下文，再做判断** —— 优先结合用户说明、项目资料、现有代码、组件和设计系统判断；截图只作视觉参考。
9. **图片素材与生成** —— 适当使用项目已有素材、AI 生成图或可合法使用的第三方图片；生成或编辑位图素材优先用 `$ui-image-generation`。
10. **代理负责验收** —— 页面就绪后先提供可打开的预览链接再验收；明确进入 review 环节时优先由未参与实现的子代理独立审查，不以实现者自检代替 review。

## 九、记忆分层：为什么"分散保存、随时找回"

设计原则：核心少量、索引可寻、知识分散。对话/任务产出的信息先分类落盘，不得随手堆进单一文件；无法判断去向时主动询问人类。

### 为什么写入侧需要三态门禁

用户痛点 P1：**"智能体容易把对话的东西记录下来，尤其过程性讨论，导致 PRD 没抓住重点"**。

病根在**写入侧**而非读取侧——读取分层再细，也拦不住智能体把讨论写进 PRD。故设三态：
- `[事实]`（客户原话/已签字需求/实测数据）→ 可进基线
- `[讨论]`（方案对比、试错、智能体推断）→ 只能进过程层
- `[否决]`（被否方案 + **理由必填**）→ 只能进过程层，压缩时必须保留理由一行

`[否决]` 必留理由的原因：否则失忆后智能体会重提已被否决的方案、重走弯路——这正是用户痛点 P2（跨端失忆）的一个成因。

`[智能体补全待确认]` 不得作 `SPEC_SOURCE` 真源的原因：未经用户确认的补全内容若成为规格真源，会把智能体的推断固化成需求，后续所有开发都建立在未经确认的假设上。

### 为什么不新建 DECISIONS.md / CHANGELOG.md / TASKS.md

deepseek 初版方案要新建这三个文件，qwen 核验发现与现有机制重叠：
- `TASKS.md` 与 `.agents/rules/compaction-recovery.md` 的 4 项恢复检查表高度重叠（第 1 项就是"TaskList 中 in_progress 任务"）
- `DECISIONS.md` 与答疑层 `项目答疑手册.md` 部分重叠
- `CHANGELOG.md` 与门禁三问第 1 问"更新基线文档（版本+变更时间）"部分重叠

两套进度记录并存 → 压缩恢复时不知以哪个为准。故改为 `project-memory.md` 内的结构化小节。

### 模块完成快照：为什么是跨端失忆的解药

用户痛点 P2：**"一套业务分 web 端和移动端，web 端做完，到移动端失忆了，要重新来"**。

根因：模块完成后的知识只留在会话上下文里，压缩即丢；且跨端需要的是**接口/数据契约**，不是实现细节。

解法：模块验收通过后产出 ≤300 字快照入常驻基线。移动端启动该模块时，装配 = 常驻基线（含 web 端快照）+ 移动端滑窗 → **读到接口契约与跨端差异，不需重读 web 端实现** → 不失忆也不爆上下文。

### 数据流闭环为什么升级为"压缩闸门"

deepseek 提出的判据（A 的输出都能被某模块接住、无孤儿数据、无凭空数据）原本只是一条质量清单。qwen 建议升级为闸门：**闭环验收通过 → 才写快照 → 才允许压缩 → 才进下个模块**。

理由：用户说"这个模块完成就压缩上下文"，但"完成"若无客观判据，就由智能体自报，等于没有门禁。闭环验收提供了可判定的"完成"定义。已补进 `hld-spec.md` 质量清单第 12 项。

## 十、AGENTS.md 与 AGENTS.template.md 的关系（用户 2026-09-19 澄清）

**`AGENTS.md` 是唯一正本**，新建项目时由 `工作台面板/server.mjs` 用 `fs.cpSync` 从 `02-模板/_project-template` **整体拷贝**（只排除 `node_modules` 和 `.git`），项目初始即带 AGENTS.md，**不存在"由 template 再生成一次"的步骤**。

`AGENTS.template.md` 由 `.agents/scripts/build-agents-template.mjs` 从 AGENTS.md **单向派生**（脚本头注释明写"AGENTS.md 是唯一正本"），仅在标题后插入维护提醒 + `{{PROJECT_INFO_SECTION}}` 占位符，其余正文与 AGENTS.md 一致。其定位接近**备份/占位参考**，不参与项目生成。

故：改 AGENTS.md 即刻对新项目生效；跑生成器同步 template 是**可选的收尾动作**（避免 template 变成过期副本误导后续维护者），不是生效前提。
