# 上下文压缩恢复

上下文被压缩后（含 PreCompact hook 触发或长会话自动摘要），立即按下表逐项检查，全部确认后才继续，不得跳过。

## 压缩前归档（压缩发生时先执行）

PreCompact hook 触发或长会话自动摘要**前**，先按记忆门禁三问（影响基线 / 项目可复用 / 工作台可复用）识别值得保留的内容：

1. 值得保留 → 写入对应记忆层（基线文档 / 项目答疑手册.md / ../../工作台答疑手册.md），再更新 project-memory.md 索引
2. 不值得保留（一次性操作、可还原信息）→ 不写入
3. 无法判断 → 先询问人类再压缩
4. 归档完成后再执行下面的恢复检查表

## 压缩保留什么（2026-10-30 定调）

压缩是把易失的对话换成磁盘上的文件，**不是把信息删掉**。按四档处理：

| 档 | 内容 | 处理 |
|---|---|---|
| **必须保留** | 基线：PRD / 系统架构 / 数据模型（已转写时含 SRS） | 已在文件里 → 压缩后**按路径重读**，不靠记忆 |
| **必须保留** | **最终输出**：这段工作产出了什么（文件路径 / 页面 / 接口 / 已通过的验证结论） | 压缩前写进 `project-memory.md` 的「任务进度 / 模块快照」，一句话 + 路径 |
| **可以不保留** | 当前功能的输入输出细节（字段级、中间数据、逐次调试的中间态） | 丢了没关系——有基线和最终输出就能重建 |
| **不必保留** | 过程讨论、被否决方案（已记 `[否决]` 的保留理由一行） | 丢 |

> 判据：**压缩后能不能凭「基线 + 最终输出」接着干**。能 → 可以压；不能 → 先补一条「最终输出」再压。

## 恢复检查表（压缩后必须逐项过）

| # | 检查项 | 具体看什么 | 判定标准 | 异常时怎么办 |
|---|--------|-----------|---------|------------|
| 1 | 任务进度 | TaskList 中 in_progress 任务及当前步骤 | 有且仅有一个 in_progress 任务 | 无 → 回到上一条用户消息重新确认目标；多个 → 合并到当前主线 |
| 2 | 未完成改动 | 最近一次 Edit/Write 的目标文件是否仍处于未完成状态 | 文件存在且内容与最后动作一致 | 丢失 → 用 git status 找回或告知用户；内容不符 → 重新读取 |
| 3 | 下一步计划 | 已确认的下一步动作是否明确 | 有明确文件路径 + 动作 + 验收方式 | 不明确 → 用一句话复述计划并请用户确认 |
| 4 | 依赖上下文 | 当前任务依赖的规范是否仍可用 | 相关规范已预加载或可按需重读 | 需要 → 只重读当前依赖的 1 个文件，禁止整库重读 |

## 恢复顺序

1. 先恢复"任务状态"（我在做什么）
2. 再恢复"文件状态"（改到哪了）
3. 最后确认"下一步"（做什么、怎么做、怎么验收）

## 禁区

- 压缩后不重复已完成的工作（不重跑已完成步骤、不整库重读知识）
- 压缩后不擅自扩大范围（只继续当前任务）
- 状态不确定时先问，不猜

## 模块完成快照（T1 落地 · 跨端不失忆的解药）

每个模块**数据流闭环验收通过后**，产出 ≤300 字快照，写入 `project-memory.md` 的「模块快照」小节（只放摘要与路径，不放正文）：

```markdown
## 模块快照：<模块名>（端：web | mobile | both）
- 状态：已完成 / 进行中（完成度 %）
- 职责：一句话
- 对外接口：契约（输入实体 → 处理 → 输出实体），不写实现
- 依赖模块：上游 X（取什么数据）、下游 Y（给什么数据）
- 数据实体：本模块读写的实体名（与数据模型对齐）
- 关键决策：≤3 条，只写结论 + 一句理由
- 跨端差异：web 已实现的部分，mobile 需注意什么（组件/交互/字段差异）
- 未完成 TODO：≤3 条
```

**跨端失忆的解法**：移动端启动某模块时，先读 `project-memory.md` 里 web 端该模块的快照（对外接口 + 跨端差异），**不需重读 web 端实现** → 不失忆，也不爆上下文。

## 快照时机：压缩后立即补（2026-10-30 定调）

旧写法是「闭环验收通过才允许压缩」——**技术上做不到**：压缩由宿主自动触发、不等人，闸门等于空文。改成任何宿主都能执行的一条：

```text
检测到压缩（上下文被摘要 / 截断） → 立即补当前模块快照 + 写清最终输出 → 再继续下一步
```

- **不等 hook、不等验收**：压缩后第一件事就是往 `project-memory.md` 写/更新当前模块快照（模板见上节），并写清**最终输出**（文件路径 / 页面 / 接口 / 已通过的验证结论）。
- **怎么知道压缩过了**（宿主不一定给信号）：出现下面任一情况，就当作压缩已发生，立刻补快照——① 想不起上一轮读过什么文件、看到过什么工具输出；② 早前的对话细节只剩「做了什么」而没有「看到了什么」；③ 文件内容与自己记忆不符。
- **没验完也照写**：状态写「进行中（完成度 x%）」+ 下一步；不允许因为「还没验完」就不写。
- **闭环是快照里的一个字段，不再是拦压缩的闸门**：
  - 判据（hld-spec.md 质量清单第 12 项）：A 模块的输出都能被某模块接住、无孤儿数据、无凭空数据。
  - 在快照里记 `数据流：闭合 / 待补（缺什么）`；`待补` 的模块不得进下一个模块。

## 示例

上一轮在改 src/prototypes/order-review/index.tsx 的状态切换逻辑，压缩后：

1. **先补快照**：在 `project-memory.md` 写当前模块状态 + 最终输出（改了哪个文件、验证到哪一步、下一步是什么）
2. TaskList 应显示"order-review 状态切换"为 in_progress → 确认
3. 读取该文件确认改动仍在 → 确认
4. 下一步：按 rules/prototype-development-guide.md 验收脚本跑一遍 → 执行
