# 上下文压缩恢复

上下文被压缩后，立即执行以下检查：

1. 检查 TaskList — 确认当前任务进度和下一步
2. 检查文件状态 — 确认未完成的改动是否还在
3. 确认下一步计划 — 不要重复已完成的工作

压缩不是暂停。确认状态后立即继续工作。

---

## 模块完成快照（T1 落地 · 跨端不失忆的解药）

每个模块**数据流闭环验收通过后**，产出 ≤300 字快照，写入常驻基线第 6 项（`project-memory.md`，条目级摘要）：

```markdown
## 模块快照：<模块名>（端：web | mobile | both）
- 状态：已完成 / 进行中（完成度 %）
- 职责：一句话
- 对外接口：契约（输入实体 → 处理 → 输出实体），不写实现
- 依赖模块：上游 X（取什么数据）、下游 Y（给什么数据）
- 数据实体：本模块读写的实体名（与数据模型对齐）
- 关键决策：≤3 条，只写结论 + 一句理由
- 跨端差异：web 已实现的部分，mobile 需注意什么（组件/交互/字段差异）
- 未完成 TODO：≤3 条
```

**跨端失忆的解法**：移动端启动某模块时，装配 = 常驻基线（含 web 端该模块快照）+ 移动端滑窗 → 读到 web 端的接口契约与跨端差异，**不需重读 web 端实现** → 不失忆，也不爆上下文。

## 快照时机：压缩后立即补（2026-10-30 定调 · 与 `_project-template` 同口径）

旧写法是「闭环验收通过 → 才写快照 → 才允许压缩 → 才进下个模块」——**技术上做不到**：压缩由**宿主自动触发、不等人**，`pre-compact.cjs` 在宿主不加载 hook 时也不执行，「才允许压缩」没有任何机制能拦住压缩。闸门等于空文，故改为任何宿主都能执行的一条：

```text
检测到压缩（上下文被摘要 / 截断） → 立即补当前模块快照 + 写清最终输出 → 再继续下一步
```

- **不等 hook、不等验收**：压缩后第一件事就是往 `project-memory.md`「四、模块快照」写/更新当前模块快照（模板见上节），并写清**最终输出**（文件路径 / 页面 / 接口 / 已通过的验证结论）。
- **怎么知道压缩过了**（宿主不一定给信号）：出现任一情况即当作已压缩，立刻补快照——① 想不起上一轮读过什么文件、看到过什么工具输出；② 早前对话细节只剩「做了什么」而没有「看到了什么」；③ 文件内容与记忆不符。
- **没验完也照写**：状态写「进行中（完成度 x%）」+ 下一步；不允许因为「还没验完」就不写。
- **最小快照优先**：字段太多会拖成「等会再写」。允许先写 3 行最小快照（模块名 / 状态 / 关键决策 ≤3），详版后补。

**闭环降级为快照里的一个字段，不再是拦压缩的闸门：**

- **闭环判据**（`hld-spec.md` 质量清单第 12 项）：A 模块的输出都能被某模块接住、无孤儿数据、无凭空数据。
- 在快照里记 `数据流：闭合 / 待补（缺什么）`；**`待补` 的模块不得进下一个模块**——约束落在「推进下一步」这个可控动作上，而不是落在「压缩」这个不可控事件上。
- 不由智能体自报完成：闭环结论须有 `verification-before-completion` 的运行输出作证据。

> **唯一可技术强制的入口是构建命令**：项目侧可在 `npm run build` 后置脚本里校验/追加快照（本模板不含构建脚本，接入项目后按需自建）。
