# 上下文压缩恢复

上下文被压缩后（含 PreCompact hook 触发或长会话自动摘要），立即按下表逐项检查，全部确认后才继续，不得跳过。

## 压缩前归档（压缩发生时先执行）

PreCompact hook 触发或长会话自动摘要**前**，先按记忆门禁三问（影响基线 / 项目可复用 / 工作台可复用）识别值得保留的内容：

1. 值得保留 → 写入对应记忆层（基线文档 / 项目答疑手册.md / ../../工作台答疑手册.md），再更新 project-memory.md 索引
2. 不值得保留（一次性操作、可还原信息）→ 不写入
3. 无法判断 → 先询问人类再压缩
4. 归档完成后再执行下面的恢复检查表

## 恢复检查表（压缩后必须逐项过）

| # | 检查项 | 具体看什么 | 判定标准 | 异常时怎么办 |
|---|--------|-----------|---------|------------|
| 1 | 任务进度 | TaskList 中 in_progress 任务及当前步骤 | 有且仅有一个 in_progress 任务 | 无 → 回到上一条用户消息重新确认目标；多个 → 合并到当前主线 |
| 2 | 未完成改动 | 最近一次 Edit/Write 的目标文件是否仍处于未完成状态 | 文件存在且内容与最后动作一致 | 丢失 → 用 git status 找回或告知用户；内容不符 → 重新读取 |
| 3 | 下一步计划 | 已确认的下一步动作是否明确 | 有明确文件路径 + 动作 + 验收方式 | 不明确 → 用一句话复述计划并请用户确认 |
| 4 | 依赖上下文 | 当前任务依赖的规范是否仍可用 | 相关规范已预加载或可按需重读 | 需要 → 只重读当前依赖的 1 个文件，禁止整库重读 |

## 恢复顺序

1. 先恢复"任务状态"（我在做什么）
2. 再恢复"文件状态"（改到哪了）
3. 最后确认"下一步"（做什么、怎么做、怎么验收）

## 禁区

- 压缩后不重复已完成的工作（不重跑已完成步骤、不整库重读知识）
- 压缩后不擅自扩大范围（只继续当前任务）
- 状态不确定时先问，不猜

## 示例

上一轮在改 src/prototypes/order-review/index.tsx 的状态切换逻辑，压缩后：

1. TaskList 应显示"order-review 状态切换"为 in_progress → 确认
2. 读取该文件确认改动仍在 → 确认
3. 下一步：按 rules/prototype-development-guide.md 验收脚本跑一遍 → 执行
