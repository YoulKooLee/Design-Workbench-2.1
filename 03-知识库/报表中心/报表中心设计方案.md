# 报表中心设计方案（BI / 数据看板）

> 整理日期：2026-10-08
> 用途：软件产品模块设计知识库。覆盖报表中心的业务场景全景、各场景解决方案、通用设计方案（最优解）与设计说明。
> 一句话本质：把"**从数据到决策**"变成平台能力——业务库只做业务操作不跑报表，数据进数仓/数据集模型化后统一出报表；回答"给谁看、看什么、怎么交互、性能怎么扛"四个问题。与导入导出（取数/导出）、搜索（数据检索）、任务调度（定时报表）、权限（行级数据权限）联动形成数据链路闭环。

---

## 一、模块概述：三层解耦，业务与报表互不影响

```
业务系统（只做业务操作，不跑报表）
   │ ETL / 数据同步（Kafka/定时任务）
   ▼
数据层（数据仓库 / 数据集模型）
   │ 离线：PostgreSQL/GP（大结果）· 实时：Kafka → ClickHouse/Druid（多维分析）
   ▼
报表服务层（查询、缓存、分发）
   │ 直连模式（数据源执行） vs 抽取加速模式（列式引擎承载分析负载）
   ▼
前端展示（固定报表 / 自助分析 / 大屏看板）
```

| 核心概念 | 说明 |
| --- | --- |
| 三层架构 | 业务库 → 数据仓库 → 报表服务，互不影响，报表不拖垮业务 |
| 数据集（Dataset） | 数据源中表 + join + 字段类型定义，变换为可复用数据对象 |
| 数据产品 | 查询数据集产出的最终形态：仪表盘/报表/自助分析 |
| 指标血缘 | 树形结构描述复杂指标依赖哪些底层指标维度，可下推复用 |
| 抽数缓存 | 数据集查询结果缓存，相同查询不再连库，定时抽取更新 |

## 二、业务场景全景

### 场景 1：管理驾驶舱 / 数据大屏
- 决策层战略大屏：核心 KPI（销售额、订单量、毛利率）一屏尽览；
- 运营层监控大屏：实时追踪（设备状态、产能、告警）；
- 政务/金融/工业分行业配色与版式。

### 场景 2：固定报表（经营分析）
- 日/周/月销售报表、财务三表、库存报表；
- 表格式明细 + 汇总，按部门/周期/区域切片。

### 场景 3：定时报表与订阅推送
- 每日 9 点自动生成前一日报表，推送给管理层（邮件/IM）；
- 与任务调度中心、消息通知中心联动。

### 场景 4：自助分析（拖拽式报表）
- 业务用户不依赖开发，拖拽维度/指标/图表自己出报表；
- 基于数据集模型，字段/join/类型预定义好。

### 场景 5：报表导出与下钻
- 报表结果导出 Excel（与数据导入导出中心联动）；
- 点击图表下钻：大区 → 城市 → 门店，联动筛选。

### 场景 6：多租户 / 数据权限隔离
- 不同部门/租户只看到自己权限范围内的数据；
- 行级数据权限 + 报表目录权限（与权限模块联动）。

### 场景 7：实时数据监控
- 秒级刷新：实时销售、实时监控、异常告警标红；
- 实时数据流 Kafka → ClickHouse/Druid 支撑。

## 三、各场景的解决方案

### 3.1 架构选型：直连 vs 抽取加速
| 模式 | 适用 | 说明 |
| --- | --- | --- |
| 直连模式 | 数据仓库性能充足 | 查询在数据源端执行，数据永远最新 |
| 抽取加速模式 | 数据量大、查询慢 | 数据同步到列式引擎（Quick Engine），分析负载与业务库解耦 |
| 混合 | 数据量分层 | 小数据直连，大数据抽取加速 |

### 3.2 存储引擎选型
| 存储 | 适用 |
| --- | --- |
| PostgreSQL | 离线结果数据（默认推荐） |
| Greenplum/GP | 数据量大 |
| ClickHouse | 多维分析、实时 |
| Druid | 实时统计数据 |
| Kafka → 实时管道 | 秒级实时指标 |

### 3.3 数据模型：数据集 + 指标血缘（美团实践）
```
数据源（表/join 定义）→ 数据集（可复用数据对象）
  → 指标定义（模板表达：销售额=Σ价格×数量）
  → 指标血缘（树形：复杂指标依赖底层指标维度，限定修饰/忽略维度/留存配置下推）
  → 下游复用同一查询语义，避免口径不一致
```
**关键**：指标口径统一（销售额、活跃用户等定义唯一），血缘保证复杂指标可拆解可复用。

### 3.4 图表选型原则（看板设计）
| 分析意图 | 图表 |
| --- | --- |
| 比较 | 柱状图、条形图、雷达图 |
| 趋势 | 折线图、面积图（时间序列） |
| 构成 | 饼图（≤5 分类）、环形图、堆叠柱状、瀑布图 |
| 分布 | 直方图、散点图、箱线图 |
| 关联 | 气泡图、相关性热力图 |

### 3.5 大屏信息架构
```
导航区（当前页面/模块）
核心指标区：3~5 个 KPI，大号数字卡片/仪表盘（放最显眼位置）
趋势区：折线/面积图（时间序列）
构成/排名区：柱状/条形
实时动态区：滚动列表/跑马灯（实时事件流）
```

### 3.6 性能优化：多级缓存
```
L1 内存 LRU：本地亚毫秒查询
L2 Redis：分布式共享（TTL 30~60s，可削减 70~90% 负载）
L3 数据库持久缓存 / 物化视图：长期复用
报表层：抽数缓存（数据集查询结果缓存 + 定时抽取更新）
```
聚合下推：在数据集查询内做聚合，不把明细拉到前端再聚合。

### 3.7 定时报表与导出
- 定时生成走任务调度中心（cron → 生成 → 存储）；
- 报表导出走导入导出中心（流式/异步/OSS/预签名）；
- 推送走消息通知中心（邮件/IM/站内信）。

## 四、通用设计方案（最优解）

### 4.1 总体架构
```
报表中心（平台通用）：
  数据集服务（数据源接入 / join / 字段模型 / 指标定义 / 指标血缘）
  报表引擎（直连 / 抽取加速双模式查询）
  看板服务（大屏配置 / 图表组件 / 下钻联动 / 实时刷新）
  调度与导出（定时报表 → 任务调度中心；导出 → 导入导出中心）
   │
存储：数据仓库（离线）· ClickHouse/Druid（实时）· Redis（查询缓存）· OSS（导出文件）
   │
集成：
  权限模块（行级数据权限 + 报表目录权限）
  任务调度中心（定时生成/刷新）
  导入导出中心（报表导出）
  消息通知中心（订阅推送）
  审计日志（报表访问/导出留痕）
```

### 4.2 核心表结构
```sql
report_dataset（数据集）：
  id, name, source_type（DB/API/文件）,
  table_name, join_config（JSON）, field_config（JSON：字段/类型/字典）,
  refresh_mode（REALTIME/SCHEDULE/ONCE）, refresh_cron, cache_ttl,
  status, create_by, create_time

report_metric（指标）：
  id, dataset_id, metric_name, expression（模板：Σ/COUNT/DISTINCT）,
  dimension_list（JSON：可用维度）, lineage_parent（指标血缘父节点）,
  cal_rule（限定修饰/忽略维度/留存配置）

report_dashboard（看板/报表）：
  id, name, type（DASHBOARD/REPORT/BIGSCREEN）,
  layout_config（JSON：Z 型布局/分区/组件）,
  chart_list（JSON：图表组件 + 数据源引用 + 交互配置）,
  refresh_interval, status, owner_id

report_schedule（定时报表）：
  id, dashboard_id, cron_expr, push_channel（MAIL/IM/INBOX）,
  recipient_list, export_format（XLSX/PDF）, status
```

### 4.3 关键设计点
- **三层解耦**：业务库不跑报表，数据仓库承担计算，报表服务只查询分发；
- **指标口径统一**：指标血缘树保证"销售额"全公司一个定义；
- **数据集复用**：业务方只写一次模型，多报表复用；
- **缓存分层**：L1 内存 + L2 Redis + L3 物化视图，热点报表秒开；
- **直连/加速双模式**：按数据量和时效自动路由；
- **大屏"给谁看"先行**：决策屏看核心指标，运营屏看实时追踪，交互按需；
- **权限贯穿**：行级数据权限 + 目录权限，导出同权限；
- **定时报表闭环**：任务调度 → 生成 → 通知推送。

## 五、设计说明

### 5.1 核心设计原则
| 原则 | 说明 |
| --- | --- |
| 业务与报表分离 | 业务库不跑报表，互不影响 |
| 数据集模型化 | 一次建模、多次复用，口径统一 |
| 指标血缘 | 复杂指标可拆解、可下推、可复用 |
| 缓存分层 | 热点报表秒开，不反复打库 |
| 直连 + 加速 | 数据量和时效决定查询路径 |
| 给谁看决定设计 | 决策屏 vs 运营屏信息密度不同 |
| 权限贯穿 | 看什么=权限范围，导出同权限 |
| 图表选型精准 | 按分析意图选图，不用装饰性 3D |

### 5.2 常见设计坑与规避
| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 报表直接查业务库 | 拖垮业务性能 | 三层架构：数仓承担计算 |
| 指标口径不一致 | 各部门报表对不上 | 指标血缘统一口径 |
| 每个报表重新建模 | 重复开发、口径漂移 | 数据集复用 |
| 无缓存 | 报表 1~2 分钟加载 | 多级缓存 + 抽数缓存 |
| 明细拉到前端聚合 | 网络/内存爆炸 | 聚合下推到数据集查询 |
| 不看受众就设计大屏 | 信息过载/无关 | 决策屏核心指标，运营屏实时 |
| 图表类型乱用 | 误导决策 | 按意图选型（比较/趋势/构成） |
| 报表不过滤权限 | 越权看数据 | 行级数据权限 + 目录权限 |
| 实时报表无降级 | 数据源抖动页面白 | 缓存兜底 + 降级提示 |
| 导出走同步 | 大报表 HTTP 超时 | 走导入导出中心异步 |

### 5.3 演进路线
```
阶段1 固定报表：SQL 写死 + 图表库，按需开发
   ↓
阶段2 报表平台：数据集模型化 + 抽数缓存 + 定时报表（调度/通知联动）
   ↓
阶段3 自助分析：拖拽式报表 + 指标血缘 + 下钻联动
   ↓
阶段4 实时大屏：Kafka → ClickHouse + 秒级刷新 + 智能告警 + 移动端
```

### 5.4 业界参考实现
- **Power BI**：数据源 → 数据引入 → 数据仓库 → BI 语义模型 → 报告；
- **Quick BI（阿里）**：数据源 → 数据集 → 数据产品，直连/抽取加速双模式；
- **Superset**：元数据库 + Redis 缓存 + Celery 异步任务 + MinIO 文件；
- **帆软 FineReport**：抽数缓存、大屏设计器、图表推荐；
- **美团 BI**：指标平台 + 指标血缘，复杂指标下推复用。
