# 工作流引擎设计方案（Workflow / 审批流）

> 整理日期：2026-09-15
> 用途：软件产品模块设计知识库。覆盖工作流引擎的业务场景全景、各场景解决方案、通用设计方案（最优解）与设计说明。
> 一句话本质：把"业务流转规则"从代码里抽出来——**流程定义（静态模板）→ 流程实例（运行时）→ 任务（人工/自动）→ 网关（分支合并）**，业务人员可视建模、引擎执行流转，不再堆 if-else。

---

## 一、模块概述：四大核心概念

```
流程定义（Process Definition）：BPMN 2.0 静态模板（XML/JSON），描述节点、流转线、条件、参与者
   ↓ 启动
流程实例（Process Instance）：定义的运行时对象，存储当前状态、变量、执行上下文
   ↓ 执行
任务（Task）：用户任务（人工审批）｜ 服务任务（自动调用接口/脚本）｜ 抄送 ｜ 定时
   ↓ 控制
网关（Gateway）：排他（if-else 单选）｜ 并行（多支并行）｜ 包容（可多可少）
```

| 层 | 说明 |
| --- | --- |
| 模型层 | 可视化流程设计器（BPMN 画布），导出流程定义 |
| 引擎层 | 解析执行流程定义：实例、任务、变量、网关路由、事件 |
| 服务层 | 7 大 API：部署、启动、任务查询、完成任务、历史、用户组、表单 |
| 集成层 | 与权限、通知（审批待办提醒）、数据字典、规则引擎对接 |

## 二、业务场景全景

### 场景 1：分级审批（最典型）
- 请假/报销/采购/合同审批：按金额区间、天数、类型条件路由不同审批链路（如请假 >3 天 → 总监审批，≤3 天 → 直接人事备案）；
- 排他网关实现条件分支，**有且最多一条分支通过**，按优先级依次匹配，默认路径兜底。

### 场景 2：多人协同审批（会签/或签/比例）
- 会签：全员同意才通过，任一人拒绝即驳回（跨部门调动、重大采购等共同担责场景）；
- 或签：一人处理即可（值班、轮岗等"谁有空谁处理"）；
- 比例会签：通过比例达阈值即通过（如超过半数），达标后剩余待办作废/跳过；
- 并行会签：法务+财务同时审批（并行网关），任意否决整体驳回。

### 场景 3：动态调整（加签/减签/转办/委派）
- 加签：办理中途邀请其他人参与（前加签/后加签）；减签：移除办理人；
- 转办：任务转给其他人办理（原办理人退出）；
- 委派：A 委派 B，B 办理完回到 A，A 再确认流程才继续（委派归还）；
- 改派：管理员调整办理人。

### 场景 4：驳回与撤回
- 驳回规则可选：驳回发起人（从头来）/ 驳回上一节点 / 驳回指定节点（采购场景常见"退回修改节点而非起点"）；
- 撤回（取回）：下一节点未处理前，发起人/当前节点可撤回再改；
- 中国式细节：驳回后重新提交是"原实例续跑"还是"新实例重发"，需产品明确定义。

### 场景 5：超时与自动处理
- 超时升级：边界事件监听审批超时，自动升级到上级/超时自动通过/转抄送；
- 审批人为空：找不到审批人时按配置自动处理（如转交上级），**流程不卡死在空节点**；
- 服务任务自动执行：邮件通知、调外部接口、写业务表、触发规则引擎。

### 场景 6：抄送与通知
- 抄送人节点（serviceTask）：消息抄送，不参与审批；
- 待办提醒：对接消息通知中心（P1 事务通知），节点到达通知办理人。

### 场景 7：中国式审批细节（比 BPMN 标准更细）
- 会签人是流程启动时确定还是到达节点时按组织实时计算；
- 同部门多人是否去重；岗位空缺时怎样降级；
- 通过比例按人数/权重/部门/层级计算；
- 弃权、超时、撤回意见、管理员代办如何计票；
- 运行中加签后分母与完成条件是否重算；
- 达到通过条件后，未办任务是取消、转抄送还是保留记录。

## 三、各场景的解决方案

### 3.1 节点类型（BPMN 映射）
| 节点类型 | 说明 | BPMN 映射 |
| --- | --- | --- |
| 开始/结束事件 | 流程起点与终点 | startEvent / endEvent |
| 用户任务 | 人工审批（指定人/角色/部门/发起人自选） | userTask |
| 服务任务 | 系统自动执行（邮件/接口/脚本） | serviceTask / scriptTask / sendTask |
| 抄送节点 | 消息抄送不参与 | serviceTask |
| 条件分支 | 按条件单选一路 | exclusiveGateway |
| 并行分支 | 多支并行 | parallelGateway |
| 包容分支 | 可同时执行多个满足条件的分支 | inclusiveGateway |
| 延迟器 | 定时等待 | intermediateCatchEvent |
| 边界事件 | 监听超时/异常 | boundaryEvent |

### 3.2 审批方式（四人模式）
| 方式 | 运行效果 | 适用 |
| --- | --- | --- |
| 依次审批 | 只放出当前顺序处理人，前一人通过后下一人 pending | 单链流转 |
| 或签 | 一人通过节点通过，其余待办标记 skipped 作废 | 谁有空谁处理 |
| 会签 | 全部待办通过后节点通过，任一驳回整体驳回 | 共同担责 |
| 比例会签 | 同意比例达阈值即通过（人数/权重/部门），剩余待办跳过 | 一般协同 |

**实现要点**：或签 = 单任务多候选；会签 = 多实例（multi-instance）；任务完成数量 ≠ 同意数量。

### 3.3 任务操作全集（运行时受控操作）
```
同意 / 拒绝（驳回：发起人|上一节点|指定节点）
加签（前加/后加）/ 减签 / 转办 / 委派（含归还）/ 改派
撤回（下一节点未处理前）/ 抄送 / 催办 / 意见留痕
```
- 转办、改派、委派全程留痕审计；
- 加签/减签需定义分母与完成条件是否重算（中国式审批关键语义）。

### 3.4 条件分支（低代码建模）
- 仿钉钉条件分支 → 引擎侧生成：排他网关 + 条件顺序流 + **默认路径**（不是简单给任务加多条出线）；
- 条件按优先级依次匹配，命中即停；条件支持表单字段、金额区间、表达式；
- 复杂条件可对接规则引擎（与"触发器"模块联动：条件评估复用规则引擎）。

### 3.5 超时与空缺兜底
- 节点配置超时策略（升级上级/自动通过/转抄送/催办通知）；
- 审批人为空自动处理（转交上级或按配置跳过），流程永不卡死；
- 发布时自动校验：空节点、无出口网关、环检测。

### 3.6 引擎选型对比
| 引擎 | 定位 | 优势 | 劣势 |
| --- | --- | --- | --- |
| Flowable | Java OA/低代码/中国式人工流底座 | 轻量、文档清晰、可嵌入、BPMN 标准 | 上层产品能力需自建 |
| Camunda 8 | 云原生新一代 | 商业支持好、实时监控、云架构 | 社区版功能受限、编排较重 |
| Activiti | 早期主流 | 历史积累多 | 社区更新慢、分裂 |

## 四、通用设计方案（最优解）

### 4.1 总体架构
```
流程设计器（可视化画布：事件/任务/网关/流 → BPMN 2.0 XML）
   │ 部署
引擎层：ProcessEngine（线程安全单例）
   ├── RuntimeService（实例启动/变量）
   ├── TaskService（任务查询/认领/完成/转办）
   ├── HistoryService（历史数据）
   ├── ManagementService（Job/表管理）
   └── FormService（表单读写）
   │
数据层：运行时表（小而快，实例结束即删）｜ 历史表（全量留痕）｜ 模型仓库表
   │
集成：权限（办理人/数据权限）· 通知中心（待办提醒）· 规则引擎（条件）· 数据字典（表单枚举）
```

### 4.2 核心数据模型（Flowable 表结构思路，可自研简化版）
```sql
-- 模型/定义
flow_model（流程模型：key/名称/版本/BPMN XML）       -- 部署时校验+版本化
flow_definition（流程定义：model_id/版本号/状态）
-- 运行时（实例结束删记录，保证小且快）
ACT_RU_EXECUTION（流程实例与执行路径：状态/当前节点/变量指针）
ACT_RU_TASK（未完成任务：办理人/到期时间/优先级/委派状态）
ACT_RU_VARIABLE（流程变量：表单数据、路由条件）
ACT_RU_JOB（异步任务：定时器/边界事件）
-- 历史（全量留痕）
ACT_HI_PROCINST（已结束实例）
ACT_HI_TASKINST（任务历史：办理人/意见/耗时）
ACT_HI_ACTINST（活动历史：节点流转轨迹）
ACT_HI_VARINST（变量历史：快照）
```

### 4.3 流程建模四要素（BPMN 2.0）
事件（开始/中间/结束）＋ 任务（用户/服务/脚本/发送）＋ 网关（排他/并行/包容）＋ 顺序流（条件/默认流）；
技术同学与业务同学看同一套模型，直接可执行。

### 4.4 关键语义设计（中国式审批）
| 决策点 | 设计建议 |
| --- | --- |
| 会签人确定时机 | 支持"定义时固定"与"到达时实时按组织计算"两种 |
| 同部门去重 | 节点级配置是否去重 |
| 比例口径 | 人数/权重/部门/层级，节点级可配 |
| 加签后分母 | 明确重算或维持，运行时保持一致 |
| 达到条件后未办任务 | 取消/转抄送/保留记录，节点级可配 |
| 驳回后重提 | 原实例续跑（保留历史）为默认，配置支持新实例 |
| 审批人为空 | 转交上级/自动跳过，发布时校验 |
| 运行时操作 | 加签/减签/转办/委派/改派/撤回，全程留痕 |

### 4.5 与周边模块协同
- **通知中心**：节点到达 → P1 通知办理人；超时 → 催办/升级通知；
- **权限模块**：办理人/候选组解析（角色/部门/数据范围）；任务列表数据权限；
- **数据字典**：表单字段枚举、审批意见字典；
- **触发器/规则引擎**：复杂条件分支复用规则引擎；服务任务可触发规则链。

## 五、设计说明

### 5.1 核心设计原则
| 原则 | 说明 |
| --- | --- |
| 流程与业务解耦 | 新增流程不改代码，业务人员可视建模 |
| 标准先行 | BPMN 2.0 建模，引擎可执行 |
| 运行时表小且快 | 实例结束清理运行时数据，历史全量留痕 |
| 流程永不卡死 | 审批人为空/超时都有兜底策略 |
| 操作全留痕 | 转办/委派/加签/驳回全程审计 |
| 语义比标准细 | 中国式审批（会签计票/驳回策略/加签分母）按产品语义实现 |

### 5.2 常见设计坑与规避
| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 用 if-else 硬写审批流 | 流程一变改代码、易错 | 流程引擎 + 可视化建模 |
| 条件分支不当网关 | 多条路径同时执行 | 排他网关 + 默认路径 |
| 会签当或签实现 | 一人同意即通过、担责失效 | 或签=多候选，会签=多实例 |
| 驳回总回起点 | 用户重复填写、体验差 | 支持驳回指定节点 |
| 审批人为空卡死 | 流程悬挂 | 空人自动处理 + 发布校验 |
| 运行时数据不清理 | 表膨胀查询慢 | 运行时/历史分表，实例结束即删 |
| 忽略中国式语义 | 计票/加签分母混乱 | 按 4.4 决策点逐项定义 |
| 撤回无限制 | 已办节点被篡改 | 仅"下一节点未处理前"可撤回 |

### 5.3 演进路线
```
阶段1 状态机硬编码：单条审批链写死在代码
   ↓ 配置化
阶段2 简单流程配置：节点+审批人+分支可视化配置（仿钉钉）
   ↓ 标准化
阶段3 BPMN 引擎：流程定义/实例/任务/网关，Flowable/Camunda 底座
   ↓ 智能化
阶段4 智能审批：AI 先审（规则预判/风险提示）、与规则引擎联动、流程分析优化
```

### 5.4 业界参考实现
- **Flowable / Camunda 8 / Activiti**：BPMN 2.0 引擎三强（选型见 3.6）；
- **钉钉审批**：条件分支优先级匹配 + 默认路径，中国式审批产品范本；
- **GFlow（Go）**：会签/票签五种阈值（全部/任一/多数决/百分比/固定票数）、动态加签减签、转办改派委派；
- **Warm-Flow**：委派/转办/加签/减签/会签/票签术语表；
- **Ruoyi-Flowable / 芋道 BPM**：Java 生态中国式审批落地参考。
