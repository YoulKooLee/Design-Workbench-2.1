# 任务调度中心设计方案（定时任务 / Job Scheduler）

> 整理日期：2026-09-24
> 用途：软件产品模块设计知识库。覆盖任务调度中心的业务场景全景、各场景解决方案、通用设计方案（最优解）与设计说明。
> 一句话本质：按时间（cron/固定间隔）自动触发任务执行——与「触发器」（事件驱动 ECA）形成互补：**触发器回答"发生了什么"，调度器回答"到点该做什么"**。解决分布式下的重复执行、失败重试、错过补跑、分片并行、依赖编排五大问题。

---

## 一、模块概述：调度中心与执行器分离

```
任务定义（cron / 固定间隔 / 一次性）
   │ 调度中心（Scheduler）：cron 解析 → 计算下次触发时间 → 到点入队
   │ 队列：待执行任务（优先级、可见性超时）
   ▼
执行器（Executor）集群：注册中心、心跳上报、拉取/接收任务并执行
   │ 执行结果上报：成功/失败/耗时/日志
   ▼
状态存储：任务定义、执行历史、运行状态
   │
配套：失败重试 · 超时控制 · 阻塞策略 · 分片广播 · misfire 补跑 · DAG 依赖 · 告警
```

| 核心概念 | 说明 |
| --- | --- |
| cron 表达式 | 时间规则（秒/分/时/日/月/周） |
| misfire（错过执行） | 调度中心宕机/任务阻塞期间错过的触发点如何处理 |
| 分片广播 | 一次触发广播到所有执行器，各拿分片序号并行处理数据子集 |
| 失败重试 | 失败后按次数+间隔自动重试 |
| 幂等 | at-least-once 投递下，业务用幂等键保证重复执行不产生副作用 |

## 二、业务场景全景

### 场景 1：业务闭环类（超时驱动）
- 订单创建 30 分钟未支付自动关闭；
- 会员到期前 3 天发续费提醒；
- **审批超时催办**：扫描工作流中 pending 超时任务，触发催办通知（与工作流引擎联动）；
- 合同到期提醒、质保期到期预警。

### 场景 2：统计报表类
- 每日凌晨生成前一日销售/活跃报表；
- 每月生成经营分析；
- 数据归档：3 个月前订单迁移历史库。

### 场景 3：数据治理与运维类
- 定时清理过期日志、无效数据、临时文件（与文件管理 temp/ 联动）；
- 数据库备份、缓存预热/清理；
- 服务健康检查、证书到期检查。

### 场景 4：数据同步与 ETL
- 跨系统定时同步（ERP↔CRM、主数据分发）；
- 离线数仓 Extract→Transform→Load 流水线（DAG 依赖）。

### 场景 5：批量分片处理
- 大数据量批处理：每日 9 点批量处理前一天待发货订单生成物流单；
- 分片广播：执行器集群各节点并行处理数据子集，水平扩容提吞吐。

### 场景 6：定时通知与推送
- 日报/周报订阅推送；
- 定时营销短信/Push；
- 与消息通知中心对接。

### 场景 7：DAG 依赖编排
- 复杂流水线：数据抽取 → 清洗 → 入仓 → 入缓存 → 出报表，上游成功才触发下游；
- 支持工作流式任务编排（SchedulerX/XXL-JOB 依赖任务）。

## 三、各场景的解决方案

### 3.1 技术选型对比
| 方案 | 适用 | 优点 | 缺点 |
| --- | --- | --- | --- |
| Spring @Scheduled | 单机、简单定时 | 零依赖、注解即用 | 集群重复执行、无监控/重试 |
| Quartz | 单机/集群、复杂规则 | 成熟、集群模式、丰富触发器 | 运维重、可视化弱 |
| **XXL-JOB** | 分布式、中小规模 | 中心化、Web 管理、失败重试/分片/路由丰富、接入简单 | 数据库锁、万级任务有调度延迟 |
| **Elastic-Job** | 大数据分片、弹性扩容 | 数据分片、失效转移、Docker 弹性 | 配置较复杂 |
| PowerJob | 新一代 | 分布式无锁、DAG 工作流、大规模 | 生态较新 |
| ShedLock | 轻量防重复执行 | 仅加分布式锁，侵入小 | 无中心化管理/调度 |

**推荐**：中小分布式系统用 XXL-JOB（成熟易用）；大数据分片用 Elastic-Job；超大规模/秒级用 SchedulerX/PowerJob（分布式无锁水平扩展）。

### 3.2 防重复执行（分布式互斥）
- **调度中心集中式**：统一调度，执行器只被动接收，天然避免多实例重复触发（XXL-JOB 模式）；
- **分布式锁**：@Scheduled + ShedLock——任务触发前抢锁，抢到者执行，其余跳过（适合简单场景）；
- **Quartz 集群**：基于数据库锁选主执行。

### 3.3 失败重试与超时
```
失败重试次数（如 3 次）+ 重试间隔（如 30 秒）
任务超时时间：超时主动中断
阻塞策略：单机串行 / 覆盖之前（丢弃在跑）/ 并行（允许叠加）
并发数：同一任务同时运行最大实例数（=1 禁止重复执行）
```
**关键**：重试必须配合**业务幂等**（如扣款操作重复重试会重复扣款）——业务用请求流水号/状态机保证"多次调用不重复生效"。

### 3.4 misfire（错过执行）策略
| 策略 | 适用 |
| --- | --- |
| 补跑（bounded catch-up） | 账单、结算类必须不丢 |
| 跳过（skip） | 心跳、实时监控类，过期无意义 |
| 立即执行一次（fire once） | 批处理类，补一次即可 |
| 无限补跑（危险） | 长宕机后引发"恢复风暴"，禁止 |

**实现**：调度层记录 `next_fire_time`，重启/恢复后扫描 `next_fire_time <= now` 的任务，按策略决定补跑/跳过。

### 3.5 分片广播（大数据并行）
```
调度中心触发任务 → 广播到执行器集群所有节点
   → 每个节点拿到：shardingIndex（序号）+ shardingTotal（总数）
   → 节点按 index % total 处理自己的数据子集
   → 新增执行器节点自动增加分片数，水平扩容
```
适用：订单批处理、数据同步、全表扫描类。

### 3.6 DAG 依赖编排
- 上游任务全部成功才触发下游；
- 调度器跟踪每个运行实例状态，完成事件驱动拓扑推进；
- 用于 ETL 流水线、复杂报表链路。

## 四、通用设计方案（最优解）

### 4.1 总体架构
```
调度中心（集群 HA）：
  任务定义管理（cron/间隔/一次性/参数）
  触发计算（cron→next_fire_time）
  待执行队列（优先级、可见性超时）
  misfire 检测（扫描到期未执行）
   │
执行器（业务应用内嵌，注册到调度中心）：
  注册发现 · 心跳上报 · 任务执行 · 结果回传 · 分片处理
   │
状态存储：
  job_def（任务定义）· job_run（执行历史/状态/日志）· sharding（分片记录）
   │
配套：失败重试/超时/阻塞策略 · 路由策略（轮询/哈希/故障转移）· 告警（对接通知中心）
```

### 4.2 核心表结构
```sql
job_def（任务定义）：
  id, name, cron_expr, trigger_type（cron/fixed/once）,
  handler（执行器 Bean/HTTP 地址）, sharding_total,
  retry_count, retry_interval, timeout, concurrency,
  misfire_policy（IGNORE/FIRE_ONCE/CATCH_UP）,
  status（启用/停用）, params（JSON）, priority

job_run（执行历史）：
  id, job_id, trigger_time, start_time, end_time,
  status（运行中/成功/失败/超时）, sharding_index,
  execute_route（哪个执行器）, fail_reason, log_url, result
```

### 4.3 执行语义
- **at-least-once**：至少执行一次（重试可能导致重复投递）；
- **exactly-once 不可达**（分布式下），靠**业务幂等键**把重复投递变成安全空操作；
- 任务执行必须幂等：以业务主键 + 状态机/唯一约束防重复生效。

### 4.4 路由策略（执行器选哪个节点）
轮询、随机、一致性哈希（同一任务固定同节点）、故障转移（跳过死亡节点）、分片广播。

## 五、设计说明

### 5.1 核心设计原则
| 原则 | 说明 |
| --- | --- |
| 调度与执行分离 | 调度中心集中触发，执行器只干活，避免多实例重复 |
| 任务必须幂等 | 重试/重复投递下不产生副作用 |
| misfire 按业务定策略 | 结算补跑、心跳跳过，禁止无限补跑引发风暴 |
| 失败必须可感知 | 失败重试 + 告警（对接通知中心）+ 执行历史可查 |
| 超时与阻塞受控 | 防止任务堆积/卡死 |
| 大数据分片并行 | 分片广播水平扩容 |
| 可观测 | 执行状态/历史/日志/耗时可视化 |

### 5.2 常见设计坑与规避
| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 多实例 @Scheduled 重复执行 | 数据重复/重复扣款 | 调度中心集中或 ShedLock 分布式锁 |
| 任务不幂等就重试 | 重复扣款/重复发货 | 业务幂等键/状态机/唯一约束 |
| 失败无重试 | 业务闭环中断（订单未关闭） | 配置失败重试次数+间隔 |
| 宕机后无限补跑 | 恢复风暴、压垮系统 | bounded misfire 策略 |
| 长任务无超时 | 任务堆积、线程占用 | 超时主动中断 |
| 大任务单节点跑 | 慢、吞吐不足 | 分片广播并行 |
| 路由到死节点 | 不断重试失败耗尽 | 故障转移跳过死亡节点 |
| cron 配置无监控 | 任务悄悄失效 | 执行历史 + 失败告警 |

### 5.3 演进路线
```
阶段1 单机：@Scheduled 简单定时
   ↓ 集群
阶段2 防重复：ShedLock/Quartz 集群模式
   ↓ 分布式
阶段3 中心化调度：XXL-JOB（Web 管理/重试/分片/路由/告警）
   ↓ 大规模
阶段4 弹性与编排：Elastic-Job 分片失效转移 + DAG 依赖 + 秒级无锁扩展
```

### 5.4 业界参考实现
- **XXL-JOB**：大众点评开源，中心化调度 + 执行器，Web 管理；
- **Elastic-Job（Apache ShardingSphere）**：数据分片 + 弹性扩缩 + 失效转移；
- **SchedulerX（阿里云）**：分布式无锁水平扩展，百万级任务、秒级调度、DAG 编排；
- **ShedLock**：轻量分布式锁，给 @Scheduled 加互斥；
- **Quartz**：老牌调度框架，集群模式 + 丰富触发器。
