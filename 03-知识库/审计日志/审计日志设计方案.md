# 审计日志设计方案（Audit Log / 操作审计）

> 整理日期：2026-09-16
> 用途：软件产品模块设计知识库。覆盖审计日志的业务场景全景、各场景解决方案、通用设计方案（最优解）与设计说明。
> 一句话本质：回答"**谁、在何时、何地、对什么对象、做了什么操作、结果如何、改前改后**"——完整记录 Who/What/When/Where/Before/After，满足合规审计、权限追溯、运维排障与责任界定。

---

## 一、模块概述：一条审计记录长什么样

一条完整审计记录（等保五要素 + 前后状态）：

```
事件类型（event_type）｜ 主体（operator：谁）｜ 客体（target：对什么）
时间（timestamp）｜ 结果（result：成败）｜ 来源（ip/user_agent/设备）
前置状态（before）｜ 后置状态（after）｜ 业务上下文（单号/流程实例ID/trace_id）
```

| 采集方式 | 说明 |
| --- | --- |
| 业务操作日志（注解+AOP） | 轻量，记录"谁做了什么"（如"张三删除了客户A"） |
| 数据变更审计 | 记录改前改后（before/after），能还原"改成什么了" |
| 全链路审计 | 登录→查询→修改→导出，串联完整操作时间线 |

三种方案成本递增、能力递增，按合规等级与业务重要性选配。

## 二、业务场景全景

### 场景 1：安全合规（强制要求）
- 等保 2.0 / SOX / GDPR / ISO27001：关键操作（登录、权限变更、数据修改、敏感访问）全链路审计留痕；
- 日志含事件类型、主体、客体、时间、结果五要素；集中管理、防本地篡改、保留期达标。

### 场景 2：权限追溯与责任界定
- "谁修改了设置""哪个用户删了数据""数据泄露来源"排查；
- 客户纠纷、内部审计时的责任界定证据链。

### 场景 3：运维排障
- 系统误操作/数据异常时，快速还原完整操作链路（时间线），辅助问题定位；
- 结合 trace_id 串联一次请求的完整调用链。

### 场景 4：异常行为检测
- 非工作时间大批量数据访问、多次登录失败、越权尝试、异常导出；
- 规则引擎匹配审计流 → 触发告警（对接消息通知中心）。

### 场景 5：敏感数据访问审计
- 医疗 EHR、财务数据、个人信息：查看/修改/导出全记录；
- 数据脱敏操作留痕（静态脱敏/动态脱敏、算法、规则 ID）。

### 场景 6：业务审计（审批/流程类）
- 审批链完整留痕：审批节点、处理人、处理时间、审批意见、前后状态；
- 人事异动、合同变更等强监管业务的审计证据链（操作时间+操作人+操作类型+异动前后状态+流程实例ID+单据号八字段）。

## 三、各场景的解决方案

### 3.1 采集模式（四种，按场景组合）
| 模式 | 适用 | 说明 |
| --- | --- | --- |
| 注解 + AOP | 通用操作日志（增删改查/审核/导入导出） | 自定义 `@AuditLog(operationType, resourceType)`，切面环绕采集操作人/IP/参数/结果，**零侵入业务代码** |
| 领域事件 | 业务日志、审核链后置动作 | 发布领域事件（如 BillAuditSuccessEvent），监听方落审计 |
| 全局异常处理 | 统一异常日志 | 关联请求参数与 trace_id |
| 异步落库 | 降低主交易链路耗时 | 日志进队列（Kafka），消费者写存储，不阻塞业务 |

### 3.2 数据脱敏（强制）
- 敏感字段不记录或脱敏：password/pwd、token/access_token/api_key/secret、Authorization/Cookie、URL userinfo；
- 请求/响应 body 默认不记录，只记有界摘要；
- 操作人 ID 可脱敏存储；敏感业务值按脱敏算法（掩码/泛化）落库。

### 3.3 防篡改与完整性
- 日志只追加不修改（append-only）；
- 哈希链（每条日志含上一条哈希）/数字签名，防删除防篡改；
- 集中收集到独立审计系统，避免分散在服务器被本地篡改。

### 3.4 保留期（合规分级）
| 日志类型 | 最短保留（示例） | 建议保留 |
| --- | --- | --- |
| 认证与访问 | 90 天（ISO27001） | 1 年 |
| 个人信息变更 | 3 年（GDPR） | 5 年 |
| 金融交易 | 5 年（商法） | 6 年 |
| 健康数据访问 | 5 年 | 15 年 |

- 按类型分级存储与归档，冷数据低成本保留；
- 医疗/金融等强监管行业按监管要求只增不减。

### 3.5 检索与时间线还原
- 多维检索：用户/IP/操作类型/对象/时间范围/结果；
- 单对象时间线：按"对象 ID + 时间"串联操作序列（如金仓示例：10:00 登录 → 10:05 查询 → 10:08 删除），一键还原事故链路。

## 四、通用设计方案（最优解）

### 4.1 总体架构（采集 → 管道 → 存储 → 消费）
```
业务系统（注解+AOP / 领域事件 / 全局异常）
   │ 异步投递（Kafka 削峰，不阻塞主流程）
审计管道（标准化：补全 trace_id/租户/IP → 脱敏 → 分级）
   │
存储分层：
   ├── ES（热数据：全文检索、多维查询、异常检测）
   ├── MySQL（温数据：合规留存、事务性审计、防篡改哈希链）
   └── 冷存储（归档：低成本长期保留）
   │
消费：
   ├── 审计检索/时间线还原（管理端）
   ├── 异常告警（规则匹配 → 通知中心）
   └── 报表与合规导出
```

### 4.2 核心表结构（审计日志表）
```sql
-- 通用操作日志（等保五要素 + 公共字段）
sys_operate_log (
  id BIGINT PK,
  tenant_id, company_id, shop_id,        -- 多租户/多组织公共字段
  trace_id VARCHAR(64),                  -- 调用链追踪
  event_type VARCHAR(50),                -- 操作类型（枚举：登录/新增/修改/删除/审批/导出…）
  operator_id VARCHAR(64), operator_name VARCHAR(64),  -- 主体（工号/系统ID，非姓名别名）
  target_type VARCHAR(50), target_id VARCHAR(64),      -- 客体（对象类型+ID）
  request_ip VARCHAR(45), user_agent VARCHAR(255), device_info VARCHAR(255), -- 来源
  result TINYINT,                        -- 结果（成功/失败）
  detail VARCHAR(2000),                  -- 操作描述（含脱敏后的参数摘要）
  create_time DATETIME(3),               -- 时间（毫秒级，可信时间戳可选）
  INDEX (operator_id), INDEX (target_type, target_id), INDEX (create_time)
);

-- 数据变更审计（before/after，可还原改前改后）
data_change_log (
  id, trace_id, operator_id, target_type, target_id,
  field_name, before_value, after_value,   -- 字段级前后值
  change_time, change_type                 -- C/U/D
);

-- 登录审计（安全型，独立表高频）
login_log (
  id, user_id, login_time, login_ip, user_agent,
  device_info, result（成功/失败/锁定）, fail_reason
);
```

### 4.3 审计字段规范（八字段证据链）
操作时间（服务器时间）｜ 操作人唯一标识 ｜ 操作类型（枚举）｜ 操作对象标识 ｜ 前置状态 ｜ 后置状态 ｜ 流程实例 ID ｜ 关联业务单据号——强监管业务（人事异动、合同）按此八字段构成完整证据链。

### 4.4 采集实现要点
- **注解 + AOP**：`@AuditLog(operationType="USER_UPDATE", resourceType="USER")`，切面 `@Around` 采集；
- 从安全上下文取操作人（JWT/user_id），从请求取 IP/UA；
- **异步**：`@Async` 独立线程或 Kafka 投递，不阻塞主响应；
- 失败兜底：审计写入失败不能影响主业务（重试/降级），但关键审计（登录/权限）需保证落库。

### 4.5 存储分级与检索
- ES：审计检索、时间线还原、异常检测规则匹配；
- MySQL：合规留存 + 哈希链防篡改（审计库独立于业务库）；
- 冷归档：按保留期策略迁移，可导出合规报告；
- 大数据量：按天/月分表分区，检索走 ES 索引。

## 五、设计说明

### 5.1 核心设计原则
| 原则 | 说明 |
| --- | --- |
| 零侵入采集 | AOP/事件/中间件，业务代码不散落日志逻辑 |
| 异步不阻塞 | 审计写入不影响主业务链路 |
| 只追加不可篡改 | append-only + 哈希链/签名，防删改 |
| 先脱敏后落库 | 敏感字段不记录或脱敏，防二次泄露 |
| 五要素齐全 | 事件类型/主体/客体/时间/结果，合规必备 |
| 分级存储归档 | 热 ES 检索、温 MySQL 留存、冷归档合规保留 |
| 审计独立 | 审计库独立于业务库，集中收集防本地篡改 |

### 5.2 常见设计坑与规避
| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 只记动作不记数据 | 查不到"改成什么了" | 数据变更审计（before/after） |
| 日志同步写库 | 拖慢主接口 | 异步投递（Kafka/@Async） |
| 不脱敏直接落库 | 审计日志成二次泄露源 | 敏感字段脱敏规则强制 |
| 日志分散在业务代码 | 改业务改日志、易漏记 | AOP 注解统一采集 |
| 无防篡改 | 日志可被删改失证 | 哈希链/签名 + append-only + 独立审计库 |
| 无保留期管理 | 存储膨胀或合规不达标 | 分级保留期 + 冷归档 |
| 忽略租户/组织字段 | 多租户无法按租户审计 | 公共字段统一保留 tenant_id 等 |
| 无 trace_id | 单次请求链路无法串联 | 全链路 trace_id 透传 |
| 审计失败影响主流程 | 主业务被审计拖垮 | 审计异步 + 失败降级（关键审计除外） |

### 5.3 演进路线
```
阶段1 操作日志：注解+AOP 单表，记录"谁做了什么"
   ↓ 合规
阶段2 合规审计：五要素 + 脱敏 + 独立审计库 + 保留期 + 检索
   ↓ 数据驱动
阶段3 数据变更审计 + 时间线：before/after、单对象操作时间线还原
   ↓ 智能化
阶段4 异常检测 + 风险审计：规则匹配审计流告警、行为画像、自动取证
```

### 5.4 业界参考实现
- **等保 2.0 日志审计体系**：五要素、集中管理、完整性保护（数字签名/哈希）；
- **EventLog Analyzer / SIEM**：统一收集 OS/DB/网络/应用日志，生成合规报表；
- **MySQL 原生审计**：init_connect + connection_log 记录连接审计；
- **Spring AOP + Kafka + ES**：注解采集 → 异步投递 → 检索，微服务标准打法；
- **Dify 企业版**：结构化审计日志 Schema + SIEM 对接规范。
