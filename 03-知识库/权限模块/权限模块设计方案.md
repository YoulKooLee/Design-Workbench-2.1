# 权限模块设计方案（Permission / Access Control）

> 整理日期：2026-09-11
> 用途：软件产品模块设计知识库。覆盖权限模块的业务场景、各场景解决方案、通用设计方案（最优解）与设计说明。
> 一句话本质：权限模块解决的是 **"谁能对什么做什么、能看什么、能看谁的"** 三个问题。

---

## 一、模块概述：权限到底在管什么

企业级权限管理不是一个 `@PreAuthorize` 注解能解决的，而是一个系统性工程。业界通常把权限体系拆成**三层防线**，分别回答三个问题：

| 层次 | 解决的问题 | 核心机制 | 作用域 |
| --- | --- | --- | --- |
| **功能权限（授权）** | 用户能执行哪些操作 | 用户 → 角色 → 菜单/按钮权限标识 | 接口级 + 按钮级 |
| **数据权限** | 用户能看到哪些数据 | 角色 → 数据范围 → SQL 条件自动注入 | 行级 |
| **多租户隔离** | 不同租户的数据彼此不可见 | 租户 → 套餐 → 自动追加 `tenant_id` | 全表级 |

完整的请求链路是层层叠加的：

```
请求进入 → 认证（你是谁）→ 功能权限（你能做什么）→ 数据权限（你能看哪些）→ 租户隔离（你是哪家公司的）→ 返回数据
```

**认证（Authentication）与授权（Authorization）必须分离**：认证确认身份（你是谁），授权决定能力（你能做什么/看什么）。微服务架构下通常由网关统一负责认证，业务服务负责鉴权。

## 二、业务场景全景

### 场景 1：功能权限（操作级权限）
- **典型需求**：不同角色的用户登录后看到不同的菜单、页面、按钮；同一个页面上 A 角色能"新建"但不能"删除"，B 角色能"查看"但不能"导出"。
- **粒度由粗到细**：菜单级 → 页面级 → 按钮级 → 接口级 → 字段级。
  - 菜单级：控制侧边栏是否显示（简单内部系统够用）；
  - 按钮级：控制页面每个操作按钮显隐（企业级管理系统的推荐粒度）；
  - 字段级：控制表单/列表每个字段的可见性（金融、医疗等高安全要求场景）。
- **关键约束**：前端按钮显隐与后端接口校验必须用**同一套权限标识**，否则"前端藏了按钮、后端没拦请求"就是安全漏洞。

### 场景 2：数据权限（行级/数据范围权限）
- **典型需求**：部门经理只能看本部门考勤记录，区域总监能看下辖所有部门销售数据，普通销售只能看自己创建的客户，超管能看全部。
- **难点**：不可能靠每个业务模块手动写 `WHERE` 实现，需要一个无侵入、可统一维护的机制。
- **典型范围（以若依系为参考，5 种）**：

| 枚举 | 名称 | SQL 效果 | 典型角色 |
| --- | --- | --- | --- |
| ALL | 全部数据 | 不追加条件 | 超管、总经理 |
| DEPT_CUSTOM | 自定义部门 | `dept_id IN (指定部门列表)` | 跨部门协作角色 |
| DEPT_ONLY | 仅本部门 | `dept_id = 当前用户部门` | 部门经理 |
| DEPT_AND_CHILD | 本部门及子部门 | `dept_id IN (本部门+全部子部门)` | 区域总监 |
| SELF | 仅本人 | `user_id = 当前用户` | 普通员工/销售 |

- 一个用户可能有多个角色，各角色数据范围不同，通常取**并集**作为最终可见范围。

### 场景 3：多租户隔离（SaaS 场景）
- **典型需求**：同一套系统服务多家公司（租户），A 公司的管理员不能看到 B 公司的客户数据；租户 A 的角色、菜单、用户不能被租户 B 看到。
- **难点**：哪些表需要按租户隔离、哪些表全局共享（如系统菜单），决策错误就是数据泄露。
- **进阶**：部分系统在租户隔离之上再叠加**组织数据权限**做双层隔离（第一层租户硬隔离 + 第二层部门软隔离）。

### 场景 4：身份认证（登录与通行）
- **典型需求**：账号密码登录、短信/验证码登录、扫码登录；企业内部多系统一次登录处处通行（SSO）；第三方平台授权登录（微信/钉钉/Google）；微服务下无状态、可水平扩展的令牌体系。
- **关键点**：会话状态管理、令牌安全存储、令牌刷新与撤销、登录态实时有效性。

### 场景 5：前端权限控制
- **典型需求**：前端不能硬编码路由表；登录后按权限动态生成菜单和路由；页面上无权限的按钮自动隐藏。
- **关键约束**：前端权限只是体验优化，**后端校验才是安全边界**，两者必须一致。

### 场景 6（进阶）：开放平台 / API 权限、AI 与大模型权限
- 开放平台场景：为第三方应用颁发 API Key，控制其可调用的接口、配额、IP 白名单。
- AI 场景（大模型网关）：API Key 绑定角色、限制可调用模型、租户预算管控、配合策略引擎（如 OPA）做动态鉴权。

## 三、各场景的解决方案

### 3.1 功能权限：四种访问控制模型

| 模型 | 核心思想 | 灵活性 | 维护成本 | 适用场景 |
| --- | --- | --- | --- | --- |
| **ACL**（访问控制列表） | 直接在用户/资源上记录权限 | 低 | 高 | 文件级控制（网盘、文档） |
| **RBAC**（基于角色） | 权限绑定角色，用户挂角色 | 中 | 中 | 企业内部系统、后台管理（事实标准） |
| **ABAC**（基于属性） | 按主体/客体/环境/操作属性动态计算 | 高 | 低（配合策略引擎） | 云服务、多租户、高安全、实时协作 |
| **RBAC + ABAC 混合** | 角色管基础授权，属性做细粒度补充 | 高 | 中 | 企业级系统的普遍最优实践 |

- **RBAC** 由 NIST 于 1992 年正式提出（David Ferraiolo 和 Rick Kuhn）。核心一句话：**不直接给用户分配权限，而是把权限赋予角色，再把角色赋予用户**。500 名员工 × 200 个权限时，维护量从 10 万条降到 10~20 个角色。
- **RBAC 分级**：
  - RBAC₀：用户 ↔ 角色 ↔ 权限，最基础三者关系（小型系统）；
  - RBAC₁：增加**角色继承**（部门经理继承普通员工权限，企业实践最常用）；
  - RBAC₂：增加**约束**（互斥角色、基数限制，如出纳与审核不能同一人）；
  - RBAC₃：继承 + 约束（大型集团企业）。
- **ABAC 四维属性**：主体属性（职位、部门、安全等级）、客体属性（文件密级、数据归属）、环境属性（时间、IP、设备、地理位置）、操作属性（动作类型）。
- **选型决策**（参考 Cerbos 等实践）：
  - 权限能清晰映射到岗位、规则宽泛稳定 → RBAC；
  - 权限依赖具体资源、上下文或用户与数据的关系 → ABAC；
  - 多租户 SaaS 的租户隔离往往需要属性/条件参与 → ABAC 或 RBAC+ABAC；
  - 角色数量爆炸、跨组织复杂结构 → 用 ABAC 或引入更多维度消解。

#### RBAC 落地：经典四表模型 + 权限标识
```
system_user_role（用户-角色） ← system_role（角色） → system_role_menu（角色-菜单） → system_menu（菜单/按钮）
```
- `system_menu.permission` 是一个权限字符串，如 `system:role:create`，是**前后端权限校验的唯一标识**：
  - 后端：`@PreAuthorize("@ss.hasPermission('system:role:create')")`
  - 前端：`auth: ['system:role:create']` 控制按钮显隐
  - 数据库：菜单管理页面统一维护
- 菜单表同时承载三种类型：目录（type=1）、菜单（type=2）、按钮（type=3），"菜单管理"页面即权限配置中心，新增权限无需改代码。

#### 功能权限校验链路
```
@PreAuthorize → 权限服务.hasAnyPermissions(userId, permissions)
  → 1. 获取用户全部启用角色
  → 2. 每个 permission 查拥有该权限的菜单 ID
  → 3. 菜单的角色集合与用户角色集合求交集
  → 4. 超管角色短路返回 true
```
设计要点：空权限短路（无需权限的接口直接放行）、超管兜底、缓存优化、**严格模式**（权限字符串找不到对应菜单记录视为无权限，防止写错标识导致绕过校验）。

### 3.2 数据权限：三种实现路线

| 方案 | 实现方式 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 业务代码手动拼接 | 每个 Service 方法里手写 `WHERE dept_id IN (...)` | 直观 | 侵入性强、易遗漏、难维护 |
| B. 注解 + AOP | 在查询方法上打注解，AOP 切面改写 SQL | 侵入小 | 需逐个方法标注，规则复杂时难表达 |
| C. ORM 拦截器自动注入（**推荐**） | MyBatis 拦截器 / MyBatis-Plus 插件，执行 SQL 前自动追加条件 | 业务代码零侵入，新表注册一行列名映射即可 | 需理解拦截器机制，注意递归 |

- **推荐方案 C 的关键实现**（以若依系为代表）：
  - 拦截器先检查当前表是否注册了部门列/用户列映射，未注册不受控制；
  - 从请求上下文获取数据权限 DTO（首次计算后缓存在请求上下文，避免重复计算）；
  - `all==true` 不追加条件；无部门 ID 且非 self 时追加 `WHERE null=null`（返回空数据）；否则拼 `WHERE (dept_id IN (...) OR user_id = ?)`；
  - 多角色数据范围取并集；
  - **防递归**：数据权限计算接口自身要关闭数据权限（如 `@DataPermission(enable = false)`），否则拦截器调用权限计算、权限计算又触发拦截器形成死循环；
  - 部门树的"本部门及子部门"查询可用**闭包表**（如 `sys_dept_closure`）优化，避免递归查树。
- 更细的实现变体：**列权限**（只能看某些列）可用 ORM 层面裁剪 SELECT 字段；PostgreSQL 还支持原生**行级安全（RLS）**作为数据库层兜底。

### 3.3 多租户隔离：三种数据库架构模式

| 方案 | 隔离程度 | 成本 | 适用场景 |
| --- | --- | --- | --- |
| A. 独立数据库（Database Per Tenant） | 最强（物理隔离、故障不扩散） | 最高（每租户独立实例/连接池/备份） | 大型企业客户、高安全/合规要求 |
| B. 共享数据库 + 独立 Schema | 高（逻辑隔离、物理共享） | 中 | 中型客户，需要一定隔离，租户量数百级 |
| C. 共享表 + `tenant_id` 字段（**SaaS 起步推荐**） | 中 | 低 | 大量小型租户、SaaS 模式 |

- **方案 C 落地要点**：
  - 所有业务表必须有 `tenant_id`，所有查询/写入自动带租户条件，任何绕过都视为严重漏洞；
  - 框架自动注入：业务表 DO 继承 `TenantBaseDO`（含 `tenant_id`），系统共享表继承 `BaseDO` 并标注忽略注解；MyBatis-Plus `TenantLineHandler` 在 SQL 执行前自动追加 `AND tenant_id = ?`；
  - `ignoreTable` 判断顺序：全局开关 → 忽略列表 → 表对应 DO 找不到 → 继承 `TenantBaseDO` 则强制隔离 → 标注忽略注解则跳过；
  - **套餐机制**：租户套餐（`tenant_package.menu_ids`）控制该租户可用哪些菜单，用于 SaaS 定价分级（基础版/高级版/旗舰版）；
  - **创建租户一键初始化**：一个事务内完成创建租户记录 + 创建管理员角色（绑定套餐菜单）+ 创建管理员用户，并切换租户上下文写入，开箱即用；
  - 安全兜底：可叠加 PostgreSQL RLS 行级安全，实现"应用层 + 数据库层"双保险。

### 3.4 身份认证：会话 vs 令牌

| 方案 | 机制 | 优点 | 缺点/场景 |
| --- | --- | --- | --- |
| Session 会话 | 服务端存储会话，HttpOnly Cookie 携带会话 ID | 可随时撤销、实现简单 | 有状态，微服务/水平扩展需共享存储（Redis） |
| JWT 令牌 | 用户信息打包进 Token，验签不查库 | 无状态、跨域友好、微服务友好 | 无法主动撤销，需黑名单/短时效配合 |
| OAuth 2.0 | 授权协议，授权码模式 | 三方登录、开放 API 的标准 | 流程较重，需要授权服务器 |
| OIDC | OAuth2 + 身份信息（ID Token） | 所有需要用户身份的场景 | 依赖 IdP |
| SSO（CAS/SAML/OIDC） | 一次登录，多系统通行 | 企业内多系统体验统一 | 需要集中身份提供方（IdP） |

- **推荐组合（微服务/前后端分离）**：JWT 双令牌 + 网关统一认证。
  - `access_token`：短时效（15~30 分钟），内存/sessionStorage 存放，负责日常业务鉴权；
  - `refresh_token`：长时效（约 7 天），必须存 `httpOnly Cookie`，只用于换取新 access_token，不参与业务请求；
  - 认证与授权分离：**网关负责认证**（校验 Token、解析用户、透传 `login-user` 头），**业务服务负责鉴权**（从 Header 解析 LoginUser，做权限校验）；
  - 需要实时撤销/黑名单时，用 Redis 记录失效 token（黑名单校验）。
- 单体部署：TokenAuthenticationFilter 校验 Token → 构建 LoginUser → 写入安全上下文。

### 3.5 前端权限控制

| 控制点 | 方案 |
| --- | --- |
| 路由/菜单 | 登录后调接口获取当前用户菜单列表 → 前端 `router.addRoute()` 动态注册 → 路由守卫 `beforeEach` 拦截（无 token 跳登录、无权限跳 403） |
| 按钮 | 自定义指令 `v-permission` / 组件 `auth` 属性：无权限直接移除 DOM 或隐藏 |
| 权限状态 | Pinia/Vuex 存储权限列表；多角色切换时**重置路由表**重新生成，避免旧路由残留 |
| 一致性 | 前端权限标识与后端 `permission` 字符串、数据库 `menu.permission` 完全一致，由菜单管理统一维护 |

### 3.6 进阶场景方案
- **字段权限**：ORM 层按权限裁剪列；或前端按字段级权限控制渲染（高安全系统）。
- **开放平台 API 权限**：应用（App）注册 → 颁发 API Key / 应用凭据 → 网关验签 + 配额 + IP 白名单 + 接口级授权。
- **AI 网关权限**：API Key 状态校验 → 租户全局预算校验 → RBAC 校验（Key 绑定角色可调模型范围）→ 策略引擎（OPA）动态策略 → 审计。

## 四、通用设计方案（最优解）

> 综合企业级实践（若依系、SAP、阿里云 RAM、AWS IAM、Cerbos 等），给出一个可直接落地的"最优解"组合。

### 4.1 总体架构：认证 + 三层防线

```
                        ┌─────────────────────────────────────────┐
 用户请求 ──▶ 网关认证 ──▶ 功能权限 ──▶ 数据权限 ──▶ 多租户隔离 ──▶ 数据
 (你是谁)  (你能做什么)  (你能看哪些)  (你是哪家公司的)
                        └─────────────────────────────────────────┘
  认证：OAuth2/JWT 双令牌，网关统一校验，LoginUser 透传
  功能：RBAC（用户-角色-菜单/按钮），权限字符串前后端统一
  数据：角色数据范围 + ORM 拦截器自动注入 SQL
  租户：tenant_id + 拦截器自动追加，套餐控制功能边界
  缓存：三层缓存保障高频校验性能
```

### 4.2 权限模型选型决策

| 决策点 | 最优解 | 理由 |
| --- | --- | --- |
| 基础模型 | RBAC（用户-角色-权限） | 业界事实标准，角色解耦用户与权限，符合组织管理直觉 |
| 权限粒度 | 按钮级 + 行级（数据权限） | 覆盖绝大多数企业应用场景 |
| 复杂/高安全场景 | RBAC + ABAC 混合 | 角色管基础授权，属性策略做细粒度补充，兼顾管理与灵活 |
| 数据权限实现 | ORM 拦截器自动注入 | 业务代码零侵入，新表注册一行列名映射即可 |
| 租户隔离实现 | 共享表 + tenant_id（起步），按客户升级 | 成本最低、SaaS 友好；大客户升级独立 Schema/独立库 |
| 认证方式 | OAuth2/JWT 无状态令牌 | 微服务友好、可水平扩展；需要实时撤销时加 Redis 黑名单 |
| 前后端一致性 | 同一套 permission 字符串 | 消除"前端藏按钮、后端没拦"的安全漏洞 |

### 4.3 数据模型（核心表结构）

```
system_user ── system_user_role ── system_role ── system_role_menu ── system_menu
                                       │  (含 data_scope / data_scope_dept_ids)
system_tenant（租户）── system_tenant_package（套餐，menu_ids 控制功能范围）
业务表：继承 TenantBaseDO（自动含 tenant_id）
```

| 表 | 关键字段 | 设计要点 |
| --- | --- | --- |
| `system_menu` | `id, name, permission, type(1目录/2菜单/3按钮), parent_id, path, component, icon, sort, status` | **不加 tenant_id**：菜单全局共享，差异在角色关联 |
| `system_role` | `id, name, code, data_scope, data_scope_dept_ids(JSON), type, status, tenant_id` | 租户级独立角色体系；自定义部门列表用 JSON 存 |
| `system_user_role` | `user_id, role_id` | 可不加 tenant_id（user/role 各自租户内唯一） |
| `system_role_menu` | `role_id, menu_id, tenant_id` | 租户级关联 |
| `system_tenant` | `id, name, package_id, contact_user_id, expire_time, websites` | 租户信息 |
| `system_tenant_package` | `id, name, menu_ids(JSON), status` | 套餐 → 菜单集合，SaaS 定价基础 |

### 4.4 权限校验链路与超管处理

```
请求 → 提取 Token → 校验（签名/过期/黑名单）→ 构建 LoginUser（userId/userType/tenantId/scopes/context）
     → @PreAuthorize 功能权限校验（角色-菜单交集，超管短路）
     → 数据权限拦截器注入 SQL（数据范围并集）
     → 租户拦截器注入 tenant_id（TenantBaseDO 判断）
```
- LoginUser.context 是请求级上下文，数据权限 DTO 首次计算后缓存于此，同一请求查多张表不重复计算；
- 超管（`code = super_admin`）在普通校验失败后再短路放行，确保不被误拦。

### 4.5 缓存与性能设计（三层缓存）

| 缓存层 | 缓存内容 | TTL/失效 | 命中率 |
| --- | --- | --- | --- |
| 基础数据缓存（Spring Cache / Redis） | 角色列表、菜单-角色映射、权限列表 | 数据变更主动失效 | 极高（基础数据变更不频繁） |
| 校验结果缓存（本地 Guava/Caffeine） | `hasAnyPermissions(userId, permissions)` 结果 | 1 分钟 | 高（同用户短时多次请求） |
| 请求上下文缓存 | 数据权限 DTO | 单次请求 | 100% |

- 分布式场景：用户权限列表缓存 Redis，Key 如 `user:perm:{userID}`，TTL 与 JWT 一致；权限变更主动清缓存，登出强制清缓存；
- 高并发网关鉴权：网关 + 本地缓存（Caffeine，TTL 30s）+ Redis 分布式缓存两级加速，命中时鉴权可到毫秒级；用布隆过滤器防缓存穿透；
- 实时性权衡：角色权限修改后最多 1 分钟生效，企业场景可接受。

### 4.6 多租户落地清单
1. 起步选**共享表 + tenant_id**，用 DO 继承 + 拦截器自动注入；
2. 明确表隔离规则：业务表强制隔离、系统表（菜单）全局共享，用忽略清单/注解管理；
3. 套餐机制控制租户功能边界，创建租户一键初始化（租户 + 管理员角色 + 管理员用户）；
4. 双保险：应用层注入 + 数据库层 RLS（高安全租户）；
5. 预留升级路径：大客户可升级独立 Schema / 独立数据库。

### 4.7 前端落地清单
1. 后端下发菜单/权限 → 动态路由 + 路由守卫；
2. 按钮用 `v-permission` 指令/`auth` 属性控制显隐；
3. 多角色切换重置路由；
4. 权限标识与后端、数据库三方一致。

### 4.8 微服务扩展
- 独立**权限中心服务**统一管理角色/权限逻辑，业务服务通过 SDK/RPC 调用；
- API 网关：统一认证 + 粗粒度授权（按路径/角色拦截）；
- 服务内部：细粒度校验（基于 JWT 解析角色/权限码）；
- 服务网格（Istio AuthorizationPolicy）：声明式服务间访问控制；
- 权限策略引擎（OPA/Cerbos）：复杂属性策略集中化、可热加载。

## 五、设计说明

### 5.1 核心设计原则

| 原则 | 说明 |
| --- | --- |
| **最小权限（Least Privilege）** | 只授予完成任务所需的最少权限，降低凭证被盗后的爆炸半径；配合临时凭证、时限授权 |
| **职责分离（SoD）** | 关键操作需多角色协同（如出纳与审核分离），防止权限滥用；特权角色分配数量应严格受限（参考 Azure 建议：特权角色分配 < 10） |
| **认证与授权分离** | 网关认证、服务鉴权，职责清晰 |
| **前后端权限一致** | 同一权限标识贯穿数据库/后端/前端，前端显隐只是体验，后端校验才是安全边界 |
| **框架承担隔离，业务专注业务** | 拦截器/注解/继承关系自动处理横切关注点，业务代码零侵入 |
| **可审计可追溯** | 权限变更与访问行为全部记录，满足等保/SOX 审计 |
| **分级授权与审批** | 数据分类分级（公开/内部/敏感/核心），敏感数据只开最少必要角色，权限变更按层级审批 |

### 5.2 常见设计坑与规避

| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 前端藏了按钮、后端没拦请求 | 越权访问 | 后端必须独立校验，前端只是体验 |
| 数据权限拦截器递归调用 | 死循环/栈溢出 | 权限计算接口自身关闭数据权限（`@DataPermission(enable=false)`） |
| 查询漏加 `tenant_id` | 跨租户数据泄露 | DO 继承 TenantBaseDO + 拦截器强制注入 + RLS 兜底 |
| 隔离表判断错误（该隔离的表没隔离） | 数据泄露 | 明确的表隔离规则 + 忽略清单审核 |
| 角色爆炸（复杂组织纯 RBAC） | 角色管理失控 | 引入 ABAC/属性维度、组织维度（角色×组织交叉授权） |
| 权限缓存不一致（改权限不生效/串权限） | 权限错误放行或误拦 | 主动失效 + TTL + 登出清理，改动最多 1 分钟生效 |
| 权限字符串写错（未注册） | 校验绕过 | 严格模式：找不到对应菜单记录视为无权限 |
| 多角色数据范围语义不清 | 越权或功能不可用 | 明确并集/交集策略（通常取并集），并在文档中固化 |
| 仅依赖 JWT 无法撤销 | 被盗令牌无法即时失效 | access_token 短时效 + refresh_token httpOnly + Redis 黑名单 |
| 特权账号长期不回收 | 内部风险 | 临时凭证、时限授权、定期权限审计 |

### 5.3 演进路线（按业务阶段升级）

```
阶段1 简单内部系统：菜单级 RBAC，四表模型
   ↓ 用户规模变大、组织层级复杂
阶段2 企业级系统：按钮级功能权限 + 行级数据权限（SQL 拦截器），三层缓存
   ↓ 对外提供 SaaS / 服务多家客户
阶段3 多租户：tenant_id 隔离 + 套餐机制；大客户升级 Schema/独立库
   ↓ 高安全、复杂动态规则、云服务/开放平台
阶段4 ABAC/策略引擎（OPA）：属性策略、动态鉴权、实时热加载
   ↓ AI 时代
阶段5 大模型权限：API Key + 模型级 RBAC + 租户配额 + 策略引擎 + 全链路审计
```

### 5.4 业界参考实现
- 若依（RuoYi）/ RuoYi-Office：RBAC + 数据权限 + 多租户的开源标杆（Java/Spring）；
- SAP S/4HANA：事务码 + 角色 = Profile + Authorization Object；
- 钉钉/飞书：RBAC + 数据权限 / RBAC+ABAC 混合；
- 阿里云 RAM、AWS IAM：云上权限最佳实践（最小权限、临时凭证、ABAC 标签授权）；
- Cerbos / OPA / OpenFGA（ReBAC）：开源策略引擎，支持复杂策略与关系权限。
