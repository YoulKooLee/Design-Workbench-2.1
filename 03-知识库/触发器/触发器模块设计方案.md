# 触发器模块设计方案（Trigger / 规则引擎）

> 整理日期：2026-09-11
> 用途：软件产品模块设计知识库。聚焦"触发器如何设计、任务如何编排"——覆盖告警、远程控制、自动化等典型业务场景。
> 一句话本质：触发器模块解决 **"什么事件启动规则、是否执行、执行什么、如何可靠执行"**，核心是 **ECA 模型**（事件 Event → 条件 Condition → 动作 Action）+ **规则链任务编排**（节点 + 关系构成的有向图）。

---

## 一、模块概述：一个底座，三类业务

触发器/规则引擎是业务自动化系统的公共底座，告警、远程控制、自动化（场景联动）三类业务都构建在它之上：

| 业务 | 回答的问题 | 在规则引擎中的体现 |
| --- | --- | --- |
| **告警** | 状态异常时如何发现、收敛、通知、闭环 | 规则（上报 → 条件 → 触发告警 → 通知/联动） |
| **远程控制** | 云端如何可靠下发指令并确认结果 | 规则的动作之一（指令下发），也可作触发源（设备事件） |
| **自动化/场景联动** | 条件满足时如何自动执行动作序列 | 规则（触发 → 条件 → 执行动作序列） |

规则引擎的设计核心只有两个问题：
1. **触发器如何设计**——用什么事件、在什么时机、以什么策略触发规则；
2. **如何编排任务**——触发后，一串动作如何组织、路由、执行、失败兜底。

---

## 二、业务场景全景

### 场景 1：告警（异常监测与通知）
- 阈值告警（温度 > 80℃）、范围判断、状态判断（设备离线）；
- 告警联动：触发后串接多个动作——推送通知、下发指令、调外部接口、写库留痕；
- 告警风暴治理：批量离线、阈值震荡时避免告警刷屏；
- 告警闭环：发生 → 通知 → 确认 → 处理 → 恢复 → 关闭，全程留痕。

### 场景 2：远程控制（指令下发）
- 实时控制：立即下发并等待结果（开关、调速、参数设置）；
- 离线控制：设备不在线时指令缓存，上线后补发；
- 批量控制：对一组设备下发相同指令；
- 状态对账：云端期望状态与设备实际状态同步（影子设备）。

### 场景 3：自动化 / 场景联动
- 设备联动：A 设备触发、B 设备动作（门磁打开 → 开灯）；
- 定时任务：按 cron 周期执行（每天 8:00 巡检）；
- 场景模式：用户一键触发一组动作（"回家模式"）；
- 跨设备/跨字段条件组合：多设备、多字段"与/或"判断；
- 规则链编排：触发后经过过滤、丰富、转换、多路动作的流水线处理。

### 场景 4（进阶）：AI 与外部事件驱动
- AI 推理结果作为触发源（图像识别异常 → 告警+联动）；
- 外部 API / Webhook 事件、智能体（MCP）调用作为事件源。

---

## 三、各场景的解决方案

### 3.1 告警：从触发到闭环
- **规则配置**（基于物模型/业务对象）：条件（阈值/范围/状态/持续时间）、级别（info/warning/critical）、动作（通知/联动/写库/转工单）、触发策略；
- **生命周期**：发生 → 通知 → 确认 → 处理 → 恢复 → 关闭，活动告警与历史告警分离；
- **治理三闸门**（告警风暴解法）：
  - 重复轰炸 → **去重合并**（同对象+同规则+同级别，时间窗口内合并为一条，展示聚合信息与次数）；
  - 边界抖动 → **滞回抑制**（触发阈值与恢复阈值分离，如 80℃ 触发、75℃ 恢复）+ 防抖（持续 N 秒）；
  - 共因群发 → **共因收敛**（按根因聚合，通知一条）+ 高优先级抑制低优先级；
  - 辅助：时间屏蔽（维护窗口）、静默、通知分组、升级策略、缓存去重（Redis 去重集合 + 事件收敛表持久化）。

### 3.2 远程控制：指令下发的三种模式
| 模式 | 机制 | 适用 |
| --- | --- | --- |
| 同步立即下发（RPC） | 实时下发 → 设备在线响应 → 返回结果 | 实时控制 |
| 异步命令缓存下发 | 云端缓存，设备上线按序串行补发（上限约 50 条） | 离线配置、休眠设备 |
| 影子模式（Device Shadow） | 云端维护 desired/reported/version，delta 收敛对账 | 状态对账、离线交互 |

- 命令状态机：待发送 → 已发送 → 已确认 → 完成；失败分支：超时 → 重试 → 失败/取消；
- 重试：消息队列 TTL + 死信队列实现延迟重试；
- 幂等：命令 ID/版本号，设备端去重。

### 3.3 自动化 / 场景联动
| 触发方式 | 说明 |
| --- | --- |
| 设备触发 | 设备上报数据/事件满足过滤条件 |
| 定时触发 | cron 表达式时间调度 |
| 手动触发 | 用户点击执行一组动作（场景模式） |
| API/外部触发 | 自定义 API 事件、Webhook |

- 场景（手动触发一组任务）vs 自动化（条件自动触发）；
- 云边协同：规则云端执行（复杂规则）或下推边缘（断网自治、低时延）。

## 四、触发器如何设计（ECA 模型）

### 4.1 模型总纲：事件 → 条件 → 动作

```
事件（Event/Trigger）  什么情况会"启动"这条规则
    ↓（触发后进入判断）
条件（Condition）       要不要真的执行？（过滤/限定）
    ↓（条件满足）
动作（Action）          执行什么？（一个或多个）
```

**与魔兽争霸3 触发器同构**：魔兽争霸3 地图编辑器触发器 = 事件（Events，何时启动）→ 条件（Conditions，是否满足才运行）→ 动作（Actions，执行什么），两者结构完全一致——用游戏触发器原理设计自动化引擎可直接迁移。区别在 IoT/业务场景额外要求：事件源类型更丰富、执行可靠性更高（离线、消息不丢、并发防抖）。

### 4.2 触发器五要素设计

| 要素 | 设计要点 |
| --- | --- |
| **1. 事件源类型** | 数据上报、业务事件、生命周期（上线/下线）、定时（cron）、API/外部事件、AI 推理结果、智能体调用 |
| **2. 触发策略** | pulse（满足即触发）/ reverse（上次不满足、本次满足才触发，边沿触发）；部分事件首次发生不触发 |
| **3. 事件间关系** | 多个触发器之间为 **OR**（任一事件满足即启动）；事件与执行条件之间为 **AND** |
| **4. 条件设计** | 条件之间为 **AND**；支持阈值/范围/状态、时间窗口、延时、防抖、表达式脚本、跨对象组合 |
| **5. 触发质量治理** | 去重、防抖、滞回、共因收敛、静默、时间屏蔽——"该触发才触发、不该触发不刷屏" |

### 4.3 触发策略细节（pulse / reverse）
| 策略 | 判定 | 适用 |
| --- | --- | --- |
| pulse（电平触发） | 本次数据满足即触发，不判断上一次 | 状态类（"门开了"） |
| reverse（边沿触发） | 上一次不满足 + 本次满足才触发 | 阈值穿越（避免每次上报都触发） |

### 4.4 触发质量治理（核心差异化能力）
- **防抖（Debounce）**：条件持续满足 N 秒才触发，过滤瞬时毛刺；
- **滞回（Hysteresis）**：触发阈值与恢复阈值分离，消除边界震荡；
- **去重窗口**：同对象+同规则在时间窗口内只触发一次/合并；
- **边沿触发**：只在状态翻转时触发。

### 4.5 事件驱动架构支撑
规则引擎订阅消息队列/事件总线（Kafka、Redis Stream、MQTT broker），事件到达才驱动规则运行；消息处理完成才 ACK（至少一次投递 + 幂等），保证不丢事件。

## 五、如何编排任务（规则链模型）

### 5.1 规则链：节点 + 关系的有向图
```
一个规则链 = 有向图（DAG）
  ├── 规则节点（Rule Node）：对消息执行的一个函数/处理单元
  └── 关系（Relation）：节点输出按关系类型路由到下游
       （Success / Failure / True / False / 自定义关系名）
```
- 消息（Message）= 一切入站事件（数据、生命周期、RPC、API 事件）；
- 执行模型为 DAG 有向无环图（非 Rete 推理网络）；
- 路由即分支：True/False 关系实现条件分流，Failure 关系实现失败兜底。

### 5.2 节点类型（编排积木）
| 类型 | 作用 | 例子 |
| --- | --- | --- |
| Filter（过滤） | 过滤/路由消息 | "温度 > 80℃" → True 进告警，False 进落库 |
| Enrichment（丰富） | 补充元数据 | 附加对象信息、租户信息 |
| Transformation（转换） | 修改消息字段 | 改类型/Payload/Metadata |
| Action（动作） | 执行操作 | 创建/清除告警、下发指令、保存数据、发通知 |
| External（外部） | 与外部系统交互 | 调 REST API、发邮件、写 Kafka、MQTT 转发 |

### 5.3 编排能力清单
串行、条件分支（True/False）、并行（一进多出）、循环/批处理、子流程（子规则链复用）、延时/定时、失败重试/死信、数据落库。

### 5.4 执行引擎设计（可靠性关键）
- **Actor 模型**：规则链/节点独立 Actor，消息不可变对象流动，天然并发与隔离；
- **消息队列 + 确认**：处理完成才 ACK，避免丢失；
- **集群分区**：多实例按消息分区处理，提交策略/处理策略控制顺序与确认；
- **任务级可靠性**：幂等（事件/命令 ID 去重）、超时中断、失败重试（TTL+死信）、失败回滚、分支跳转；
- **动态编排（新趋势）**：AI Agent 实时生成临时 DAG 任务图，替代静态 JSON 流程。

### 5.5 规则链 vs 触发器（关系）
- 触发器回答"什么事件启动、是否执行"——规则链的入口；
- 规则链回答"启动后怎么处理"——一个触发器可接入一条规则链自由编排；
- 产品呈现：简单场景用"触发器+条件+动作"三栏表单（低门槛），复杂场景用可视化规则链画布（高灵活），底层同一套引擎。

## 六、通用设计方案（最优解）

### 6.1 总体架构
```
数据/事件源（设备、业务系统、定时、API）
      │ 统一事件流（Event Bus）
      ▼
┌──────────────────────────────────────────┐
│ 规则引擎                                  │
│  触发器层（事件源/触发策略/防抖去重）      │
│  → 条件评估层（阈值/窗口/脚本）           │
│  → 规则链编排（节点 DAG 执行）            │
└──────────────────────────────────────────┘
      │ 动作执行（异步、可重试、幂等）
      ▼
  告警中心 / 指令下发（含影子）/ 通知 / 数据落库 / 外部API
```

### 6.2 触发器设计规范（清单）
1. 统一事件模型：所有触发源归一为统一事件，进统一消息总线；
2. ECA 三段式：触发器（OR）→ 条件（AND）→ 动作；触发策略提供 pulse/reverse；
3. 触发质量治理内建：防抖、滞回、去重、边沿触发，作为规则配置项而非业务代码；
4. 事件溯源：每次触发记录事件 ID、触发规则、条件快照、执行结果；
5. 冷热分离：高频事件走流式规则引擎（毫秒级），低频复杂规则走异步处理。

### 6.3 任务编排设计规范
1. 规则链 DAG：五类节点 + Success/Failure/True/False 关系路由；
2. 编排能力：串行、并行、分支、循环、子流程、延时、失败兜底，全部可视化配置；
3. 执行可靠性：Actor 隔离；处理完成才 ACK；幂等 ID；TTL+死信重试；超时中断；失败回滚；
4. 可观测：消息流转轨迹（进入时间、经过节点、结果）可查；
5. 分租户/分级限流：防一条异常规则打爆引擎。

### 6.4 数据模型（核心表结构）
```
automation_rule（自动化规则：触发器+条件+动作配置）
rule_chain（规则链）── rule_node（规则节点）── rule_relation（节点关系）
alarm_rule（告警规则）── alarm_record（告警记录）
command_record（指令记录：下发状态机）
```
| 表 | 关键字段 | 设计要点 |
| --- | --- | --- |
| `automation_rule` | trigger_json（事件源+策略）、condition_json、action_json、enabled、cron | 规则配置 JSON 化，执行器解析 |
| `rule_chain` / `rule_node` / `rule_relation` | 链配置、节点类型与配置、关系类型 | DAG 图持久化，前端画布渲染 |
| `alarm_rule` | 条件、级别、触发策略、动作、去重窗口/滞回参数 | 治理参数作为规则配置 |
| `alarm_record` | 状态（active/acked/recovered/closed）、start/end_time、count、handler | 生命周期 + 合并次数 |
| `command_record` | 状态机、request_id、expire_time、retry_count | 命令状态机 + 幂等 |

### 6.5 告警治理落地
1. 规则级：防抖（持续时间）、滞回（双阈值）、触发策略（pulse/reverse）；
2. 系统级：去重合并（窗口内同类合并+计数）、共因收敛、分级抑制、静默/时间屏蔽、通知分组；
3. 闭环：全生命周期 + 升级策略 + 审计留痕。

## 七、设计说明

### 7.1 核心设计原则
| 原则 | 说明 |
| --- | --- |
| 规则与业务解耦 | 新增规则不改代码 |
| 可靠不丢事件 | 事件进队列，处理完成才确认（至少一次投递 + 幂等） |
| 触发质量优先 | 宁可少触发、不误触发：防抖/滞回/去重内建为规则配置 |
| 可视化优先 | 触发器三栏表单 + 规则链画布，业务人员自助配置 |
| 可观测可审计 | 触发轨迹、执行链路、告警闭环全程留痕 |
| 云边协同 | 关键规则下推边缘，断网自治 |

### 7.2 常见设计坑与规避
| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 阈值震荡不处理 | 告警风暴 | 滞回双阈值 + 防抖 + 去重窗口 |
| 批量对象同时故障 | 共因群发刷屏 | 共因收敛 + 分级抑制 + 通知分组 |
| 事件丢失（消费即删） | 漏告警、漏联动 | 队列 + 处理完成才 ACK |
| 重试导致重复执行 | 重复开关、重复通知 | 幂等 ID + 消费端去重 |
| 离线对象指令丢失 | 控制不生效且无感知 | 命令缓存 + 影子模式 + 状态反馈 |
| 单条规则打爆引擎 | 全平台联动瘫痪 | Actor 隔离 + 租户级限流 + 规则复杂度上限 |
| 触发与条件关系混乱 | 规则行为不可预期 | 固化语义：触发器 OR、条件 AND |
| 条件只判断本次数据 | 每次上报都触发 | reverse 边沿触发 |

### 7.3 演进路线
```
阶段1 单点规则：简单触发器（事件 → 条件 → 动作）
   ↓ 联动复杂
阶段2 场景联动 + 规则链：可视化编排、跨对象联动、定时任务、告警治理
   ↓ 量大、高可靠
阶段3 流式规则引擎：Actor 模型 + 消息分区集群 + 云边协同
   ↓ 接入 AI
阶段4 策略引擎 + AI 编排：AI 推理结果作事件源；AI Agent 动态生成 DAG 任务图
```

### 7.4 业界参考实现
- **ThingsBoard**：开源物联网平台，规则链 + Actor 模型执行引擎，业界标杆；
- **华为云 IoTDA / 阿里云 IoT**：设备联动规则、场景编排、影子、命令下发；
- **AWS IoT Core**：Device Shadow（desired/reported/delta）、Rules Engine；
- **RuleGo / Node-RED / Windmill**：轻量规则引擎与自动化编排；
- **Prometheus Alertmanager**：告警分组、抑制、静默——告警治理通用参考；
- **魔兽争霸3 地图编辑器**：触发器 = 事件/条件/动作，可视化规则编辑的经典范本。
