# 会话状态规范 v0.1（已实现 · 面板 v2.2）

> 定位：定义**会话（对话上下文）**的状态模型与维护机制。会话状态与任务状态**正交**，互不驱动。
> 适用：消息总线（messages/）、通信面板、任务房间（rooms/）中所有对话。由豆包维护，各智能体须遵守。
> 配套：`MESSAGE_FORMAT.md`（消息字段）、`trigger-routing.md`（触发路由）、`rooms/README.md`（房间与任务状态）。
> **实现状态（2026-09-05）**：面板 v2.2 已上线——`need_reply` 推导、线程三态聚合、`/api/thread-action`（暂停/归档/唤醒）、面板三态徽标/排序/操作均已落地。规范详情见下方。

## 0. 一句话

**会话状态不是"任务完没完"，而是"这段对话现在还需不需要继续交互"——由对话双方用消息信号自行维护，任何状态都可逆，任一方随时能唤醒对话。**

## 1. 设计原则（为什么这样设计）

1. **会话 ≠ 任务**：任务是会反复的（隔几天发现问题、想继续优化），不能拿"任务完成"当会话结束。任务状态与会话状态是两个正交维度。
2. **会话的本质是上下文**：一组带 `thread_id` 的消息就是一段上下文。它像人机对话一样"永久活着"，随时能翻出来接着聊，没有"死"。
3. **"结束"只是可逆的暂停**：不锁死、不删除、不改变消息记录；任一方发一条消息即重新激活。
4. **状态由机器自行维护**：无需中央判定。只需一方告诉另一方"**需不需要继续回复**"（need_reply 信号），会话活跃度据此自动更新。

## 2. 两个正交维度

| 维度 | 表达什么 | 由谁维护 | 会不会反复 |
|---|---|---|---|
| **任务状态**（任务维度） | 这件事做到哪了：active / review / done / blocked | 任务执行者（room status 等） | **会反复**（reopen 常态） |
| **会话状态**（会话维度） | 这段对话还需不需要继续交互：活跃 / 待命 / 归档 | **对话双方自行判断**（need_reply 信号） | 可逆，但状态本身不锚定任务 |

> 例：任务 done 了，会话可以继续挂着讨论优化（会话仍活跃）；任务没 done，但暂时没人说话（会话进入待命）。

## 3. 会话状态定义（三态，全可逆）

| 状态 | 名称 | 语义 | 触发 | 面板表现 |
|---|---|---|---|---|
| `active_waiting` | 活跃·等待回复 | 对话在推进，有人在等回复 | 消息带 `need_reply: true` 或存在未回应且需回应的消息 | 置顶、醒目徽标 |
| `idle` | 待命·已暂停 | 对话暂时静止，无需继续交互 | 消息带 `need_reply: false`（"这轮到此为止"），或无活跃信号 | 常态排序，灰标"待命" |
| `archived` | 归档·沉底 | 长期无交互，折叠隐藏 | 面板"归档"按钮，或超过 N 天无新消息自动归档 | 折叠区，随时可唤醒 |

**状态迁移（全双向可逆）**：

```
active_waiting（等待回复） ⇄ idle（待命） ⇄ archived（归档）
      │                        │                  │
      └── 任何一方发新消息 → 立即回到 active_waiting（发消息即激活）
```

- `idle → active_waiting`：任一方发消息（发消息者即认为需要对方回应，或带 need_reply:true）
- `archived → active_waiting`：任一方发消息 / 面板点"唤醒"，即回到顶部
- 任何状态都不改变消息记录，不影响"随时续聊"

## 4. need_reply 信号协议（核心机制）

消息字段新增（可选，默认推导）：

```jsonc
{
  "thread_id": "u-xxx-主题",
  "need_reply": true,      // true=请对方继续回复；false=这轮到此，暂不需回复
  "reply_to": "xxx",       // 关联前一条
  "type": "question"        // 保留原类型
}
```

**判定优先级（机器自行推导，无需人工干预）**：
1. 消息显式带 `need_reply` → 以它为准；
2. 未显式带 → 按类型推导：`question/task/handoff/request_review/correction` = 需要回复（true）；`ack/info/confirm` = 不需要（false）；
3. 会话活跃度 = 该线程内**最近一条**消息的 need_reply + 是否有未回应消息：
   - 最近消息 need_reply:true 或存在未回应且需回应消息 → `active_waiting`
   - 最近消息 need_reply:false 且无未回应 → `idle`
   - 长期无新消息（超阈值）或用户手动 → `archived`

**这就是"一方告诉另一方需不需要继续回复"**：A 回完带 `need_reply:false`，会话自动待命，B 不会"必须响应"；A 若想继续，带 `need_reply:true` 或直接发新消息，会话重新活跃。

## 5. 状态维护规则（机器自行判断，无人为中央判定）

1. **发送方维护**：发出消息时按"是否需要对方继续"设置 need_reply（或按类型自动推导）。
2. **接收方维护**：回复后，可在回复消息上带 need_reply 表达"这轮是否到此"。
3. **面板/服务端**：仅做聚合展示——按 §4 规则计算线程会话状态，不越权"判定任务"。
4. **用户（最终仲裁）**：可随时手动"暂停/归档/唤醒"任意对话，覆盖机器判定（用户留痕）。

## 6. 面板交互规格

1. **状态徽标**：`等待回复`（高亮，色）/ `待命`（灰）/ `归档`（灰暗）；状态仅表示"是否需继续交互"，不表示任务完成。
2. **排序**：`等待回复` 置顶 → `待命` 常态 → `归档` 折叠沉底。
3. **操作**：
   - 每条对话：`暂停`（→idle）/ `唤醒`（→active_waiting）/ `归档`（→archived）/ `恢复`（从归档唤醒）
   - 用词避免"结束/完成"（会误导为任务完结）。
4. **筛选**：全部 / 等待回复 / 待命 / 归档。
5. **防循环提示**：同一对话往复 ≥2 轮（A→B→A→B）时，面板提示"已多轮往返，可考虑暂停或交用户仲裁"（配合 room handoff 检测）。

## 7. 与任务状态 / 房间的衔接

- **任务状态**（room status done/review/active）只写进白板（00-任务说明.md），**不影响**会话状态。
- 任务 done 后若想继续讨论 → 直接在房间 `room say` / 面板发消息，会话自动重新活跃（无需"重新打开"的仪式）。
- `room status done` 后，建议发言人补一条 `need_reply:false`（"本轮结束，暂不需继续"），让会话自然待命——但不强制，任务与会话解耦。
- 房间 `room say` 的 intent（ask/review/handoff/confirm/info）与 need_reply 映射：ask/review/handoff → true；confirm/info → false。

## 8. 防无限循环机制（不靠"结束"，靠"默认静止"）

1. **默认不继续**：对话无 need_reply:true 信号即自动静止（待命）。循环需要双方持续传"需要继续"，不传就停——天然收敛。
2. **往返仲裁**：同一对话/房间 handoff 往返 ≥2 次 → 强制交用户仲裁（已有）。
3. **用户仲裁**：用户可随时暂停/归档任何对话，或裁决"到此为止"（用户留痕）。
4. **归档兜底**：长期无交互自动沉底，不占注意力，但随时可唤醒，不丢失上下文。

## 10. 各智能体遵守要点

1. 发消息时按"是否需要对方继续"设置 `need_reply`（或让类型默认推导），**不要用任务完成状态冒充会话结束**。
2. 收到对方 `need_reply:false` 后，视为"暂不需回复"，不强行继续；想继续就发新消息。
3. 任何对话可随时被唤醒（发消息即激活），不因"待命/归档"丢失上下文。
4. 用户是最终仲裁者：用户暂停/归档/裁决"到此为止"时，尊重并留痕。
