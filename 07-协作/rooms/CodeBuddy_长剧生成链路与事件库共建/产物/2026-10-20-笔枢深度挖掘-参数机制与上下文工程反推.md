## 一、先说方法论：为什么"参数怎么发挥作用"只能部分回答

**关键限制（必须诚实标注）**：`pov_firewall` / `hidden_info` / `public_info` / `revealed_chapter` / `trigger_words` / `current_intensity` 这 6 个字段在 **152 个前端文件里全部 0 命中**`[源码]`。

这说明它们是**纯后端字段**——前端只透传 `character_state` 槽位的 JSON 原文展示，不解析内部结构。所以：

- ✅ 能确证的：**这些参数存在、结构如档案 §5.8 所载**（CodeBuddy 实测抓到的响应体）
- ❌ 不能确证的：**后端拿它们做了什么**（是否真注入 prompt、如何裁剪、权重多少）

但**上下文装配的骨架能反推**，因为有三个前端可见的硬证据：`COMPONENT_KEYS`（五组件计量）、`MODE_STAGES`（阶段裁剪）、`APPLY_ORDER`（16 种资源类型）。下面 §二 就是基于这三条 + 报价实测数字反推的。

## 二、反推：笔枢的上下文工程结构（五层）

### 2.1 第一层 · 资源寻址层（地基，最值得抄）

`assistant-cite-core.js` 全文 473 行，核心是一套**三段式资源坐标**`[源码]`：

```
(resource_type, resource_key, field_path)
```

- `CITEABLE_TYPES = {world, character, book, outline, chapter, custom_setting_definition}` — 6 类可引用资源
- `resource_key` 按类型严格校验：
  - `world` → 必须是 6 维之一（`WORLD_DIMENSIONS` 白名单）
  - `book` → 只允许 `"story_plan"` 一个字面量
  - `outline` → 必须匹配 `/^(volume|near_term):([1-9][0-9]*)$/`（**卷纲与近纲成对寻址**）
  - `chapter` → 必须匹配 `^([0-9]+):guide$`，且规范化为 4 位补零（`0001:guide`）
  - `custom_setting_definition` → 必须是 UUID
- `field_path` 校验极严：`validFieldPath()` 要求每段匹配 `/^[A-Za-z0-9_]+$/`、禁 `..`、禁纯数字段、禁 `__proto__`/`prototype`/`constructor`/`*`（`BLOCKED_SEGMENTS`）、总长 ≤256
- 自定义设定走**只读 JSON Pointer**（`/content/xxx`），注释明写「never the built-in field write path」——**用户自定义结构与内置结构用两套寻址，不混**
- `immutable = {character:"name", outline:"volume_number", chapter:"chapter_number"}` — **主键字段禁止被引用改写**

**这套寻址支撑了四件事**（这是它真正的价值，不只是"能引用"）：

| 用途 | 实现 | 源码位置 |
|---|---|---|
| **精确引用** | `citeField()` 定位到字段级，Agent 改哪一格清清楚楚 | cite-core:390 |
| **字段所有权** | `fieldOwner = "field:{bookId}:{type}:{key}:{path}"` 拼成唯一 owner 串 | cite-core:189 |
| **编辑守卫/写锁** | `createEditGuard()` 用 Map 按 `(book,type,key)` 计数加锁，`generation` 递增失效 | cite-core:314-361 |
| **精确刷新** | `editIdentities()` 把 read plan 展开成 identity 列表，只失效被改的资源 | refresh-core |

> 💡 **对我们的意义**：我们的数据是"表 + 行"，**没有统一寻址层**。要做上下文工程（按字段注入、按字段校验、按字段留痕），这层是前置。第 3 块方案里的 `ConstraintPack` 其实就是一个专用寻址层——可以泛化。

### 2.2 第二层 · 上下文装配层（五组件，有账单）

`book-data-volume-core.js` 里的 `COMPONENT_KEYS` 逐字`[源码]`：

```js
COMPONENT_KEYS = {
  world:                "bdv_comp_world",
  characters:           "bdv_comp_characters",
  custom_settings:      "bdv_comp_custom_settings",
  story_plan_and_style: "bdv_comp_story",   // 注意：故事蓝图与文风档案合并成一个组件
  story_plan:           "bdv_comp_story",   // 两个别名映射同一组件
  style:                "bdv_comp_story",
  outline:              "bdv_comp_outline",
  outlines:             "bdv_comp_outline",
}
```

**这就是它上下文的全部构成——五块，不多不少**。配 CodeBuddy 实测的报价数字`[实测]`：

| 组件 | tokens | 占比 | 推断内容 |
|---|---|---|---|
| `characters` | 6712 | **47%** | 角色卡（22字段 × 出场角色数）——**最大头** |
| `world` | 4582 | 32% | 世界观 6 维 22 字段 |
| `story_plan_and_style` | 3006 | 21% | 故事蓝图 4 模块 + 文风档案 |
| `outlines` | **0** | 0% | ← **细纲阶段不注入卷纲** |
| `custom_settings` | 0 | 0% | 该账号未建自定义设定 |
| 合计 billable | **14300** | | raw 16824 → 减免 2524（约 15%） |

**三个反推结论**：

1. **角色是上下文的最大开销（47%）**——所以它把角色卡做成四阶段渐进生成（§4.2），且 `chapter_character_state` 单章要跑 **5m45s**（全流程最慢的一步）。角色深度是用时间和 token 换的。
2. **组件按任务类型变化**：`outlines: 0` 说明生成细纲时**不注入卷纲**。这不是 bug——细纲的上游是 `world_state`（世界状态机）而非卷纲。→ **上下文不是一锅端，是按任务裁剪的**。
3. **减免 15% 说明有去重/共享**：`billable < raw`（14300 < 16824），`meter_version: "book-data-v1"` 是计量版本号——**它的上下文计量本身是可演进的独立子系统**。

### 2.3 第三层 · 预算分档层（膨胀显式化）

`TIER_BOUNDS` 逐字`[源码]`：

```js
TIER_ORDER  = ["standard","extended","large","extra_large","unsupported"]
TIER_BOUNDS = [
  {key:"standard",    upper:32000,  multiplier:1},
  {key:"extended",    upper:64000,  multiplier:2},
  {key:"large",       upper:128000, multiplier:4},
  {key:"extra_large", upper:256000, multiplier:8},
  {key:"unsupported", upper:null,   multiplier:null},
]
MODES = {off:true, shadow:true, enforce:true}   // ← 三态开关
UNIT_TOKENS = 1000
```

- `inferTierKey()`：按 billable_tokens 落档；`unsupported` = 超 256k 直接不支持
- UI 文案 `bdv_next_tier: "下一档 · {tier}"`、`bdv_range_value: "{amount}k 标准 Token，区间 {lower}k–{upper}k"` — **提前告诉用户"再加设定就要翻倍价钱"**
- **`MODES.shadow` 是关键设计**：影子模式=算账但不拦截。→ 计费/限额类硬约束上线前先 shadow 跑一段，观察误伤，再切 enforce。**这是我们做校验器该抄的上线姿势**（V13 信息集校验若直接 enforce，误拦会堵死生产）
- `STALE_CODES` 收录 8 种报价失效码（`quote_stale`/`quote_expired`/`quote_mismatch` × 带不带 `book_data_` 前缀）——**报价与参数强绑定**，设定一改报价就失效

### 2.4 第四层 · 阶段化生成层（不是一次 prompt 全出）

两条流水线的阶段表 `[源码]`（`prose-stage-core.js` 整读，89 行）：

**建书期分工**（`dimensionMeta` 逐字）：

| 世界维度 | 负责的 Agent 工种 |
|---|---|
| `core_laws` 核心法则 | 世界观架构师 Worldbuilder |
| `space_time` 时空地理 | 地理志官 Cartographer |
| `society` 社会权力 | 设定考据员 Lore Keeper |
| `history_culture` 历史文化 | 设定考据员 Lore Keeper |
| `existence` 存在基础 | 世界观架构师 Worldbuilder |
| `information` 信息传播 | **信息志官 Signal Keeper** |

→ **6 维世界观 = 4 个工种分工生成**，不是一个 prompt 吐 22 字段。`WORLD_DIM_VERB` 还给了每维专属动词（core_laws「正在立法」、space_time「正在勘舆」、history_culture「正在修史」）——**连进度文案都按工种定制**。

**章节期裁剪**（`MODE_STAGES` 逐字，这是最硬的证据）：

```js
MODE_STAGES = {
  full:              PROSE_STAGE_SEQ 全部 11 阶段,
  world_state:       ['prepare_context','world_state','world_ready'],
  outline_director:  ['prepare_context','intent_dispatch','chapter_guide','guide_ready'],
  character_state:   ['prepare_context','character_state'],
  writer_group:      ['prepare_context','intent_dispatch','storyboard','skeleton','compose','body_ready'],
}
```

**读出三件事**：

1. **`prepare_context`（翻阅前情与设定卷宗）是唯一出现在所有模式里的阶段** → 它就是上下文装配的执行点，p=0.05（最先跑）
2. **`writer_group` 不含 world_state / chapter_guide / character_state** → 写手不重算这些，**直接消费前置任务的产物**（落在 chapter state 的 9 个槽位）。这解释了为什么四层门禁（`production-readiness`）必须先行
3. `catalog()` 里：`skeleton` 阶段**只在 `writer_type==='muti'` 时保留**；单写手时 `compose` 的 p 从 0.90 改 0.85、文案改「单写手落笔成文」→ **写手群多一个"骨架写手"环节**（6+2 Agent 的分工证据）

`chapterStageKinds()` 更 revealing——**任务完成后刷新哪些资源**`[源码]`：

| 任务/阶段 | 刷新的资源 |
|---|---|
| `chapter_world_state` / `world_ready` | `["chapter_world"]` |
| `chapter_outline_director` / `guide_ready` | `["chapter_guide"]` |
| `chapter_character_state` | **`[]`（空！）** |
| `body_ready` / writer 任务 / polish | `["chapter_body"]` |
| **`post_hoc`** | **`["chapter_guide","hooks","debts"]`** |

→ **`post_hoc`（后验）会回写细纲、伏笔台账、债务台账**！这解释了它为什么只要 **12 秒 / 1 笔力**`[实测]`——后验不是重写正文，是**结算**：把本章新产生的伏笔/债务登记进总账、更新细纲状态。这正是我们 V2.0 里 director「回写状态层」那一步的成熟实现。

→ `chapter_character_state` 刷新为空，说明角色状态产物**不走门户资源刷新**，直接落 chapter state 槽位（9 槽之一）。

### 2.5 第五层 · 块级编辑回填层

`blockFromField()` 的注释逐字`[源码]`：

> `// Tag every block with its source content field key so editors can splice the raw value back into the full dimension JSON on save.`

机制：把嵌套 JSON **拆成 UI 块**（`type: list/cards/rel`）展示，每块带 `key`（源字段名），编辑后**按 key 拼回完整 JSON**。`mapWorldDimension()` 里 `skip` 集合排除 `id/book_id/resource_type/resource_key/revision_id/base_version/version/status/created_at/updated_at/essence` 共 11 个元字段——**元数据与内容分离**。

→ 价值：**结构化设定既可被人编辑、又不丢失未展示字段**。我们的目标线录入端（阶段 2a 两步向导）是同一思路，但它做得更彻底（块级 + 原样回填）。

## 三、参数怎么发挥作用（三类逐个拆）

### 3.1 角色卡：22 字段 → 四阶段生成 → 三处消费

**生成阶段**（`CAST_STAGE_IDS` 逐字，**档案未记载**）`[源码]`：

```js
CAST_STAGE_IDS = ["skeleton", "beliefs", "voice", "deep_profile"]
```

| 阶段 | 产物 | 对应档案字段 |
|---|---|---|
| `skeleton` 骨架 | 扁平字段 | name/true_name/role/gender/age/aliases |
| `beliefs` 信念 | 嵌套对象 | beliefs/belief_source/author_perspective/surface_goal/deep_desire |
| `voice` 声线 | 嵌套对象 | **voice 五子字段**（见 §4.1） |
| `deep_profile` 深度画像 | 嵌套对象 | deep_fear/secrets/bottom_line/traumas/contradictions/arc_description/world_position |

`api-bridge` 注释逐字印证：「Engine character schema (**wf-nvl-character**): skeleton fields are **flat**; beliefs/deep dimensions arrive as **nested objects**」→ **引擎侧有 `wf-nvl-character` 这个 workflow 定义**，骨架扁平、深度嵌套是刻意设计（骨架字段可索引，深度字段整块注入）。

**消费点（三处，可确证）**：

1. **上下文组件**：`characters` 占 47% token（§2.2）——整卡注入
2. **UI 展示**：`CastProfile` 注释「renders pos/anchor/rels/depth **unconditionally** — always emit the full 三段式 shape, **blank where the engine has no data yet**」→ **空字段也渲染**，让创作者看见"这里还缺"（跟我们的"有意留空 vs 漏填必须可区分"是同一诉求，它用 UI 解决）
3. **章节角色状态**：`chapter_character_state` 任务产出 `character_state`（scars/drives/identity/snapshot/pov_firewall/relationships），**是角色卡在"本章"的投影**——静态卡 + 动态状态两层

**`essence`（精要）机制**（**档案未记载**）`[源码]`：每个世界维度和角色都有 `essence` 字段，`mapWorldDimension()` 里：

```js
var essence = contentObject(value).essence;
var lead = (essence != null) ? localizedSummary(essence) : fields[0].v;
```

→ **`essence` 是该资源的"一句话精要"，优先于第一个字段作为 lead 展示**。且 `essence` 被排除在 `fields` 之外单独处理（在 `skip` 集合里）。这就是**分层压缩**：全量字段用于编辑，essence 用于摘要/列表/（推断）上下文裁剪。

### 3.2 世界观：6 维 22 字段 → 分工生成 → 三处消费

- **`force_relations`（势力关系）**：`screens-world` 里 `blocks.find(block => block.key === 'force_relations')` 精确取块 → **关系图谱的数据源**（档案 §12.9 已指出：图谱用的是这个静态表，**不是** §5.8 的四维运行时数值——两套数据没打通，是它的缝）
- **`key_locations[].controlling_force`**：地点带控制势力 → 推断用于"角色去某地会遇上谁"（`[推断]`，前端无消费逻辑）
- **`core_laws.essence` 被拿去当书名**：`create.worldName = leadZh.split(/[。——；，,\n]/)[0].slice(0,20)` → **核心法则的第一句前 20 字直接当世界名**。这是个很聪明的做法：法则即世界观身份证
- **`WORLD_STAGE_IDS = WORLD_DIMENSIONS.slice()`** → 6 维**各自是一个生成阶段**，可单独刷新（`resource_key: dimension`）

### 3.3 世界事件：镜头内外二分 + 暗线四态

`api-bridge` 的 `wsmSkeleton()` 逐字给出结构`[源码]`：

```js
{ world_time, time_advanced, forces:[], undercurrents:[], on_camera:[], off_camera:[], power_shift }
```

**参数作用**：

| 参数 | 取值域 | 作用（UI 文案坐实） |
|---|---|---|
| `forces[].distance` | `dist_near`近 / `dist_mid`中 / `dist_far`远 | **势力可及性**——远的势力本章不该出场（推断为门禁依据） |
| `forces[].status` | 自由文本 | 势力当前态势 |
| `undercurrents[].status` | `ust_dormant`休眠 / `ust_active`进行中 / `ust_accel`加速 / `ust_closing`收束 | **暗线生命周期四态** |
| `undercurrents[].last_active_chapter` | 章号 | 上次活跃章 → 太久没动=该推进或该收 |
| `on_camera_events[]` | 文本数组 | 镜头内=本章写到的 |
| `off_camera_events[]` | 文本数组 | **镜头外=本章没写但世界照样发生的** |
| `power_shift` | 文本 | 格局变动（`c-badge terra` 专属徽章渲染） |
| `time_advanced_days` | 数字 | UI 渲染为 `"+N 天"` |

`undercurrent_progress` 与 `state.undercurrents` 是**两份数据按 name 合并**（`progressByName[String(flow.name)]`）→ 暗线的"静态定义"与"本章进展"分开存，展示时 join。**这跟我们的 `GoalLine`（定义）+ `GoalStage.status`（进展）分层完全同构**。

**最有价值的一句 UI 文案**（`tg_warn_d` 逐字）`[源码]`：

> 「世界状态按章推进——**提前生成的后续卷可能与实际走向偏离。建议随写随生。**」

→ **它自己都不建议预生成卷纲**。这是我们"章纲按集生成、不一次排完全季"的强力外部佐证——不是我们保守，是这条路走过的人回头立的牌子。

## 四、六项新发现（档案未记载，全部源码坐实）

### 4.1 `voice` 声线 = 5 个子字段（**这是最该抄的一块**）

档案 §5.2 只列了 `voice`（声线）一个字段名。`api-bridge` 的 `fieldLabel` 表逐字揭示其内部`[源码]`：

| 子字段 | 中文 | 作用推断 |
|---|---|---|
| `voice_positioning` | 声线定位 | 这个人说话的总体调性 |
| `syntax_fingerprint` | **句法指纹** | 句式习惯（长短句、是否省略主语、标点癖好） |
| `emotion_patterns` | 情绪模式 | 情绪如何外显 |
| `forbidden_speech` | **言语禁区** | 他绝不会说的话 |
| `cognitive_bias` | 认知偏向 | 他看事情的固有偏差 |

实测佐证（档案 §5.8）：墨离的 `identity.speech_style` = 「语调漫不经心，常用**祈使句和省略主语的判断句**」——这就是 `syntax_fingerprint` 的落地形态。

> 💡 **为什么这块最该抄**：`forbidden_speech`（言语禁区）是**负向约束**，比正向描述更能锁住人设。我们的角色卡有「说话方式」（`Archetype.speech_style`）但只有正向描述。**"他绝不会说什么"是防 OOC 最有效的一条**，而且可代码校验（正文出现禁区词 → 拦）。

### 4.2 `APPLY_ORDER`：16 种资源类型的全集清单

`portal-resource-refresh-core.js` 逐字`[源码]`：

```js
APPLY_ORDER = ["chapters","chapter_body","chapter_guide","chapter_world",
               "hooks","debts","world","world_dimension","characters","character",
               "story_plan","style_profile","outlines","outline_pair","billing","books"]
```

**这是它整个数据模型的资源清单**（刷新有先后序，故得名）。按性质分四组：

| 组 | 资源 | 对应我们的 |
|---|---|---|
| **章级产物** | chapters / chapter_body / chapter_guide / chapter_world | Episode / script / EpisodeBeat / （缺）世界状态 |
| **跨章台账** | **hooks / debts** | Foreshadowing（4a 已扩列）/ **（缺）债务表** |
| **书级设定** | world / world_dimension / characters / character / story_plan / **style_profile** / outlines / outline_pair | 世界观 / 角色 / （缺）故事蓝图 / **（缺）文风档案** / 卷纲 |
| **运营** | billing / books | — |

→ **两个我们完全没有的资源类型**：`style_profile`（文风档案，与 story_plan 合并计量）和 `debts`（债务台账，独立于 hooks）。

**`hooks` 与 `debts` 分开建表**是有道理的：hook 是"故事层等着翻开的牌"（读者视角），debt 是"角色之间记着的账"（带 `from_char`/`to_char` 方向）。**我们 4a 把两者合并进 `Foreshadowing.kind = hook/debt`**——当时是我裁的（"债与钩的分野"注释在 `engine.py:395`）。看到它分表 + 共用生命周期字段（`status`/`expected_payoff`/`last_advanced`），**我们的合表 + kind 区分是等价且更省的做法，不改**。但 `from_char`/`to_char` 方向字段我们缺（4a 建了 `creditor`/`debtor` 列但未写值，已在待办）——**这轮确认了它该补**。

### 4.3 `MODES.shadow`：影子模式（校验器上线姿势）

见 §2.3。`{off, shadow, enforce}` 三态。

> 💡 直接可用于我们第 3 块的 **V13 信息集校验**：先 shadow（算但不拦，只记录命中率）→ 看误拦率 → 再 enforce。避免"新校验一上线就把生产堵死"。

### 4.4 `post_hoc` 回写细纲 + 双台账（结算而非重写）

见 §2.4 末。`post_hoc` → `["chapter_guide","hooks","debts"]`。

> 💡 我们 V2.0 的 director「回写状态层」该照这个范围定：**回写章纲状态 + 伏笔台账 + 债务台账，不回写正文**。12 秒 / 1 笔力的成本也印证了"结算很便宜，可以每章都做"。

### 4.5 `chapter_character_state` 刷新为空 → 双层角色数据

静态角色卡（书级 `characters`）+ 动态章节状态（章级 `character_state` 槽位）**是两份数据、两条刷新路径**。动态层含 `snapshot`（location/possessions/current_goal/physical_state/social_situation/emotional_baseline/current_constraints）——**7 个"此刻"字段**。

> 💡 我们的 `Character` 表是静态的，`CharacterArcNode` 是弧线关键点，**缺"某集此刻状态"这一层**。这是长篇崩坏的高发区（第 30 集的角色该带第 29 集的伤）。建议在 M8 上下文工程里补 `episode_character_state`。

### 4.6 `blockFromField` 块级回填 + 11 个元字段 skip

见 §2.5。**元数据（id/version/status/时间戳/essence）与内容字段分离**，编辑只碰内容。

## 五、它身上的三条缝（我们可超越处）

1. **关系图谱与运行时数值没打通**（档案 §12.9 已指出，我复核确认）：图谱用静态 `force_relations`，四维数值（trust/conflict/intimacy/dependency）只在 `character_state` 里，**不进图谱、不随章节演进**。→ 我们把关系数值直接驱动图谱，就能做"关系随剧情演进"。
2. **`params_hash` 前端 0 命中**`[源码]`：说明报价绑定校验全在后端，前端只透传。**它的上下文计量对用户是黑箱**（只看到档位和价钱，看不到"哪块设定最贵"）——而 `COMPONENT_KEYS` 明明已经分好组件了，UI 却没做组件级钻取。→ 我们做上下文预算时可以把"哪块占多少"直接可视化。
3. **预生成卷纲它自己都不推荐**（`tg_warn_d`），但产品里还留着这个按钮 + 警告弹窗。→ 说明这条路它试过、退回来了。我们别走。

## 八、一句话总结

**笔枢的上下文工程 = 三段式资源寻址（地基）+ 五组件计量装配（有账单）+ 分档预算（膨胀显式化）+ 阶段化生成（不一次全出）+ 块级编辑回填（人机共改）。**

它最值得我们抄的不是某个字段，是**"上下文是被计量、被寻址、被裁剪的工程对象"**这件事本身——我们的 `ConstraintPack` 已经是这个方向的起点，A2/A3 两条把它补齐。

而它最大的缝（关系图谱不随剧情演进、预生成卷纲自己都不推荐）恰好都在我们 V2.0 已经选对的路上：**推演产状态、状态驱动一切、章纲按集随写随生**。
