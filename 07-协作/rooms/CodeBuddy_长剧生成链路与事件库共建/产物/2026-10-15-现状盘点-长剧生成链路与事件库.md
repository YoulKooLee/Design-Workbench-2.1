# 现状盘点 · 长剧生成链路与事件库

## 零、用户这次的思路（原话摘要）

> AI 能生成剧情，但只能生成短剧，不适合长剧，所以要有上下文工程管理。
> 设想：拟好世界观、剧情框架、人物设定 → 做**世界模拟器**，按时间推演人物剧情（期间可添加事件）→ 模拟完成后回填季规划、集规划 → 每集内容依然装配上下文由 AI 生成。
> 世界模拟参照**鬼谷八荒**：NPC 和主角通过**结构化参数**互动。游戏框架固定、事件随机且参数化、讲究因果链。事件随机且合理，**可以作为素材辅助 AI 写小说**。
> 事件只是素材，而且是**上帝视角**；剧情还是要 AI 按**人物视角**讲故事，要把故事讲得精彩。
>
> 两个问题：① 上游全靠事件库推演剧情，剧情也会崩；② 事件库怎么建——目的是保证剧情随机、合理、因果链完整，用途是塞进上下文去生成剧情。
>
> 调整后的四阶段链路：
> 1. 总体框架（LLM 按三幕七支柱生成）
> 2. LLM 拆分故事线路：多角色多阵营目标线 + 时间线切片，故事分阶段（主角倒排计划）
> 3. 推演**必然事件**（冲突、对抗、人物关系变化）+ **随机事件**（事件库抽取）
> 4. 事件素材 + 边界进上下文，LLM 写剧本
>
> 事件库从**网文/小说套路**里提取（例：海滩看女主穿比基尼、泡温泉；修仙的上古秘境、宗门大比、炼丹大比、师傅夺舍）。格式化包括但不限于：触发条件（适合什么题材/世界观背景/阶段）、参与者、几种剧情走向及结果（最好能按参数出结果）、有没有携带剧情 NPC（如任务事件的任务 NPC）。

### 2.1 关键矛盾：架构铁律 vs 用户的 LLM 四阶段

现有铁律写的是「推演是纯代码、一次模型都不调」（`pools.py:3-5`）。这套铁律**只适用于第③步的推演**，因为它保证了可复现（同一份种子必然跑出同一串事件，出了问题能 replay）。

用户链路里①总体框架、②拆分线路、④写剧本**三步都要 LLM**。所以铁律要改写为**分层**：

| 环节 | 用谁 | 为什么 |
|---|---|---|
| ① 框架 / ② 拆分 | LLM | 创造性，一次性产物，人能在界面上改 |
| ③ 推演（掷骰、抽签、清算） | **纯代码，确定性** | 必须可复现、可回放、可 diff；掺 LLM 就再也调不动 |
| ④ 写剧本 | LLM | 这是 AI 的强项（用户原话：讲得精彩） |

**这条要请千问/用户确认**：哪些环节允许调模型，写进铁律，避免日后有人把 LLM 塞进推演里（那会直接废掉"因果链可核验"这条价值）。

用户要的格式化四要素，对照后端 `EventTemplate` 现有字段：

| 用户要的 | 现有字段 | 缺口 |
|---|---|---|
| 触发条件·阶段 | `goal_alignment.stage_tags`（如 `['调查','正面对抗']`） | ✅ |
| 触发条件·尺度 | `time_scale`（`day` 日常 / `month` 阶段 / `year` 时代 / `epoch` 纪元，`pools.py:54-55`） | ✅ |
| 触发条件·支柱 | `pillar_fit`（适配第几支柱，只抬不禁） | ✅ |
| 触发条件·角色 | `required_tags`（16 个性格标签）+ `min_realm` + `required_equipment` | ✅ |
| 触发条件·**题材/世界观** | **无** | ❌ 池子直接叫 `SHANHAI_EVENT_POOL`（山海题材写死），换题材/世界观就没法复用 |
| 参与者 | `cast`（`a` 主体 / `b` 对手 / 路人） | ⚠ 只有主/对手二分，没有"多阵营"（用户第②步要的多阵营在这里就断了） |
| **剧情走向与结果（按参数出结果）** | `slots` / `slot_fallback`（**文本填槽**） | ❌ 现有是"往模板句子里填词"，**不是分支走向**。想要"三种走向按参数出"，要加 outcome/branch 层 |
| 后果 | `consequences`（list）、`negative` | ✅ |
| 埋伏笔 | `plants_foreshadowing`（模板上的文本） | ✅（注：在模板不在事件行） |
| **携带剧情 NPC** | **无** | ❌ 后端没有。**但原型层有**——`2026-09-26 四阶段推演链路.md:57` 写着「`neededNpcs` = 参与者里查无角色卡的那部分，剧情需要却没建卡的 NPC 被标成橙色『缺卡』」。也就是说：这个概念 09-26 在原型里做出来过，**后端把它丢了** |
| 冷却/互斥 | `cooldown`、`blocks` | ✅ |
| 权重 | `weight_day` / `weight_month` / `weight_year` | ✅ |

### 3.1 「必然事件」目前也没有位置

现在所有事件都是**随机抽签 + 掷骰**。用户的「必然事件」（第三幕必须有一场背叛、某两方必须在某阶段撞）现在只有 `pillars` 的粗粒度影子，没有单独机制。

⚠ 这条与正在批的阶段 4 直接相关：目标线三表的 `GoalConflict` 就是"必然在某个阶段撞一场"，它现在缺的是**"必然发生、只是早晚/形态随机"**这层语义——现设计是"到窗口才掷骰、掷不中就不发生"。
