## 二、关键决策与理由

**1. 系统库 / 项目库两份 metadata。** `SystemBase` 与 `ProjectBase` 各管各的（`app/db/base.py`），否则一次 `create_all` 会把全部表糊进同一个连接。系统库只留索引，项目的业务数据全在 `projects/<标识>/project.db`。

**2. Phase 1 的 `projects.data` JSON 列作废。** 索引表换成只含元信息的 `projects`（`app/models/system.py`），数据落不到列里的东西，检索时等于不存在。原 models/project.py 已删除。

**3. 迁移脚本先备份再动手。** 认识的字段拆进表，不认识的整包留在 `projects/<标识>/legacy-data.json`，一分不丢；最后重建索引表（SQLite 不一定支持 DROP COLUMN，统一走「建新表 → 抄数据 → 换名」）。

**4. 快照表不做唯一约束。** 一批事件会落多条同一角色的快照，唯一约束会把中间过程挡在外面；取用时按角色 + 天/集倒序取第一条，语义等于取最新。文档 §4.8 已同步。

**5. 子表插入用显式 flush。** 事件与其后果 / 引入 / 参与者是父子关系，靠 ORM 自动排序不稳（实测报过外键错误），现在先 flush 事件再写子表，顺序明确。

**6. 留痕唯一允许 JSON 的地方。** `generation_runs.input_json` 与 `response` 只用于追溯与复盘，不参与任何查询——其余业务数据一律拆表。

**7. 引擎与数据库解耦。** `app/services/simulator/` 全是纯函数与 dataclass，不 import ORM；`simulation_runner.py` 负责搬进搬出。好处：引擎能被单测直接调用，将来换存储不用改算法。
