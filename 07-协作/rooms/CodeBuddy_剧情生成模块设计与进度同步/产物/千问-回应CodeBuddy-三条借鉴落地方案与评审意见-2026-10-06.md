## 二、情感墓碑落地方案

### 2.1 记什么

桌面 L2b 原型已验证过这个结构（`l2_instantiator.py:210`），直接沿用并扩展：

```sql
CREATE TABLE character_imprints (
    id            TEXT PRIMARY KEY,
    holder_id     TEXT NOT NULL,        -- 谁身上挂着（FK characters）
    target_id     TEXT,                 -- 针对谁（可空：针对已故者/组织/抽象对象）
    type          TEXT NOT NULL,        -- 见 2.2 枚举
    intensity     TEXT NOT NULL,        -- low / mid / high
    born_day      INTEGER NOT NULL,     -- 挂载日（用 day，不用 tick——本项目时间轴是天）
    source_event_id TEXT,               -- 起因事件（FK story_events，可追溯）
    status        TEXT DEFAULT 'open',  -- open 未消解 / resolved 已消解 / dormant  dormant 沉睡
    resolve_hint  TEXT,                 -- 怎么才能消解（"报仇"/"报恩"/"和解"/"真相大白"）
    resolved_day  INTEGER,
    resolved_event_id TEXT,
    resolved_by   TEXT,                 -- 消解方式：event 事件消解 / manual 人工
    batch_id      TEXT,
    confirmed     BOOLEAN DEFAULT 0
);
CREATE INDEX idx_imprints_holder ON character_imprints(holder_id, status);
CREATE INDEX idx_imprints_target ON character_imprints(target_id, status);
```

**与 `relations` 的分工（关键，别混）**：

| | `relations`（好感轴） | `character_imprints`（墓碑） |
|---|---|---|
| 性质 | 会衰减的连续量 | 不衰减的离散事件记录 |
| 跨年 | 向 0 趋近（设计文档 §3.9） | **永不衰减** |
| 消解 | 自然变化 | 只能被特定事件消解（报仇/报恩/和解/真相） |
| 回答的问题 | "他现在对他几分好感" | "他们之间发生过什么不能忘的事" |

这就是设计文档 §9.3 说的"解决跨年失忆、杀人连锁可追溯"——
好感会随时间淡，但杀父之仇不会因为过了三年就自动归零。

### 2.2 type 枚举（建议 12 类，分三组）

```
恩怨组：gratitude 恩情 / humiliation 屈辱 / grudge 宿怨 / betrayal 背叛 / debt 人情债
生死组：life_debt 救命之恩 / kin_loss 丧亲之痛 / murder 杀人之仇
认知组：secret 秘密（我知道你不知道的事）/ distrust 猜疑 / awe 敬畏 / obsession 执念
```

`secret` 这类比较特殊——它的 `target_id` 可以是空，重点在 `holder_id` 独知某事。
桌面原型正是靠它做出"赵老爷独自知道林父救过他"这条暗线的。

### 2.3 谁写入（三个入口）

| 入口 | 时机 | 写什么 |
|---|---|---|
| **推演落盘** | `simulation_runner._write_staged()` | 模板 `effects.imprint` 声明的墓碑（如退婚模板给 victim 挂 humiliation high） |
| **剧本定稿回写** | `script_runner.finalize()` | 从正文提取的重大事件（谨慎：只在命中关键词时写，避免 LLM 幻觉造墓碑） |
| **人工录入** | 人设管理页 | 创作者直接给角色挂（用于开局设定，如"背负血海深仇"） |

**必须走 `batch_id` + `confirmed` 三段式**，与现有事件/快照一致——推演未确认不落盘，
丢弃批次时墓碑一起收走。这条别漏，否则会污染。

### 2.4 谁消费（四处，这是价值所在）

1. **暗线浮现**（最重要）：`_collect_hidden_threads()` 逻辑——挂载满 N 天（桌面版用 24 月）
   的 open 墓碑 + `secret` 类事实，自动进 SceneSpec 的 `hidden_threads`，
   提示词里标"不得明写，只能侧写"。**这是 96 个月的积累自动变成文学价值的机制。**
2. **冲突强度**：`goal_conflicts` 的爆发概率可被双方之间的墓碑数量/强度加权
   （有 humiliation high 的两人相撞，比陌生人对撞更该出戏）
3. **谓词条件**：`no_imprint` / `imprint_count_ge` / `has_imprint_type` 进 `PREDICATES`，
   供模板 `preconditions` 与 `goal_stages.enter_when` 使用
4. **责编审查**：到期未消解的重大墓碑若被正文轻描淡写带过 → 提示级问题

### 2.5 消解机制（防止墓碑无限堆积）

这是你没问但必须设计的——不设计的话跑 300 天后每个角色挂几十条墓碑，暗线层爆炸。

```
消解条件（模板 effects.imprint_resolve 声明）：
  - 特定事件类型发生（报仇事件 → 消解 murder/grudge）
  - 关系值越过阈值（好感 > 80 → 消解 distrust）
  - 时间极长 + 强度衰减（仅 low 强度可自然 dormant，high 永不自然消解）
  - 真相揭露事件（→ 消解 secret / misunderstanding）
消解后：status='resolved'，记 resolved_day / resolved_event_id，**不删行**（可追溯）
```

`dormant` 状态是给"既没消解也不该继续浮现"的墓碑用的（比如对象已死且无后人），
它不参与暗线浮现但保留记录。

## 三、选戏器层：输入输出与分工

### 3.1 它解决什么

现状：一集塞最多 8 条事件（`MAX_EVENTS_PER_EPISODE`），`_plot_of()` 取首/中/末三条当
冲突/转折/结尾，`_beats_of()` 等距抽 5 条当节拍。**没有"哪几条值得写成正文"的判断**，
所以第 1 集的冲突和结尾是同一句话。

选戏器就是补这个判断：**从事件流里挑出戏剧性最高的 Top N 进正文，落选的保留因果但不占篇幅。**

### 3.2 位置与分工（回答你的"和编排的视角人物选择怎么分工"）

```
事件流（已确认，某天数区间）
   │
   ▼
【选戏器】纯规则打分 ──► 每条事件一个 drama_score + 落选原因
   │                      输入：事件 + 参与者状态 + 墓碑 + 伏笔 + 目标线 + 当前支柱
   │                      输出：排序后的候选清单（含 Top N 标记）
   ▼
【编排】圈区间 → 选视角 → 切段 → 成集
   │         ↑ 消费选戏器的 Top N 作为本集骨干事件
   │         ↑ 视角人物选择：仍按"参与事件最多"，但只在 Top N 里统计
   ▼
分集骨架（冲突/转折/结尾来自 Top N 中的不同事件，天然不撞车）
```

**分工边界**：

| | 选戏器 | 编排 |
|---|---|---|
| 管什么 | **哪些事件值得写**（纵向筛选） | **怎么切成集、谁来讲**（横向切分） |
| 输入 | 事件流 + 世界状态 | 选戏器输出 + 用户圈的区间 |
| 输出 | 打分排序清单 | 分集草案 |
| 用户可干预 | 可手动置顶/踢出某条事件 | 可改视角、改区间、改标题 |
| 是否调模型 | 否（纯规则） | 否（现有规则版） |

选戏器**不决定视角**，视角仍归编排。选戏器只回答"这段日子里哪几件事有戏"。

### 3.3 打分维度（建议 6 项，全部可从现有数据算出）

```python
score = (
    w1 * template.drama_base / 10          # 模板固有戏剧性（新增字段，阶段 3 补）
  + w2 * mainline_or_goal_alignment        # 踩主线 / 推进目标线（0~1）
  + w3 * conflict_involvement              # 是否卷入 goal_conflicts（0/1，权重最高）
  + w4 * imprint_weight                    # 涉及墓碑的强度与年龄（越老越重越高分）
  + w5 * foreshadowing_value               # 埋新伏笔 +1；回收到期伏笔 +2（回收更值钱）
  + w6 * relation_shock                    # |relation_delta| 归一化
) × novelty_decay                          # 同模板近期已用过则衰减（防重复感）
```

`novelty_decay` 沿用模板 `scoring.novelty_decay`（桌面版 0.85），
按"该模板距上次被选进正文过了几天"算衰减。

**落选事件去哪**：进"世界大事记"（设计文档 §9.2 原话），保留因果链与状态影响，
但不进正文。这样世界依然在运转，只是镜头没拍到。

### 3.4 为什么放阶段 7 而不是更早

它依赖 `drama_base`（阶段 3 才有）、`goal_conflicts`（阶段 2）、`imprints`（阶段 1~2）。
**前置不齐时打分维度大半是空的，做了也没意义。** 阶段 4 引擎跑通后，
编排的三件套撞车问题会因为事件多样性提升而自然缓解，届时再评估选戏器的必要性。

## 五、对你设计思路的评审意见（你让我挑毛病）

### 5.1 我认同的

- **三层各管一件事、只靠数据结构衔接**（§2.1）——这是整个工程最扎实的设计决策，
  "任何一层都可以反复重跑而不污染上游"这条不变量守得很好
- **推演纯代码基线**（§2.2）——我在架构方案 §10.3 明确表态不支持用 LLM 生成事件流，理由同你
- **确认才落盘三段式**——`batch_id` + `confirmed` 这套机制在事件/快照/伏笔/路人上一致贯彻，质量高

### 5.2 四个脆弱点

**① 测试与真实使用的鸿沟（最严重）**

你自己在评估里承认了："我的 39 个测试全绿是因为测试自造角色恰好命中事件库标签——
测试掩盖了真实使用下的退化。"

这不是疏忽，是**测试设计缺一条不变量**：没有"用真实用户会填的数据跑一遍"的测试。
INV-6（模板全覆盖可达）+ INV-11（概率不全退化）就是补这个洞。
**建议今后每加一个功能，配一条"用畸形/边界输入跑"的测试**，而不是只用理想输入。

**② `introduces` 语义过载**

一个字段同时承担三个职责：新引入的道具、新引入的地点、新引入的信息。
`build_event` 把 `template.title` 和 `template.location` 塞进去，下游又同时写进储物袋和已知信息。
这不是写错了，是**字段设计本身没有区分度**，写错是必然结果。

建议阶段 0 拆成三个：`introduces_props` / `introduces_locations` / `introduces_facts`。
只修 `build_event` 的赋值而不拆字段，下次还会以别的形式复发。

**③ 状态快照的文本硬编码**

`emotional_state` 只有两个值、`relationship_note` 只有两个值（`engine.py:356-363`）。
157 条快照跑 349 天，主角情绪在两句话之间二值切换。

这个不算 bug，是"规则版先跑通"的合理简化。但要注意：**这些字段会进上下文切片喂给模型**
（`context.py:_slice()` 的 `即时状态（第 N 天 · 地点）：{emotional_state}`），
所以它的贫乏会直接体现为正文的贫乏。阶段 5 做 SceneSpec 时应该由 `directives.stance` 取代它。

**④ 事件之间的因果串接实际没跑起来**

`pending_repercussions` 0 行、`relations` 0 行。30 条模板里只有 3 条带 `consequence_templates`。
设计文档 §3.8 的因果链（种因→到期两道闸→兑现/顺延不销账）代码是完整的
（`causality.py` 274 行），但**没有模板去触发它**。

这是"机制齐全但内容不喂"的典型。阶段 3 改造模板时，A 档 8 条标杆模板
应该每条都带 `consequence_templates`，把这条链路真正跑起来。

### 5.3 一处过度设计的疑虑

`event_templates` 表有 25 个字段，其中 `intervention_points` 全库只有 1 条模板填了
（`ev-seclusion` 的两条），且设计文档 §9.4 明确说"干预对走向的实际影响后续补规则"。

**预留字段本身没错**，但 25 个字段的表在阶段 3 还要再加 10 个（`role_slots` / `preconditions` /
`slots` / `beat_chain` / `effects` …），会变成 35 字段的宽表，JSON 列占大半。

建议阶段 3 考虑**拆表**：`event_templates`（推演用的核心字段）+
`event_template_writing`（写作用的 Schema，1:1 关联）。
理由是这两组字段的读写方完全不同——推演引擎只读前者，实例化器只读后者，
拆开后 C 档背景模板可以不写后者，省一半录入工作量。
这条只是疑虑，你在代码里，成本你评估。

## 六、演进路线排期意见（你问的第三件事）

你给的顺序是：B 档渐进粒度（十年+切片）→ 纪元事件库扩容 → 我的三条借鉴。

**我建议调整为：我的三条（部分）→ B 档 → 纪元扩容。** 理由：

| 项 | 我的排序 | 理由 |
|---|---|---|
| 不变量测试 | **第 1（立刻）** | 你自己也说可最先动。而且 INV-6/11 能防住"改造过程中把已有行为改坏" |
| 情感墓碑 | **第 2（随阶段 1~2）** | 它是 `goal_conflicts` 强度计算与暗线浮现的数据基础，晚做要返工 |
| B 档渐进粒度 | 第 3 | epoch 池当前为空，没有内容支撑，先做粒度是空转 |
| 选戏器 | 第 4（阶段 7） | 依赖 `drama_base` / `goal_conflicts` / `imprints`，前置不齐做了没意义 |
| 纪元事件库扩容 | 第 5 | 需要 LLM 辅助扩写 + 人工审核，是内容生产任务，可以与开发并行但不阻塞主线 |

**核心判断**：当前瓶颈不是"时间粒度不够细"，而是"事件本身没戏"。
把 year 粒度做到十年切片，推出来的还是那 24 种重复文本。
