# 剧情生成模块诊断与改造方案

## 0. 结论先行

用户判断准确，但问题比"事件库都是普通句子"更深一层。实测这个项目的真实产出：

```
155 条已确认事件 → 只有 24 种不同文本，重复率 85%
   13 次 · 林凡受不了药老的隐瞒，当场堵住他，问他到底在替谁做事。
   10 次 · 林凡看到一件旧物，突然想起那个再没回来的人。
    9 次 · 林凡在天没黑之前就把该问的都问了回来。
```

第 1 集编排产出的三件套：

```
冲突: 林凡在天没黑之前就把该问的都问了回来。
转折: 林凡听不进劝，当场做了决定，事后才发现收不了场。
结尾: 林凡在天没黑之前就把该问的都问了回来。   ← 与冲突完全相同
```

**根因是双重的，且互相锁死：**

1. **事件库模板信息量不足**：30 条模板的 `description` 中位 26 字、最长 37 字，`consequences` 全部恰好 2 条。它是一句话摘要，不是可写的戏。
2. **世界状态信息量不足**：`relations` 0 行、`pending_repercussions` 0 行、`event_walkons` 0 行、`props`/`scenes`/`world_realms` 全 0 行、archetype 体系 7 张表全 0 行。即使模板升级，也没有材料可供实例化填空。

**只改事件库文本不解决问题**——因为把 26 字扩成 2000 字所需的材料（谁和谁什么关系、谁知道什么、地点什么样、有什么暗线）在当前世界状态里根本不存在。两层必须一起改。

桌面那套 L2b/L3 原型已经给出了正确答案：`SceneSpec` 的结构与 `World`/`Fact`/`imprint` 的世界模型。改造方案的主体就是把它移植进后端，并适配漫剧而非小说的产出形态。

## 1. 诊断：七个问题（按严重度）

### ① 性格标签体系断裂 —— 推演的核心机制完全没在工作 【最致命】

设计文档 §3.3 的核心规则是"有什么性格，就遇到什么事"：

```python
# engine.py:507 chance_for()
trait = 0.0
for tag in template.required_tags:
    found = character.trait(tag)
    if found:
        trait = max(trait, TRAIT_PROBABILITY.get(found.intensity, 0.0))
base = (trait or BASE_CHANCE) * weight_of(template, unit)   # BASE_CHANCE = 0.1
```

实测两套标签体系**交集为空**：

| | 标签 |
|---|---|
| 事件库要求的（17 个） | 中立、冲动、利他、利己、善交际、善变、多疑、孤僻、守信、急躁、正道、沉稳、直率、薄情、邪道、重情、隐忍 |
| 项目角色实际持有的（2 个） | 坚韧（林凡 high）、护短（药老 mid） |

后果：`trait` 恒为 0，所有模板的命中概率一律退化为 `BASE_CHANCE = 0.1 × 权重`。实测：

```
ev-confront      required=['急躁','直率']   -> chance=0.1
ev-quiet-help    required=['隐忍','利他']   -> chance=0.1
ev-night-sneak   required=['多疑','孤僻']   -> chance=0.1
ev-keep-promise  required=['守信','正道']   -> chance=0.08
```

**"性格驱动事件"变成了"纯随机抽卡"。** 这直接解释了 85% 的文本重复率——概率全相等时，抽到什么完全看池子大小（30 条）和随机数。

连带失效的还有 `personality.py` 的性格演化：`VOLATILE_TAGS = ['冲动','急躁','多疑','善变','利己']`，项目角色一个都没有，所以 155 条事件跑完，两个角色的性格标签一次都没变过。

**根因**：前端人设页允许自由填写性格标签，而事件库用的是固定的 17 词枚举，两边没有约束关系，也没有映射层。`character_tags`、`archetypes`、`archetype_behaviors`、`archetype_taboos` 这几张表明显是为解决这个问题设计的（原型体系），但全空、代码里也未使用。

### ② 事件文本 = 模板句子换人名，没有实例化层

```python
# engine.py:315
action = _fill(template.description, a, b)      # 就是 str.replace('{a}', 人名)
consequences = [_fill(c, a, b) for c in template.consequences]
```

对比桌面 L2b 产出的 `scene_spec.yaml`，信息量差距是数量级的：

| 维度 | 后端事件（现状） | L2b SceneSpec |
|---|---|---|
| 地点 | `路上`（2 字） | name / type / capacity / features / newly_created |
| 在场者 | 2 个人名 | 5 人，各带 slot / tier / age / gender / identity / realm / faction / speech_style / appearance / known_info / created_now / stance |
| 群演 | 无 | size / composition / behavior_hint |
| 关系 | 无（relations 表 0 行） | 6 组双向数值 + 墓碑（类型/强度/挂载时长） |
| 信息不对称 | 无 | 每人一份 known_info，`Fact.secret_of` 标记专属秘密 |
| 暗线 | 无 | 自动浮现 2 条（96 个月未消解的墓碑 + 专属秘密） |
| 动机 | 无 | primary / evidence / secondary_hint / forbidden_motive（规则推导） |
| 槽位 | 无 | 4 个多值槽（仪式物 / 言辞风格 / 结果分支 / 由头） |
| 节拍 | 无 | 3 拍，各带 weight / must / forbid / variant / variant_basis |
| 收尾 | 无 | ending_hook / pov / word_budget |

**约 1:50 的信息量差距。** 一句话模板要变成一场戏，中间必须有实例化层来填空，而填空材料只能来自世界状态——这正是问题 ①③④ 的地方。

### ③ 因果链完全没运转

设计文档 §3.8 的因果链（种因 → 到期两道闸 → 兑现/顺延不销账）是长篇一致性的核心机制。实测：

```
pending_repercussions   0 行
relations               0 行
event_walkons           0 行
```

30 条模板里只有 3 条带 `consequence_templates`（`ev-betray`/`ev-power-trade`/`ev-socialize`）。而 `relations` 表 0 行意味着：

- `relation_delta` 无处可写，好感变化全部丢失
- `_rel()` 类谓词（`relation_lt`、`witness_relation_gt`）永远返回 0，任何基于关系的前置条件都不成立
- 设计文档 §3.9 的跨年衰减没有作用对象

**"第 40 集接住第 1 集埋的线"这个核心承诺，当前无法兑现。**

### ④ 伏笔只埋不收，且高度重复

```
foreshadowings  39 行，状态分布 {'planted': 39}，已回收 0 条
39 条伏笔去重后只有 7 种文本：
    9 次 · 这个人情日后会被上门讨还
    6 次 · 药老替林凡压下的那件事，日后有人认得出来
    6 次 · 那笔交易的最后一行小字，迟早会来找药老结账
```

`plants_foreshadowing` 是模板级固定字符串，同一模板每抽中一次就复制一条。伏笔台账里躺着 9 条一模一样的"人情债"，既没有回收路径（`payoff_at` 全 NULL），也无法区分是哪一次埋的。

设计文档 §4 的责编审查有"到期未收 → 阻塞"这一项，但因为台账本身是垃圾数据，这项检查形同虚设。

### ⑤ 储物袋与已知信息被污染 【明确 bug】

```python
# engine.py:317
introduces = [_strip_slots(template.title), template.location] if template.plants_foreshadowing else [template.location]
# engine.py:323-325
bag = [*previous_bag, *introduces]           # 塞进储物袋
knows_about = [*prev.knows_about, *introduces]  # 塞进已知信息
```

`introduces` 装的是**事件标题和地名**，却被同时当成道具和事实写进状态。实测数据库：

```
储物袋 194 条，去重 23 种：一时冲动、住处、噬骨沼、埋物、客栈、山道、岔路口、市集、探听消息、提出一笔交易、改换立场、旧栈道…
已知信息 205 条，去重 28 种：（同一批字符串）
```

**林凡的储物袋里装着「集市」「山道」「一时冲动」。** 这些字段会经 `context.py:_slice()` 的 `已知：…` 喂给编剧模型，直接污染正文。

### ⑥ 状态快照只有两种情绪，且被串字段

```python
# engine.py:356-363
emotional_state = '刚惹了麻烦，气还没顺下去' if template.negative else '比出发时沉得住一点'
relationship_note = f'对{b}有愧，也有点迁怒' if template.negative else f'对{b}的戒心松了一层'
```

实测 157 条快照：

```
emotional_state:  {'比出发时沉得住一点': 116, '刚惹了麻烦，气还没顺下去': 39,
                   '林凡趁众人熟睡，独自去查白天不敢问的地方。': 2}   ← 事件文本串进了情绪字段
relationship_note: {'对药老的戒心松了一层': 117, '对药老的戒心松了一层'...: 39, '': 1}
```

跑 349 天，主角的情绪状态只在两句话之间二值切换。第三条数据说明剧本回写链路（`script_runner`）把 `action` 写进了 `emotional_state` 字段——这是第二个明确 bug。

### ⑦ 编排三件套必然重复，选戏机制缺失

```python
# orchestration_runner.py:135 _plot_of()
conflict = events[0].action.strip()
turn = next((e.action.strip() for e in events[1:] if e.on_mainline), '')
if not turn and len(events) > 1:
    turn = events[len(events) // 2].action.strip()
ending = events[-1].action.strip()
```

三件套直接取事件 `action` 原文。由于事件文本重复率 85%，冲突/转折/结尾必然撞车。实测：

```
第 1 集：冲突 == 结尾（同一句）
第 5 集：转折 == 结尾（同一句）
```

而 `_beats_of()` 的节拍也是 `f'第 {e.day} 天 · {e.action}'`，等距抽 5 条——**节拍不是戏剧节拍，只是事件列表的时间戳标注**。

深层缺失：一集塞 8 条事件（`MAX_EVENTS_PER_EPISODE`），但没有"哪几条值得写成正文"的筛选。设计文档 §9.2 已规划"选戏器层"（按戏剧性挑 Top 3~5 条进正文，落选进世界大事记），标注为"已派未实施"。

避免误判，以下几项经查是好的：

## 3. 一个必须先定的差异：漫剧剧本 ≠ 小说正文

桌面 L3 的产出是**小说正文**（`word_budget: 1800~2200字`，第三人称限制视角，白描）。

本项目的产出是**漫剧剧本**：`writer.py:168-173` 钉死的格式是

```
场次头固定写成：第 N 场 · 第 D 天 · 地点
台词行固定写成：角色名：「台词」
写 4 到 6 场，总长度控制在 1200 字以内
```

实测第 1 集正文 489 字，形态是「场次头 + 环境描写 + 角色：动作 + 角色：台词」，下游 `shots` 表（21 行）要按场拆镜、出图、配音视频。

**这个差异决定 L3 的输出层怎么写，但不影响 SceneSpec 的价值**——cast / known_info / relations / hidden_threads / beats / slots 这套结构对漫剧剧本同样适用，甚至更需要（分镜要明确的视觉锚点，`appearance`、`features`、`stance` 正是出图提示词的原料）。

需要调整的是：

| | 桌面 L3（小说） | 本项目（漫剧） |
|---|---|---|
| 输出格式 | 连续段落正文 | 场次头 + 台词行 + 动作行 |
| 单场篇幅 | 一章 2000 字 | 一场 200~400 字，一集 ≤1200 字 |
| 节拍落点 | 3 拍分配全章字数 | 3 拍映射到 3~6 场 |
| 视角 | 第三人称限制视角 | 镜头视角（POV 影响的是镜头而非叙述人称） |
| 额外产出 | 无 | 需给分镜层留视觉锚点（`appearance`/`features`/道具形态） |

`StyleProfile` 的禁用词表、铁律 7 条、章末核对器 7 项**全部可直接复用**。

## 4. 改造方案

### 4.1 目标链路

```
现状：推演 → 事件流 → 编排(切段+三件套) → 剧本(四层切片 → writer → reviewer) → 定稿
                                              ↑ 这里信息量已经耗尽

改造：推演 → 事件流 → 编排(切段+选戏) → 【L2b 实例化】→ SceneSpec → 【L3】→ 剧本 → 核对 → 定稿
         ↑                    ↑                  ↑
    性格标签打通        戏剧性打分         SPEC-1~9 校验
    关系网/因果账运转   Top 3~5 进正文     不过不生成
```

关键插入点是 **L2b 实例化层**，位置在编排之后、剧本之前。它把「一条事件 + 当前世界状态」实例化成「一份可写的场景规格」。

### 4.2 四个改造层

#### 第 0 层：止血（独立于大改造，建议先做）

都是明确 bug，不改架构也该修：

1. **`introduces` 污染储物袋与已知信息**（问题 ⑤）：拆分语义——道具进 `bag`、事实进 `knows_about`、地名既不进袋也不进已知。需要模板显式声明 `introduces_props` / `introduces_facts`，而不是从 title/location 自动生成。
2. **`emotional_state` 被串字段**（问题 ⑥）：查 `script_runner` 的回写路径，修正字段映射。
3. **`template_id` 回填脚本**：把 `template_id_of(event.id)` 的结果写回老项目，恢复溯源与世界事件周期统计。
4. **`_plot_of` 去重**：三件套撞车时至少不要输出完全相同的两句。

#### 第 1 层：世界状态扩容（L2b 的 `World` 对应物）

这是所有后续工作的地基。没有它，模板升级了也没材料可填。

| 表 | 动作 | 对应 L2b |
|---|---|---|
| `characters` | 补 `tier` / `gender` / `realm` / `faction` / `status` / `speech_style` / `appearance` / `identity`（现有 `age_base` / `role` / `slot` / `desc` / `current_goal` / `drive` 可复用） | `Char` |
| **`facts`（新建）** | `id` / `text` / `secret_of` / `planted_day`。**信息不对称的唯一真源**，`known_info` 从它派生 | `Fact` |
| **`imprints`（新建，墓碑）** | `holder_id` / `type` / `target_id` / `intensity` / `born_tick` / `status` / `resolve_hint`。**暗线自动浮现的基础** | `Char.imprints` |
| `relations` | 表已存在（0 行），真正写起来：推演结算 `relation_delta` 时落库 | `Char.relations` |
| `pending_repercussions` | 表已存在（0 行），让 `consequence_templates` 真正种账 | — |
| `scenes` / `props` | 表已存在（0 行），补 `type` / `capacity` / `features`；道具需登记形态（出图要用） | `Location` |
| **`character_tags`（启用）** | 解决问题 ①：把自由填写的性格标签映射到事件库的 17 词枚举，或反过来让事件库接受项目级标签 | — |

**问题 ① 的两种解法**，需要拍板：

- **A. 约束输入**：前端人设页的性格标签改为从 17 词枚举中选（可多选 + 强度 low/mid/high）。改动小，但限制了角色设计的自由度。
- **B. 映射层**：保留自由输入，新增标签映射表（"坚韧" → ["隐忍","守信"]，"护短" → ["重情","利他"]）。灵活，但映射本身要维护，且可能一对多导致概率计算歧义。
- **C. 启用 archetype 体系**：`archetypes` / `archetype_behaviors` / `archetype_taboos` 三张表已建好但全空，设计意图明显是"原型 → 派生行为标签"。这是最完整的方案，也最重。

我倾向 **A + 部分 B**：主标签走枚举保证推演可用，别名走映射表兼容已有项目。

#### 第 2 层：事件库模板 Schema 升级

保留现有推演字段（`time_scale` / `life_line` / `weight_*` / `cooldown` / `duration_days` / `blocks` / `is_world` / `cycle_days` / `required_tags` / `required_equipment` / `min_realm`），新增写作字段：

| 新增字段 | 作用 | 替代现有的 |
|---|---|---|
| `role_slots` | 带 `requires` / `creatable` / `create_tier` / `count` 的角色槽 | `cast: ['a','b']`（只说要几个人，不说要什么人、找不到怎么办） |
| `preconditions` | 结构化谓词元组 `(谓词名, *参数)` | 无 |
| `slots` + `slot_conditions` + `slot_fallback` | 多值槽 + 条件化抽样 | 无 |
| `beat_chain` | 3 拍，带 `drama_weight` / `must_contain` / `requires_facts` / `forbid` / `variants` | 无 |
| `branch_effects` | 分支对应的效果（关系变化/墓碑/伏笔回收） | 无 |
| `effects` | 结构化效果 `relation_delta` / `imprint` / `status_change` / `hook_plant` | `consequences: ['两句自然语言']` |
| `reveals` | 谁在本事件后知道了什么事实 | 无（这是 `known_info` 演进的唯一机制） |
| `scene_requirements` | 地点类型 / 容量 / 群演规模 / 氛围提示 | `location: '路上'` |
| `drama_base` | 戏剧性基准分，供选戏器打分 | 无 |
| `provenance` | 来源审计（handcrafted / extracted / llm_assisted + reviewed_by） | 无 |

`description` **保留**，降级为"事件流列表里给人看的一句话摘要"，不再承担写作职责。

**分级策略**：不是所有事件都值得做完整 Schema。

| 档 | `drama_base` | Schema 完整度 | 处理方式 |
|---|---|---|---|
| 高戏剧性 | ≥ 7 | 完整（role_slots + beat_chain + slots + effects） | 实例化为 SceneSpec，单独成场写正文 |
| 中 | 5~7 | 轻量（role_slots + effects，无 beat_chain） | 并入某场，提供素材 |
| 低（日常琐事） | < 5 | 仅摘要 | 只进事件流/世界大事记，不进正文 |

这对应设计文档 §9.2 的"选戏器层"：每集从候选事件按戏剧性挑 Top 3~5 条进正文，落选保留因果。

**存量 30 条怎么升级**（工作量最大的一块）：

建议手工做 3~5 条标杆（含"当众退婚"这类高戏剧性桥段）确立 Schema 与质量基线，再用 LLM 辅助批量扩写其余，**逐条过 `validate_template()` 静态闸门后人工审核入库**。设计文档 §4.4 已认可这条路："模型辅助扩写模板入库后与内置模板同等待遇，推演照常读，从此不必再调模型。"

`provenance.method` 记 `llm_assisted`、`reviewed_by` 记审核人，满足版权审计。

#### 第 3 层：L2b 实例化器 + SPEC 校验

移植桌面 `l2_instantiator.py`（1219 行）到 `backend/app/services/instantiator/`，改造点：

1. **`World` 换成 ORM 读视图**：现有 `ProjectSnapshot` 已是"引擎只认 dataclass 不认 ORM"的模式，实例化器沿用同一套（新增 `FactView` / `ImprintView` / `LocationView`）。
2. **`PREDICATES` 谓词表移植**：桌面版 14 个谓词（`relation_lt` / `status_gap_gt` / `romance_eligible` / `has_open_hook` / `eligible_partner_of` …），全部纯函数、可单测。
3. **`SPEC-1~9` 校验器移植**：这是"不过不生成"的闸门，防止把矛盾规格喂给模型浪费 token。
4. **`test_validators.py` 的负向测试移植为 pytest**：12 类缺陷注入，验证校验器没有盲区。

**移植时必须修掉桌面原型的三个已知缺陷**（我上一轮已发现）：

| # | 缺陷 | 位置 | 修法 |
|---|---|---|---|
| 1 | `PROMPT_TEMPLATE` 写死"这是全书开篇不久的一章，此前无正文需要承接" | `l3_narrator.py:176` | 改为从上一集正文/事件流派生承接段；这是长篇连续性的关键缺口 |
| 2 | 关键见证人只按 `status` 挑，新建 P3 路人会压过既有 P2 角色 | `l2_instantiator.py:770` | 改为 `(tier 优先级, status)` 复合排序，或排除 `created_now` 的角色 |
| 3 | 离线样例与规格不符（`仪式物=婚书` 写成"聘礼清单"；`crowd.size=26` 写成"六十来个人"超出 `capacity=50`），核对器未检出 | `l3_narrator.py:84-127` | 核对器补两项检查：槽位取值一致性、人数与容量一致性 |

#### 第 4 层：L3 叙事层（适配漫剧）

移植 `l3_narrator.py`，改造点：

1. **输出格式改为漫剧剧本**：场次头 + 台词行 + 动作行（沿用 `writer.py` 已钉死的格式约定，下游 `parse.py:parse_scenes()` 才能拆场）。
2. **篇幅预算改小**：一场 200~400 字，一集 ≤1200 字；3 拍映射到 3~6 场而非分配全章字数。
3. **`StyleProfile` 直接复用**：禁用词 17 个、铁律 7 条、感官侧重、200 字范文样本。
4. **章末核对器 7 项复用**，补 2 项（见上表缺陷 3）。
5. **与现有 `reviewer.py` 六项审查合并**：现有审查是"事后检查正文"，核对器是"检查是否越权"，两者互补不重复——建议合并为一个审查阶段，共用 `review_issues` / `review_reports` 表。
6. **`llm.py` 三后端复用**：`rule` / `cli` / `api` 已实现，桌面版的百炼直连（`call_bailian`）可作为第四种 provider 并入，或统一走 `api` 模式（百炼是 OpenAI 兼容端点）。注意桌面版按密钥前缀自动选端点的逻辑（`pick_endpoint()`）值得保留。

## 5. 分阶段建议

| 阶段 | 内容 | 依赖 | 价值 |
|---|---|---|---|
| **一：止血** | 第 0 层 4 个 bug + 问题 ① 的标签打通（方案 A） | 无 | 立刻让推演从"纯随机"回到"性格驱动"；储物袋不再装地名；三件套不再撞车 |
| **二：地基** | 第 1 层世界状态扩容（`facts` / `imprints` / `relations` / `scenes` 落数据） | 阶段一 | 关系网与因果账真正运转，伏笔可回收，暗线有来源 |
| **三：实例化** | 第 2 层模板 Schema（先 3~5 条标杆）+ 第 3 层 L2b 移植 + SPEC 校验 + 负向测试 | 阶段二 | 事件能变成 SceneSpec，"一句话"变成"一场戏" |
| **四：叙事** | 第 4 层 L3 适配漫剧 + 核对器 + 与 reviewer 合并 + 多集承接 | 阶段三 | 正文质量跃升，且跨集不崩 |
| **五：铺量** | 存量 30 条模板批量升级（LLM 辅助 + 人工审核）+ 选戏器 + epoch 池扩库 | 阶段四 | 长篇可持续性 |

阶段一是纯 bug 修复，风险低、见效快，且与后续阶段无冲突。阶段二开始是架构改造，需要动数据模型（新增 2 张表 + `characters` 补列），要考虑现有 6 个项目的迁移——项目已有 `_ADDED_COLUMNS` 手工补列机制（`project_db.py:73`）可复用。

## 6. 关键决策点

1. **性格标签打通走哪条路**：A 约束输入（枚举选）/ B 映射层（自由填 + 别名表）/ C 启用 archetype 体系（最重）。我建议 A + 部分 B。
2. **改造深度**：只做阶段一止血，还是一路做到阶段四？
3. **存量 30 条模板**：全部升级到完整 Schema，还是只升级高戏剧性子集（按 §4.2 分级策略，估计 8~12 条）、其余保持轻量？
4. **现有 6 个项目的数据**：迁移适配，还是当作测试数据清掉重来？（`projects/7e2320734f424d9ea75581e8b7c25aac` 这份数据质量已不可用——储物袋装地名、155 条事件 24 种文本）
5. **L3 的模型通道**：桌面版卡在 `sk-sp-` 密钥过期。后端 `llm.py` 已有 `cli`（CodeBuddy）/ `api`（OpenAI 兼容）/ `rule` 三后端，是统一走后端现有通道，还是保留桌面版的百炼直连作为第四种？
