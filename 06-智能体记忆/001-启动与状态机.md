# 001-启动与状态机

> 类目：工作台启动 / 项目状态机 / Make 联动。覆盖"必点两次"系列根因与修复。

## 1. 必点两次真凶：launch-log 解析 append 模式 bug（2026-08-13）✅

- **场景**：用户报告"启动开发栈必点两次"。第一次启动即使 PS1 还在跑（14.6 秒），浏览器立即打开却显示"Make 客户端未启动"；第二次启动才成功。
- **根因**：server.mjs 的 launch-log 状态解析用 `txt.includes('AXHUB_LAUNCH_STATUS: done')` 匹配**整个日志文件**——但日志是 **append 模式**，旧启动的 done 标记永远残留，第一次点击时读到的是上次的 done。
- **修复**：从 `txt.lastIndexOf('启动 <relative>')` 切片，只检测**当前这次启动的尾部**。
- **验证**：清空日志后启动，T+2s~T+12s 正确返回 running，T+14.6s 返回 done。
- **教训**：append 模式日志的"最后一次状态"必须按时间切片，不能全文 includes 匹配。

## 2. 必点两次根因与修复：状态机缺"启动中"过渡态（2026-08-12）✅

- **场景**：第一次点"启动开发栈"Make 客户端没启动、项目显示"已停止"，第二次点才成功。
- **根因**：状态机没有 starting 过渡态。POST /api/projects/open spawn PS1（首次 70 秒/后续几十秒），此刻 Vite 未起、心跳文件不存在；前端每 5 秒轮询 GET /api/context/current 触发 reconcileWorkspaceCtx，isProjectAlive=false → 立即降级 stopped。等 70 秒 PS1 完成时项目早被标 stopped，Make active 未切。
- **修复**：
  1. 新增 starting 状态，onProjectStarted 把启动项目设为 starting（非直接 editing/active）；
  2. reconcileWorkspaceCtx 对 starting **不降级**（Vite 已起则补升级 editing/active）；
  3. PS1 stdout 含 `AXHUB_LAUNCH_STATUS: done` 时调 markProjectRunning 把 starting→editing/active + syncMakeActiveProject；
  4. 前端 ctxStatusMap 加 `starting:'启动中'`。
- **验证**：启动后 1.5 秒显示 starting，22 秒 Vite 就绪后自动转 active 且 Make active 切到目标项目。
- **教训**：异步启动流程必须有"启动中"过渡态，不能用 reconcile 在启动未完成时判死。

## 3. 启动流程 Vite+Make 双依赖校验（2026-08-12）✅

- **场景**：starting 状态修复后又暴露新 bug——reconcile 升级 starting→editing 只看 Vite 心跳，但 Make Admin 53817 单独部署（PS1 步骤 7）若超时，Vite 起来了 Make 还没就绪，项目被错升 editing，浏览器打 53817 报 ERR_CONNECTION_REFUSED。
- **修复**：
  1. reconcile 升级 starting→editing/active 必须 **Vite+Make 都健康**（新增 isMakeAlive() 检查 53817 端口）；
  2. PS1 stdout 含 `AXHUB_LAUNCH_STATUS: failed` 时调 markProjectStopped 把 starting 降 stopped，让用户看到启动失败，不依赖前端。
- **验证**：T+0s 启动→T+5s status=starting（Vite down Make UP）→T+10s status=editing（Vite+Make 都 UP）。
- **教训**：跨服务启动流程的"完成"必须等到所有依赖服务就绪，单一服务（Vite）就绪≠整体完成。

## 4. Make 联动时序：spawn 后不能立即同步调（2026-08-12）✅

- **场景**：启动开发栈后 Make 客户端没聚焦到刚启动的项目（activeProjectId 错位，如指向 demo-showcase 而非刚启动的学校卫生）。
- **根因**：server.mjs 的 /api/projects/open 在 spawn PS1 之后**立即**调 syncMakeActiveProject(relative)，但 Make 53817 是 PS1 步骤 3 才启动的，HTTP 探测 status=0 失败。
- **修复**：在 child.stdout 监听里加判断——若输出含 `AXHUB_LAUNCH_STATUS: done`（PS1 8 步全走完、Make 已就绪），再调一次 syncMakeActiveProject(relative)。原有 spawn 后的调用保留作 best-effort。
- **验证**：手动 PUT http://localhost:53817/api/projects/active {projectId:"学校卫生"} 可立即切 active，浏览器刷新即可看到——修复有效旁证。
- **教训**：跨进程联动的调用时序必须等依赖服务就绪。

## 5. touchProjectCtx intent 优先级 + reconcile 双向校准（2026-08-12）✅

- **场景**：工作台状态显示 bug（启动中/已停止乱跳）。
- **规则**：
  1. touchProjectCtx **不应无差别覆盖 intent**。优先级：stopped=5, running=4, ready=4, opening=3, focus=2, created/copied=1。旧 intent 优先级 > 新 intent 优先级时保留旧值。
  2. reconcileWorkspaceCtx 必须**双向校准**：running 死了→降级 stopped；opening 但实际活着→升级 running。
- **教训**：状态显示 bug 的根因往往不是 reconcile，而是 touchProjectCtx 被频繁调用覆盖 intent。

## 6. 工作台模型：单项目单状态 + 多智能体维度（2026-08-12）✅

- **模型**：workspace.json = `{ agents: {codebuddy:{editing}, workbuddy:{editing}}, projects: [{relative, name, status, editor, ...}] }`。
- **status 三态**：editing（被某智能体编辑，隐含已启动，每智能体至多 1 个）/ active（启动但非编辑焦点）/ stopped（被动停止，进程死但保留展示可重启）。
- **主动停止**（停止工作台.cmd）直接删 workspace.json，不保留历史。
- **关键函数**：readWorkspaceCtx（兼容旧 intent 迁移）、setEditing（切换编辑焦点，冲突返 AGENT_CONFLICT 409）、onProjectStarted、markProjectStopped、reconcileWorkspaceCtx、syncMakeActiveProject。
- **API 变更**：POST /api/context/current 只收 {agent, relative}；GET 返回 {agents, projects}。
- **停止工作台.cmd**：清理项目级 `.workbuddy/current.json`，用通配符 `%~dp001-*\*` 匹配 01-项目 目录避免中文乱码（.cmd 必须 GBK）。
