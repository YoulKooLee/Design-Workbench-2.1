2. **决定性证据**：该进程 I/O 计数 —— **写操作 5,400–6,400 次/秒，写字节恒为 0 B/s**，读 0/s、其他操作 0/s。即「纯 0 字节写死循环」，不是磁盘扫描、不是网络、不是请求压力。
3. **触发条件在 `launcher.ps1` L94–102**：启动 `server.mjs` 时设了 `RedirectStandardOutput/Error = $true`，并用 **`Start-Job` 拉一个后台 PowerShell job 去 `ReadToEnd()`** 当管道读端。launcher 窗口一关（L122 还明确提示「**可放心关闭本窗口**」），job 随会话终止 → **管道读端消失** → node 的 stdout/stderr 变成坏管道。
4. **放大器在 `server.mjs` L12–13**：`process.on('uncaughtException')` / `unhandledRejection` 处理器把异常**吞掉**，且处理器内部又调 `console.error` —— 而 console.error 写的正是那个已坏的流 → 再次抛错 → 再进处理器 → **自激循环**。这解释了「0 字节写」：每次写都失败，一个字节都没落地。
5. **后果**：事件循环被占满 → 面板 HTTP 响应被拉到 ~480ms → 用户感知「卡住」。内存侧另有加成：**已用 82%（15.6GB 仅剩 2.9GB）**，WorkBuddy 自身跨 5 进程 ≈2.8GB、千问 ≈1.3GB、Memory Compression 491MB。

**修复方向**：① 立即 —— 只重启 `:7788` 面板（不必动 make/vite）；② 长效 —— `launcher.ps1` 改为**直接用 `Start-Process -RedirectStandardOutput <文件>` 落盘**（不经 Start-Job 管道），或给 `server.mjs` 的错误处理器加「流已销毁就不再 console」的保护；③ 该脚本 L122 的「可放心关闭本窗口」提示与 Start-Job 设计**自相矛盾**，属真缺陷。

**可复用诊断手法（Windows 上查「服务卡住/无响应」）**：
`Get-CimInstance Win32_Process` 取 `WriteOperationCount` / `ReadOperationCount` / `WriteTransferCount` **两次采样求差值** → 「写操作高、写字节 0」即锁定空写死循环；再对 HTTP 打 5 次同一端点看**延迟是否为固定地板**（与响应体大小无关＝事件循环被占，而非慢查询）；最后查 `ParentProcessId` 是否还活着（父死＋管道＝高危组合）。
