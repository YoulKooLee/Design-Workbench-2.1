# 搜索中心设计方案（全文检索 / Search Center）

> 整理日期：2026-09-30
> 用途：软件产品模块设计知识库。覆盖搜索中心的业务场景全景、各场景解决方案、通用设计方案（最优解）与设计说明。
> 一句话本质：把"**从业务库里找数据**"从 LIKE 扫表升级为"**倒排索引 + 相关性排序**"的通用检索能力——回答"搜什么能搜到、搜到后怎么排、怎么让用户好搜"三个问题；与文件管理（文档检索）、导入导出（数据可搜）、数据权限（结果过滤）联动。

---

## 一、模块概述：正排变倒排

```
业务数据（订单/商品/文档/用户）写库 → 索引同步（实时/准实时）
   → Elasticsearch 建倒排索引（分词 → 词典 + 倒排表）
   → 查询：用户输入 query
      → 查询理解（分词/纠错/同义词/拼音）
      → 检索召回（倒排索引秒查候选文档）
      → 相关性排序（BM25 + 业务权重）
      → 过滤聚合（数据权限/类目/价格/品牌）
      → 输出（分页 + 高亮 + 搜索建议）
```

| 核心概念 | 说明 |
| --- | --- |
| 倒排索引 | 词 → 文档列表的映射（书末索引页），检索 O(1) 定位候选，不扫全表 |
| 分词 | 把文本切成词项：中文用 IK 等分词器，"中华人民共和国" → 中华/人民/共和国 |
| BM25 | 行业标准相关性打分：词频饱和 + 文档长度归一，替代 TF-IDF |
| 索引同步 | 业务库数据变化 → 同步到 ES 的过程（实时/定时/双写） |

## 二、业务场景全景

### 场景 1：后台管理系统列表搜索（业务数据检索）
- 订单按单号/手机号/收货人搜、用户按姓名/手机号搜、日志按关键字搜；
- 替代 `LIKE '%xxx%'`——数据量大后 LIKE 全表扫慢到不可用。

### 场景 2：商品/内容电商搜索
- 搜"手机"→ 返回标题/描述/品牌命中的商品；
- 相关性排序（销量、评价、新品、价格竞争力综合加权）。

### 场景 3：文档/附件全文检索
- 搜索 PDF/Word/笔记正文内容（与文件管理联动，正文入库可搜）。

### 场景 4：搜索联想（Autocomplete / Suggest）
- 用户输入"苹"即时提示"苹果/苹果手机/苹果平板"；
- 支持拼音（输"pingguo"也出"苹果"）、大小写、繁简。

### 场景 5：拼写纠错（Did you mean）
- 输"苹里手机"提示"您是不是想找：苹果手机"。

### 场景 6：多条件过滤与聚合
- 搜索结果按品牌/价格区间/类目/库存过滤（filter）；
- 侧边栏聚合：品牌列表、价格分档、类目树（facets）。

### 场景 7：同义词与业务词典
- "手机"="移动电话"、"电脑"="计算机"；
- 维护业务自定义词典（人名、产品名、专有名词）。

### 场景 8：个性化排序（电商进阶）
- 按用户历史（品牌偏好、价格区间）调整排序；
- 商业加权：库存、毛利、活动位。

## 三、各场景的解决方案

### 3.1 技术选型：什么量级用什么
| 方案 | 适用 | 优点 | 缺点 |
| --- | --- | --- | --- |
| MySQL LIKE | 千级小数据、临时 | 零成本 | 全表扫、慢、无相关性 |
| MySQL FULLTEXT | 万级单字段 | 简单 | 中文分词弱 |
| **Elasticsearch** | 业务检索主流 | 倒排+BM25+聚合+高可用，毫秒级 | 运维重、有学习成本 |
| OpenSearch（阿里云）/Solr | 企业级/电商 | 托管、行业算法 | 商业化付费 |
| 向量检索（Qdrant/Milvus） | 语义搜索/推荐 | 语义匹配 | 与倒排融合才有好效果 |

**推荐**：业务系统搜索用 **ES 倒排索引为主**；语义搜索需求再叠加向量检索（hybrid 双路召回 + RRF 融合）。

### 3.2 索引同步：业务库 → ES
| 方式 | 适用 | 说明 |
| --- | --- | --- |
| 定时全量重建 | 小数据/字典类 | 每日重建索引 |
| 实时增量（MQ 事件） | 业务数据 | 业务写库发事件 → 消费者更新 ES 文档 |
| Binlog 监听（Canal） | 强一致场景 | 监听 DB binlog 增量同步，不侵入业务 |
| 双写 | 简单场景 | 业务同时写 DB + ES，注意一致性风险 |

**一致性兜底**：增量可能丢 → 定时全量对账（diff 补偿），保证"最终一致"。

### 3.3 查询链路：召回 → 排序 → 过滤 → 输出
```
query 输入
  → 查询理解：分词 / 纠错（编辑距离）/ 同义词扩展 / 拼音归一（中文转拼音字段）
  → 召回：倒排索引按词查候选文档列表（不碰全量数据）
  → 排序：BM25 相关性得分 + 业务权重加权
       （标题命中权重 > 描述 > 标签；销量/库存/新品加权）
  → 过滤：数据权限（只能看自己有权限的数据）+ 类目/价格/品牌 filter
  → 聚合：侧边栏 facets（品牌/价格档位/类目）
  → 输出：分页（search_after 代替深分页）+ 高亮片段（<em>标记命中词）
```

### 3.4 搜索联想（Autocomplete）方案
```
两层架构：
  Tier1 预构建：Top N 高频 query 建 Trie / FST，每个前缀节点预存 Top-K 建议
      → 查询 O(前缀长度)，Redis 缓存 prefix→建议列表（TTL 10min）
  Tier2 实时热点：Redis ZSet 每 5 分钟统计突增 query（3× 基线标记 trending）
      → API 层合并：高频建议 + 实时热点建议
拼音支持：为每个词存 pinyin 字段（分析器生成），前缀匹配拼音
```

### 3.5 高亮与摘要
- 命中词用 `<em>` 标记，返回片段（context 前后截取）；
- 摘要基于命中上下文生成，不是简单截头。

### 3.6 数据权限过滤（关键）
- 搜索结果必须叠加用户数据权限（与权限模块联动）：
  - 方案 A：查询时拼 filter（数据范围/部门/可见性字段）；
  - 方案 B：写入时打权限标签（document 带 scope 字段），查询 filter 过滤；
- **导出权限同理**：搜索能看到的才能导出（与导入导出中心联动）。

### 3.7 性能与稳定性
- 索引分片（shard）路由，支持水平扩容；
- 查询用 `search_after` 代替大 offset 深分页（与导入导出游标同理）；
- 只返回列表页字段（瘦身），详情页再回业务库补查；
- 停用词过滤（的/了/吗）、大小写归一。

## 四、通用设计方案（最优解）

### 4.1 总体架构
```
业务系统（数据源）：
  订单/商品/文档/用户等业务库
   │ 索引同步（MQ 事件 / Canal binlog / 定时全量 + 对账补偿）
   ▼
搜索中心（平台通用）：
  索引管理（索引模板/分词器/字段映射/词典）
  查询服务（理解 → 召回 → 排序 → 过滤 → 聚合 → 输出）
  建议服务（联想 Trie/FST + 热点 + 拼音）
  运维（分片/副本/监控/重建）
   │
存储：Elasticsearch 集群（倒排索引 + 聚合数据）
   │
集成：
  权限模块（搜索结果数据权限过滤）
  数据字典（词典/同义词/停用词管理）
  导入导出中心（可搜数据可导出）
  审计日志（敏感检索留痕，可选）
```

### 4.2 索引文档设计（以订单/商品为例）
```json
{
  "id": "订单/商品ID",
  "title": "标题（text 分词，boost 高）",
  "description": "描述（text 分词，boost 中）",
  "tags": ["标签"], 
  "category": "类目（keyword 精确过滤）",
  "brand": "品牌（keyword 聚合）",
  "price": 199.9,             // numeric 区间过滤
  "status": "ACTIVE",          // 状态过滤（软删/下架不入索引）
  "scope": "tenant:100:dept:20",  // 数据权限标签（写入时打标）
  "pinyin_title": "shouji"     // 拼音字段（拼音搜索）
  "suggest": ["苹果", "苹果手机"]  // completion 字段（联想）
}
```

### 4.3 关键设计点
- **写库即建索引**：业务写库 → 事件异步同步 ES，读走 ES、写走 DB（CQRS 读写分离）；
- **一致性补偿**：增量丢失靠定时全量对账兜底；
- **查询理解前置**：分词/纠错/同义词/拼音在查询层统一处理，业务无感；
- **排序公式化**：`finalScore = BM25 相关性 × w1 + 业务分（销量/新品/库存）× w2 + 个性化分 × w3`，权重可配置；
- **数据权限必过滤**：搜索可见性 = 数据权限可见性；
- **深分页用 search_after**：稳定高效；
- **词典可运营**：同义词/停用词/业务词通过后台维护，无需发版。

## 五、设计说明

### 5.1 核心设计原则
| 原则 | 说明 |
| --- | --- |
| 倒排索引替代 LIKE | 全表扫变词→文档 O(1) 定位 |
| 读 ES 写 DB | 读写分离，业务库零压力 |
| 查询理解统一 | 分词/纠错/同义词/拼音在搜索层一次做掉 |
| 相关性可调 | BM25 + 业务权重加权，权重可配置 |
| 权限贯穿检索 | 结果先过数据权限过滤 |
| 建议两层 | 高频 Trie/FST + 实时热点 Redis |
| 索引最终一致 | 增量 + 定时对账补偿 |

### 5.2 常见设计坑与规避
| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 用 LIKE 搜大数据 | 全表扫慢到超时 | ES 倒排索引 |
| 中文不分词直接搜 | 搜"手机"匹配不到"智能手机" | 中文分词器（IK）+ 同义词 |
| 索引与业务库不一致 | 搜到旧数据/搜不到新数据 | MQ 增量 + 定时对账 |
| 排序只有 BM25 | 销量高的排后面 | 业务权重加权排序 |
| 深分页大 offset | 越翻越慢、内存暴涨 | search_after |
| 搜索结果不过滤权限 | 越权看到他人数据 | 查询拼数据权限 filter |
| 返回全字段 | 网络/内存浪费 | 只返回列表页字段，详情回查 |
| 联想不做拼音 | 用户要切输入法 | 拼音字段 + completion |
| 同义词写死在代码 | 改词典要发版 | 词典后台化运营 |
| 同步失败不补偿 | 永久性丢数据 | 定时全量对账 diff |

### 5.3 演进路线
```
阶段1 LIKE 搜索：小数据直接 SQL 模糊查
   ↓
阶段2 引入 ES：核心业务表建索引，分词 + BM25 + 分页高亮
   ↓
阶段3 检索体验：联想/拼音/纠错/同义词 + 过滤聚合 facets
   ↓
阶段4 智能排序：业务权重 + 个性化 + 数据权限统一过滤 + 语义向量混合检索
```

### 5.4 业界参考实现
- **Elasticsearch**：Lucene 之上的分布式搜索，倒排索引 + BM25；
- **阿里云 OpenSearch**：电商行业算法版（停用词/纠错/词权重/聚合/filter）；
- **Amazon A9 排序**：BM25 + 销量 + 评价 + 价格竞争力 + 毛利多信号加权；
- **电商 Hybrid Search**：倒排 + 向量双路召回 + Reciprocal Rank Fusion 融合。
