# 数据字典与元数据管理设计方案（Data Dictionary & Metadata）

> 整理日期：2026-09-13
> 用途：软件产品模块设计知识库。覆盖数据字典与元数据管理的业务场景全景、各场景解决方案、通用设计方案（最优解）与设计说明。
> 一句话本质：该模块分两个层次——**运行时字典**解决"枚举值/参数统一管理、动态调整不改代码"，**治理层元数据**解决"数据资产可见、标准可执行、血缘可追溯、安全可分级"。

---

## 一、模块概述：两个层次，一条主线

| 层次 | 回答的问题 | 核心能力 |
| --- | --- | --- |
| **运行时字典**（Data Dictionary） | 下拉框/状态/标签的数据从哪来？枚举变了要不要改代码？ | 字典类型 + 字典项管理、字典翻译（ID→NAME）、多级缓存热更新 |
| **治理层元数据**（Metadata） | 系统里有哪些数据？字段什么意思？标准怎么执行？血缘怎么查？ | 元数据采集、数据资产目录、数据标准、血缘与影响分析、分级分类 |

**一条主线**：字典是"标准"，元数据是"现状"。数据标准通过字典落地（建表强制引用），元数据把落地结果管起来（目录/血缘/安全）。两个层次共用同一套"配置-发布-审计"管理骨架。

---

## 二、业务场景全景

### 场景 1：下拉框数据源（最普遍）
- 查询过滤下拉框：列表页筛选条件（状态、类型、难度）来自字典；
- 数据编辑下拉框：新增/编辑表单的候选值来自字典，**字典项 ID 作为业务表字段值**存入业务表；
- 列表显示：业务表存 ID，接口返回前把 ID **翻译成 NAME**（字典翻译）；
- 统计图表维度：图表维度/图例使用翻译后的字典名称。

### 场景 2：枚举值统一管理与动态调整
- 状态字段（订单状态、审核状态）、类型字段（业务类型、来源类型）、标签字段（颜色/徽标）；
- 字典项支持增删改、排序、启停用、颜色扩展（如 MES 字典项的 label 颜色）；
- **变更不发布、不重启**，运行时可调整，前端下拉即时生效。

### 场景 3：数据标准与建表规范（治理核心）
- 建标准字典库：存数据项的标准名称、业务定义、数据类型、长度、值域、编码规则；
- 强制落地：新建表流程中强制引用字典——输入字段名自动匹配标准数据项，字段名/类型/注释自动填充不可随意改；未匹配触发"新增数据标准申请"，Owner 审批通过后**该新数据项同时加入字典**；
- 解决"标准写在文档里、执行在系统外"的脱节问题。

### 场景 4：元数据资产目录
- 表/字段/分区/数据源级元数据管理（名称、类型、注释、Owner、标签、最近访问）；
- 数据地图与全文搜索（表名/字段名/注释检索）；
- 敏感数据识别：按字段名正则（`.*phone.*`、`.*id_card.*`）自动打分级标签（公开/内部/敏感/机密），Owner 人工确认。

### 场景 5：数据血缘与影响分析
- 表间血缘（一张表从哪些表加工而来）、字段级血缘（字段对应源表哪个字段）；
- 血缘天然是**图结构**，用图数据库存储，一次遍历取完整链路；
- 影响分析：改一张源表/字段，反查所有下游表、指标、报表，评估爆炸半径。

### 场景 6：多租户字典隔离与共享
- 租户间数据天然隔离（tenant_id 注入）；
- **系统级字典**（所有租户共享，如全局状态枚举）+ **租户级字典**（各租户自定义）；
- 默认租户的字典可同步下发到其他租户。

### 场景 7：系统参数配置（进阶）
- "可调参数"不应写死在代码：L1 字典表（枚举）+ L2 配置表（业务开关）+ L3 系统参数（运维参数）三层；
- 运行时热更新，无需发版。

## 三、各场景的解决方案

### 3.1 字典类型与来源（三种承载方式）
| 方式 | 说明 | 适用 |
| --- | --- | --- |
| 常量/枚举字典 | Java 枚举类注解标记（代码内定义） | 稳定不变、纯代码可维护的枚举（如性别） |
| 表驱动字典 | 字典表动态维护，运行时改 | 前端下拉、有变化调整的枚举（主流） |
| 数据源字典 | 字典项来自 SQL/外部数据源动态查询 | 数据量大的业务字典（如从部门表取） |

**主流做法**：表驱动为主（两张表：字典类型定义 + 字典项明细），少量稳定枚举用代码枚举；两者可共存（mldong 模式：枚举类 + 自定义字典服务）。

### 3.2 字典翻译机制（ID → NAME）
- 业务表字段存**字典 ID**，接口返回前由服务端统一翻译为 NAME，绑定到返回对象（如 `difficulty` + `difficultyName`）；
- **翻译必须在服务端**：保证前后端口径一致，前端只负责展示；
- 支持批量翻译（列表页一次翻译整列）、递归翻译（树形字典）、翻译失败降级（返回原 ID）。

### 3.3 缓存与热更新（多级缓存）
```
本地内存缓存（ConcurrentHashMap，全量加载，毫秒级）
   ← 版本号/变更广播（Redis pub/sub 或事件）失效
Redis 缓存（跨实例共享）
   ← TTL + 主动失效
数据库（dict_type / dict_item）
```
- 启动时全量加载到本地内存；字典变更 → 更新 DB → 发布变更消息 → 各节点失效本地缓存重载；
- 避免"全表缓存 + 直接清空"导致缓存雪崩：用**版本号 + 按字典编码定向失效**。

### 3.4 多租户方案
- 所有字典表含 `tenant_id`；数据库中间件自动注入租户条件；
- 查询优先级：租户级字典 → 系统级字典（tenant_id=0）合并返回；
- 默认租户字典同步：事务内忽略租户过滤读取默认租户数据，复制到目标租户；
- 共享数据通过显式关联表控制（避免共享表被误隔离）。

### 3.5 树形字典
- 邻接表（parent_id）+ 路径枚举（path）混合模型，避免递归查询性能问题；
- 支持层级展开、层级下拉、父子联动。

### 3.6 元数据管理（治理层，Atlas 模式）
- **数据模型**：Type（元数据类型定义，可继承）→ Entity（类型实例，即具体元数据对象）→ Classification（分类/标签）→ Attribute（属性）→ Lineage（血缘）；
- **存储**：血缘/关系用图数据库（JanusGraph/Neo4j），业务元数据用关系库（MySQL），搜索用 ES；
- **采集**：核心数据源（Hive/Spark）用 Hook 实时采集（零侵入，加一行类名），外围数据源（MySQL/PG）用定时 Pull；经 Kafka 统一接入；
- **数据标准落地**：标准字典库（定义层）+ 建表强制引用（执行层），未匹配字段走"新增标准申请"审批流；
- **安全分级**：正则自动打标（覆盖 80% 敏感字段）+ Owner 确认 + Ranger 细粒度权限同步。

## 四、通用设计方案（最优解）

### 4.1 总体架构
```
管理端（字典管理 / 标准管理 / 元数据目录 / 血缘可视化 / 分级分类）
   │
服务层（字典查询&翻译 API / 标准匹配 / 搜索 / 血缘分析 / 审批）
   │
数据层（dict_type/dict_item ｜ 标准字典库 ｜ 元数据存储：图库+关系库+ES）
   │
采集层（Hook 实时采集 ｜ Pull 定时采集 ｜ Kafka 统一接入）
   │
数据源（业务库 / Hive / Spark / Kafka / 对象存储）
```

### 4.2 核心表结构（表驱动字典，业界主流同构）
```sql
-- 字典类型定义表
CREATE TABLE dict_type (
  id BIGINT PRIMARY KEY,
  tenant_id BIGINT,                -- 租户隔离
  dict_code VARCHAR(50) UNIQUE,    -- 字典编码（前端/API 唯一标识）
  dict_name VARCHAR(100),          -- 字典名称
  is_system TINYINT,               -- 是否系统内置（内置禁删）
  status TINYINT DEFAULT 1,        -- 1启用 0停用
  remark VARCHAR(200)
);
-- 字典项明细表
CREATE TABLE dict_item (
  id BIGINT PRIMARY KEY,
  tenant_id BIGINT,
  dict_code VARCHAR(50),           -- 所属字典
  item_label VARCHAR(100),         -- 显示文本
  item_value VARCHAR(100),         -- 存储值（业务表存这个）
  sort INT DEFAULT 0,              -- 排序
  color VARCHAR(50),               -- 标签颜色（可选）
  parent_id BIGINT, path VARCHAR(255),  -- 树形字典（邻接表+路径）
  status TINYINT DEFAULT 1,        -- 1启用 0停用
  create_time, update_time
);
```

### 4.3 字典 API 与前端约定
- `GET /dict/{code}`：查某字典全部启用项（下拉用）；
- `GET /dict/translations?codes=a,b,c`：批量取翻译映射（列表翻译用）；
- 服务端返回对象约定：`{ "value": "1", "label": "启用" }` 或字段 + 翻译字段（`status` + `statusName`）；
- 前端框架可封装 `useDict(code)` / `dict-tag` 组件（下拉、标签、级联统一消费）。

### 4.4 元数据模型（治理层）
```
Type 定义（表、字段、指标等）→ Entity 实例（具体某张表）
  ├── Classification：分级标签（敏感/公开）、业务标签
  ├── Lineage：血缘边（源→目标，字段级）
  └── Attribute：属性（类型、注释、Owner、更新频率）
```
- 血缘用图存储：`(源表)-[produced_by]->(目标表)`，一次图遍历取全链路；
- 搜索用 ES：表名/字段名/注释/标签多字段索引。

### 4.5 变更与发布流程（防乱改）
```
编辑（草稿）→ 审批（Owner/管理员）→ 发布（生效+广播缓存失效）→ 审计留痕
```
- 关键字典变更建议走审批；历史变更可回滚查询；
- 字典项停用而非删除（保留历史数据引用完整性）；
- 编码一旦使用不可修改（改了历史数据全错），只能停用+新增。

### 4.6 分级分类落地
- 正则自动识别（字段名命中 `phone`/`id_card`/`salary` 等 → 自动打"敏感/机密"标签）；
- Owner 人工复核确认；
- 标签驱动权限：治理平台配置的策略同步到 Ranger 生效（底层细粒度权限）。

## 五、设计说明

### 5.1 核心设计原则
| 原则 | 说明 |
| --- | --- |
| 运行时配置与代码解耦 | 枚举变化改字典不改代码、不重启 |
| 翻译统一在服务端 | 保证跨端口径一致 |
| 编码不可变、项只停用 | 保护历史数据引用完整性 |
| 多级缓存定向失效 | 版本号 + 按字典编码失效，防雪崩 |
| 标准嵌入流程而非文档 | 建表强制引用字典，未匹配走审批 |
| 元数据关系用图存储 | 血缘/影响分析一次遍历 |
| 变更可审计可回滚 | 草稿→审批→发布→留痕 |

### 5.2 常见设计坑与规避
| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 字典编码随意修改 | 历史业务数据含义错乱 | 编码不可变，改新增+停用 |
| 翻译放前端 | 各端口径不一致 | 服务端统一翻译 |
| 全量清缓存 | 缓存雪崩、瞬时打爆 DB | 版本号 + 定向失效 |
| 树形字典递归查 | 层级深时性能崩 | 邻接表 + path |
| 忽略租户隔离/同步 | 数据串租户、租户字典缺失 | tenant_id 中间件注入 + 系统级/租户级合并 + 默认租户同步 |
| 标准只写文档不执行 | 数据标准形同虚设 | 建表强制引用 + 未匹配走申请审批 |
| 无审批直接改生产字典 | 线上下拉错乱 | 草稿→审批→发布 |
| 血缘用关系库递归 | 表越多查询越慢 | 图数据库存储血缘 |

### 5.3 演进路线
```
阶段1 运行时字典：dict_type/dict_item + 翻译 + 缓存热更新（多数系统到此即可）
   ↓ 治理需求
阶段2 数据标准：标准字典库 + 建表强制引用 + 申请审批
   ↓ 资产化
阶段3 元数据平台：采集（Hook/Pull）→ 目录/搜索 → 血缘/影响分析 → 分级分类
   ↓ 生态化
阶段4 治理中台：接入 Atlas/DataHub、与质量/安全/生命周期联动
```

### 5.4 业界参考实现
- **若依 / JeecgBoot / ContiNew Admin**：dict_type + dict_item 主从表 + 字典翻译 + 多租户（国内框架事实标准）；
- **橙单**：字典翻译（服务端 ID→NAME 绑定返回对象）、常量/表/数据源三类字典；
- **Apache Atlas**：Type/Entity/Classification/Lineage 元数据模型 + Hook 采集（Hadoop 生态标配）；
- **DataHub / Amundsen**：实时采集、数据目录、搜索体验；
- **腾讯云/大厂数据治理实践**：标准字典嵌入建表流程 + 分级分类（正则打标）+ Ranger 权限同步。
