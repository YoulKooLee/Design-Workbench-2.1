# 消息通知中心设计方案（Notification Center）

> 整理日期：2026-09-14
> 用途：软件产品模块设计知识库。覆盖消息通知中心的业务场景全景、各场景解决方案、通用设计方案（最优解）与设计说明。
> 一句话本质：统一消息发送管理平台——**业务与技术分离**：业务方只管"发什么、发给谁"，平台负责"模板渲染、渠道路由、频控、幂等、重试降级、状态回执"。与触发器模块的告警通知天然衔接。

---

## 一、模块概述：一个平台，多通道触达

通知中心把所有触达渠道（站内信、短信、邮件、Push、微信公众号、企业微信、钉钉、飞书、Webhook）收口为**统一 API + 统一模板 + 统一管理**：

```
业务系统（审批/告警/订单/公告…） → 统一通知 API（类型+接收人+参数）
   → 模板渲染 → 渠道路由 → 频控/去重 → 多通道队列 → 渠道供应商
   → 发送状态回执 → 站内信存储 → 已读/撤回/统计
```

| 角色 | 关注点 |
| --- | --- |
| 业务方 | 低接入成本（四步：注册应用 → 创建消息类型 → 模板管理 → 接口对接） |
| 平台方 | 渠道扩展性、发送可靠性、成本控制、可观测 |
| 接收方 | 及时、不过度打扰、可管理偏好 |

## 二、业务场景全景

### 场景 1：业务提醒（事务型通知）
- 审批待处理、工单流转、工资到账、订单状态变更、设备告警（对接触发器/告警中心）；
- 特点：高频、强时效、需要"必达"，通常多通道齐发（站内信 + 短信/IM）。

### 场景 2：验证码 / 安全通知（P0 关键型）
- 注册/登录验证码、密码找回、异地登录提醒、支付确认；
- 特点：短信/邮件为主，**绕过限频、最高优先级**，强时效（5 分钟有效）。

### 场景 3：系统公告 / 广播（站内信广播）
- 全平台公告、版本更新、停机通知；
- 特点：Fanout 广播到所有用户，站内信 + 重要公告可叠加弹窗。

### 场景 4：营销 / 运营触达（P2 营销型）
- 活动推送、召回、订阅内容；
- 特点：批量 fanout、强频控（防打扰）、用户可退订、避开深夜时区。

### 场景 5：用户偏好与订阅管理
- 每用户可配：哪些消息类型接收、走哪些渠道、免打扰时段、退订营销；
- 特点：偏好检查在入队前执行——**用户已退订的绝不发送**。

### 场景 6：站内信中心（收件箱）
- 未读/已读状态、未读角标计数、消息分类与过滤、批量已读、删除/归档、撤回（如 24h 内）；
- 特点：推拉结合——在线实时推送，上线/刷新增量拉取。

### 场景 7：发送管理与可观测
- 模板管理（业务类别 × 渠道）、发送记录查询、送达状态追踪（成功/失败/重试中）、失败重发、成本统计（各渠道费用）、可达性分析。

## 三、各场景的解决方案

### 3.1 多通道支持与统一抽象
- 统一发送服务接口：`send(request)` / `queryResult(logId)` / `retry(logId)`；
- 每渠道一个**处理器（Provider）**实现同一接口，策略模式接入各厂商（阿里云/腾讯云/SMTP/各 IM 机器人）；
- 新渠道接入 = 新增一个 Provider + 管理端配置，业务无感。

### 3.2 模板管理（业务类别 × 接收渠道）
- 以「业务类别」区分消息来源，以「接收渠道」区分推送载体；
- 同一业务小类复用同一组参数（如 `{userName}`、`{orderNo}`），不同渠道各自模板（短信限长、邮件可富文本）；
- 模板变量渲染后发送，参数与业务类别联动，无需重复配置。

### 3.3 优先级与限频
| 优先级 | 场景 | 策略 |
| --- | --- | --- |
| P0 关键 | 验证码、安全告警 | **绕过限频**，最高优先级队列 |
| P1 事务 | 订单、审批、告警 | 正常发送，超限排队 |
| P2 营销 | 活动、召回 | 强限频，超限丢弃或顺延 |

- **每用户每渠道限频**（示例：Push ≤ 20/小时、邮件 ≤ 5/天、短信 ≤ 3/天）；
- **全局限频（令牌桶）**：同一用户单位时间触达总量封顶（如 3 条/天、12 条/周），超出进队列次日发——除 P0；
- 时区感知：营销类通知避免当地深夜（3AM）发送。

### 3.4 渠道降级与回退链
- 主渠道失败 → 自动回退备选渠道（如邮件失败 → 站内信 + 短信降级）；
- 按通道隔离 worker 池：单一渠道供应商故障（如短信服务商挂掉）不影响 Push/邮件；
- 每供应商加**熔断器**：连续失败熔断，自动故障转移，无需人工干预。

### 3.5 可靠性与幂等
- **写前持久化**：通知先落库（PostgreSQL）再进队列——broker 崩溃不丢消息；
- **至少一次投递 + 强去重**：分布式外部供应商无法保证 exactly-once，目标为"至少一次 + 多层级幂等抑制重复"；
- 唯一消息 ID + Redis 去重键（处理前检查、处理后写入，TTL 约 24h）；
- 重试：指数退避；持久失败进**死信队列**人工/定时重发。

### 3.6 站内信存储与已读（推拉结合）
- **推**：用户在线 → 实时推送（WebSocket/长轮询）；
- **拉**：用户上线/刷新 → 按"已读最大 ID"增量拉取未读消息；
- 数据模型：消息表（单条消息）+ 用户消息状态表（用户维度已读 ID/状态）——**避免每用户复制全量消息**；
- 未读计数 = 用户已读最大 ID 之后的消息数；批量已读、分类过滤、撤回（24h 内可撤）。

### 3.7 广播与定向（队列路由）
- Fanout 交换机：系统广播（全员公告）；
- Topic 交换机：定向用户（`user.{userId}`）；
- 万人群/大广播：拉模式 + 订阅者分片处理，避免瞬间写放大。

## 四、通用设计方案（最优解）

### 4.1 总体架构（四层）
```
接入层：统一通知 API（REST + SDK）｜ 应用注册 ｜ 消息类型
   ↓（写前落库，再入队）
服务层：模板渲染 ｜ 渠道路由 ｜ 优先级队列 ｜ 频控（令牌桶）｜ 去重（Redis）｜ 偏好检查
   ↓（按通道独立队列）
通道层：渠道处理器（Provider）｜ 各通道 worker 池隔离 ｜ 熔断器 ｜ 重试/死信
   ↓
供应商：短信(阿里云/腾讯云)｜邮件(SMTP/云邮件)｜Push(APNs/FCM/厂商)｜站内信(自建)｜IM机器人(企微/钉钉/飞书)｜Webhook
   ↓
回执：送达状态 ｜ 已读状态 ｜ 统计报表 ｜ 成本核算
```

### 4.2 核心数据模型
```sql
-- 消息模板（业务类别 × 渠道）
message_template (id, biz_type, channel, title_tpl, content_tpl, params_json, status)
-- 消息实例（发送前先落库）
message_record (id, message_id(幂等键), biz_type, receiver, channel, content, priority,
                status(待发送/发送中/成功/失败/重试中/死信), retry_count, send_time)
-- 站内信（消息 + 用户状态分离，避免复制放大）
inbox_message (id, biz_type, title, content, link, expire_at, extra_json)
user_message_status (user_id, message_id, is_read, read_time)  -- 或：用户已读最大ID
-- 用户偏好
user_notify_pref (user_id, biz_type, channel, enabled, quiet_start, quiet_end)
-- 发送日志/回执
send_log (id, record_id, provider, provider_msg_id, status, raw_response, cost)
```

### 4.3 发送主流程
```
业务调用 send(biz_type, receivers, params)
  → 校验（应用/类型/接收人合法性）
  → 偏好检查（退订/免打扰 → 拦截）
  → 频控检查（P0 绕过；超限按优先级 排队/丢弃）
  → 模板渲染（按渠道选模板、填变量）
  → 落库 message_record（写前持久化）
  → 入队（按渠道独立队列 + 优先级）
  → 渠道处理器发送 → 更新状态 + 写回执
  → 失败：指数退避重试 → 死信队列
```

### 4.4 可靠性矩阵
| 风险 | 对策 |
| --- | --- |
| broker 崩溃丢消息 | 写前落库，消费后更新状态 |
| 重试重复发送 | 唯一 message_id + Redis 去重键 |
| 单渠道故障拖垮全局 | 通道独立 worker 池 + 熔断器 |
| 用户被轰炸 | 每用户/每渠道限频 + 全局限频 + 偏好 |
| 营销深夜打扰 | 时区感知 + 免打扰时段 |
| 历史追溯 | 全量 send_log + 状态机 |
| 超大面积广播 | Fanout + 拉模式分片，防止写放大 |

### 4.5 管理端能力
- 应用/消息类型管理、模板管理（含渠道差异化）、发送记录查询、失败重发、送达率/成本统计、用户偏好总览、渠道健康监控。

## 五、设计说明

### 5.1 核心设计原则
| 原则 | 说明 |
| --- | --- |
| 业务与技术分离 | 业务方只声明"类型+接收人+参数"，渠道/模板/频控由平台管 |
| 至少一次 + 强去重 | 分布式外部供应商不追求 exactly-once，用幂等抑制重复 |
| 写前持久化 | 先落库再入队，broker 崩溃不丢 |
| 通道隔离 | 单一渠道故障不影响其他渠道（隔离故障域） |
| 用户至上 | 偏好检查在入队前、退订即停、限频防打扰、时区感知 |
| 可观测可审计 | 全链路状态追踪、成本核算、记录可查 |

### 5.2 常见设计坑与规避
| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 无幂等键 | 重试产生重复通知，用户投诉 | 唯一 message_id + Redis 去重 |
| 通知逻辑散落在业务代码 | 改通知要改业务、风险高 | 统一通知 API，业务只声明类型 |
| 不检查偏好 | 骚扰已退订用户 | 入队前偏好检查 |
| 无频控 | 短信轰炸/通知疲劳 | 每用户每渠道限频 + 全局限频 |
| 单渠道队列共用 | 一渠道故障阻塞全部 | 通道独立 worker 池 + 熔断 |
| 失败即弃 | 关键通知丢失 | 指数退避重试 + 死信队列 |
| 每用户复制全量消息 | 存储爆炸 | 消息表 + 用户状态表分离（推拉结合） |
| 忽略时区 | 深夜营销被卸载 | 时区感知 + 免打扰时段 |
| 模板参数硬编码 | 每次发版改文案 | 模板管理 + 变量渲染 |

### 5.3 演进路线
```
阶段1 单渠道站内信：消息表 + 已读未读 + 广播
   ↓ 多渠道
阶段2 统一通知中心：多通道 + 模板管理 + 发送记录
   ↓ 规模化
阶段3 中台化：写前持久化 + 幂等 + 频控 + 熔断降级 + 优先级队列 + 成本核算
   ↓ 智能触达
阶段4 智能路由：按用户偏好/历史送达率/渠道成本动态选渠道，A/B 触达策略
```

### 5.4 业界参考实现
- **Novu / SuprSend**：开源多渠道通知基础设施（模板、偏好、webhook、React 通知中心组件）；
- **企业微信 IM**：已读回执、撤回（24h）、万人群、消息存储优化——站内信/IM 状态管理参考；
- **Halo NotificationCenter**：订阅、模板、多通道通知器、已读 API 设计；
- **西北工业大学消息平台**：统一消息发送管理（应用注册 → 消息类型 → 模板 → 对接）；
- **经典系统设计案例**：优先级路由（P0/P1/P2）、通道独立队列、Redis 幂等去重、指数退避 + 死信。
