# 开放世界叙事引擎 · 详细设计文档 v1.0

> 定位：把原《可行性评估：开放世界叙事引擎——AI角色自主模拟系统》中"多角色 Agent 自主模拟"的技术路线，替换为**规则引擎模拟世界 + LLM 选择性叙事**的低成本路线。
>
> 一句话原则：**世界不需要语言模型来运转，需要语言模型的只是把它讲出来。**

---

## 0. 设计原则（贯穿全文的硬约束）

| 编号 | 原则 | 含义 |
|---|---|---|
| P1 | 模拟与叙事分离 | 世界演化由确定性规则引擎完成，LLM 只负责把已发生的事写成文字 |
| P2 | 因果必须可寻址 | 任何"情感""恩怨""伏笔"都必须是结构化数据，能被查询、被加权、被回收 |
| P3 | LLM 只提工单，不改历史 | 审计层的输出只能影响**未来**的抽样权重，绝不能重写**已发生**的事件记录 |
| P4 | 状态即存档 | 不维护"真相文件"副本，结构化存档本身就是唯一事实来源 |
| P5 | 成本集中在叙事层 | 模拟层、选戏层零 LLM 调用，可无限次免费测试与调参 |
| P6 | 主线约束作用于世界层 | 强制推进主线时改变世界初始条件与事件池权重，绝不对角色下指令 |

---

## 1. 总体架构

```
┌──────────────────────────────────────────────────────────────────┐
│  L0 人机交互层                                                     │
│  角色卡编辑 │ 任务树调整 │ 剧情干预 │ 事件库管理 │ 读档回溯 │ 状态面板 │
└───────────────────────────────┬──────────────────────────────────┘
                                │
┌───────────────────────────────▼──────────────────────────────────┐
│  L1 世界模拟内核（纯代码，零 LLM 调用）                              │
│                                                                    │
│   角色卡 + 关系双轨（快值 / 情感墓碑）+ 事件模板库（300~1000 条）      │
│   → 过月结算：需求生成 → 对象选择 → 动作选择 → 掷骰 → 效果结算         │
│   → 产出：干编年史（chronicle，结构化事件流）                        │
│                                                                    │
│   主线事件注入器（RimWorld Storyteller 思路，作用于世界层）           │
└───────────────────────────────┬──────────────────────────────────┘
                                │ 每月数十~上百条干事件
┌───────────────────────────────▼──────────────────────────────────┐
│  L2 戏剧选戏器（纯代码 + 规则打分，零 LLM 调用）                      │
│   打分 → 每章取 Top 3~5 条进正文，其余入"世界大事记"（可查不写）        │
└───────────────────────────────┬──────────────────────────────────┘
                                │ 选中事件 + 角色卡切片 + 上章摘要
┌───────────────────────────────▼──────────────────────────────────┐
│  L3 叙事层（唯一的常态化 LLM 消费点，每章约 5~7 次调用）               │
│   章纲 → 分场景正文 → 章末摘要 →（可选）内心戏追问                     │
└───────────────────────────────┬──────────────────────────────────┘
                                │ 正文（不回写状态，只回写摘要索引）
┌───────────────────────────────▼──────────────────────────────────┐
│  L4 审计与回收层（LLM，限 P0 角色，过月后异步，不进正文链路）           │
│   产出 audit_ticket（结构化 diff）→ 规则闸门校验 → 应用到 L1 存档       │
└──────────────────────────────────────────────────────────────────┘

外围（一次性建设期）：
┌──────────────────────────────────────────────────────────────────┐
│  事件库建设流水线：小说语料 → LLM 拆章提取 → 归一化聚类 → 人工闸门      │
│                    → 事件模板库（持续扩充）                          │
└──────────────────────────────────────────────────────────────────┘
```

**关键数据流方向（与原方案的本质差异）：**

```
原方案：LLM 生成正文 → 事后抽取状态 → 审计抽取错误 → 误差静默累积污染
新方案：规则引擎模拟 → 结构化干事件流 → 选戏 → LLM 只写选中的 → 状态天然一致
```

原方案里"状态是正文的下游产物"，所以必须做抽取+审计+33维校验；新方案里"正文是状态的下游产物"，状态永远先于正文存在且由代码写入，一致性问题**从根上消失**，回溯也变成简单的读档重放。

**性格数值的消费方式（实现 P2）：**

```python
# need_type 权重 = 基础权重 × (1 + Σ 敏感度_i × (trait_i - 5) / 5)
NEED_WEIGHT_MODIFIERS = {
  "self_growth": {"curious": +0.8, "cautious": +0.3},
  "revenge":     {"vengeful": +1.5, "proud": +0.8, "loyal": +0.4},
  "family":      {"loyal": +1.2, "compassionate": +0.5},
  "romance":     {"loyal": +0.5, "impulsive": +0.4},
  "faction":     {"loyal": +0.9, "proud": +0.3},
  "conflict":    {"impulsive": +1.2, "vengeful": +0.8, "cautious": -0.9},
  "social":      {"curious": +0.5, "impulsive": +0.3, "greedy": +0.3},
  "survival":    {"cautious": +1.0, "greedy": +0.4},
  "health":      {"cautious": +0.6},
}
```

> 设计依据：鬼谷八荒的"内在性格 8 种 × 外在性格 12 种只影响行为抽样权重与好感修正"、太吾绘卷的"七元赋性决定奇遇判定与互动倾向""立场决定敌对行为权重 0~10"。均为查表加权，无任何自然语言推理。

### 2.2 关系双轨制：解决"跨年失忆"

| 轨道 | 字段 | 衰减 | 作用 |
|---|---|---|---|
| **快值** | `relations.*.fast_value` | 每年一月向 0 衰减（幅度随星级递增，-60~60 区间免疫） | 决定 relation_label、互动解锁门槛、日常好感修正 |
| **情感墓碑** | `imprints[]` | **不自动衰减**，只能被消解事件清除 | 持续给特定 need/行为加权重，是"三章前埋的仇今天爆发"的数据基础 |

**墓碑行为学规则：**

```python
# 1. 对 need 权重的放大
for imp in char.imprints if imp.status == "open":
    if imp.type in NEED_TRIGGER_MAP[need]:        # humiliation → revenge/conflict
        w *= 1 + 0.5 * imp.intensity

# 2. 对对象选择的偏置（revenge 类需求优先选墓碑对象）
if need == "revenge":
    candidate_weight[imp.target] *= 1 + 1.2 * imp.intensity

# 3. 容量上限：防止角色被历史压死
MAX_OPEN_IMPRINTS = 5
# 超出时，intensity 最低者降级为 faded（权重减半，不再参与对象偏置，
# 但仍保留在档案里供叙事层做回忆素材）
```

**消解（resolve）的唯一合法途径：**
1. 事件模板的 `effects.resolve_imprint` 字段命中（如"当众反制"模板消解 humiliation）；
2. L4 审计层提交 `imprint_resolve` 工单且通过规则闸门（须能引用 source_event 或人工确认）。

> 对照：鬼谷八荒只有单轨快值，故出现玩家吐槽的"跨年失忆"——仇恨数值衰减到 0 后 NPC 表现如无其事。CK3 的恩怨/谋划系统、RimWorld 的心情记忆系统本质都是双轨设计，这是行业已验证的解法。

### 2.3 事件模板 `events/templates/<id>.yaml`

```yaml
schema_version: 1
id: grudge_humiliation_public
title: 当众折辱
category: conflict                 # conflict/social/growth/romance/family/faction/treasure/info/disaster
domain_tags: [武侠, 仙侠, 都市, 古代]   # 用于按题材过滤
reusability: reusable              # reusable / one_shot（一次性剧情节点）
drama_base: 7                      # 选戏器基础分 1-10

roles:                             # 抽象角色位，不是具体人名
  - {slot: aggressor, require: "status > victim.status + 10"}
  - {slot: victim}
  - {slot: witnesses, count: ">=1", optional: true}

preconditions:                     # 条件门，全部满足才可入池
  - expr: "location.type == 'public'"
  - expr: "status_gap(aggressor, victim) > 0"
  - expr: "relation(aggressor, victim).fast_value < 60"
  - expr: "not aggressor.has_imprint(type='humiliation', target=victim)"
  - expr: "world.tick > act_1.start_tick"       # 阶段门

effects:
  relation_delta: {aggressor→victim: "-15..-40"}   # 区间掷骰
  imprint:
    on: victim
    type: humiliation
    intensity: "1..3 by (aggressor.status - victim.status) / 30"
    resolve_hint: "需一次当众反制或对方明确道歉"
  world: {location.heat: +1}                       # 地点"热度"，影响后续遭遇率
  resource: {victim.wealth: -5}

slots:                             # 参数化槽位：数量决定"有效多样性"
  - {name: 场合, pool: [药铺门前, 集市, 宗门广场, 酒楼, 拍卖会, 比武台]}
  - {name: 由头, pool: [争夺药材, 质疑出身, 拒婚, 旧怨重提, 无端挑衅, 比试落败]}
  - {name: 见证人身份, pool: [镇上熟人, 同门师兄弟, 陌生过客, 主角]}
  - {name: 结果分支, pool: [受害者忍下, 受害者反击失败, 第三方出面化解, 受害者当场离去]}

cooldown:
  same_template: 60                # 同模板对同一角色对的冷却月数
  same_category: 6                 # 同类事件冷却（防连续同型）
  global_repeat_penalty: true      # 近 N 月内已用过的模板，权重按次数指数衰减

requires_systems: [status, relation, location, resource]   # 人工闸门用：依赖的世界子系统
narrative_hint: "重点写围观者的反应与受害者的克制，避免直接写内心独白"
```

**规模与性能（回答"几百种会不会影响引擎"）：**

| 项 | 结论 |
|---|---|
| 结算复杂度 | 每 tick 对每角色做一次"条件过滤 + 加权抽样"，1000 条模板 × 200 角色 = 20 万次条件判断/月，纯 Python 也在百毫秒级；用 numpy 向量化或预建条件索引可再降一个量级 |
| 行业先例 | RimWorld 原版数百事件、创意工坊 mod 叠加数千条仍流畅；CK3 手写事件文件本就是数千条量级 |
| 真正的瓶颈 | **不是数量，是每条模板的元数据质量**（preconditions 是否可判定、slots 是否充分、cooldown 是否合理）。1000 条 sloppy 模板不如 300 条精细模板 |
| 有效多样性算术 | `感知变化数 ≈ 模板数 × 槽位组合 × 世界状态上下文`。300 条模板 × 平均 4 个槽位 × 不同人物/地点/数值背景 → 玩家（读者）感知的变化在数千种量级，再叠加叙事层的文字差异 |
| 建议规模路线 | 起步 300 条（覆盖 8 大 category）→ 扩到 800~1000 条 → 之后靠槽位扩充而非模板数扩充 |
| 理论上限参考 | 普罗普对民间故事的功能分析为 36 种；ATU 故事类型索引约 2000 类。人类叙事骨架本就是有限集，1000 条模板足够，缺的是组合与呈现 |

### 2.5 主线任务树 + 事件注入器

```yaml
# quest_tree.yaml
main_line:
  act_1:
    title: 风起青萍
    tick_range: [1, 36]
    key_events:                       # 目标状态，不是剧本
      - {id: k1, state: "主角已知晓自身异能", deadline_tick: 12}
      - {id: k2, state: "主角与林月结识", deadline_tick: 18}
      - {id: k3, state: "主角遭遇第一次追杀", deadline_tick: 30}
    must_reach_state: ["主角离开边陲小镇", "与黑衣门结仇"]
    injection:                        # 世界层强制推进（P6）
      - {for: k1, at_tick: 8, scope: world,
         template: awakening_anomaly, params: {location: 边陲小镇_后山}}
      - {for: k3, when: "progress >= 0.6 or tick >= 24",
         scope: world, template: faction_raid,
         params: {faction: 黑衣门, location: 边陲小镇}}
    escalation:                       # 注入后仍未达标时的升级阶梯
      - {after_ticks: 6, action: "提升黑衣门相关事件全局权重 ×1.5"}
      - {after_ticks: 12, action: "提升主角所在地点的遭遇率"}
      - {after_ticks: 18, action: "触发 world_crisis（黑衣门直接封锁小镇）"}
    hard_stop: false                  # 永不直接命令角色行动
    side_quests_unlocked: [sq_001, sq_002]
    next_act: act_2

side_quests:
  - id: sq_001
    title: 铁匠铺的秘密
    trigger: {type: location, value: 边陲小镇_铁匠铺,
              requires: ["relation(player, 王铁匠).fast_value > 30"]}
    plot_hook: 铁匠是隐居的前朝高手
    reward: 玄铁剑
    status: locked                    # locked/available/active/completed/failed/expired
    expire_condition: "tick > act_1.tick_range[1] + 12"
```

**P6 的实现要点：** 注入器只能做三件事——(a) 在世界里制造既成事实（反派打来了），(b) 调整事件池权重，(c) 调整地点热度/遭遇率。**绝不能给角色 Agent 下指令。** 这样 NPC 是在"已经变了的世界"里自发反应，避免"前一刻在逛街下一刻精准踩点"的出戏感。

### 2.6 伏笔表

```yaml
# hooks.yaml
- id: hk_007
  desc: 林月失散多年的哥哥
  planted_tick: 15
  planted_by: ev_0312
  type: character_secret
  resolve_condition: "存在事件使 lin_yue.knows 包含 '哥哥的下落'"
  expected_window: [80, 200]
  status: open                        # open / resolved / expired
  linked_imprints: [imp_0011]
  escalation: {overdue_ticks: 40, action: "提升 family/info 类事件权重并生成回收工单"}
```

> 伏笔遗忘问题在本架构里**不是概率性崩坏，而是可测试的 bug**：`status == open && tick > expected_window[1]` 就能被单元测试抓出来。

### 2.7 审计工单 diff schema（L4 的唯一输出形态）

```yaml
audit_ticket:
  schema_version: 1
  character: lin_yue
  tick: 137
  model_tier: mid                     # 中档模型即可
  proposals:
    - kind: imprint_promote           # 墓碑升级
      target: imp_0032
      change: {intensity: 2 → 3}
      reason: "近 20 月内 3 次触发回避 zhao_heng 的行为，说明创伤强度被低估"
      confidence: 0.82

    - kind: imprint_demote            # 墓碑降级
      target: imp_0019
      change: {intensity: 3 → 2}

    - kind: imprint_resolve           # 判定已实质消解
      target: imp_0004
      evidence_event: ev_2190         # 必须引用具体事件

    - kind: value_adjust              # 快值微调
      field: relations.zhang_wei.fast_value
      delta: -10
      reason: "ev_2288 中主角隐瞒伤情，符合信任受损"

    - kind: recovery_order            # ★ 回收工单（核心价值）
      imprint: imp_0032
      action: schedule_event
      event_tags: [conflict, 当众, 反制]
      preferred_roles: {aggressor: lin_yue, victim: zhao_heng}
      window: [140, 180]              # 期望触发月区间
      weight_boost: 2.5
      fallback: "窗口内未触发 → 转为叙事层内心独白素材，并把墓碑降级为 faded"

    - kind: hook_nudge                # 伏笔提示
      hook: hk_007
      suggestion: "提升 family 类事件在 lin_yue 上的权重 ×1.3"

  rejected_by_rules:                  # 被闸门拒绝的项，留档以便调参
    - {kind: value_adjust, delta: -200, reason: "超出单月累计上限 ±30"}
```

**规则闸门（代码实现，一票否决）：**

| 规则 | 阈值 |
|---|---|
| 单角色单 tick 最多应用条数 | 3 |
| `value_adjust` 单月累计绝对值 | ≤ 30 |
| `imprint_resolve` 必须携带 `evidence_event` 或人工确认标记 | 强制 |
| `recovery_order.window[0]` | ≥ current_tick + 3 |
| 任何提议修改 `tick < current_tick` 的记录 | 直接拒绝（P3） |
| `confidence` | < 0.6 丢弃 |
| 提议引入新 imprint 类型（不在枚举内） | 直接拒绝 |

> **为什么必须是"工单"而不是"事实"**：审计层本身也是 LLM，也会编造"情感逻辑"。工单形态意味着每条建议都可被规则拒绝，最坏结果是"某伏笔晚几章回收"，而不会污染状态。这是 P3 的工程落地。

## 3. L1 模拟内核算法

### 3.1 过月结算主循环

```python
def advance_month(world):
    world.tick += 1

    # 阶段 1：世界层（注入器、地点刷新、派系行动）
    apply_storyteller_injections(world)          # 主线强制推进，见 2.5
    refresh_locations_and_factions(world)
    apply_yearly_decay_if_january(world)          # 快值衰减（鬼谷式）

    # 阶段 2：角色层，按"重要性 + 本月活跃度"排序处理
    for char in sorted(world.characters, key=priority):
        if not is_active_this_tick(char, world):  # P2 背景 NPC 可跳过（降频结算）
            continue
        need    = sample_need(char)               # 3.2
        target  = sample_target(char, need, world)# 3.3
        tmpl    = sample_template(char, need, target, world)  # 3.4
        if tmpl is None:
            continue
        result  = resolve(tmpl, char, target, world)          # 3.5
        world.chronicle.append(result)

    # 阶段 3：后处理
    check_quest_progress(world)
    check_hook_expiry(world)
    enforce_imprint_capacity(world)               # MAX_OPEN_IMPRINTS
    snapshot_if_checkpoint(world)

    # 阶段 4：异步审计（仅 P0 角色，不阻塞）
    queue_audit_jobs([c for c in world.characters if c.tier == "P0"])
```

**降频结算（成本控制）**：P2 背景 NPC 不必每月结算，按 `1 / (1 + distance_to_player)` 的概率跳过，或每 3 月批量结算一次。太吾绘卷数千 NPC 能跑起来，靠的就是分级调度而非全量模拟。

### 3.2 需求生成

```python
def sample_need(char):
    weights = {}
    for need, mods in NEED_WEIGHT_MODIFIERS.items():
        w = NEED_BASE_WEIGHT[need]
        w *= 1 + sum(k * (char.traits[t] - 5) / 5 for t, k in mods.items())
        # 情感墓碑放大（P2 因果可寻址）
        for imp in open_imprints(char):
            if imp.type in IMPRINT_NEED_MAP[need]:
                w *= 1 + 0.5 * imp.intensity
        # 情境修正
        if char.hp < 40:  w *= 2.0 if need == "health" else 1
        if char.wealth < 20: w *= 1.6 if need == "survival" else 1
        weights[need] = max(w, 0.01)
    return weighted_choice(weights)
```

### 3.3 对象选择

```python
def sample_target(char, need, world):
    cands = visible_characters(char, world)        # 同地点 / 关系网内 / 已知晓
    w = {}
    for c in cands:
        base = 1.0
        base *= relation_modifier(char, c, need)   # 好感/敌对决定倾向
        if need == "revenge":
            for imp in open_imprints(char, type="humiliation|betrayal"):
                if imp.target == c.id:
                    base *= 1 + 1.2 * imp.intensity  # ★ 墓碑偏置
        if need == "family":
            base *= 3.0 if is_kin(char, c) else 1
        w[c.id] = base
    # 允许"陌生对象"（鬼谷：互动对象不一定来自关系网）
    w["__stranger__"] = 0.3 * len(cands)
    return weighted_choice(w)
```

### 3.4 模板选择（条件门 + 加权抽样 + 新鲜度控制）

```python
def sample_template(char, need, target, world):
    pool = [t for t in TEMPLATE_DB
            if t.category in NEED_CATEGORY_MAP[need]
            and all(eval_pre(p, char, target, world) for p in t.preconditions)
            and not in_cooldown(t, char, target, world)
            and t.domain_tags & world.genre_tags]

    if not pool: return None

    w = {}
    for t in pool:
        v = t.weight_base
        v *= imprint_boost(t, char)                    # 墓碑匹配的模板加权
        v *= repetition_penalty(t, char, world)        # 指数衰减，防套路
        v *= quest_relevance_boost(t, world)           # 与主线/支线相关者加权
        w[t.id] = v
    return weighted_choice(w)

def repetition_penalty(t, char, world):
    n = count_used(t.category, char, last_n_ticks=24)
    return 0.7 ** n            # 同类事件连用 3 次后权重降到 34%
```

### 3.5 效果结算

严格按模板 `effects` 执行；所有随机项用**带种子的 RNG**并记录 `rolls`，保证可复现、可回溯。结算后：
- 更新 `fast_value`、`imprints`、`knows`、`resource`、`location.heat`；
- 检查是否命中 `hooks[].resolve_condition`；
- 检查是否命中其他角色的 `imprint.resolve_hint`；
- 追加 chronicle 记录（含完整 slots 与 rolls）。

### 3.6 引擎不变量（写成单元测试）

```
INV-1  chronicle 只追加，永不改写
INV-2  任何 fast_value ∈ [-300, 300]
INV-3  任何角色 open imprints 数 ≤ MAX_OPEN_IMPRINTS
INV-4  imprint.status == resolved ⇒ 存在 evidence_event
INV-5  hook.status == open ⇒ tick ≤ expected_window[1] + overdue_grace
INV-6  同角色对的同模板事件间隔 ≥ cooldown.same_template
INV-7  act_N.must_reach_state 在 tick_range[1] 前必须全部达成
INV-8  给定 (存档, rng_seed) 重放必须逐 tick 完全一致
```

INV-8 是整个系统可调试性的基石——LLM 方案永远做不到这一点。

## 4. L2 戏剧选戏器

### 4.1 打分公式

```python
def drama_score(ev, world, chapter_plan):
    s = ev.template.drama_base                          # 模板基础分 1-10
    s += 2.0 * normalized_abs(ev.rolls.relation_delta)   # 关系变化幅度
    s += 3.0 if involves_P0(ev) else 0                   # 主线人物交叉
    s += 2.5 if touches_open_hook(ev) else 0             # 触碰未回收伏笔
    s += 2.0 if creates_or_resolves_imprint(ev) else 0   # 产生/消解墓碑
    s += 1.5 * novelty(ev, recent_selected)              # 与近期已选事件的类型差异
    s -= 2.0 if same_category_as_last(ev, chapter_plan) else 0
    s += 1.0 if ev.slots.见证人身份 == "主角" else 0        # 主角目击 → 可直接入戏
    s += pending_recovery_order_boost(ev, world)         # 审计工单指定的优先
    return s
```

### 4.2 每章配额与叙事弧

一章取 **3~5 条**，并按配比组合避免单调：

| 位置 | 功能 | 偏好 category |
|---|---|---|
| 开场 | 承接上章 / 建立场景 | social, info |
| 发展 | 推进关系或目标 | growth, family, romance |
| 转折 | 冲突或意外 | conflict, disaster |
| 收束 | 留钩子 | info（新信息）/ conflict（未解决） |

配比不满足时，从"世界大事记"里降分补位，或允许 L1 追加模拟 1~2 个 tick 直到出现合适事件（**引擎可以为了戏剧性多跑几个月，这是纯代码方案独有的自由**）。

### 4.3 落选事件

进 `world_log.md`（可查询的"世界大事记"），不写正文。这既是读者可查的世界厚度，也是叙事层需要时的素材池（"最近江湖上都在传……"）。

## 5. L3 叙事层

### 5.1 调用清单与预算（每章）

| # | 调用 | 输入 | 输出 | 必需 |
|---|---|---|---|---|
| 1 | 章纲编排 | 选中事件 + 上章摘要 | 场景切分与视角安排 | ✅ |
| 2~4 | 分场景正文 | 单场景事件 + 角色卡切片 + 文风样本 | 1200~2000 字正文 | ✅ |
| 5 | 章末摘要 | 本章正文 | 300 字摘要 + 关键事实抽取 | ✅ |
| 6~7 | 内心戏追问（可选） | 单角色卡 + 当前情境 | 100~200 字内心独白素材 | ⭕ 可开关 |

**每章 5~7 次调用**，其中正文生成可用中档模型，章纲与摘要可用轻量模型。

### 5.2 正文生成 prompt 结构

```
【你的任务】把下列"已经发生的事实"写成小说正文。你不负责决定发生什么，只负责讲好。

【本章场景】第 {n} 场 / 共 {m} 场
【时间地点】{tick} 年 {月} · {地点}（{地点描述}）
【已发生的事实】（不可更改，不可增删）
  - 事件：{template.title}
  - 参与者：{aggressor} 对 {victim}，见证人 {witnesses}
  - 具体情境：{slots 实例化结果}
  - 结果：{结果分支}
  - 数值后果（供你把握分寸，不要写进正文）：好感 {delta}，{victim} 留下强度 {intensity} 的屈辱感

【出场角色切片】
  {name}：{identity}，{status}，性格倾向（用行为体现，不要直述）：{traits 的自然语言映射}
  说话风格：{speech_style}
  绝对禁忌：{taboo}
  此刻情绪：{emotion}
  此刻目标：{current_goal}
  他知道：{knows}
  他不知道：{在场其他角色的 hidden_motivation 等}   ← ★ 信息不对称是戏剧性来源
  心里压着的事：{open imprints 的 narrative_seed}

【上章摘要】{chapter_summary}
【文风要求】{style_profile}
【视角】{POV 人物 / 全知}
【字数】{n} 字

【硬性约束】
1. 只写上述已发生事实，不得新增重大情节、不得让角色做出事实之外的决定
2. 不得违背角色 taboo
3. 角色只知道"他知道"列出的信息
4. 不要解释性旁白，用动作与对话呈现性格
```

**要点：`他知道 / 他不知道` 这对字段是叙事层最大的价值杠杆。** 规则引擎天然维护信息不对称（`knows` 列表），LLM 方案里这个信息极难保持一致。

### 5.3 视角与文风控制

- **视角**：默认单一 POV 人物（推荐主角或本章关系变化最大的角色），避免多 Agent 方案那种"视角割裂像跑团记录"的通病。
- **文风**：`style_profile.yaml` 存句长分布、禁用词表、禁用句式、参考片段。可从你喜欢的公版文本提取统计指纹。
- **去 AI 味**：维护疲劳词表（"刹那间""不由得""仿佛"等）+ 句式单调检测，作为章末摘要阶段的自检项。

### 5.4 一致性保障（为什么本方案几乎不需要审计正文）

正文不产生新事实 → 不存在"正文与状态矛盾"。唯一残留风险是 LLM 在描写时**擅自补充细节**（写了个不存在的丫鬟）。对策：
- 章末摘要阶段做一次轻量对账（正文里出现的专名是否在角色/地点/物品表中）；
- 允许 LLM 提议新增背景实体，但必须写入 `world_state.pending_entities`，由人工或规则闸门批准后才入库。

## 6. L4 审计与回收层

| 维度 | 设计 |
|---|---|
| 覆盖范围 | **仅 P0 角色**（主线 3~8 人）。P1 每 3 月一次，P2 不审计 |
| 触发时机 | 过月结算后**异步**执行，不阻塞模拟，不进正文生成链路 |
| 输入 | 该角色近 N 月压缩事件日志（每条一行）+ 现存 imprints 清单 + 当前关系快照。**不含正文全文** |
| 输出 | `audit_ticket`（2.7 的严格 schema） |
| 权限 | 只能提工单；工单必须过规则闸门；**永不改写历史** |
| 闭环 | `recovery_order` → 提升 L1 事件池中匹配模板的权重 → 后续 tick 自然触发 → 触发后消解墓碑 |
| 失败降级 | 工单连续 3 次被闸门全拒 → 该角色审计降频至每 6 月一次，并记录调参线索 |

**成本**：每 tick 每 P0 角色 1 次中档模型调用（输入约 2~4k tokens）。摊到每章（约 1~2 个 tick）≈ +1~2 次调用，占整体预算 <20%。

**审计层解决的具体问题：**
1. 墓碑强度标定偏差（引擎按公式给的 intensity 与叙事逻辑不符）；
2. 长期未消解的墓碑 / 伏笔（生成回收工单，避免"埋了不收"）；
3. 快值的语义漂移（数值变化与关系实质不匹配）；
4. 角色行为轨迹的"人设一致性"复核（相当于给 P0 角色配一个廉价的专职审稿人，替代原来每人一个 Agent 的昂贵方案）。

## 7. 事件库建设流水线

### 7.1 语料来源与版权边界

**硬边界：提取的是结构与功能，不是表达。** 这既是版权安全线，也是工程正确做法——照抄原文表达会让事件模板和原书的具体设定绑死，无法复用。

| 可用 | 说明 |
|---|---|
| 中国古典公版 | 《西游记》《水浒传》《三侠五义》《聊斋志异》《儿女英雄传》《儒林外史》等 |
| 民间故事 / 传说集 | ATU 类型索引体系成熟，天然适合结构提取 |
| 公版外国文学（含公版译本） | 大仲马、基督山伯爵式的恩怨结构极适合本引擎 |
| 你自有或已授权的文本 | 最佳来源 |
| ❌ 金庸、古龙等近现代作品 | **仍在版权保护期内**（作者身故后 50 年）。仅可作为"你个人阅读时的灵感来源"，不得进入自动提取流水线，产出物也不得分发 |

> 更正：本文档前一版讨论中曾把金庸、古龙列为"公版书"，这是错误的。古龙（1985 年逝世）作品约 2036 年进入公版，金庸（2018 年逝世）约 2069 年。

### 7.2 流水线

```
语料 → ① LLM 拆章提取（结构化事件实例）
     → ② 归一化聚类（相似实例合并为带槽位的抽象模板）
     → ③ 可表达性检查（requires_systems 是否已建）
     → ④ 人工闸门（筛除、改名、调 drama_base、补 slots）
     → ⑤ 入库 + 版本号
     → ⑥ 验证指标回归测试
```

**① 提取 prompt 见《事件模板提取-试跑报告》**（已实测迭代）。

**② 归一化**：按 `(category, roles 数量, effects 类型签名)` 分桶，桶内用 embedding 相似度聚类，簇心作为模板骨架，簇内差异转化为 `slots` 的 pool 取值。

**③ 可表达性检查（自动）**：模板 `requires_systems` 中若有当前引擎未实现的子系统（如"婚约""官职""族谱"），标记为 `blocked`，不入库。这是防止事件库膨胀但大部分无法触发的关键闸门。

**④ 人工闸门清单**：
- precondition 是否全部可用表达式判定（不能出现"两人气氛微妙"这种）；
- slots 是否 ≥ 3 个（不足则多样性贡献太低）；
- cooldown 是否合理；
- `narrative_hint` 是否给了叙事层可执行的指引；
- 是否与本世界题材冲突（domain_tags）。

**⑥ 验证指标：**

| 指标 | 定义 | 目标 |
|---|---|---|
| 事件重复率 | 100 年模拟中，同角色对触发同模板的比例 | < 5% |
| 新鲜度半衰期 | 读者（你）开始识别出套管所经过的 tick 数 | > 120 tick |
| category 覆盖均衡度 | 各 category 触发占比的基尼系数 | < 0.3 |
| 墓碑回收率 | open imprint 在 60 tick 内被 resolve 的比例 | > 60% |
| 伏笔回收率 | hook 在 expected_window 内 resolved 的比例 | > 80% |
| 主线达标率 | INV-7 通过率 | 100%（不达标说明注入器/升级阶梯要调） |

### 7.3 建设期成本

一次性投入。按拆 200 部书 × 每部 40 章 × 每章 1 次提取调用 ≈ 8000 次调用，可用最便宜的模型；产出 2000~4000 条候选实例，归一化后约 500~1200 条模板。**只在建设期发生，之后运行期零额外成本。**

## 8. 成本模型

### 8.1 调用量对比

| 方案 | 每章 LLM 调用 | 100 章总量 | 模拟层可离线测试 |

### 8.2 Token 量级（供你按实际单价换算）

| 项 | 每章 | 100 章 |
|---|---|---|
| 输入 tokens | 15k~25k | 1.5M~2.5M |
| 输出 tokens | 8k~12k | 0.8M~1.2M |

> 具体金额请用你所选模型的官网单价代入。数量级判断：正文用中档/轻量国产模型时，一部 30 万字长篇在**几十到一两百元**区间；原多 Agent 方案用强模型会到**四位数**。

### 8.3 降本开关

| 开关 | 效果 | 代价 |

| 章纲+摘要合并为一次调用 | 每章 -1 次 | 编排质量略降 |
| 提高选戏器阈值 | 每章少写一个场景 | 节奏变慢 |

| **S1** | **模拟内核骨架**：角色卡 + 双轨关系 + 过月结算 + 20~30 条手写模板 + chronicle 导出 | **0 元** | 跑 100 个 tick，导出的干编年史你自己读着"有戏"；INV-1~INV-8 全部单元测试通过 |
| **S2** | 主线注入器 + 升级阶梯 + 伏笔表 + 冷却/新鲜度控制 | 0 元 | 3 幕主线全部按时达标（INV-7）；事件重复率 <5%；伏笔回收率 >80% |
| **S3** | 选戏器 + 叙事层接入，产出第 1 章正文 | 少量 | 连续 5 章盲读，无视角割裂、无 OOC、无"跑团记录感"；专名对账 100% 通过 |
| **S4** | L4 审计层 + 回收工单闭环 | 少量 | 人工植入 10 个"该收未收"的墓碑，审计层在 3 tick 内为 ≥7 个生成有效回收工单 |
| **S5** | 事件库流水线（提取 → 归一化 → 闸门），扩到 300 条 | 一次性 | 6 项验证指标全部达标；模板从 30 → 300 后新鲜度半衰期显著延长 |
| **S6** | L0 交互层：读档回溯、干预、状态面板 | — | 改第 N 章一个设定后重放，得到自洽新世界线 |

**S1 是全局成败的预演，且完全免费。** 如果规则引擎产出的干编年史不好看，后面加多少 LLM 都救不回来——反之若干编年史已经有戏，叙事层只需要"不破坏"它。

## 10. 风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| **模板感** | 读者识别出套路 | ① 参数化槽位（≥3/模板）② 重复惩罚指数衰减 ③ 同类冷却 ④ 叙事层文字差异 ⑤ 库扩到 800~1000 条 ⑥ 用"新鲜度半衰期"指标持续监控 |
| **情感不连续** | 恩怨莫名其妙消失 | 双轨制（imprint 不衰减）+ L4 审计标定强度 + 回收工单闭环 |
| **事件库依赖供给** | 世界丰富度停滞 | 提取流水线一次投入长期复用；槽位扩充比新增模板更划算；L1 可"为戏剧性多跑几 tick" |
| **规则引擎产出平淡** | 干编年史没戏 | S1 就验证；调 drama_base、提高冲突类基础权重、加强主线注入时机 |
| **叙事层擅自加设定** | 出现不存在的实体 | 硬性约束 prompt + 章末专名对账 + pending_entities 闸门 |
| **审计层幻觉** | 编造情感逻辑 | 工单形态（只影响未来权重）+ 规则闸门一票否决 + 连续拒绝则降频 |
| **P2 NPC 世界显得空** | 背景人物是布景 | 分级降频结算 + world_log 世界大事记 + 叙事层可引用大事记做背景 |
| **主线与自然演化冲突** | 关键事件迟迟不发生 | 升级阶梯（世界层三级施压），永不下角色指令 |
| **版权** | 语料合规 | 严格公版 + 只提取结构不提取表达 + 近现代作品不入流水线 |

## 11. 与原方案差异对照

| 维度 | 原方案（多角色 Agent） | 本方案（规则引擎 + 选择性叙事） |
|---|---|---|
| 世界演化 | 每个角色一个 LLM Agent 逐轮决策 | 纯代码查表加权抽样，零 LLM |
| 状态来源 | 正文的下游产物（需抽取） | 正文的上游事实（代码直写） |
| 一致性 | 概率性崩坏，需 33 维审计补救 | 结构化不变量，可单元测试 |
| 情感连续性 | 靠 prompt 里的角色记忆 | 情感墓碑（imprint）显式建模 |
| 主线强制 | 给角色 Agent 塞指令 → 行为突变出戏 | 世界层注入 + 升级阶梯 → 角色自发反应 |
| 回溯 | 需重算后续所有自然语言状态 | 读档重放，确定性可复现 |
| 伏笔管理 | 靠 LLM 记住 | 结构化 hook + 过期检测（可测试） |
| 每章成本 | 20~50 次强模型调用 | 5~9 次调用，正文可用中档模型 |
| 调参迭代 | 每次都要付费全量生成 | L1/L2 免费跑一万次 |
| 文学质量出口 | 多 Agent 拼接，视角割裂 | 单一叙事层 + 单 POV，可控文风 |
| 差异化定位 | 与 InkOS 等已有系统高度重叠 | "游戏化任务树 + 规则世界模拟"作为叙事骨架，是现有工具未覆盖的层 |

## 附录 B：术语表

| 术语 | 含义 |
|---|---|
| tick | 一个模拟回合，默认 = 1 个月（对齐鬼谷八荒"过月"、太吾绘卷"月份更替"） |
| 干编年史 (chronicle) | L1 产出的结构化事件流，无自然语言修饰 |
| 干事件 | 编年史中的一条记录 |
| 情感墓碑 (imprint) | 不自动衰减的情感事件记录，是长期因果的数据载体 |
| 快值 (fast_value) | 会衰减的关系数值 |
| 选戏器 (casting) | L2 打分器，决定哪些干事件进入正文 |
| 事件注入器 (storyteller) | 主线推进装置，作用于世界层（借名 RimWorld AI Storyteller） |
| 回收工单 (recovery_order) | L4 产出、影响未来事件权重的结构化建议 |
| P0/P1/P2 | 角色重要性分级，决定结算频率与是否享审计 |
| 槽位 (slots) | 事件模板的参数化位置，是"有效多样性"的主要来源 |
