# 信息系统原型设计的上下文治理方案

> 针对 vibepm-dev-agent v1.7 的两个实测痛点：bug 修复污染设计上下文、大系统跨端失忆
> 编制日期：2026-09-05

---

## 一、问题诊断（定位到现有文件）

### 问题 1：bug 修复污染原型设计上下文

现有工程包的相关约定：

| 位置 | 现状 | 问题 |
| --- | --- | --- |
| `.agents/skills/feature-dev/SKILL.md:216` | 步骤 4 明确「主线程直接写，不用 Agent（避免重复加载上下文的开销）」 | 生成与修复共用同一上下文 |
| `.agents/skills/feature-dev/SKILL.md:372` | 步骤 6.3「page-reviewer 有 ❌ → 立即修复」 | 修复动作在主线程，且**立即**执行 |
| `.agents/knowledge/conventions/debugging.md` | 四阶段流程完备（根因→模式→假设→实现） | 但每个阶段的产物（完整堆栈、边界证据、被否决的假设、回滚记录）**没有外置出口**，只能写在对话里 |
| `.agents/rules/agent-runtime.md:41` | 降级表「只读子 Agent」一行：需 Bash/写文件则改扮演 | bug 修复必然需要写文件 → 按现有规则**必然回落主会话** |

**根因三条：**

1. **未区分「生成任务」与「修复任务」的上下文属性**。生成任务是长程累积的（设计意图必须一路保留），修复任务是短程现场性的（错误堆栈用完即弃）。现有流程把两者塞进同一条会话流。
2. **调试中间产物没有文件出口**。`debugging.md:44-52` 要求「读完整堆栈」「在边界处记录进入数据、退出数据」「列出所有差异，不要假设这个不重要」——这些要求本身正确，但没规定写到哪里，于是全部灌进上下文。
3. **批量生成期间缺少 bug 缓办机制**。步骤 6.3 是「立即修复」，所以每生成一个页面都可能插入一轮完整调试，设计上下文被反复打断、反复稀释。

### 问题 2：大系统跨端失忆

现有真源体系：

| 位置 | 承载内容 | 视角 |
| --- | --- | --- |
| `AGENTS.md:288` 铁律「规格先行」 | SRS 为研发唯一真源 | — |
| `templates/docs-structure.md:13` | SRS 最低要求：3.1 总体功能架构、3.3 页面功能清单、3.5 功能详细设计、6.1 数据字典 | **页面视角** |
| `.agents/skills/feature-dev/SKILL.md:85-109` | 步骤 1 按 3.1→3.3→3.5→6.1 顺序读取 | **页面视角** |
| `hld-design` / `lld-design` 技能 | 系统架构、模块划分、表结构、API | **技术视角** |
| `templates/README-DEV.template.md` | 每个子项目一份实现规范（路由、Mock、布局） | **单端视角** |
| `.agents/rules/compaction-recovery.md` | 全文 9 行：查 TaskList、查文件状态、确认下一步 | **仅进度** |
| `.agents/hooks/pre-compact.cjs` | 只快照「已编辑文件」+「code-reviewer 是否调用」 | **仅文件** |

**根因五条：**

1. **缺一层「端无关的业务运行模型」**。SRS 是页面视角（3.3 按页面列清单、3.5 按页面组织详设），HLD/LLD 是技术视角（架构、表、接口）。中间那层「这个系统实际怎么跑」——单据怎么流转、状态机有哪些跃迁、admin 与 mobile 各自在流程里扮演什么角色、哪个模块生产数据哪个消费——**没有任何文件承载**。`diagram-generator` 技能能画流程图，但产物只是文档插图，不是可被按需加载的真源。

2. **SRS 的按需读取策略天然割裂跨端逻辑**。`SKILL.md:93` 要求「找到目标功能对应的所有行」——做 admin 交易列表时读的是 admin 那几行，做 mobile 交易详情时读的是 mobile 那几行。**两次读取之间没有共同上下文交集**，跨端流程一致性无人守护。

3. **恢复协议太薄，且不含业务层**。`compaction-recovery.md` 只恢复「任务进度」和「文件状态」。压缩后模型知道「我做到第 5 个功能了」，但不知道「交易单有 6 个状态、mobile 端只能操作其中 2 个」。

4. **README-DEV.md 按子项目分份，加剧割裂**。`docs-structure.md:24` 只建议在 SRS 菜单 3.1 标注端别（`admin（PC 后台）> 用户管理`），这是**导航标注**而非**职责边界定义**。admin 与 mobile 各有一份 README-DEV.md，两份文件之间没有任何交叉引用。

5. **delivery-plan 排序策略放大了失忆窗口**。`SKILL.md:405-409` 步骤 7 的推荐规则是「优先当前层级 → 同层按 ID 最小」，**纯依赖驱动，不考虑端别**。结果很可能是 admin 的 20 个功能全做完再开始 mobile 的 20 个，同一模块的两端任务之间隔了几十万 token。

## 二、解决架构

两条主线，都遵循工程包已有的「规范外置」铁律（`AGENTS.md:290`：规范存于 `.agents/knowledge/`，执行前按需读取，不靠记忆）——把它从**规范外置**扩展到**业务模型与会话状态外置**。

```
┌─────────────────────────────────────────────────────────────┐
│  主会话（设计上下文 · 长程累积 · 只保留意图与决策）          │
│                                                             │
│  feature-dev 步骤 1-5 生成 ──► 步骤 6 审查 ──► 步骤 7 收口  │
│         │                          │                        │
│         │ 读                       │ 发现 bug               │
│         ▼                          ▼                        │
│  ┌──────────────┐          ┌───────────────┐                │
│  │ 外置真源层   │          │ 隔离执行层    │                │
│  │（主线二）    │          │（主线一）     │                │
│  ├──────────────┤          ├───────────────┤                │
│  │ CURRENT.md   │          │ fixer 子Agent │                │
│  │ system-model │          │ 白名单约束    │                │
│  │ 模块卡片     │          │ 三行结论回灌  │                │
│  │ SRS 相关章节 │          │ 调试记录外置  │                │
│  │ README-DEV   │          │ BUG-BACKLOG   │                │
│  └──────────────┘          └───────────────┘                │
│         ▲                                                   │
│         │ 收口写回                                          │
│  consistency-reviewer（跨端一致性守卫）                     │
└─────────────────────────────────────────────────────────────┘
```

## 三、主线一：Bug 修复的上下文隔离

### 3.1 任务分类与派发策略

新增 `.agents/rules/context-partition.md`：

| 任务类型 | 上下文属性 | 执行位置 | 回灌内容 |
| --- | --- | --- | --- |
| 生成类（feature-dev 步骤 1-5、frontend-design） | 长程累积，须保留设计意图 | 主会话 | — |
| 审查类（page-reviewer、code-reviewer） | 短程，结论导向 | 独立派发（现有机制） | 结构化发现清单 |
| **修复类（新增 `fixer` 角色）** | **短程，现场导向，用完即弃** | **强制独立派发** | **仅三行结论** |
| 阻断性修复（build 失败、白屏、路由不可达） | 短程 | 独立派发 | 仅三行结论 |

`fixer` 回灌格式硬约束（写入 `.agents/agents/fixer.md`）：

```
BUG-{编号} 修复结论
根因：{一句话，指明 文件:行号 与错误机制}
改动：{文件路径列表，每文件一行说明改了什么}
证据：{复现命令 → 修复前输出 → 修复后输出}
状态：DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED
```

**禁止回灌**：完整堆栈、失败假设、试错过程、中间 diff、依赖树、`git log`。这些留在子 Agent 上下文里，随任务结束一起丢弃。

### 3.2 无独立派发能力时的降级：调试外置

现有 `agent-runtime.md:41` 的降级路径会让 bug 修复必然回落主会话。新增降级规则（补进 `agent-runtime.md` 降级表）：

主会话扮演 `fixer` 时，调试中间产物**必须写入文件而非对话**：

- 路径：`docs/99-调试记录/BUG-{编号}.md`
- 结构：错误现场（完整堆栈）→ 复现步骤 → 边界证据 → 假设清单（含被否决的及否决理由）→ 最终根因 → 改动 → 验证
- 对话里只输出 §3.1 的三行结论 + 一句「完整调试记录见 {路径}」

这样即使在同一会话，污染也被限制在「写文件」这一个动作里；「读文件」只在确有需要时发生，且读的是结论段而非全过程。

### 3.3 修复防火墙

写入 `fixer` 派发 prompt 的强制约束（扩展 `spawn-subagent.md` Prompt 结构要求第 5 条「约束条件」）：

1. **改动白名单**：prompt 里列出允许修改的文件；白名单外一律不得改动。确需改动 → 返回 `BLOCKED` 并说明理由，由主会话决策。
2. **禁止顺手改进**：只修根因。`debugging.md:69` 已有「不做顺手改进」但缺强制力，现在由白名单兜住。
3. **禁止改配置**：把 `config-protection` hook 的覆盖范围扩到 `fixer`（不得改 eslint / tsconfig / vite.config 来消除报错）。
4. **临时 hack 必须标注**：无法根治时的绕行方案统一标 `// FIXME(BUG-{编号}):`，并登记进 BUG-BACKLOG，收口时清理。
5. **三次失败即上报**：`debugging.md:78` 的三次失败规则触发后，`fixer` 必须返回 `BLOCKED`，禁止在主会话继续尝试第 4 次。

### 3.4 Bug 缓办与修复窗口

修改 `.agents/skills/feature-dev/SKILL.md` 步骤 6.3，引入分级：

| 级别 | 判定 | 处理 |
| --- | --- | --- |
| **P0 阻断** | build / type-check 失败、页面白屏、路由不可达、数据完全错乱 | 立即派发 `fixer`，修完继续 |
| **P1 功能缺陷** | 某子功能不工作、校验失效、Mock 数据异常 | **登记不修** → `docs/99-调试记录/BUG-BACKLOG.md`，继续下一个功能 |
| **P2 体验/规范** | 样式偏差、文案、非阻断 lint 警告 | 登记不修 |

**修复窗口**：一轮批量生成结束（步骤 7 无可继续功能，或用户暂停）后，统一开窗口，按 P1 → P2 顺序集中派发 `fixer`。

理由：批量生成期间的设计上下文是最贵的资产，为一个非阻断 bug 打断它，代价远高于稍后集中修复。且集中修复时同类 bug 往往能一次性找到共同根因——`debugging.md:84`「每次修复揭示新的共享状态/耦合问题」正是这种信号，分散修会一直误判为独立 bug。

BUG-BACKLOG.md 格式：

```markdown
| 编号 | 级别 | 模块/端别 | 症状（一句话） | 登记时间 | 状态 |
| --- | --- | --- | --- | --- | --- |
| BUG-012 | P1 | 交易管理/admin | 导出 CSV 中文乱码 | 2026-09-05 | 待修 |
```

### 4.1 Token 预算表（前置约束，最重要）

外置真源一旦膨胀，就会变成第二个失忆源。所以先定预算，再谈结构：

| 文件 | 行数上限 | 加载策略 | 超限处理 |
| --- | --- | --- | --- |
| `docs/00-工作状态/CURRENT.md` | 60 | **每次任务开始必读，全量** | 精简，不允许超 |
| `docs/02-业务模型/INDEX.md` | 80 | 每次必读，全量 | 精简 |
| `docs/02-业务模型/system-model.md` | 600 | 每次必读，全量 | **强制按域拆分** |
| `docs/02-业务模型/system-model-{域}.md` | 400 / 份 | 按当前模块所属域加载 | 再拆子域 |
| `docs/03-模块上下文/{模块}-{端别}.md` | 120 / 张 | 按需，**同时最多 3 张** | 精简 |
| `{PROJECT_PATH}/README-DEV.md` | 200 | 每次必读（现有 page-spec-loader 已加载） | 精简 |
| SRS | 无上限 | **只读相关章节**（现有行为不变） | — |

每次任务实际常驻加载量 ≈ `60 + 80 + 600 + 120×2 + 200 ≈ 1180 行`，可承受。

## 七、两个反模式警告

**1. 不要把 system-model 写成第二份 SRS。**

system-model 记「系统怎么跑」（流程、状态机、端别边界、跨模块依赖），SRS 记「页面要什么」（字段、控件、校验、文案、提示语）。同一信息出现两处 = 必然失同步，失同步比缺失更糟。

判断标准一句话：**这条信息改动之后，需要同时改两个端吗？** 需要 → system-model；不需要 → SRS。

**2. 不要指望「更大的上下文窗口」或「更频繁的总结」解决失忆。**

总结是有损压缩，每做一次就丢掉一部分业务细节，多轮总结后必然失真——这正是你遇到的「流程图、逻辑全忘记」的成因之一。正确方向是**外置 + 按需精确加载**：真源永远在文件里，上下文只承载当前任务需要的那一小片，且每次都能从文件重新拉取无损版本。

这也是工程包 `AGENTS.md:290`「规范外置，执行前按需读取，不靠记忆」铁律的自然延伸——现在只是把「规范」的范围扩展到「业务模型」与「会话状态」。这条铁律本身是对的，只是原先覆盖得不够。
