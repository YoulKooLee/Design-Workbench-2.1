# 方案：框架接入推演引擎（让七支柱从"能查"变"驱动"）

## 零、为什么现在做这个

阶段 1 交付了框架层：`story_pillars`（7 支柱）+ `world_reveal_layers`（4 揭示层）建表、4 个接口、前端页，端到端能查（我起 TestClient 实测 GET /framework 返回 7 支柱 4 层）。

**但 framework / pillar / current_pillar / reveal_query 目前只活在 `framework_service.py`，engine 和 orchestration 都没消费它。** 我 grep 过整个 `services/`，除了 framework_service 自己，没有任何推演或编排代码引用 pillar。

这意味着：用户精心配了七支柱，推演时引擎**根本不看**。这正是我之前诊断 `main_quest` 的"装饰品"毛病——建了、存了、能查了，但不驱动任何决策。框架不接入推演，阶段 1 就只是半张皮。

本方案解决"接入推演"这一步。编排层消费框架（回填 ep_from/ep_to、支柱配额提示）留到阶段 2 之后，不在本方案。

---

## 一、核心设计：照 main_quest 的先例，经 ProjectSnapshot 注入

### 1.1 为什么不能直接调 framework_service

`framework_service.current_pillar(db, day)` 要查数据库。但推演引擎是**纯函数**——`datatypes.py` 开头写明"引擎只认这些 dataclass，不认 ORM 对象"，`simulate_fast_forward(project: ProjectSnapshot, ...)` 收的是 snapshot 不是 session。这是可复现性（`roll(seq,salt,tag)` 同输入同输出）的地基，不能破。

所以框架数据必须**在 runner 层读好、塞进 snapshot**，engine 只读 snapshot。

### 1.2 现成的先例：main_quest

`ProjectSnapshot`（datatypes.py:173）已经有 `main_quest: MainQuestView | None` 字段。`load_snapshot`（simulation_runner.py:272）在 runner 层用 ORM 读出来填进去，engine 里 `chance_for(template, character, quest, unit)` 只读 `quest` 不碰 db。

**框架接入完全照抄这个模式**，不发明新机制。

## 二、五处改动（按依赖顺序）

### 改动 1：datatypes.py 新增 PillarView + ProjectSnapshot 加字段

```python
@dataclass(frozen=True)
class PillarView:
    """七支柱的推演读视图。engine 只认这个，不认 ORM 的 StoryPillar。"""
    seq: int
    name: str = ''
    act: str = ''
    weight: float = 0.0
    day_from: int | None = None
    day_to: int | None = None
    reveal_layers: tuple[int, ...] = ()   # 本支柱允许揭示的世界观层号
```

`ProjectSnapshot` 加一个字段（照 main_quest 的样子）：

```python
    main_quest: MainQuestView | None = None
    pillars: list[PillarView] = field(default_factory=list)   # 新增；空=项目没配框架
```

**空列表是合法的默认值**——老项目、没配框架天数的项目，pillars 为空，后续所有框架逻辑自动跳过，退回纯性格+尺度抽签。这保证向后兼容，不会让旧路径崩。

### 改动 2：抽一个共享纯函数 resolve_pillar_seq（消除双份逻辑）

现在 `framework_service.current_pillar(db, day)`（:327）的判定逻辑是：先看支柱有没有 day_from/day_to，有就按区间命中；没有就按 weight 累积摊。engine 也要算"当前第几支柱"，但不能碰 db。

**两处逻辑必须一致，否则框架页显示的支柱和推演实际用的支柱会漂移。** 做法：把核心判定抽成纯函数，两边共用。

放 `datatypes.py`（或新建 `framework_core.py`，你定）：

```python
def resolve_pillar_seq(pillars: list[PillarView], day: int) -> int | None:
    """第 day 天落在第几支柱。纯函数，framework_service 与 engine 共用。

    判法与 framework_service.current_pillar 一致：
      1. 有支柱填了 day_from/day_to 且 day 落在区间内 -> 该支柱（精确）
      2. 否则按 weight 累积摊（total = 最大 day_to）
      3. 都判不出 -> None（框架没落到天数上）
    """
    if not pillars:
        return None
    for p in pillars:
        if p.day_from is not None and p.day_to is not None and p.day_from <= day <= p.day_to:
            return p.seq
    total = max((p.day_to or 0) for p in pillars)
    if total <= 0:
        return None
    cursor = 0.0
    for p in sorted(pillars, key=lambda x: x.seq):
        cursor += p.weight
        if day <= total * cursor:
            return p.seq
    return sorted(pillars, key=lambda x: x.seq)[-1].seq
```

然后 `framework_service.current_pillar` 改为：`effective_pillars(db)` 的结果转成 `list[PillarView]` 后调 `resolve_pillar_seq`——**删掉它自己那份重复的区间/weight 判定**，避免两处漂移。engine 也调同一个函数。

### 改动 3：pools.py 给 EventTemplate 加 pillar_fit 字段

```python
    # 适配的剧情支柱（1~7）；空 = 不限，任何支柱都能出（日常琐事默认空）
    pillar_fit: list[int] = field(default_factory=list)
```

**标注策略（关键，决定工作量）**：不是 45 条全标。

| 尺度 | 是否标 pillar_fit | 理由 |
|---|---|---|
| year（12 条）| **必标** | 时代级大事件最该受叙事阶段牵引（突破境界该在中段、宗门被灭该在转折点） |
| epoch（5 条）| **必标** | 纪元级事件更是支柱专属（天地异变=终极考验） |
| month（9 条）| 选标 | 阶段级事件按需标，日常型留空 |
| day（19 条）| **留空** | 日常琐事是血肉，任何支柱都该有，标了反而束缚 |

空 pillar_fit = 不限 = 按原概率走，不抬升不排除。**只有 year/epoch（17 条）需要逐条标，工作量可控。**

### 改动 4：engine.py 主循环算当前支柱 + chance_for 加抬升

**4a 主循环**（engine.py:745-790 那个 `for slice_index` 循环里）：

```python
        at = truncate_to_unit(...)
        today = day_of(at)
        current_pillar = resolve_pillar_seq(project.pillars, today)   # 新增，纯函数
```

把 `current_pillar` 往下传给 `pick_template_for`。

**4b chance_for 加参数**（engine.py:516，现签名 `(template, character, quest, unit)`）：

改成 `(template, character, quest, unit, current_pillar=None)`。在算完 base、主线加成之后，加**框架适配抬升**：

```python
    base = (trait or BASE_CHANCE) * weight_of(template, unit)
    base = min(1.0, max(0.05, base))
    hits = mainline_hits(template, quest)
    p = base + (1 - base) * min(1, hits * MAINLINE_PULL) if hits else base
    # 框架适配抬升：与主线加成【取较大者，不叠加】（避免两个抬升相乘失控，沿用 V1.1 §6.2 结论）
    if current_pillar is not None and current_pillar in template.pillar_fit:
        p_pillar = base + (1 - base) * PILLAR_PULL
        p = max(p, p_pillar)
    return p
```

- `PILLAR_PULL` 新常量，建议 0.25（比主线 MAINLINE_PULL 弱一点，框架是"倾向"不是"命令"）
- **加法抬升不是乘法**：沿用 CodeBuddy R1 的结论和 V1.1 §6.2 的修订——四连乘会失控压穿 0.05 下限导致回退。这里绝不重蹈覆辙
- **与主线加成取 max 不叠加**：一个事件若既踩主线又适配支柱，抬一次够了，叠两次概率爆表
- `current_pillar is None`（框架没配天数）→ 抬升不生效，退回原 chance_for 行为

**4c 是否用 pillar_fit 做硬门控？—— 默认不，留开关**

硬门控（pillar_fit 不含当前支柱就排除模板）风险大：某支柱下符合条件的模板太少 → pass_gates 抽空 → 又触发全池回退 → 刚修好的 day 塌方换个形式复发。

所以 **MVP 只做软抬升，不做硬排除**。但给"终极考验""关键反转"这类强专属事件留一个可选硬门控字段（如 `pillar_only: bool`，默认 False），个别模板需要"只能在支柱6出现"时才打开。这个你评估要不要 MVP 就做，还是留到阶段3。

### 改动 5：load_snapshot 填充 pillars

`simulation_runner.py:272` 的 `load_snapshot`，构造 ProjectSnapshot 时加：

```python
    from app.services import framework_service
    pillar_dicts = framework_service.effective_pillars(session)
    pillars = [
        PillarView(seq=p['seq'], name=p['name'], act=p['act'], weight=p['weight'],
                   day_from=p['day_from'], day_to=p['day_to'],
                   reveal_layers=tuple(p['reveal_layers']))
        for p in pillar_dicts
    ]
    return ProjectSnapshot(..., pillars=pillars)
```

注意：`effective_pillars` 内部会 `ensure_seeds`（幂等灌种子），load_snapshot 在推演前调它，种子会在首次推演时灌好。这条路径要测（见 INV-15）。

## 三、数据流全景（改后）

```
framework_service.effective_pillars(db)   [ORM 层，runner 调]
        │  转成 list[PillarView]
        ▼
ProjectSnapshot.pillars                    [纯数据，随 snapshot 传入]
        │
        ▼
simulate_fast_forward 主循环:
   today = day_of(at)
   current_pillar = resolve_pillar_seq(snapshot.pillars, today)   [纯函数]
        │
        ▼
pick_template_for(..., current_pillar) → chance_for(tpl, char, quest, unit, current_pillar)
        │
        ▼
   适配当前支柱的 year/epoch 模板概率被抬升（加法，与主线取 max）
        │
        ▼
   同一天数、不同支柱 → 抽出的大事件类型不同（框架开始驱动剧情）
```

engine 全程不碰 db，可复现性不破；框架没配时 pillars 空 → 全链路退回原行为。

## 五、给你评估的问题

1. **resolve_pillar_seq 放哪**：datatypes.py（和 PillarView 一起）还是新建 framework_core.py？我倾向前者，少一个文件。
2. **PILLAR_PULL 取值**：我建议 0.25（弱于主线）。你有没有更好的初值？这个数会直接影响框架的"牵引力度"，太弱等于没接，太强会压过性格驱动。
3. **pillar_only 硬门控**：MVP 就做，还是留到阶段3？我倾向留到阶段3——先验证软抬升够不够，不够再加硬门控，避免一上来就把池抽空触发回退。
4. **pillar_fit 标注谁来做**：year/epoch 17 条的支柱适配，是你按题材判断直接标，还是我先给一份建议标注表你审？我倾向你先标一版（你熟这套世界观），我复核合理性。
