## 四、C2 多走向（event_outcomes）

### 4.1 表（采纳豆包 §4.3，两处改名）

```
event_outcomes（项目库，新表）
  id            String(36) PK
  template_id   String(64) FK→event_templates(id) ON DELETE CASCADE
  order_no      Integer        -- 判定顺序，升序第一个命中即选
  cond_expr     Text NULL      -- 条件 DSL；NULL=无条件兜底走向
  outcome_summary Text NOT NULL -- ★改名点1：豆包原名 result_text，
                                 --   4a 已裁决=素材事实句非正文，改名钉死语义
  prob          Float NULL     -- 条件全不中时的兜底权重
  effects_json  Text NOT NULL DEFAULT '{}' -- ★改名点2：豆包 effects，
                                 --   统一 JSON 列 _json 后缀惯例
  UNIQUE(template_id, order_no)
```

约束（写进验收）：每模板**至多一条 `cond_expr IS NULL`** 且必须 `order_no` 最大（兜底在最后）；`effects_json` 的键只允许 §4.3 白名单；**内置 57 条本批灌 0 条 outcomes**（内容属 D 批，空表短路照跑）。

### 4.2 条件 DSL（安全解析器，非 eval）
- 语法：`<路径> <运算符> <值>`，AND/OR 组合**限 3 层**；运算符 `>= > == != < <= in has not_has`。
- 路径白名单（解析器只认这些前缀，**未知路径=解析错误、入库/启动即失败，不许静默 false**）：
  `a.<attr>` / `b.<attr>`（attr ∈ 角色状态账本既有字段：realm/health/emotional/trait/bag 等，以 `datatypes.py` 状态视图实际字段为准，实现前 CodeBuddy 列清单回报，见 §十二 Q2）；
  `b.relation(a)`（→ `RelationView.affinity`，唯一关系维度，见 §二.5）；
  `world.<stmt_type>.<target_id>`（→ world_states 表，§五）；
  `count.<event_type>.<days>`（近 N 天同类事件计数）。
- 解析器手写字法（tokenizer + 递归下降，3 层嵌套不需要第三方库）；**禁止 eval / ast.literal_eval / 动态 getattr 拼接**。
- 判定流程照豆包 §6.2：order_no 升序首个命中即选（纯函数、确定性）；全不中→按 prob 加权 `roll(seq, salt, 'outcome:'+template_id+order)`；同输入必同走向可回放。

### 4.3 effects 结算（纯函数，本批**不接引擎主循环**）
键白名单照豆包 §6.3 但砍掉没有落点的项：`status_delta` / `relation_delta`（单维 affinity ±N）/ `props`+`bag` / `plant_foreshadowing` / `pending`。**`know_facts` 本批不做**（角色信息集字段全库不存在——CodeBuddy 核查第 5 条已证实 `know_facts/knowsAbout` 0 命中，V13 走的是 GoalConflict 潜伏态；信息集真身排 E 批）。
结算器写成**可单测纯函数** `apply_outcome_effects(effects, ledger) -> ledger'`；接进推演 STEP4 = D 批与内容一起做（那时才有真走向可结算）。C 批的抽卡路径只把走向结构+cond 展示给 writer 选，不结算。

### 4.4 走向参数绑账本（缺口 2 的正解）
writer 选走向**不是自选数值**：抽卡返回的每个候选附带「可选项 = cond 已求值为真的走向 + 兜底走向」列表（用与约束包同一份账本求值），writer 只能从这个列表里挑——**代码算值域、LLM 选其一**，这就是"参数必须绑账本"的实现形式。挑了列表外的值 → 校验失败打回（hard，同 B 批 forbidden 口径）。

## 六、C4 抽卡台账与冷却粒度

### 6.1 台账表

```
draw_ledger（项目库，新表）
  id / beat_id(FK EpisodeBeat SET NULL) / template_id / outcome_order_no(NULL=未选走向)
  cast_json(当次角色组合) / day / ts
```

每次抽卡返回 K=3 候选**不记账**，**writer 选定后记一行**（防"抽了不用"污染统计）。

### 6.2 衰减公式（缺口 4 的裁决）
> 同套路换角色算不算重复？——**算，但减半**。

排序权重 = `drama_base` × 衰减：
- 该 template **同角色组**（cast 集合相等）近 30 个台账条目内用过 → ×0.3；
- 该 template **不同角色组**用过 → ×0.6；
- 没在窗口内用过 → ×1.0。

窗口参数（30 条）落 `Project.settings_json` 键 `draw_ledger_window`，可调 0~100（0=关台账）。
**边界澄清**：这套衰减只作用于抽卡服务；推演引擎的 `cooldown_until`（模板组级、硬互斥）一字不动——两个冷却是两套消费者，不合并（合并=动基线，理由同 §2.3）。

## 七、抽卡服务（M4 运行时形态，新文件 `app/services/pattern_library.py`）

```python
def draw_patterns(db, *, genre, stage_tag, cast_ids, beat_kind, k=3, salt_key) -> list[PatternCandidate]
def commit_draw(db, *, beat_id, template_id, outcome_order_no, cast_ids, day) -> DrawRecord
```

- `PatternCandidate`：模板全文 + 槽位表 + 可走向列表（§4.4 算好的值域）+ walkon 配置（`needs_walkon`/名字池）+ 当前衰减系数 + `essence`（§十三）。
- 检索顺序=第 1 块 §三原文：**题材闸门 → 阶段闸门 → 关系/标签过滤 → drama_base×衰减加权 → roll 抽 K**。阶段闸门=`goal_alignment.stage_tags ∩ 当前活跃阶段.stage_tags ≠ ∅` 抬权（不是硬滤——阶段不匹配的仍可见但排后，防池小饿死，与引擎"倾向不是命令"同一哲学）；关系过滤=cast 两两 affinity 档（can_bond/敌火线）对上模板 `required_tags`+`negative` 即过。
- **确定性**：`salt_key=f'{beat_id}:{ledger_seq}'`——同集同账本序号重抽必同结果（可审计可复盘）；writer 要换一批就 `ledger_seq+1`。
- 空表/全滤光 → 返回空列表+逐项过滤原因（人审看板用），**不抛错**（空表短路先例）。
- 本批交付**服务 + 单测 + 一个只读 REST 端点**（`GET /projects/{pid}/patterns/draw?…`），writer 真实接线在 F 批。
