## 一、批次总览与依赖

```
4a 冲突引擎化+伏笔扩表（进行中·不停）
 │ 产出「必然冲突日历」+ 伏笔催办
 ▼
批次B 章纲层落地（M3）← 4a 验收后立即
 │ 约束包 Schema + EpisodeBeat 扩字段 + 章纲校验器
 ▼
批次C 套路库结构化（M4 Schema 侧）
 │ 题材闸门 + 多走向 + 随身NPC + 抽卡台账
 ▼
批次D 内容侧填充（M4 内容 + M2 原型服务）
   套路提取管线 + 首批非修仙套路 + archetype_service

批次E 上下文工程（M8）+ 规则库体系化（M6 代码层） ← **可与 C/D 并行**（不碰 engine.py）

批次F LLM 生成化 + 人审穿透（M1/M2/M9） ← 依赖 E
```

**依赖理由**（不是随便排的顺序）：
- **4a→B**：约束包的核心输入就是 4a 产出的「必然冲突日历」+ 扩表后的伏笔台账，4a 没完 B 无法定字段。
- **B→C**：套路引用要挂在 beat 上（`EpisodeBeat` 扩字段先定），否则 C 的抽卡结果无处落库。
- **C→D**：套路内容必须按 C 定稿的 Schema 填，先填内容后定 Schema = 返工。
- **E 可并行**：上下文装配器不碰 `engine.py`，与 C/D 无代码冲突；但它要给 F 用，所以必须早于 F。
- **F 最后**：LLM 生成化依赖 E 的装配器（没有装配器，LLM 拿不到上下文）。
