## 一、为什么这一块是当前最大悬空点

闭环模拟《凤仪宫变》走通第 1 集时，**章纲那一段全是我手写伪 JSON 顶上的**——代码侧零实现。读码实证如下（不是我推断）：

| 现状 | 位置 | 问题 |
|---|---|---|
| `EpisodeBeat` 只有 `id/episode_id/seq/content` 四字段 | `models/project_lib/episodes.py:73-81` | 一个 beat 只是一句话，**没有"发生在第几天""引用哪个事件""出场谁"**，无法被校验 |
| beats 由纯代码拼串生成 | `orchestration_runner.py:125-132` `_beats_of()` = `f'第 {e.day} 天 · {e.action.strip()}'` | 章纲=事件流水账，**没有视角、没有戏剧结构**，正是 V2.0 要治的"上帝视角倒设定" |
| 三件套直接取 `action` 原文 | `orchestration_runner.py:135-156` `_plot_of()` | 冲突/转折/结尾都是事件原句，阶段0 bug#4 靠 `used` 集合防撞车——**治的是症状不是病根** |
| 引擎侧无任何"给 writer 的输入契约" | — | writer 拿到什么、不许写什么，**全凭提示词口述**，无法校验、无法回归 |

**结论**：链路五段里，①②（框架/目标线）有表有服务、④（推演）4a 刚交付、⑤（剧本）writer/reviewer 在跑，**唯独③章纲层是空的**。这一层不落地，"LLM 起草章纲 + 推演校验 + 人审"就永远停在纸面。

## 二、约束包（ConstraintPack）：引擎给 writer 的输入契约

### 2.1 设计原则（三条，违反即打回）

1. **只读快照，不含指令**：约束包只说"世界此刻是什么样、什么必须发生、什么不许出现"，**绝不说"你应该这样写"**。写法是 writer 的活——这是 V2.0 红线"引擎不生成剧情文本"的落地形式。
2. **零新增数据源**：所有字段必须能从**既有表**导出（`world_assertions` 在 C 批次前恒为空列表，走 4a「空表短路」同一先例）。约束包生成器不许读任何新表、不许调 LLM。
3. **必须落痕**：生成的约束包整体写入 `GenerationRun.input_json`（`kind='constraint_pack'`）。这张表的 docstring 明写"全文里唯一允许用 JSON 的地方——只用于留痕，不参与检索"（`models/project_lib/trace.py:24`），**天生就是为这种快照准备的**，不用新建表。

### 2.2 Schema（dataclass，纯函数返回，不落库）

```python
@dataclass(frozen=True)
class ConstraintPack:
    pack_version: str = 'v2.0'

    # —— 段1 范围与视角 ——
    ep_day_from: int                      # 本集覆盖起始天
    ep_day_to: int                        # 结束天
    viewpoint_character_id: str | None    # 视角角色（None=全知视角，须人审确认）
    viewpoint_name: str
    pillar: PillarView | None             # 当前支柱（复用 datatypes.resolve_pillar_seq，不另算）
    target_minutes: float | None

    # —— 段2 在场与可用素材 ——
    cast: list[CastEntry]                 # 谁在场、为什么在场、是否被进行中事件占用
    must_events: list[MustEvent]          # 必然事件（driver='clash'，4a 产出）——必须落地
    material_events: list[MaterialEvent]  # 素材事件（该窗口已确认的常规事件）——可选用

    # —— 段3 伏笔账 ——
    foreshadow_due: list[FsEntry]         # expected_payoff_day 落在本窗口 → 必须处置
    foreshadow_open: list[FsEntry]        # 仍 open、本窗口可回收的
    plant_budget: int                     # 本集最多可新埋几条（防伏笔通胀）

    # —— 段4 世界与状态 ——
    world_assertions: list[WorldAssertion]  # C 批次前恒为 []
    state_snapshot: dict[str, str]          # 视角角色的关系/情绪/伤势等（从账本导出）

    # —— 段5 禁止事项 ——
    forbidden: list[ForbiddenItem]        # 不许出现的事实，逐条带 reason
```

**子结构（关键字段与来源）**：

| 子结构 | 字段 | 数据来源（既有表） |
|---|---|---|
| `CastEntry` | `character_id` / `name` / `in_scene_reason` / `busy_until_day` | `EventParticipant` + `StoryEvent.ends_day`（进行中事件→占用）；`busy_until_day` 直接复用批次 A-2 的 `_ongoing_blocks` 判定（`engine.py:676` `pass_gates` / `:254` 对手位），**不另写一套互斥逻辑** |
| `MustEvent` | `event_id` / `day` / `action` / `conflict_id` / `over_what` / `both_holders` | `StoryEvent(driver='clash')` + `EventConsequence` + `GoalConflict.over_what`；4a 已保证 `driver='clash'` 可事后认出冲突产出 |
| `MaterialEvent` | `event_id` / `day` / `action` / `location` / `time_scale` / `on_mainline` | `StoryEvent(confirmed=True, day∈窗口, driver≠'clash')` |
| `FsEntry` | `fs_id` / `content` / `kind` / `planted_day` / `expected_payoff_day` / `status` / `tied_character_id` | `Foreshadowing`（4a 扩列后字段齐全：`kind`/`expected_payoff_day`/`last_advanced_day`/`resolved_event_id`） |
| `WorldAssertion` | `stmt_type` / `target_id` / `attr` / `value` | `world_states`（**C 批次建表后接入**；本批恒空） |
| `ForbiddenItem` | `code` / `text` / `reason` | 见 §2.3 |

### 2.3 `forbidden` 从哪来（这是约束包最有价值的一段）

模拟里 writer 最容易犯的错不是写得不好看，是**写出世界里不成立的事**。`forbidden` 逐条生成规则：

| code | 触发条件 | 数据来源 |
|---|---|---|
| `CHAR_ABSENT` | 角色不在 cast 内（含 `busy_until_day > 本集`＝被闭关/远行占用） | `EventParticipant` + `ends_day` |
| `CHAR_DEAD` | 角色已死亡/退场 | `Character.status`（须核实枚举值，见 §八待裁 Q3） |
| `REVEAL_LEAK` | 引用了**尚未到揭示层**的世界观设定 | `world_reveal_layers` + `GoalStage.world_reveal`（阶段 1 已建、已接 engine） |
| `GOAL_UNKNOWN` | 让角色表现出他**不该知道**的目标/冲突 | `GoalLine.holder_id` + `GoalConflict.status='latent'`（潜伏期冲突双方都还没意识到） |
| `TIMELINE_AHEAD` | 引用了本窗口之后才发生的事 | `StoryEvent.day > ep_day_to` |
| `FS_EARLY` | 提前回收了 `expected_payoff_day` 远在未来的伏笔（烧牌） | `Foreshadowing.expected_payoff_day` |

> ⚠ 设计取舍：`forbidden` 是**生成时穷举**还是**校验时按需查**？我倾向**生成时穷举并落痕**——因为它要进 `input_json` 给 writer 看（写前约束），校验器复用同一份（写后拦截），一份数据两处用，口径不会漂。这也正是笔枢 `pov_firewall` 的做法（前置注入 + 后置拦截同一套规则），我们比它多一层"落痕可复盘"。

### 2.4 生成器签名（纯函数，无 db 写）

```python
def build_constraint_pack(
    db: Session,                 # 只读
    ep_day_from: int,
    ep_day_to: int,
    viewpoint_character_id: str | None = None,
) -> ConstraintPack: ...
```

- **落在哪个文件**：建议 `app/services/simulator/constraint_pack.py` 新建（不进 `engine.py`——engine 是推演纯函数区，约束包是编排侧读取，混进去会污染职责；也不进 `orchestration_runner.py`——那里是 HTTP 编排流程，约束包要能被 writer/director 两侧独立调用）
- **确定性**：同一 `(day_from, day_to, viewpoint)` 输入必须产出**逐字节相同**的约束包（列表排序键固定：先 day 再 event_id）。这是可回归的前提，也是 INV-28 的断言对象。
- **空表短路**：无目标线/无冲突/无伏笔的项目，约束包仍须正常产出（`must_events=[]`、`foreshadow_due=[]`、`world_assertions=[]`、`forbidden` 只含 `CHAR_ABSENT`/`TIMELINE_AHEAD` 这类不依赖目标线的条目），**不许抛错、不许返回 None**。老项目照跑。

## 三、章纲校验器（BeatValidator）：writer→director 的代码层

### 3.1 定位：它是 director 两层里的「代码层」，不是新角色

模拟里我把 beats 写成伪 JSON 后，**逐条人肉核了时间线、信息集、伏笔额度**——那套判断必须变成代码，否则每集都要人肉核，长篇 100 集不可能。

- 落在 `ReviewReport.source='rule'`（`trace.py:51` 注释明写"'rule' 纯规则 / '{provider}-assist' 规则+模型补充意见"）——**天然就是两层校验的落点，不用新建表**
- 每条问题落 `ReviewIssue`：`level` ∈ `high/medium/low`，`type` 对应 SRS 六项检查，`message` + `suggestion` 必填
- **`level='high'` = 硬失败**：代码层不过，整集章纲打回，不进 LLM 语义审。这是 V2.0 红线"director 代码层不过=硬失败"的落地

### 3.2 13 条校验规则（每条都标了数据来源，不是空口规则）

| # | 规则 | 判定 | level | 依据字段 |
|---|---|---|---|---|
| V1 | **beat 天数落在本集窗口内** | `ep_day_from ≤ beat.day ≤ ep_day_to` | high | 新增 `EpisodeBeat.day` |
| V2 | **beat 引用的事件真实存在且已确认** | `beat.event_id` 在 `StoryEvent(confirmed=True)` 里 | high | 新增 `EpisodeBeat.event_id` |
| V3 | **必然事件全部被至少一个 beat 承接** | `must_events` 的 event_id 集合 ⊆ beats 引用的集合 | high | `driver='clash'` |
| V4 | **出场角色都在 cast 内** | `beat.cast_ids ⊆ cast.character_id` | high | `EventParticipant` |
| V5 | **不引用 forbidden 条目** | beat 文本/引用事件不命中任一 `forbidden.code` | high | 约束包段5 |
| V6 | **视角一致**：非视角角色的内心活动不许出现 | 视角外角色的"心想/暗想/内心"类表述 → 拦截 | high | `viewpoint_character_id` + 关键词表 |
| V7 | **伏笔到期必须处置** | `foreshadow_due` 每条要么被某 beat 回收、要么显式标注延期理由 | high | `expected_payoff_day` |
| V8 | **新埋伏笔不超额度** | `新埋条数 ≤ plant_budget` | medium | `plant_budget` |
| V9 | **beat 顺序与时间单调** | `seq` 递增时 `day` 不减 | medium | `seq` + `day` |
| V10 | **beat 数量在合理区间** | `1 ≤ len(beats) ≤ MAX_BEATS(=5)` | medium | `orchestration_runner.py:34` |
| V11 | **三件套不撞车**（沿用阶段0 bug#4 结论） | `plot_conflict/plot_turn/plot_ending` 两两不同源事件 | medium | `_plot_of` 的 `used` 集合思路升级为显式校验 |
| V12 | **正文不含未填槽残留** | 章纲/正文里无 `{}` 或 `{中文槽名}` | high | 批次 A-1 护栏同一正则来源 `pools.SLOT_PATTERN` |
| V13 | **信息集不越界**：角色不许用他不知道的事实做决定 | 见 §3.3 | high | `GoalConflict.status` + `known_facts` |

### 3.3 V13「信息集」怎么判（最难的一条，说清边界）

- **能代码判的部分**：角色 A 参与的冲突 `GoalConflict.status='latent'`（潜伏期）→ A 的 beat 里不许出现对另一方的**明确指控/摊牌**表述；`world_reveal_layers` 尚未揭示的设定关键词出现在 beat 里 → 拦截。这两条是**白名单/黑名单可穷举**的。
- **不能代码判的部分**：动机合理性、"他会不会这么想"→ **交 director LLM 层**（`source='{provider}-assist'`），不在本批做。
- ⚠ **不许为了通过率放松 V13**：这条是防"全知视角倒设定"的最后一道代码闸，模拟里 writer 最容易在这翻车。若实测误拦率高，回来商量关键词表粒度，**不许降级成 medium 或删掉**。

### 3.3.1 上线姿势：三态开关（借鉴笔枢 `MODES`，**修正本方案原设计**）

> 本节为 2026-10-20 二回挖掘笔枢源码后**新增**，修正 §3.2/§3.3 原本"13 条一律 enforce"的设计。
> 依据：笔枢 `book-data-volume-core.js` 逐字 `MODES = {off:true, shadow:true, enforce:true}`——
> 它的上下文计量/限额硬约束支持**影子模式**（算账但不拦截）。

**问题**：V6（视角一致）与 V13（信息集）都依赖**关键词/语义判断**，误拦率未知。若一上线就 `enforce`，
误拦会直接堵死生产（章纲一律打回、人审队列空转）——这是我们踩不起的。

**方案**：给校验器加**规则级三态开关**（不是全局开关）：

| 态 | 行为 | 适用 |
|---|---|---|
| `off` | 不跑该规则 | 明确不适用的项目类型 |
| `shadow` | **跑、记录、不拦**：命中写入 `ReviewIssue(level='info')`，不影响 `passed` | 新规则上线首期 |
| `enforce` | 跑且拦（按 §3.2 的 level 定阻塞） | 误拦率验证达标后 |

**落地要求**：
1. V6 / V13 **默认 `shadow` 起步**，其余 11 条默认 `enforce`（它们是硬事实校验：天数、事件存在性、槽残留，误拦率天然为 0）
2. `shadow` 期必须**报数**：交付时给出「命中数 / 疑似误拦数 / 误拦率」，误拦率 < 10% 才允许切 `enforce`
3. 三态配置落 `project_settings`（已有表，`settings_json` 里加 `beat_validator_modes` 键），**每项目可独立调**
4. ⚠ **不许用 shadow 规避责任**：shadow 期的命中仍须逐条人看，不是"先放着"。这条写进验收项。

> 为什么这条重要：它把"新校验规则"从**一次性赌注**变成**可观测的灰度过程**。我们之前 A-1 槽名护栏、
> A-2 互斥都是直接 enforce（因为它们是 0 误拦的硬事实），但 V6/V13 不是——语义判断必须有灰度期。

### 3.4 校验器签名

```python
def validate_beats(
    db: Session,               # 只读
    pack: ConstraintPack,      # 复用 §2 生成器产出，不重新算
    beats: list[BeatDraft],    # writer 起草的章纲
) -> list[ReviewIssueDraft]: ...
```

**关键设计**：校验器**接 `ConstraintPack` 而不是重新查库**——写前约束和写后拦截用**同一份数据**，口径不可能漂。这是它和"另写一套校验逻辑"的本质区别。

## 四、数据层：EpisodeBeat 扩列（扩表不建表）

### 4.1 为什么必须扩列

现状 `EpisodeBeat` 只有 `seq/content`，**一个 beat 就是一句话**，V1/V2/V4/V9 四条 high 规则全都无从判起（没有 day、没有 event_id、没有 cast）。这不是"锦上添花"，是章纲校验器的**前置条件**。

### 4.2 扩列清单（6 列，全部 nullable/带默认值）

| 新列 | 类型 | 默认 | 用途 |
|---|---|---|---|
| `day` | Integer | NULL | V1 天数校验、V9 单调 |
| `event_id` | String(120) | NULL | V2 事件溯源、V3 必然事件承接（FK→`story_events`，`ondelete='SET NULL'`） |
| `cast_json` | Text | `'[]'` | V4 出场角色（值对象数组，同 `EventTemplate.tags` 破例先例，见 `episodes.py` 同目录 `events.py:114-115` 注释） |
| `beat_kind` | String(20) | `'normal'` | 区分 `normal`/`clash`/`payoff`/`plant`，供 V3/V7/V8 归类 |
| `source` | String(20) | `'rule'` | `'rule'` 代码拼串 / `'writer'` LLM 起草 / `'human'` 人审改过——**人审穿透的落点** |
| `note` | Text | `''` | 人审批注（模拟里"第三处证据留下集"就是写在这） |

### 4.3 老库兼容（照 4a 同一先例）

- 走 `project_db.py:73-93` 的 `_ADDED_COLUMNS` 白名单自动补列，**不写迁移脚本、不建新表**
- 老库既有 beats 的 `day/event_id` 为 NULL → **V1/V2 对 NULL 跳过不报错**（否则老项目章纲一律红），但 `beat_kind='normal'` + `source='rule'` 补默认值
- 这条必须写成测试（INV-30 的反向：故意给老库 beats 塞 NULL，校验器不许崩）

## 五、与编排层的衔接（改 `_beats_of` / `_plot_of`，不另起管道）

V2.0 红线之一是"L6 不另起管道"，章纲层同理——**不许新建一套并行的章纲生成器**，要在既有编排流程里升级：

| 现有函数 | 改造 |
|---|---|
| `_beats_of()`（`orchestration_runner.py:125`） | 保留"规则版拼串"作为**兜底路径**（`source='rule'`），但产出改成结构化 `BeatDraft`（带 day/event_id/cast），不再只返回字符串。writer 起草时以它为素材、以约束包为边界，产出 `source='writer'` 的 beats |
| `_plot_of()`（`:135`） | `used` 集合防撞车的逻辑**升级为显式校验 V11**，原函数保留但不再是唯一防线 |
| `plan_episodes()`（`:162`） | 草案生成后**多一步**：调 `build_constraint_pack` → 落 `GenerationRun(kind='constraint_pack')` → 调 `validate_beats` → 结果落 `ReviewReport(source='rule')`。校验不过则草案标 `status='rejected'`，**不进人审队列**（人审只看过了代码层的） |
| `confirm_batch()` / `confirm_episode()`（`:280`/`:317`） | 人审改过的 beat 打 `source='human'` + `note` 留批注；确认后**约束包重算一次**（因为人审可能改了窗口/视角），确保下游 writer 拿到的是终版约束 |

> ⚠ 一个顺序坑：`plan_episodes` 现在是"先切段再拼 beats"。加约束包后必须**先定段（day_from/day_to/viewpoint）→ 生成约束包 → 起草 beats → 校验**，不能反过来。否则约束包里的 `must_events` 和 beats 对不上。

## 六、新增不变量（INV-28~31，全部要带反向验证）
