## ② 脚本稳定性与跨机器失效

### 2.1 【最高危】编码规范 v1 与体检工具 v3 策略完全相反

这是当前最严重的问题，因为它会**持续制造新的不稳定**。

| | `docs/01-协作规范/脚本编码规范.md`（v1.0 + v1.1，09-17 11:54） | `messages/tools/编码体检.ps1`（v3，09-18 09:05） |
|---|---|---|
| `.cmd` / `.bat` | **一律 UTF-8 带 BOM**（"硬性"） | **转为 GBK 无 BOM + CRLF** |
| `.ps1` | UTF-8 带 BOM | UTF-8 带 BOM ✅ 一致 |
| 依据 | "本机 Windows 代码页为 **65001**，cmd.exe 按 UTF-8 解析；若文件是 GBK，中文行会被乱码解析成 `'鎏崾静蛔瓒希?for' 不是内部或外部命令`" | "适用：Windows 936（GBK）系统与 65001（UTF-8）系统均可" |

**本机实测**（我跑的，不是推断）：

```
chcp                        → Active code page: 65001
cmd /c chcp                 → Active code page: 65001
注册表 HKLM\...\CodePage\ACP   → 936
注册表 HKLM\...\CodePage\OEMCP → 936
「Beta: 使用 Unicode UTF-8 提供全球语言支持」→ 未开启
```

即：**cmd.exe 会话代码页是 65001，而系统 ANSI/OEM 是 936**。这正好落进 v1 文档描述的"GBK 文件在 65001 下乱码"场景，而 v3 工具却把全部 `.cmd/.bat` 转成了 GBK。

**为什么现在还能跑**：`启动工作台.cmd` 的中文只出现在 `echo` 提示、`title` 和注释里，**关键路径拼接 `%~dp0工作台面板`、`%~dp007-日志` 也在其中**。我按 GBK 解码该文件，这些行是完整正确的中文（因为文件确实是 GBK）；但 cmd.exe 在 65001 下读取时会把这些 GBK 字节当 UTF-8 解析 → **路径变量本身就可能变成乱码**。这解释了用户反馈的"功能不怎么稳定"：同一个脚本，取决于当次 cmd 会话的实际代码页（受 `chcp` 调用顺序、父进程环境、是否从资源管理器双击影响），有时正常有时失败。

**连带缺陷：`编码体检.cmd` 自相矛盾**

该文件本身是 GBK 无 BOM，但第 2 行是 `chcp 65001 >nul`。切到 65001 之后再读自己后续的 GBK 中文行：

```
实测解码结果：title 宸ヤ綔鍙拌剼鏈紪鐮佷綋妫€      ← 原为「工作台脚本编码体检」
```

而第 8 行 `powershell ... -File "%~dp0编码体检.ps1"` 中的"编码体检"四字同样会被解码成乱码 → **`powershell -File` 找不到脚本，体检工具自身很可能一运行就失败**。
（⚠️ 我**没有实际运行**它 —— 因为它会自动改写全仓脚本编码，属破坏性操作。此结论基于字节级解码推演，建议你手动双击一次 `编码体检.cmd` 验证。）

**修复方向**（二选一，必须统一，且同步更新文档）：
- **方案 A（推荐）**：`.cmd/.bat` 全部改为**纯 ASCII**，中文提示移到 `.ps1`（UTF-8 BOM）里由 PowerShell 输出。彻底摆脱代码页依赖，任何语言的 Windows 都能跑。这也满足 DeepSeek 主因2 提的"要么纯 ASCII 去中文"。
- **方案 B**：坚持 GBK，则必须 ① 更新 `脚本编码规范.md` 到 v3 口径消除矛盾；② 每个 `.cmd` 首行加 `chcp 936 >nul`（而非 65001）；③ README 明确声明"仅支持中文 Windows"；④ 加 `.gitattributes` 防 CRLF 转换破坏 GBK 字节。

### 2.2 `07-鏃ュ織` 乱码目录：根因已 100% 实证

```
「07-日志」的 UTF-8 字节 = 30 37 2D E6 97 A5 E5 BF 97
把这串字节按 GBK(936) 解码 = 「07-鏃ュ織」      ← 与实际目录名逐字符一致
```

**成因**：某进程以 UTF-8 写出路径字符串，被另一进程按 GBK 解读后 `mkdir`，于是创建了这个乱码目录。

- 提交时 CRLF → LF 存入仓库；clone 到另一台机器时 LF → CRLF 还原。对纯 ASCII 无害，但对 **GBK 编码的 .cmd 文件，Git 会把它当文本做行尾转换**。GBK 双字节序列中若第二字节恰为 `0x0A`/`0x0D`（GBK 尾字节范围 0x40–0xFE，不含这两个，但**首字节 0x81–0xFE 与多字节边界在 Git 的文本启发式判定下仍可能被误判为二进制或触发转换**），字节序列即被破坏 → 另一台机器上 `.cmd` 语法错误或中文全乱。

#### Bug 1 · `isProjectAlive` 缺 `await`，项目状态永远判错 —— 确定性 Bug

```js

  ...
  const isOpen = new Promise((resolve) => { ... });

```

| 调用点 | 写法 | 结果 |
|---|---|---|
| `server.mjs:286` | `const alive = await isProjectAlive(p.relative)` | ✅ 正确 |
| `server.mjs:301` | `const alive = await isProjectAlive(p.relative)` | ✅ 正确 |

#### Bug 2 · 15 处 `spawn` 中 10 处无 `error` 监听，且全文件无未捕获异常兜底


**后果**：Node 的 `child_process.spawn` 在目标可执行文件不存在时，会**异步 emit 一个 `error` 事件**；若无人监听，该事件升级为 `uncaughtException`，**直接终止整个面板进程**。

- `:1482` `spawn('rundll32.exe', ...)`、`:1497` `spawn('cmd', ['/c','start',...])`、`:1514` `spawn(node, [m], ...)`（启动智能体监听）同理。

叠加 §2.4 的硬编码路径：新机器上这些 spawn 的目标大概率不存在 → 无 error 监听 → 无 uncaughtException 兜底 → **面板进程直接死掉**。这是"跨机器打不开"最直接的代码级机制。

### 3.3 【死结】技能 description「运行时预加载」声明无任何实现支撑

这是工程包上下文管理**最严重的逻辑缺陷**，因为它让技能路由机制在两种情况下都会失败。

`AGENTS.md` 三处做出同一个断言：

| 行 | 原文 |
|---|---|
| `:18` | 技能匹配只用会话启动时**已预加载**的 SKILL.md description；命中后仅加载那一个技能 |
| `:84` | 该字段**已由运行时在会话启动时预加载进上下文**，直接凭已有信息匹配即可——**严禁**为了「查触发词」去 Read 这些 SKILL.md 文件 |
| `:90` | 用**已预加载的技能 description**（无需读任何文件）比对本次意图 |

**实测四处可能的实现载体，全部为空**：

| 载体 | 实测内容 | 是否注入 description |
|---|---|---|
| `skills-lock.json` | `{"version": 1, "skills": {}}` —— **skills 是空对象** | ❌ |
| `.agents/hooks/session-start.cjs` | 只 `clearState()` 清 3 个状态文件，返回的 `additionalContext` 是硬编码的 3 条强制清单文字（技能检查 / code-reviewer / 验证），**不含任何技能名或 description** | ❌ |
| `.agents/settings.json` | 顶层键只有 `hooks`，**全文无 "skill" 字样** | ❌ |
| `.agents/hooks.json` | 6 类 hook（sessionStart/preToolUse/postToolUse/preCompact/stop），无技能注入 | ❌ |

**死结的两个分支**：

- **分支 A（智能体守规矩）**：遵守"严禁 Read SKILL.md"→ 上下文里**根本没有** 52 个技能的 description → 无法做任何触发词匹配 → **技能路由整体失效**，`:90` 的"先匹配后动手"、`:93` 的"未命中才用通用能力"都无从执行。智能体只能靠 `AGENTS.md:80-227` 那 148 行的技能清单表格猜，而该表 `:82` 自己声明"本表不是完整触发词表……实际触发条件以各自 SKILL.md 的 description 为准"。
- **分支 B（智能体不守规矩）**：为了拿到触发词去 Read SKILL.md → 52 个文件合计 442 KB ≈ **11 万 token**，正是 `:84` 警告的"挤爆上下文"。若误用 Glob 递归则连 references 一起带进来，3.32 MB ≈ 80 万+ token，**必然溢出**。

**两条路都通不到"正确路由"**。这就是为什么工作台会表现出"技能有时触发有时不触发"的不稳定 —— 取决于当次会话的智能体是否遵守了那条无法遵守的禁令。

> 注：这个机制在**某些客户端上可能确实存在**（比如 Claude Code / 豆包 / 千问这类宿主自带技能发现能力，会把 SKILL.md 的 frontmatter description 自动注入系统提示）。但工程包**不能假设宿主一定提供**，而且 `skills-lock.json` 这个文件的存在本身说明原设计是打算自己做锁定的 —— 它现在是空的，说明该机制**设计了但没实现完**。

**修复方向**：
1. **短期**：把 52 个技能的 `name` + `description` 抽取生成一份**紧凑索引**（预计 8–15 KB / 3–5 千 token），放在 `.agents/skills/INDEX.md`，由 `session-start.cjs` 通过 `additionalContext` 真实注入。同时填充 `skills-lock.json`（记录版本号与哈希，便于校验索引是否过期）。
2. **配套**：`AGENTS.md:84` 的措辞从"已由运行时预加载"改为"已由 `session-start` hook 注入 `.agents/skills/INDEX.md`"，让声明与实现一致、可验证。
3. **生成脚本**：写一个 `scripts/build-skills-index.mjs`，遍历各 SKILL.md 的 frontmatter 自动生成索引，避免手工维护漂移（这正是 P1-3 对 AGENTS.template.md 该做却没做的事）。

### 3.4 上下文预算护栏：只有文字警告，无技术强制

DeepSeek P0-2 要求"加 token 预算 hook，或把知识库挂 MCP/检索层，或在 AGENTS.md 顶部加上下文预算自检硬提示"。豆包落地的是**第三个（最弱的那个）**：

> `AGENTS.md:20` **每次操作前自检**：凡即将执行 Read / Glob / 目录扫描且目标可能命中上述三个目录（含通配符、递归），先停下估算一次调用是否可能带进 > 2 万 token —— 会则改为精确路径 Read 单个文件，不得整目录读。

**问题**：这是纯自然语言约束，依赖智能体自觉。而已有的 hook 体系（`gateguard.cjs` / `config-protection.cjs`）**证明技术护栏是可行的** —— `hooks.json` 里 `preToolUse` 已经能拦截 `Write|Edit|MultiEdit`，`postToolUse` 已经在 `Read` 上挂了 `gateguard`。

**这意味着加一个 `preToolUse` 的 `context-budget` hook 完全在现有架构能力内**：匹配 `Read|Glob|Grep`，检查目标路径是否命中高危目录（`.agents/skills/`、`.agents/knowledge/`、根级 `rules/references/`、`src/themes/`）且是否为递归/通配，命中则返回阻断提示 + 建议的精确路径。**这是当前性价比最高的一处加固**，且能顺带覆盖 §3.2 的三个炸点。

`.agents/hooks/gateguard.cjs` 只有 1,211 B，说明现有 hook 都很轻量，新增一个不会有性能负担。
