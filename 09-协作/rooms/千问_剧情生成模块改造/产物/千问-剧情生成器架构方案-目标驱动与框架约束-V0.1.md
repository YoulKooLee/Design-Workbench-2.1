# 剧情生成器架构方案 · 目标驱动与框架约束

## 0. 这份方案要解决什么

用户原话（2026-10-06）：

> 大框架+事件流，当框架确定，用户有了目标，在目标的路上填充事件，从而丰富剧情。
> 比如魔兽争霸战役剧情，世界观就是燃烧军团入侵，阿尔萨斯触发事件（系列任务）拯救巫妖王，
> 与巫妖王合体；伊利丹触发事件，灭杀巫妖王，两人在对抗过程中形成精彩的剧情。
> 当前我们的事件库完全没法用，我希望事件库是一个结构化信息，能够给AI衍生出剧情，
> 且符合世界观和剧情框架。

拆成三个要求：

1. **先有框架，再填事件**——不是抽卡抽出一条流水账，而是沿既定骨架推进。
2. **目标驱动**——角色有目标，事件是目标推进的手段；**多角色目标对抗产生精彩剧情**。
3. **事件库要结构化**——能被 AI 衍生，且受世界观与框架双重约束。

---

## 1. 魔兽例子拆解：当前架构缺的到底是什么

把用户给的例子逐元素拆开，对照现状：

| 魔兽元素 | 剧情机制 | 当前后端 | 缺口 |
|---|---|---|---|
| 燃烧军团入侵 | 世界观级持续压力 | `world_rules` 2 行文本；`WORLD_EVENT_POOL` 5 条一次性背景板 | 世界观不会「持续施压」，只是静态条目 |
| 阿尔萨斯拯救→堕落→合体 | **角色目标线，阶段化推进** | `MainQuestView(goal/done_when/stage/obstacle)` 全局**单条** | 只有一个全局主线，角色没有自己的目标线 |
| 伊利丹灭杀巫妖王 | **第二条目标线** | 无 | 完全缺失 |
| 两人对抗 | **目标冲突 → 事件生成** | 无 | 完全缺失，这是「精彩」的来源 |
| 系列任务 | 目标推进的具体步骤链 | 事件之间无因果串接（`pending_repercussions` 0 行） | 事件是散点，不成链 |
| 合体的必然性 | 框架节点的宿命感 | 无框架概念 | 事件不知道该落在故事的哪个位置 |

**结论：当前引擎是「反应式」的——性格标签决定角色遇到什么琐事。用户要的是「目标式」的——角色想要什么，为了得到它会做什么，两条欲望相撞就是戏。**

现有的 `main_quest` 只被 `engine.py:mainline_hits()` 用作概率加成（撞上主线就把概率往上抬），它是**装饰品而非驱动力**。

叠加《诊断报告》的实测数据：155 条事件只有 24 种文本（重复率 85%）、性格标签交集为空导致概率全退化成基线 0.1、关系网/因果账/路人表全 0 行、储物袋装着「集市」「山道」。**当前链路即使修好所有 bug，也写不出魔兽那样的剧情——因为它没有「目标」和「冲突」这两个概念。**

## 2. 目标架构：七层

```
L0 世界观底色     燃烧军团入侵 / 五域两天蛊修 / 弱肉强食
   │              不可违反的铁律 + 持续施压的世界态势
   ▼
L1 剧情框架       三幕 × 七大支柱
   │              每个支柱 = 世界认知状态 + 主角情绪 + 必办事项 + 允许的揭示层
   ▼
L2 目标线         多角色 / 多阵营，各自阶段化推进，声明冲突关系
   │              阿尔萨斯线 ↔ 伊利丹线（在「冰封王座」相撞）
   ▼
L3 事件库         结构化剧情单元：声明服务哪个目标阶段 / 适配哪个支柱 / 揭示哪层世界
   │              不是成品句子，是给 AI 的生成指令
   ▼
L4 事件流         推演产出：目标推进事件（骨干）+ 性格日常事件（血肉）+ 世界事件（背景）
   │              冲突检测在这一层触发
   ▼
L5 场景规格       SceneSpec 实例化（移植桌面 L2b）+ SPEC-1~9 校验闸门
   │
   ▼
L6 剧本正文       L3 叙事层（移植桌面 l3_narrator，适配漫剧场次格式）+ 章末核对器
```

L5/L6 沿用桌面原型（已验证可行，资产清单见《诊断报告》§7）。**本方案的重点是 L1~L4，这四层当前基本不存在。**

## 3. L1 剧情框架层

### 3.1 数据模型：`story_pillars`（新表）

七大支柱不是硬编码常量，而是**每个项目可配**——因为不是所有故事都用三幕式（用户说"后续可以摸索其他架构"）。

```sql
CREATE TABLE story_pillars (
    id            TEXT PRIMARY KEY,
    project_id    TEXT,              -- 系统库级为 NULL（内置模板）
    framework     TEXT NOT NULL,     -- 'three_act_seven_pillar' / 其他架构标识
    act           TEXT NOT NULL,     -- ACT1 / ACT2 / ACT3
    seq           INTEGER NOT NULL,  -- 1~7
    name          TEXT NOT NULL,     -- 现况建立 / 触媒事件 / ...
    -- 戏剧功能
    duty          TEXT,              -- 这个节点必须完成什么（"把主角推出去"）
    pov_emotion   TEXT,              -- 主角情绪曲线（平静/疑惑/愤怒/震撼/崩溃/燃/怅然）
    -- 世界观同步演变（三幕式文档 §4 的核心要求）
    world_duty    TEXT,              -- 对世界观的作用（"确立基调"/"揭示最重要隐藏设定"）
    reveal_layers TEXT DEFAULT '[]', -- 本节点允许揭示的世界观层号，JSON 数组
    -- 篇幅与位置
    weight        REAL DEFAULT 0.14, -- 占全书体量比例（ACT2 的 ④ 约 0.5）
    day_from      INTEGER,           -- 落到故事时间上（推演时回填）
    day_to        INTEGER,
    ep_from       INTEGER,           -- 落到集次上（编排时回填）
    ep_to         INTEGER,
    status        TEXT DEFAULT 'pending'  -- pending / active / done
);
```

内置种子按《三幕式剧情结构》七节点灌入（`framework='three_act_seven_pillar'`），项目可覆写。

### 3.2 数据模型：`world_reveal_layers`（新表）

三幕式文档 §8 的硬要求："ACT 2 的四层揭示要均匀分布，避免一次性倒设定"、"关键反转（节点⑤）前必须埋至少 3 处伏笔"。这两条必须可校验，否则只是口号。

```sql
CREATE TABLE world_reveal_layers (
    id             TEXT PRIMARY KEY,
    layer_no       INTEGER NOT NULL,   -- 1~N
    content        TEXT NOT NULL,      -- "仙蛊稀有但真实存在，前世记忆是最大金手指"
    pillar_earliest INTEGER NOT NULL,  -- 最早可在第几支柱揭示
    pillar_latest   INTEGER NOT NULL,  -- 最晚必须揭示（防拖到结尾才倒设定）
    planted_count   INTEGER DEFAULT 0, -- 已埋了几处伏笔（节点⑤前须 ≥3）
    status          TEXT DEFAULT 'hidden'  -- hidden / hinted / revealed
);
```

大爱仙尊案例的四层直接可录入：

| 层 | 内容 | 最早 | 最晚 |
|---|---|---|---|
| 1 | 仙蛊稀有但真实存在，前世记忆是最大金手指 | ④ | ④ |
| 2 | 「天地一拍」专杀重生者——有东西在针对他 | ④ | ④ |
| 3 | 「天意」概念，历代尊者都在跟天意博弈 | ④ | ⑤ |
| 4 | 义天山真相：魔尊幽魂、星宿仙尊、影宗，全是万古棋局 | ⑤ | ⑤ |

**校验规则**（进 SPEC 或独立一致性检查）：
- 事件声明 `reveal_layer=N`，若当前支柱 < 该层 `pillar_earliest` → 违规（提前倒设定）
- 全书推进到 `pillar_latest` 之后该层仍 `hidden` → 违规（该揭没揭）
- 节点⑤ 之前 `planted_count < 3` → 阻塞（伏笔不足，反转不成立）

### 3.3 框架如何约束推演

推演前先问框架两件事：

1. **当前在第几支柱**（按故事天数 / 集次进度换算）
2. **这个支柱允许什么**（`reveal_layers` 白名单、`duty` 必办事项、`weight` 篇幅配额）

然后事件抽签时，`pillar_fit` 不含当前支柱的模板**降权或排除**。这就实现了"ACT1 不该出现终极考验级事件"。

## 4. L2 目标线层（本方案的核心增量）

### 4.1 数据模型：`goal_lines`（新表）

```sql
CREATE TABLE goal_lines (
    id             TEXT PRIMARY KEY,
    holder_id      TEXT NOT NULL,      -- 角色 id，或 faction:xxx 表示阵营目标
    holder_kind    TEXT DEFAULT 'character',  -- character / faction / world
    title          TEXT NOT NULL,      -- "拯救巫妖王并与其合体"
    goal           TEXT NOT NULL,      -- 想要什么
    motive         TEXT,               -- 为什么想要（驱动力的根）
    done_when      TEXT NOT NULL,      -- 完成条件（可判定）
    priority       INTEGER DEFAULT 5,  -- 1~10，冲突时谁让路
    status         TEXT DEFAULT 'active',  -- dormant / active / achieved / failed / abandoned
    current_stage  INTEGER DEFAULT 0,  -- 指向 goal_stages.seq
    -- 框架挂接
    pillar_start   INTEGER,            -- 从第几支柱开始活跃（阿尔萨斯线从②起）
    pillar_end     INTEGER,            -- 到第几支柱必须收束
    is_main        BOOLEAN DEFAULT 0,  -- 是否主角线（原 main_quest 迁移到这里）
    created_at     DATETIME,
    updated_at     DATETIME
);
```

### 4.2 数据模型：`goal_stages`（新表）

阶段化是「系列任务」的本质。阿尔萨斯不是一步合体的，是六步走过去的。

```sql
CREATE TABLE goal_stages (
    id            TEXT PRIMARY KEY,
    goal_id       TEXT NOT NULL,       -- FK goal_lines
    seq           INTEGER NOT NULL,    -- 1~N，阶段顺序
    name          TEXT NOT NULL,       -- "屠城斯坦索姆"
    enter_when    TEXT,                -- 进入条件（结构化谓词，见 4.4）
    done_when     TEXT NOT NULL,       -- 完成条件
    -- 推进手段：这个阶段会被哪类事件推进
    stage_tags    TEXT DEFAULT '[]',   -- JSON: ["复仇推进","力量获取"]
    -- 代价与转折
    cost          TEXT,                -- 完成这个阶段要付出什么（堕落/失盟友/受伤）
    turn_hint     TEXT,                -- 转折提示（"假胜利"/"假失败"，对应三幕中点）
    world_reveal  INTEGER,             -- 本阶段揭示第几层世界观
    status        TEXT DEFAULT 'pending',  -- pending / active / done / blocked / skipped
    day_started   INTEGER,
    day_done      INTEGER
);
```

魔兽例子录入后长这样：

```
goal_lines: 阿尔萨斯
  goal: 阻止瘟疫、守护洛丹伦
  motive: 王子的责任与骄傲
  done_when: 瘟疫源头被清除
  stages:
    1. 调查瘟疫          stage_tags=[调查, 责任推进]   cost=无
    2. 追击恐惧魔王      stage_tags=[复仇推进, 调查]   cost=部下伤亡
    3. 屠城斯坦索姆      stage_tags=[极端手段]         cost=失去乌瑟尔与吉安娜  turn_hint=假胜利
    4. 寻找霜之哀伤      stage_tags=[力量获取]         cost=灵魂被侵蚀          world_reveal=2
    5. 弑父              stage_tags=[极端手段, 堕落]   cost=人性
    6. 与巫妖王合体      stage_tags=[力量获取, 终局]   turn_hint=真失败

goal_lines: 伊利丹
  goal: 消灭巫妖王，夺取力量
  motive: 被囚万年的怨恨与对力量的渴望
  done_when: 巫妖王被击杀
  stages:
    1. 获得古尔丹之颅    stage_tags=[力量获取]         world_reveal=1
    2. 化身恶魔          stage_tags=[蜕变]             cost=族人不认
    3. 进攻冰封王座      stage_tags=[终局, 正面对抗]
```

### 4.3 数据模型：`goal_conflicts`（新表）——「精彩」的发生器

这是用户例子里最关键的一环："两人在对抗过程中形成精彩的剧情"。

```sql
CREATE TABLE goal_conflicts (
    id             TEXT PRIMARY KEY,
    goal_a         TEXT NOT NULL,      -- FK goal_lines
    goal_b         TEXT NOT NULL,
    conflict_type  TEXT NOT NULL,      -- 见下表
    over_what      TEXT,               -- 争夺对象（"巫妖王的头颅"/"狐仙福地传承"）
    -- 触发窗口
    stage_a_at     INTEGER,            -- A 线推进到第几阶段时冲突激活
    stage_b_at     INTEGER,
    pillar_at      INTEGER,            -- 应在第几支柱爆发（⑥终极考验）
    -- 结果
    resolution     TEXT,               -- 谁胜 / 两败 / 妥协
    resolved_at    INTEGER,            -- 实际爆发的天数
    status         TEXT DEFAULT 'latent'  -- latent 潜伏 / active 激化 / resolved 已决
);
```

`conflict_type` 枚举（每种对应不同的事件生成策略）：

| 类型 | 含义 | 魔兽例 | 生成的事件类型 |
|---|---|---|---|
| `zero_sum` | 零和：一方达成则另一方必败 | 阿尔萨斯合体 vs 伊利丹灭杀 | 正面对抗、决战 |
| `rivalry` | 竞争：同一资源 | 两条线都想要霜之哀伤 | 抢夺、截胡、赛跑 |
| `ideology` | 理念冲突：目标不互斥但手段不容 | 乌瑟尔 vs 阿尔萨斯屠城 | 劝阻、决裂、背叛 |
| `misunderstanding` | 误解：信息不对称导致的对抗 | — | 冲突升级、真相揭露 |
| `alliance_strain` | 同盟内部张力：共同目标但利益分配不均 | 方源与影宗合作 | 试探、留后手、反水 |

**为什么这张表是核心**：有了它，推演引擎可以在两条目标线各自推进到指定阶段时，**主动生成一场对抗事件**，而不是等随机抽签碰运气。伊利丹线推到第 3 阶段 + 阿尔萨斯线推到第 6 阶段 → `zero_sum` 冲突激活 → 生成「冰封王座决战」事件。

这就是「框架确定、目标确定、在路上填充事件」的机制实现。

### 4.4 目标线的谓词化

`enter_when` / `done_when` 必须是**可判定的结构化谓词**，不能是自然语言（这是桌面 L2b 的核心经验："禁止自由文本条件"，见 `l2_instantiator.py:100`）。

复用并扩展 L2b 的 `PREDICATES` 表：

```python
# 已有（L2b 移植）
"relation_lt", "status_gap_gt", "has_open_hook", "no_imprint", "romance_eligible", ...

# 本方案新增（目标线专用）
"goal_stage_reached"  : (goal_id, stage_seq)          # 某线推进到某阶段
"goal_status_is"      : (goal_id, status)             # 某线达成/失败
"conflict_active"     : (conflict_id)                 # 某冲突已激化
"world_layer_revealed": (layer_no)                    # 世界观第 N 层已揭示
"pillar_at_least"     : (pillar_seq)                  # 故事已推进到第 N 支柱
"imprint_count_ge"    : (char_id, type, n)            # 某类墓碑累积到 n 条
```

## 5. L3 事件库结构化改造

### 5.1 核心观点：从「事件成品」到「事件生成器」

这是用户"事件库完全没法用"的根因。对比：

**当前**（`pools.py:108`）：
```python
EventTemplate(
    id='ev-confront',
    title='{a}质问{b}',
    description='{a}受不了{b}的隐瞒，当场堵住他，问他到底在替谁做事。',
    consequences=['{b}只说出一半真相', '{a}对{b}的信任下降'],
    location='路上', cast=['a', 'b'],
)
```
这是一句**已经写完的话**。引擎只做 `str.replace('{a}', 人名)`（`engine.py:315`）。AI 拿到它能干什么？只能照着抄一遍。没有衍生空间。

**改造后**：
```python
EventTemplate(
    id='ev-confront',
    drama_class='conflict_confrontation',     # 事件类：冲突-质问
    drama_base=7.5,                           # 戏剧性基准分（供选戏器打分）

    # ── 框架与目标挂接（新增，本方案核心）──
    goal_alignment={
        'stage_tags': ['责任推进', '调查', '复仇推进'],  # 能推进哪类目标阶段
        'progress': 1,                                   # 推进量（1 个阶段步进）
    },
    pillar_fit=[2, 3, 4],                    # 适配第 2~4 支柱（触媒/第一次目标/追求）
    world_reveal=None,                       # 本事件不揭示世界观（或指定层号）

    # ── 角色槽（从 cast:['a','b'] 升级）──
    role_slots=[
        RoleSlot(key='initiator', required=True,
                 requires=[('has_grievance_with', 'target')],   # 必须有积怨
                 traits_bias={'急躁': 0.5, '直率': 0.3}),
        RoleSlot(key='target', required=True,
                 requires=[('holds_secret_from', 'initiator')]), # 必须藏着事
        RoleSlot(key='bystander', required=False, count=(0,2),
                 requires=[('same_location_or_faction', 'initiator')],
                 creatable=True, create_tier='P3', create_p=0.4),
    ],

    # ── 前置条件（结构化谓词，可判定）──
    preconditions=[
        (('relation_lt', 'initiator', 'target', -10), '质问需要积怨'),
        (('has_fact_gap', 'initiator', 'target'), '必须存在信息差'),
        (('pillar_at_least', 2), 'ACT1 之前不该有质问'),
    ],

    # ── 多值槽 + 条件化抽样（衍生空间的来源）──
    slots={
        '质问由头': ['隐瞒身份', '隐瞒行踪', '与敌方接触', '隐瞒伤情', '私藏物品'],
        '质问场合': ['私下', '当众', '第三方在场', '战斗中'],
        '施压方式': ['直接逼问', '设局试探', '摆出证据', '以情相逼'],
        '结果分支': ['逼出半真相', '彻底翻脸', '被反将一军', '对方沉默离场', '第三方打断'],
    },
    slot_conditions={
        '结果分支': {
            '逼出半真相':   [('relation_lt', 'initiator', 'target', 20)],
            '被反将一军':   [('status_gap_gt', 'target', 'initiator', 20)],
```

## 6. L4 目标驱动推演引擎

### 6.1 改造点：在现有循环里插入目标层

现有 `simulate_range()` 的循环是（`engine.py:693` 起）：

```
for slice in slices:                    # 时间切片
    for char in all_characters:         # 全角色循环
        template = pick_template(char)  # 性格抽签
        if hit: build_event()
```

改造为：

```
for slice in slices:
    pillar = current_pillar(day)              # ① 问框架：现在第几支柱
    active_goals = goals_active_at(pillar)    # ② 哪些目标线在活跃

    # ③ 冲突优先：本切片是否到达某个 conflict 的爆发窗口
    for conflict in conflicts_due(slice, active_goals):
        event = build_clash_event(conflict)   # 生成对抗事件（骨干戏）
        advance_stage(conflict.goal_a); advance_stage(conflict.goal_b)

    # ④ 目标推进：有活跃目标的角色优先推目标
    for goal in active_goals:
        char = goal.holder
        stage = goal.current_stage_obj()
        template = pick_template_for_stage(char, stage, pillar)  # 按 stage_tags + pillar_fit 筛
        if hit:
            event = build_event(...)
            apply_goal_progress(goal, template.effects.goal_progress)

    # ⑤ 性格日常：填充血肉（沿用现有逻辑，但受 pillar_fit 约束）
    for char in all_characters:
        template = pick_template(char, pillar)   # 新增 pillar 过滤
        if hit: build_event(...)

    # ⑥ 世界事件：沿用现有逻辑，但可承载「世界观持续施压」
    if world_event_due(slice): build_world_event()

    # ⑦ 揭示层检查：本切片是否该推进 world_reveal_layers
    check_reveal_schedule(pillar)
```

**关键设计取舍**：

- **目标推进事件与性格日常事件共用同一个事件池**，靠 `goal_alignment.stage_tags` 与 `pillar_fit` 筛选。不新建第二套引擎，A 档已落地的切片/冷却/持续/互斥/可复现全部复用。
- **冲突事件优先级最高**（在 ③），因为它是「精彩」的来源，不能被日常琐事挤掉。单切片 6 条上限的规则保留，但冲突事件占位保底。
- **主角保底逻辑保留**（A 档已实现），但改为「主角的目标线保底推进」而非「主角保底出一条事件」——目标线的推进比随机事件更有意义。

### 6.2 概率公式扩展

现有（`engine.py:507`）：
```
p = clamp(性格强度 × 粒度权重, 0.05, 1.0) + 主线加成
```

改为：
```
p_char    = 性格强度概率（high 1.0 / mid 0.6 / low 0.3 / 无匹配取 0.1）
w_unit    = 粒度权重
w_pillar  = 支柱适配系数（pillar_fit 含当前支柱 → 1.0；相邻 → 0.5；不含 → 0.1）
w_goal    = 目标对齐系数（stage_tags 命中当前阶段 → 1.5；同线其他阶段 → 1.0；无关 → 0.6）
w_drama   = 戏剧性系数（drama_base / 10，用于选戏倾斜）

p_base  = clamp(p_char × w_unit × w_pillar × w_goal, 0.05, 1.0)
p_final = p_base + (1 - p_base) × min(1, 主线命中 × 0.4)
```

`w_goal` 是本方案最重要的乘子：**目标对齐的事件概率抬到 1.5 倍**，这样"在目标的路上填充事件"才成立，而不是目标归目标、事件归事件。

### 6.3 必须先修的前置：性格标签打通

《诊断报告》问题①：事件库要求 17 个标签（冲动/急躁/多疑/隐忍/重情…），项目角色实际持有「坚韧」「护短」，**交集为空 → `p_char` 恒为 0.1 → 一切退化成纯随机**。

这个不修，上面的概率公式全是空转。方案：

- **主标签走枚举**：前端人设页的性格标签改为从 17 词（可扩）中选，带强度 low/mid/high。
- **别名映射表兜底**：新增 `trait_aliases` 表，把自由填写的词映射到枚举（坚韧→[隐忍, 守信]、护短→[重情, 利他]）。映射一对多时取概率最高者，避免歧义。
- **启用 archetype 体系**（`archetypes` / `archetype_behaviors` / `archetype_taboos` 三张表已建好但全空）：原型→派生标签，作为人设页的快速填充入口。

### 10.1 我认为最值得投入的三件事

1. **`goal_conflicts` 表**——这是「精彩剧情」的机制化。没有它，再多事件也只是流水账。用户举魔兽例子，重点不在阿尔萨斯做了什么，而在**他和伊利丹的目标必然相撞**。
2. **事件库的槽位 + 变体组合空间**——4 个槽 × 各 4~5 取值 + 3 拍变体，一条模板能衍生数百种不同场景。这是解决 85% 重复率的根本手段（当前 30 条模板 = 30 种文本，天花板就在那里）。
3. **世界观分层揭示的可校验性**——`world_reveal_layers` 带 `pillar_earliest/latest`，让"避免一次性倒设定"从口号变成 CI 能拦的违规。

### 10.2 三个风险

1. **过度设计**：七层架构 + 5 张新表，如果用户只想快速看到能用的剧情，这个体量偏重。**缓解**：阶段 0~2 就能让魔兽案例跑起来（框架 + 双线 + 冲突），不必等到阶段 6。建议以「阶段 2 结束能演示魔兽双线对抗」为第一个里程碑。
2. **目标线的维护成本**：用户要为每个重要角色手工录入目标线与阶段，这是创作负担。**缓解**：提供 archetype 式的目标线模板（复仇线/夺宝线/守护线/野心线），用户选模板后改具体名词，而非从零写。
3. **推演可控性下降**：目标驱动 + 冲突触发引入了更强的确定性，可能削弱 A 档「每个人各自发生着什么」的涌现感。**缓解**：保留性格日常事件层（⑤）作为血肉，目标事件只做骨干；`w_goal` 是 1.5 倍而非 10 倍，非对齐事件仍有机会。

### 10.3 我不建议做的

- **不建议用 LLM 直接生成事件流**。设计文档 §1 的架构基线（用户 2026-09-29 拍板）明确「事件模拟是纯代码，一次模型都不调」，我认同这个判断：LLM 生成事件流会导致长篇一致性崩溃（第 40 集接不住第 1 集），而这正是规则引擎的优势。模型只用在 L6 写正文，以及 L3 一次性扩库（入库后即为纯代码资产）。
- **不建议一次性重构引擎**。A 档 39 个测试是宝贵资产，增量插入 + 保持可回归比推倒重来安全。
