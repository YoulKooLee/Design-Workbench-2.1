# session-handoff — 任务衔接交接包（Handoff Pack）

> **本文件是整个多智能体协作系统最关键的交接机制。**
> 当用户在某个智能体处理不下去、决定转交给另一个智能体，或复杂任务需要多智能体分工时：
> 1. 当前智能体在本文件写好「任务断点」（进度 / 已试错 / 推理注释 / 下一步 / 产物路径）。
> 2. 用户把相关段落复制给新智能体，或新智能体直接读本文件。
> 3. **新智能体必须优先读本文件**，看懂"任务进行到哪、为什么这么做、别踩什么坑、交付物在哪"，然后无缝续接。
> 4. 接手后如有新进展，回写本文件对应条目，让下一次转交也能继续。
>
> 协作规则总纲见 `agent-collaboration.md`，本文件是具体的交接记录。

---

## 一、怎么用（给转交者）

- 每次任务进行到关键阶段 / 结项 / 转交前，由当前智能体更新本文件。
- 每个任务一节，只保留**进行中**的；已完成的移到 `_archive/YYYY-MM/`。
- 更新时按下方「交接包模板」填全字段，**尤其是推理注释**——这是下游智能体理解你思路的唯一途径。
- 多智能体并行分工时，主管智能体在本节创建主任务，各工作者在自己的条目下更新子任务进度。

## 二、怎么用（给接手者）

1. 先看「当前进行中任务」一节，找到与你相关的条目。
2. 顺着「输入材料」和「接手必读文件」去读对应文件。
3. 重点看「推理注释」——**关键决策、已排除方案、已知风险、假设前提**，这些是前任的经验，不要重复试错。
4. 遵循「已知坑/别碰」。
5. 干完后，把进展回写本文件，并告知用户。
6. 遇到需要访问真实工程文件但找不到时，回 `README.md` / `projects-index.md` 查路径。

## 五、交接质量自检（转交前必过）

- [ ] 下游智能体**不看我的对话历史**，仅凭这个交接包能不能继续？
- [ ] 「推理注释」有没有写清"为什么"，而不仅是"做了什么"？
- [ ] 所有文件路径是不是绝对路径或本目录相对路径？
- [ ] 「已排除方案」有没有写清楚？（这是最有价值的信息）
- [ ] 验收标准是不是可判断的？（不是"做好就行"，而是具体可验证的条件）
- [ ] 需用户确认的点有没有列出来？（不要自己替用户做关键决策）

## 六、历史交接示例（已完成，归档参考）

> 以下是已完成任务的交接示例，展示"断点写得够细，接手者不提问就能干"。
> 更多历史 → `_archive/`。

### 示例：结构监测 Vite 构建报 `Cannot find module @rollup/rollup-win32-x64-msvc`

**基本信息**
- 来源：CodeBuddy
- 目标：任意
- 模式：路由分诊

**任务上下文**
- 目标：修复 arm64 Windows 上 vite build 因 rollup 架构错配失败
- 项目：`01-项目\结构监测`

**推理注释**
- 已排除方案：✗ `npm install rollup --force` → 无效（治标不治本，x64 包仍残留）
- 关键决策：必须删干净 node_modules + package-lock 后重装，让 npm 正确解析 arm64 原生包

**正解（接手者直接照做）**
1. 删除 `node_modules` + `package-lock.json`
2. `npm i`
3. 确认 `node_modules/@rollup/` 只含 `rollup-win32-arm64-msvc`，无 `-x64-*` 残留
4. **重启 53817** make-server

**验收**：`vite build` 不再报 x64 模块找不到。

## 七、维护约定

- **只有「进行中」任务放第三节**，最多 3 条（避免堆积）。
- 任务完成 → 移到 `_archive/YYYY-MM/` 归档。
- 新智能体接手后若任务方向变化，**先与用户确认再改**断点，不要擅自篡改前任的记录。
- 多智能体并行任务：主管智能体维护主任务条目，各工作者在子任务条目下更新，不要互相覆盖。
- 本文件与 `agent-collaboration.md` 保持一致，规则冲突以 `agent-collaboration.md` 为准。
