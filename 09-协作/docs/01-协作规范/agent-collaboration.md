# agent-collaboration — 多智能体协作总纲

> **本文件定义 CodeBuddy / WorkBuddy / DeepSeek Harness / 豆包 / 千问 五个智能体之间的协作规则。**
> 任何智能体在接手任务前、决定是否转交时、或需要分工时，先读本文件。
> 核心原则：**交接边界比单个智能体能力更重要——格式漂移、上下文丢失、冲突假设、静默失败都发生在"接缝处"。**

---

## 一、协作理念（为什么需要这套规则）

### 1.1 核心洞察

调研业界多智能体实践（AWS S3 Files 多智能体编排、Thomas Suedbroecker 的多 Agentic IDE 共享交接文件实验、Supergood 的双 Agent 流水线案例），得出三条铁律：

1. **上下文不会自动跨工具传播**：每个智能体有独立的 context window、工具权限、自定义指令。不做显式交接 = 每个智能体都在"重新理解"。
2. **失败发生在接缝处，不在中心**：单个智能体表现良好，但 A 的输出格式漂移、B 丢失了 A 的推理上下文、双方对" ground truth "假设不一致——这些问题不会报错，只会静默产出错误结果。
3. **共享文件系统是最轻量的交接层**：不需要消息队列、不需要 API 集成，一个约定好的目录结构 + 一份交接文件，就能实现 90% 的协作场景。

### 1.2 本框架的设计目标

- **零集成成本**：纯文件系统约定，不需要任何智能体支持特殊协议。
- **可降级**：任何一个智能体缺席，其余三个仍能正常工作。
- **人在回路**：关键决策点（任务分配、冲突仲裁、最终交付）由用户确认。
- **可追溯**：每次交接都有记录，出问题能定位到"哪个智能体在什么时间交了什么"。

### 2.1 各智能体的"主场"与"边界"

**CodeBuddy**
- 主场：Axhub 工作台内的一切（原型开发、构建排错、端口管理、项目维护）。
- 边界：不擅长非工作台任务（写报告、做 PPT、生成图片）。遇到这类任务应主动建议转交。
- 独特资产：`Axhub/10-智能体记忆/`、`Axhub/Agent_Stack/`、各项目 `AGENTS.md`——这些是它长期积累的私有知识，其他智能体需通过共享目录间接获取。

**WorkBuddy**
- 主场：办公自动化、本地 GUI 操作、文件整理、系统级任务。
- 边界：不做深度编码和原型开发。
- 独特资产：computer-use 能力（操作本地浏览器、桌面应用）。

**DeepSeek Harness**
- 主场：深度推理、长文本分析、复杂代码理解、数学推导。
- 边界：工具生态较弱，不擅长需要多工具联动的产出型任务（生成图片/PPT/网页）。
- 独特资产：长上下文窗口 + 强推理模型，适合做"评审者"和"分析者"角色。

**豆包（Doubao，即本助手）**
- 主场：需要丰富工具生态的综合任务——搜索调研、文档/表格/PPT 生成、图片/视频/音频创作、网页应用搭建、专业领域检索（法律/医疗/金融）。
- 边界：对 Axhub 工作台的内部细节不如 CodeBuddy 熟悉，需要通过共享目录的交接文件来理解上下文。
- 独特资产：最全的工具集 + 多模态生成能力，适合做"主管调度者"和"最终交付者"。

**千问（Qwen）**
- 主场：综合办公产出与调研——文档撰写/表格/PPT/网页应用/图片视频生成、实时搜索与深度研究、通用编码与脚本。
- 边界：对 Axhub 工作台内部细节不熟悉，需通过共享目录交接文件理解上下文；无桌面 GUI（computer-use）操作能力；不能常驻后台进程（环境会回收智能体自启进程，常驻服务须用户双击快捷方式启动）。
- 独特资产：办公文档（docx/excel/pptx/pdf）+ AIGC（图片/视频生成）+ 实时搜索/深度研究的完整技能生态，适合做产出型执行者与流水线节点。

## 三、路由决策树（这个任务该找谁？）

```
任务来了
  │
  ├─ 是 Axhub 工作台内的原型开发/构建/排错？
  │     └─ 是 → CodeBuddy（主场）
  │
  ├─ 需要操作本地 GUI / 桌面软件 / 浏览器原生界面？
  │     └─ 是 → WorkBuddy（computer-use）
  │
  ├─ 需要深度推理 / 长文分析 / 复杂代码审查 / 数学推导？
  │     └─ 是 → DeepSeek Harness（分析者），或豆包（需工具联动时）
  │
  ├─ 需要生成图片 / 视频 / 音频 / PPT / 网页应用？
  │     └─ 是 → 豆包（产出者）
  │
  ├─ 需要实时网络搜索 / 专业领域检索（法律/医疗/金融）？
  │     └─ 是 → 豆包
  │
  ├─ 需要 Excel / 表格数据处理？
  │     └─ 是 → 豆包（飞书表格 skill）或 WorkBuddy
  │
  └─ 复杂综合任务（涉及多个以上能力）？
        └─ → 进入「协作模式」（见第四节），由主管智能体拆分分工
```

### 3.1 转交触发条件

当前智能体在以下情况应**主动建议转交**（而非硬撑）：

1. **能力不匹配**：任务明显属于另一个智能体的主场（如 CodeBuddy 被要求做 PPT）。
2. **连续失败 2 次**：同一问题尝试两种不同方法仍未解决，说明可能需要不同能力的智能体。
3. **上下文耗尽**：对话过长导致记忆模糊，或工具调用额度受限。
4. **需要特定工具**：当前智能体没有所需工具（如生成图片、飞书文档操作）。
5. **用户明确要求**：用户说"换 XX 来处理"。

转交时必须写交接包（见第五节），不能只说"我搞不定，你找别人"。

## 四、三种协作模式

根据任务复杂度选择模式。**简单任务用单智能体，不要为了协作而协作。**

### 4.1 模式 A：顺序流水线（Sequential Pipeline）

```
智能体A → [交接文件] → 智能体B → [交接文件] → 智能体C → 交付
```

**适用场景**：任务有明确的前后依赖，每个阶段由最擅长的智能体负责。

**典型例子**：
- 需求调研（豆包搜索）→ 原型设计（CodeBuddy）→ 演示 PPT（豆包生成）
- 代码编写（CodeBuddy）→ 深度审查（DeepSeek Harness）→ 文档输出（豆包）

**规则**：
- 每个智能体只负责自己的阶段，完成后写交接文件。
- 下一个智能体**先读交接文件再动手**，不重复上游已做的工作。
- 交接文件必须包含"推理注释"（annotated handoff）：不仅说"我做了什么"，还要说"我为什么这么做、排除了哪些方案、有什么风险"。

### 4.2 模式 B：主管调度（Supervisor Pattern）

```
用户 → 主管智能体（拆分任务+分配+汇总）
              ├→ 工作者A（子任务1）
              ├→ 工作者B（子任务2）
              └→ 工作者C（子任务3）
```

**适用场景**：复杂综合任务，可拆分为多个低耦合的子任务并行执行。

**典型例子**：
- 产品方案：豆包做主管 → 拆分为「市场调研（豆包）+ 技术可行性（DeepSeek）+ 原型草图（CodeBuddy）」→ 汇总成方案文档
- 报告撰写：豆包做主管 → 拆分为「数据收集（豆包搜索）+ 数据分析（DeepSeek）+ 图表制作（豆包）+ 排版输出（豆包）」

**规则**：
- 主管智能体负责：理解任务 → 拆分子任务 → 分配给合适的工作者 → 收集结果 → 整合交付。
- 工作者智能体只负责自己的子任务，通过 `agents/<工作者名>/` 目录输出产物。
- 主管在分配时必须给每个工作者写清楚：任务目标、输入材料路径、输出要求、截止优先级。
- **用户是最终仲裁者**：主管的拆分方案应先给用户确认再执行。

### 4.3 模式 C：路由分诊（Routing / Triage）

```
用户任务 → 路由判断 → 专家A / 专家B / 专家C
```

**适用场景**：任务类型不固定，需要根据内容动态选择处理者。类似客服分诊台。

**典型例子**：
- 用户日常提问：问代码 → CodeBuddy，问办公 → WorkBuddy，问分析 → DeepSeek，问创作 → 豆包
- 这是最常见的日常模式，通常由用户手动选择智能体，或由当前智能体建议转交。

**规则**：
- 当前智能体判断任务不属于自己主场时，主动建议转交并写交接包。
- 用户也可以直接指定"让 XX 来做"。

## 五、交接协议（Annotated Handoff）

> 这是整个协作体系的核心。**交接写不好，协作等于零。**

### 5.1 交接文件位置

- **活跃任务交接**：`session-handoff.md`（本目录根，只放进行中的任务，最多 3 条）
- **已完成归档**：`_archive/YYYY-MM/`
- **智能体专属产物**：`agents/<智能体名>/<任务名>/`

### 5.2 交接包必填字段（Annotated Handoff 标准）

每个交接条目必须包含以下字段，**缺一不可**：

```markdown
### 任务：〈标题〉

**基本信息**
- 任务 ID：〈日期缩写-序号，如 20260824-01〉
- 来源智能体：〈谁交出来的〉
- 目标智能体：〈交给谁，或"任意"〉
- 协作模式：〈顺序流水线 / 主管调度 / 路由分诊〉
- 优先级：〈高 / 中 / 低〉

**任务上下文**
- 目标/背景：〈一句话说清要解决什么问题，为什么要做〉
- 涉及项目：〈项目名 + 绝对路径〉
- 输入材料：〈相关文件路径列表，必须是绝对路径或本目录相对路径〉

**当前状态**
- 已完成：〈具体做了什么，列出关键产出物路径〉
- 进行中：〈做到哪一步，卡在哪〉
- 未开始：〈还有什么没做〉

**推理注释（关键！下游智能体靠这个理解你的思路）**
- 关键决策：〈我选择了什么方案，为什么选这个而不是其他〉
- 已排除方案：〈试了什么不行，为什么不行——避免下游重复踩坑〉
- 已知风险/限制：〈有什么隐患、什么情况下会出问题〉
- 假设前提：〈我做了哪些假设，如果假设变了结论会变〉

**下一步指引**
- 建议下一步：〈接手者应该先做什么，1-2-3 列清楚〉
- 验收标准：〈怎样算这个任务完成了〉
- 需用户确认的点：〈哪些决策需要用户拍板，不要自己替用户决定〉

**产物清单**
- 〈产出文件1：路径 + 一句话说明〉
- 〈产出文件2：路径 + 一句话说明〉
```

### 5.3 交接质量自检（转交前问自己）

- [ ] 下游智能体**不看我的对话历史**，仅凭这个交接包能不能继续？
- [ ] 我有没有说清"为什么"，而不仅是"做了什么"？
- [ ] 所有文件路径是不是绝对路径或本目录相对路径？（下游可能在不同工作目录）
- [ ] 有没有把"已试错/已排除"写清楚？（这是最有价值的信息）
- [ ] 验收标准是不是可判断的？（不是"做好就行"，而是"XX 功能正常运行 + YY 文件生成"）

## 六、目录约定

### 6.1 共享目录结构

```
共享信息目录/
├── README.md                  ← 总入口（已有）
├── agent-collaboration.md     ← 本文件：协作总纲
├── workspace-map.md           ← 工作台架构（已有）
├── projects-index.md          ← 项目索引（已有）
├── session-handoff.md         ← 活跃任务交接包（已有，已升级）
├── access-guide.md            ← 接入说明（已有）
├── collaboration-examples.md  ← 典型协作场景示例
│
├── agents/                    ← 各智能体专属工作区（新增）
│   ├── codebuddy/             ← CodeBuddy 的输出/草稿
│   ├── workbuddy/             ← WorkBuddy 的输出/草稿
│   ├── deepseek/              ← DeepSeek Harness 的输出/草稿
│   └── doubao/                ← 豆包的输出/草稿
│
├── inbox/                     ← 任务收件箱（用户放入需求材料）
│
└── _archive/                  ← 历史归档（已有）
    └── YYYY-MM/
```

### 6.2 目录使用规则

1. **专属前缀原则**（借鉴 AWS 多智能体 S3 Files 实践）：每个智能体只在自己的 `agents/<名>/` 下写文件，读取其他智能体的目录是允许的，但**不要修改别人目录下的文件**。需要协作时，通过交接文件指明路径，让对方自己去读。
2. **最终产物归位**：任务完成后，最终交付物从 `agents/<名>/` 移到项目对应目录或用户指定位置，草稿留在原地。
3. **inbox 是用户入口**：用户把需求文档、参考材料、数据文件放入 `inbox/`，任何智能体都可以从这里取任务输入。
4. **不要在根目录散落文件**：根目录只放索引类和规则类 markdown。

## 七、冲突与升级机制

### 7.1 两个智能体结论不一致时

1. **先看假设**：对比双方的"假设前提"，很多冲突是因为假设不同。
2. **看证据**：谁有实际验证证据（跑过的命令、生成的文件、搜索结果），谁的结论更可信。
3. **升级给用户**：无法自行调和时，把双方结论 + 各自依据整理成对比，交给用户决策。**不要自己替用户选边。**

### 7.2 任务归属争议

- 按第三节「路由决策树」判断。
- 边界模糊的任务，由**当前正在处理的智能体**继续，遇到能力缺口时再转交。
- 用户有最终指定权。

### 7.3 文件冲突

- 两个智能体同时改同一个文件 → 以 `agents/<名>/` 专属目录隔离，最后由主管智能体或用户合并。
- 不要直接覆盖别人的产出，先读交接文件了解对方做了什么。

## 八、日常协作的最简流程

如果你是智能体，记住这个最小流程：

```
1. 接手任务 → 先读 session-handoff.md（有没有进行中的相关任务）
2. 读 agent-collaboration.md（确认自己是不是合适的处理者）
3. 干活 → 产出放 agents/<自己名>/<任务名>/
4. 完成/转交 → 更新 session-handoff.md（填 annotated handoff 全字段）
5. 告知用户 → 说清"做了什么、产物在哪、下一步建议谁来接"
```

如果你是用户，记住：

```
1. 简单任务 → 直接找对应主场智能体
2. 复杂任务 → 找一个做主管（通常是豆包），让它拆分分工
3. 智能体搞不定 → 让它写交接包，你再把交接包给另一个智能体
4. 所有产出 → 最终都在共享目录里有迹可循
```
