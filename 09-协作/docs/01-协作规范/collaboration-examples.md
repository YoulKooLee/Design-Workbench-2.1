# collaboration-examples — 典型协作场景示例

> 本文档通过真实场景演示四个智能体如何配合。每个场景包含：任务描述、协作模式选择、具体流程、交接包示例。
> 规则总纲见 `agent-collaboration.md`，本文件是"怎么用"的实战参考。

## 场景一：CodeBuddy 搞不定 → 豆包接手（最常见的转交）

### 任务
用户在 CodeBuddy 里要求"给结构监测项目做一个项目汇报 PPT"。CodeBuddy 做了两轮发现自己不擅长 PPT 生成，决定转交。

### 协作模式
路由分诊（CodeBuddy → 豆包）

### 流程

```
1. CodeBuddy 判断：PPT 生成不是我的主场（能力矩阵显示豆包主力）
2. CodeBuddy 写交接包到 session-handoff.md：
   - 目标：结构监测项目汇报 PPT
   - 输入材料：项目路径、已有的 dashboard 原型截图、需求文档
   - 已完成：整理了项目核心数据（24项监测项、告警逻辑）
   - 推理注释：PPT 应包含项目背景、技术架构、功能演示、数据展示四部分
   - 产物：已导出的原型截图放在 agents/codebuddy/结构监测PPT素材/
3. 用户切换到豆包，说"看共享目录的交接包，帮我做 PPT"
4. 豆包读 session-handoff.md → 读素材 → 用飞书幻灯片 skill 生成 PPT
5. 豆包完成后回写交接包，告知用户产物位置
```

### 交接包关键片段

```markdown
### 任务：结构监测项目汇报 PPT

**基本信息**
- 来源：CodeBuddy → 目标：豆包
- 模式：路由分诊

**任务上下文**
- 目标：生成一份结构监测项目的汇报 PPT（约15页），用于客户演示
- 项目：C:\Users\游翔\Documents\AI work\产品设计工作台\01-项目\结构监测

**推理注释**
- 关键决策：PPT 结构建议为 项目背景→技术架构→功能演示→数据展示→总结
- 已排除：直接用代码生成 PPT（CodeBuddy 无此能力，试了两次效果差）

**产物清单**
- 原型截图：agents/codebuddy/结构监测PPT素材/（5张 dashboard 截图）
- 项目数据摘要：agents/codebuddy/结构监测PPT素材/数据摘要.md
```

## 场景二：复杂产品方案（主管调度 + 并行分工）

### 任务
用户要做一个"企业应急管理系统"的完整产品方案，包含市场调研、技术架构、原型设计、方案文档。

### 协作模式
主管调度（豆包做主管，拆分后并行分工）

### 流程

```
1. 用户找豆包："帮我做企业应急管理系统的产品方案"
2. 豆包（主管）分析任务，拆分为 4 个子任务：
   ① 市场调研与竞品分析 → 豆包自己（搜索能力强）
   ② 技术架构设计 → DeepSeek Harness（深度推理强）
   ③ 核心页面原型 → CodeBuddy（Axhub 主场）
   ④ 方案文档整合 + PPT → 豆包自己
3. 豆包先跟用户确认拆分方案和优先级
4. 用户确认后，豆包在 session-handoff.md 创建主任务，
   并分别给 DeepSeek 和 CodeBuddy 写子任务交接包
5. 三个智能体并行工作，产出各放 agents/<自己名>/应急管理方案/
6. 豆包收集各方产出，整合成完整方案文档 + 汇报 PPT
7. 交付用户，归档交接包
```

### 主管给工作者的子任务交接包示例

```markdown
### 子任务：应急管理系统技术架构设计（给 DeepSeek Harness）

**基本信息**
- 来源：豆包（主管）→ 目标：DeepSeek Harness
- 模式：主管调度（子任务②）
- 主任务 ID：20260824-01

**任务上下文**
- 目标：设计企业应急管理系统的技术架构，涵盖预案/演练/处置三大模块
- 输入材料：
  - inbox/应急管理需求.docx（用户提供的需求）
  - agents/doubao/应急管理方案/市场调研摘要.md（豆包已完成的调研）

**要求**
- 输出：技术架构文档（Markdown），含系统架构图描述、模块划分、接口设计、数据流转
- 重点：Web管理端 + 移动端的双端架构，预案等级划分（二级/三级）的状态机设计
- 产出放：agents/deepseek/应急管理方案/技术架构.md

**推理注释（主管给的上下文）**
- 用户是产品经理，方案需要能落地开发，不要太学术
- 参考了消防/实验室事故/设备故障三类突发事件场景
- 后续 CodeBuddy 会基于你的架构做原型，模块划分要清晰可映射到页面
```

## 场景三：顺序流水线（调研 → 原型 → 文档）

### 任务
用户要为一个新的"智慧医疗慢病监管大屏"做从需求到原型的完整产出。

### 协作模式
顺序流水线（豆包 → CodeBuddy → 豆包）

### 流程

```
1. 豆包：搜索调研高血压/糖尿病/脑卒中十大病种的分类和监测指标
   → 产出：agents/doubao/慢病大屏/调研摘要.md
   → 写交接包给 CodeBuddy

2. CodeBuddy：基于调研结果，在 Axhub 工作台创建新项目并做 dashboard 原型
   → 产出：Axhub/01-项目/慢病监管/ 下的原型代码
   → 写交接包给豆包（含预览地址、已实现的功能、未完成的部分）

3. 豆包：基于原型生成项目说明文档 + 演示截图整理
   → 产出：agents/doubao/慢病大屏/项目说明.docx
   → 交付用户
```

### 流水线交接的关键点

- **每一段交接都必须有推理注释**：豆包告诉 CodeBuddy"我为什么选这十个病种"，CodeBuddy 告诉豆包"我为什么用堆叠图而不是折线图"。
- **下游不重新做上游的工作**：CodeBuddy 不需要重新搜索病种分类，直接读豆包的调研摘要。
- **如果某一段卡住**：在交接包里写清卡在哪，用户可以决定是让当前智能体继续还是换一个。

## 场景四：DeepSeek 做代码审查（专家评审）

### 任务
CodeBuddy 完成了一个复杂功能（如数字孪生的告警联动规则引擎），需要深度代码审查。

### 协作模式
顺序流水线（CodeBuddy → DeepSeek Harness → CodeBuddy）

### 流程

```
1. CodeBuddy 完成编码，自测通过
2. CodeBuddy 写交接包给 DeepSeek Harness：
   - 代码路径、设计思路、已知顾虑
   - 要求：审查架构合理性、安全性、性能隐患
3. DeepSeek Harness 深度审查代码，输出审查报告：
   - agents/deepseek/告警引擎审查/审查报告.md
   - 含问题清单（严重/中等/建议）+ 改进建议
4. DeepSeek 写交接包回 CodeBuddy（或直接给用户）
5. CodeBuddy 根据审查报告修改代码
6. 修改完成后可再交 DeepSeek 复审一轮
```

### 审查交接包示例

```markdown
### 任务：告警联动规则引擎代码审查

**基本信息**
- 来源：CodeBuddy → 目标：DeepSeek Harness
- 模式：顺序流水线（审查阶段）

**任务上下文**
- 目标：审查数字孪生项目的告警联动规则引擎代码
- 代码路径：C:\Users\游翔\Documents\AI work\产品设计工作台\01-项目\Digital Twin\数字孪生\src\prototypes\rule-engine\

**推理注释（提交者给审查者的上下文）**
- 关键决策：规则引擎采用事件驱动架构，告警触发后通过规则链匹配联动动作
- 已知顾虑：规则嵌套层级较深（最多5层），担心性能和可维护性
- 假设前提：单项目同时活跃告警不超过100条
- 请重点审查：规则匹配算法的时间复杂度、并发安全、规则配置的校验逻辑

**要求**
- 输出：审查报告，按 严重/中等/建议 三级分类
- 每个问题给出：位置（文件+行号）、问题描述、改进建议
- 产出放：agents/deepseek/告警引擎审查/审查报告.md
```

## 场景五：WorkBuddy 处理本地 GUI 任务

### 任务
用户需要批量整理本地文件、操作某个桌面软件、或在浏览器里完成重复性操作。

### 协作模式
路由分诊（→ WorkBuddy）

### 典型场景

- **批量文件整理**：用户说"把下载文件夹里的 PDF 按月份分类"→ WorkBuddy 用 computer-use 或脚本操作。
- **桌面软件操作**：用户说"帮我在 Excel 里做一个数据透视表"→ WorkBuddy 操作本地 Excel。
- **浏览器自动化**：用户说"帮我登录某个后台系统导出数据"→ WorkBuddy 用 browser-use 操作。

### 与其他智能体的配合

- WorkBuddy 完成操作后，如果产出需要进一步分析（如导出的数据需要做图表），写交接包给豆包。
- 如果 WorkBuddy 操作中发现需要写复杂脚本，转交 CodeBuddy 或豆包。

## 通用原则总结

| 原则 | 说明 |
|---|---|
| **先判断要不要协作** | 简单任务单智能体搞定，不要为了协作而协作 |
| **交接包是硬通货** | 每次转交必须写全字段，尤其是推理注释 |
| **专属目录不互改** | 各智能体只写自己的 agents/<名>/，读别人的可以 |
| **用户是最终仲裁者** | 任务拆分、冲突解决、最终交付都需用户确认 |
| **产出可追溯** | 所有中间产物和最终交付都在共享目录有记录 |
| **搞不定就转** | 连续失败2次或能力不匹配，主动建议转交，不要硬撑 |
