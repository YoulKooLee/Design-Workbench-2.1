### 2.2 基线链（定稿）

```
客户需求 → PRD（产品探索真源）→ SRS（需求规格真源，驱动研发链路）
```

## 三、上下文装配协议（对 P3 · 本终稿最核心的产出）

### 3.1 装配公式（三层）

```
【常驻基线】每次会话都在，条目级摘要，禁止全文灌入
  1. 需求清单     feature-list 条目（id + 一句话 + 优先级 + 状态）
  2. 数据模型     实体清单 + 关系（1:N / N:M）+ 关键字段（概念 ER，引用 hld-spec 数据架构）
  3. 总体架构     分层 + 模块清单 + 模块依赖（每模块标注端：web / mobile / both）
  4. 业务架构     核心业务流程 + 角色 + 领域边界
  5. 模块间数据流 接口契约表（源模块 → 目标模块 → 数据实体 → 方向）
  6. 已完成模块快照 见 §五（每条 ≤ 300 字）

【模块滑窗】进入某模块时装配，离开时卸载
  7. 当前模块设计方案   该模块 HLD 章节 + LLD
  8. 该模块组件清单     由 manifest 反查（§六）
  9. 上下游契约切片     只取与本模块相关的接口行，不取整表

【按需检索】永不常驻
  10. 过程讨论 / 历史会话 / 被否决方案（§四过程层）
  11. 其他模块的设计细节
  12. src/themes 全量、组件库全量、Vibe vendor（§八）
```

### 3.2 预算与硬红线

| 层 | 体量 | token（估，1 token≈2 中文字符） | 占 200K 窗口 |
|---|---|---|---|
| 常驻基线 1-6 | ≤ 40 KB | ≈ 20K | 10% |
| 模块滑窗 7-9 | ≤ 20 KB | ≈ 10K | 5% |
| AGENTS.md + 系统提示（实测启动基线） | 33.5 KB | ≈ 14.4K（**实测**） | 7.2% |
| **合计** | | **≈ 44K** | **≈ 22%** |
| 留给生成与对话 | | ≈ 156K | 78% |

**硬红线（必须是可校验断言，不是文字警告）：**
- 常驻基线 ≤ 40 KB / 20K token
- 单模块装配（基线 + 滑窗）≤ 120 KB / 60K token
- **超限 → 阻断并强制压缩，不允许"继续但注意"**

## 四、写入侧三态门禁（对 P1 · deepseek v1 未覆盖）

**病根在写入侧**：读取分层再细，也拦不住智能体把讨论写进 PRD。三条规则：

### 4.1 三态标注（写入基线前必须归类）

| 标记 | 内容 | 去向 |
|---|---|---|
| `[事实]` | 客户原话 / 已签字需求 / 实测数据 | **可进基线** |
| `[讨论]` | 方案对比、试错过程、智能体推断 | **只能进过程层**（`project-memory.md` 讨论小节） |
| `[否决]` | 被否方案 + **否决理由（必填）** | **只能进过程层**，压缩时理由必须保留一行 |

### 4.2 来源标注

PRD/SRS 每条需求带来源（客户第 N 次沟通原话 / 设计讨论结论 / 智能体补全待确认）。**`[智能体补全待确认]` 的内容不得作为 `SPEC_SOURCE` 真源。**

### 4.3 压缩时保留规则

- 过程层可丢，**基线层不可丢**
- `[否决]` 条目压缩时**必须保留理由一行** —— 否则失忆后重走弯路（这正是 P2 的一个成因）

### 4.4 落地载体【T1 新增】

**不新建 `DECISIONS.md`/`CHANGELOG.md`/`TASKS.md`**（deepseek v1 原方案，已同意撤回）。改为在现有 `project-memory.md` 内设 3 个结构化小节，并显式声明属过程层：

```markdown
## 决策记录（过程层·压缩可丢·永不进基线）
## 变更流水（过程层·压缩可丢·永不进基线）
## 任务进度（过程层·与 compaction-recovery.md 对齐）
```

理由：`AGENTS.md:528-575` 已有五层记忆 + 门禁三问；`.agents/rules/compaction-recovery.md` 恢复检查表第 1 项就是「TaskList 中 in_progress 任务」—— 新建 `TASKS.md` 会与之形成**双份进度记录**，压缩恢复时不知以哪个为准。用现有文件的小节，同时给 P1 的"过程讨论"一个明确去处，不再飘进 PRD。

## 五、模块完成快照 + 数据流闭环压缩闸门（对 P2 · 跨端失忆解药）

### 5.1 模块完成快照【T1 新增】

每个模块**验收通过后**产出 ≤300 字快照，写入常驻基线第 6 项：

```markdown
## 模块快照：<模块名>（端：web | mobile | both）
- 状态：已完成 / 进行中（完成度 %）
- 职责：一句话
- 对外接口：契约（输入实体 → 处理 → 输出实体），不写实现
- 依赖模块：上游 X（取什么数据）、下游 Y（给什么数据）
- 数据实体：本模块读写的实体名（与数据模型对齐）
- 关键决策：≤3 条，只写结论 + 一句理由
- 跨端差异：web 已实现的部分，mobile 需注意什么（组件/交互/字段差异）
- 未完成 TODO：≤3 条
```

**跨端失忆的解法**：移动端启动「用户管理」模块时，装配 = 常驻基线（含 web 端该模块快照）+ 移动端滑窗 → **读到 web 端的接口契约与跨端差异，不需重读 web 端实现** → 不失忆，也不爆上下文。

### 5.2 数据流闭环 = 压缩闸门【采纳 deepseek v1 §四，升级为门禁】

deepseek v1 §四 的判据（**A 的输出都能被某模块接住、无孤儿数据、无凭空数据**）是真增量，qwen 实测现有 `hld-spec.md` 11 项质量清单**无此闭环判据**。

**升级为压缩闸门**（关键设计）：

```
模块数据流闭环验收通过 → 才写模块快照 → 才允许压缩上下文 → 才进下个模块
```

这样用户说的「模块完成就压缩」有了**可判定的"完成"定义**，不由智能体自报。落地：补进 `hld-spec.md` 质量清单作**第 12 项**。

## 六、组件 ↔ 文档映射 manifest（采纳 deepseek v1 §五 + qwen 跨端扩展）

### 6.1 用途

改细节时**反查 manifest → 只加载"单模块 + 单组件说明"，不整库重读** —— 正是解决 qwen 三重审查报告 §3.2 溢出炸点的正确思路，与 context-budget hook 互补。

### 6.2 字段（qwen 扩 `platforms` + `status` 支持跨端）【T1 新增】

```json
{
  "component": "UserTable",
  "module": "user-management",
  "docRef": "SRS#3.2 / HLD#user-management",
  "platforms": ["web", "mobile"],
  "dataEntities": ["User", "UserRole"],
  "status": "web:done | mobile:todo"
}
```

`platforms` + `status` 让"web 做完、mobile 未做"在 manifest 里可见，滑窗装配据此只加载相关切片。

### 6.3 与现有 4 个 json 的关系（必须声明，否则又是双份真源）

现有 `component-registry.json`(4.6KB)、`components.catalog.json`(58KB)、`layout.manifest.json`、`pages.catalog.json` 都在**组件库侧**，无"组件→文档章节→模块"反向映射。**新 manifest 引用它们、不复制它们**：manifest 只存映射关系（component→docRef/module/platforms），组件本体仍由组件库 json 定义。落地时在 manifest 头部注明这层引用关系。
