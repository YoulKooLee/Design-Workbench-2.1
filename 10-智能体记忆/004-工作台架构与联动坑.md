# 004-工作台架构与 Make 联动坑

> 类目：Axhub 工作台（Make 管理服务端 + dev stack 启动流程）的架构事实与联动 bug 根因。
> 与具体项目原型设计（如结构监测）无关，挪自结构监测任务的 AI 内部记忆，集中沉淀到工作台记忆库。

## 1. 工作台整体架构 [原ID 73515890]

- 工作台根：`C:\Users\游翔\Documents\AI work\Axhub\`（01-项目/02-模板/axhub-manager/06-运行脚本）。
- 环境：Windows arm64 + Node v24+；原生包必须匹配 arm64。端口：工作台 7788、Make 53817、Vite 517xx。
- 各项目 node_modules 里 esbuild/rollup 错配会 ERR_CONNECTION_REFUSED / `Cannot find module @rollup/rollup-win32-arm64-msvc`，用 `npm install` 解决，不要删锁文件。

## 2. 53817 make-server active 错位根因与根治补丁 [原ID 30964272]

- 根因：53817 make-server 全局单例。`activeProjectId` 被其他项目 dev stack 启动时的 `setActiveProject`（cli.mjs，无保护）覆盖，导致本项目预览代理 `resolveRuntimeOriginForProxy` 拿不到正确 `runtime.origin` → 503「Make 客户端未启动」→ 预览页缺 bootstrap + `axhub.quickEdit` handler → 握手失败。
- 关键事实：
  - `/prototypes/*` 强制要求 projectId（URL 或 referer），否则 503。
  - `axhub.quickEdit` 握手处理器在 make-server 顶层路由 `/runtime/quick-edit.js`，与 dev-template-bootstrap 无关。
  - `__RUNTIME_ORIGIN__` 不在预览页是预期的。
  - 注册表 `~/.axhub/make/projects.json`，activeProjectId 即当前 active。
- 已实施根治补丁（2026-08-26）：给 cli.mjs 的 `setActiveProject(id)` 加保护——当前 active 项目 runtime 仍在运行、且新目标项目尚未运行时，不抢占 activeProjectId（用 `readServerInfo`+`isLiveMakeClientRuntime` 同步判断）。
  - 原文件备份：`C:\Users\游翔\Documents\AI work\Axhub\03-备份\make-cli.mjs.pre-patch.bak`
  - 重装后一键复打：`C:\Users\游翔\Documents\AI work\Axhub\03-备份\apply-active-guard.mjs`（node 运行）
  - 风险：想把 active 切到一个"尚未运行"的项目会被保护拦住（需该项目 runtime 起来后再切），属可接受取舍。
- 旧记忆「isReusableRuntimeOrigin 严格匹配→端口冲突」因果链在 v0.6.21 不成立（cli.mjs 无该函数），作废。

## 3. 启动开发栈必点两次根因与修复 [原ID 76268127]

- 根因不是 syncMakeActiveProject 失效，而是**状态机没有"启动中"过渡态**：POST `/api/projects/open` 时 spawn PS1（首次 70 秒/后续几十秒），此刻 Vite 还没起来、心跳文件不存在；前端每 5 秒轮询 `GET /api/context/current` 触发 `reconcileWorkspaceCtx`，`isProjectAlive` 返回 false → 立即把项目降级 stopped。等 PS1 完成时项目早被标 stopped，且 Make active 未切 → 浏览器看到「Make 客户端未启动」。第二次点启动时 PS1 检测到 Vite 已就绪秒 done，syncMakeActiveProject 立即生效 → 成功。
- 修复：
  1. 新增 `starting` 状态，`onProjectStarted` 把启动项目设为 starting（而非直接 editing/active）。
  2. `reconcileWorkspaceCtx` 对 starting 不降级（若 Vite 已起则补升级 editing/active）。
  3. PS1 stdout 含 `AXHUB_LAUNCH_STATUS: done` 时调 `markProjectRunning` 把 starting→editing/active + syncMakeActiveProject。
  4. 前端 ctxStatusMap 加 `starting:'启动中'`。
- 补充（2026-09-03）：另有一条**独立根因**也会表现为「启动失败 / 要点两次 / 点了没反应」——PS1 读心跳 JSON 未指定 UTF-8 编码，见本文件第 5 条。二者表现相似但成因不同，排查时先按第 5 条验证 `Read-JsonFile`。

## 4. Make 联动时序：syncMakeActiveProject 必须等依赖就绪 [原ID 52220761 / 79558564]

- 启动开发栈没启动 Make 客户端的根因：server.mjs 的 `/api/projects/open` 在 spawn PS1 之后立即调 `syncMakeActiveProject(relative)`，但 Make 53817 是 PS1 步骤 3 才启动的，HTTP 探测 status=0 失败。
- 修复：在 `child.stdout` 监听里加判断——若输出含 `AXHUB_LAUNCH_STATUS: done`（PS1 8 步全走完、Make 已就绪），再调一次 `syncMakeActiveProject(relative)`。原 spawn 后调用保留作 best-effort。
- activeProjectId 错位（指向 demo-showcase 而非刚启动的项目）→ 浏览器 `http://localhost:53817/?projectId=xxx` 显示「Make 客户端未启动」。
- 手动验证：`PUT http://localhost:53817/api/projects/active {projectId:"xxx"}` 可立即生效。

## 5. 【PS1 读 JSON 必须显式 UTF-8】[新增 2026-09-03]

- 现象：项目名 **9 个汉字**（奇数个 UTF-8 字节）必现「点启动开发栈 → 等 120 秒 → 失败」；4 字项目（结构监测/健康档案/数字孪生）一切正常。
- 根因：`06-运行脚本/launch-project.ps1` 的 `Read-JsonFile` 用 `Get-Content $path -Raw`（未指定编码），PowerShell 5.1 默认按 **ANSI/GBK** 解码 UTF-8 心跳文件；中文路径字节错位后**吞掉 JSON 里的转义反斜杠**，剩下那个 `\` 把闭合引号转义掉 → `ConvertFrom-Json` 抛错 → 返回 `$null`。
  - 实测报错：`jsonParse=FAILED: 传入的对象无效，应为":"或"}"` + `"projectRoot": "...宕傚北鍥藉瀹為獙瀹ら」鐩?,`（闭合引号被吞）。
  - 奇偶性不是简单按「项目名长度」判定，而是**整条路径的中文 UTF-8 字节序列**与后续字节的配对关系；同一台机器上项目名是唯一变量。
- 连锁故障链（一个 bug 拖垮整条启动流程）：
  1. `Test-ViteAlive` 读不出 port → 第 2 步打印「未检测到可复用的 Vite」（**尽管 Vite 活得好好的**）
  2. 第 6 步 `Stop-ProjectVite` **杀掉健康的 Vite** → 端口尚未释放就启动新 Vite + `--strictPort` → `Error: Port 51720 is already in use` → 崩溃
  3. 等待循环里的 `Get-JsonPort` 同样读不出 → **即使新 Vite 起来了也判「未就绪」** → 两次 60 秒超时 → throw
  4. throw 导致**第 7 步注册流程根本不执行** → 项目永不注册进 Make（见第 6 条）
- 已实施的修复（三处，均在 launch-project.ps1）：
  1. `Read-JsonFile` → `Get-Content -Raw -Encoding UTF8`
  2. `Test-ViteAlive` 增加兜底：JSON 解析失败但心跳 `mtime < 20s` 时，用 `Get-ProjectVitePort` 从进程列表反查本项目 Vite 真实端口并复用，避免杀掉健康进程
  3. `Stop-ProjectVite` 之后轮询 `Test-PortFree`（200ms × 50 次，最多 10 秒），等端口真正释放再启动
- 铁律：PS1 里凡是读取 `.axhub/make/*.json` 的地方，必须带 `-Encoding UTF8`。
- 验证标准：启动日志第 2 步出现「检测到本项目 Vite 已在运行 (端口 XXXX)，直接复用」且总耗时 < 20 秒。

## 6. 【Make 注册后必须切 active】[新增 2026-09-03]

- 现象：Vite 正常、项目也已注册，浏览器打开仍显示「管理服务尚未启动 / 启动管理服务」。
- 根因：`launch-project.ps1` 第 7 步只做了 `POST /api/projects/make/register-existing`（或 PATCH 更新），**没有调用 `PUT /api/projects/active`**；Make 53817 是全局单例多项目共用，activeProjectId 仍停在别的项目上。
- 双重失守：Vite 端的 `vite-plugins/autoStartMakeServerPlugin.ts` 里 `registerOfficialProject()` 是**有** `activateProject()` 的，但 PS1 启动时设了 `AXHUB_MAKE_SKIP_AUTO_START_SERVER=1`，该插件跳过自动注册 → 两端都没激活。
- 修复：第 7 步注册/更新之后紧跟 `PUT /api/projects/active {projectId}`。
- 判据：启动完成后 `GET http://localhost:53817/api/projects` 的 `activeProjectId` 必须等于本项目 id，且本项目 `runtimeStatus.running === true`。
- 排障入口：项目不在 `/api/projects` 列表里 = 第 7 步没跑到（通常是被第 5 条的 throw 打断）；在列表里但 active 不是它 = 没做 active 切换。

## 7. 【新建/复制项目丢点文件：filter 子串误伤】[新增 2026-09-03]

- 现象：新建的项目完全没有 `.gitignore`、`.gitkeep`、`.git-template-backup/`（实测崂山项目丢失 35 个这类文件）。
- 根因：`axhub-manager/server.mjs` 两处 `fs.cpSync` 的 filter 用 `!lp.includes('\\.git')` 做**子串匹配**来排除 `.git` 目录，连带误伤一切以 `.git` 开头的合法文件。
- 修复：改为 `path.basename(lp) !== '.git'` 精确匹配。涉及两处：`POST /api/projects`（从模板新建）与 `/api/projects/copy`（项目复制）。
- 连带坑：结构监测自己也是在缺陷期创建的，它同样丢了这 5 个点文件；所以用结构监测派生的新模板，必须**先从旧模板补回** `.gitignore`、`admin/.gitignore`、`admin/.husky/_/.gitignore`、`admin/public/annotations/.gitkeep`、`src/resources/.gitkeep`、`.agents/skills/drawio-generator/.gitignore`。
- 老模板的 `admin/.gitignore` 是 **GBK** 编码，补回后需转 UTF-8 无 BOM。

## 10. 【pnpm 布局：依赖真实内容在 .pnpm 里，别只看顶层】[新增 2026-09-03]

- 识别特征：项目根目录存在 `pnpm-lock.yaml`，或 `package.json` 里有 `"packageManager": "pnpm@..."` → 该项目用 pnpm 安装。当前模板锁定 `pnpm@10.20.0` / `lockfileVersion: '9.0'`。
- 目录结构：
  - `node_modules/.pnpm/` = 虚拟存储（virtual store），每个子目录是一个包的**真实内容**，命名 `<包名>@<版本>[_<peer依赖哈希>]`，scope 包的 `/` 被替换成 `+`（如 `@babel+core@7.29.7`）；名字过长会被截断后接哈希。
  - `node_modules/<包名>` 顶层只是**符号链接**，指向 `.pnpm/<包名>@<版本>/node_modules/<包名>`。
  - 内容是硬链接到 pnpm 全局 store，**磁盘占用不按目录大小累加**。
- **排查坑（实测踩过）**：判断原生模块是否齐全时，只看 `node_modules/@rollup`、`node_modules/@esbuild` 顶层会**误判为"缺失"**——pnpm 布局下顶层只放 package.json 里直接声明的包。必须同时扫 `node_modules/.pnpm/`。PS1 第 5 步的 `Test-NativePresent` 已内置 pnpm 分支（递归扫 `.pnpm` 匹配包名叶节点），不要绕过它自己写检测。
- **禁止在 pnpm 项目里跑 `npm install`**：npm 会把 pnpm 装的包判定为"多余包"批量删除（实测一次删掉 67 个）。PS1 第 4 步已按 `pnpm-lock.yaml` / `packageManager` 自动分流到 `npx -y pnpm@10 install`。
- 模板必须**同时**带 `package.json` 的 `packageManager` 和 `pnpm-lock.yaml`，两者缺一会让新项目重新解析依赖、装到未验证的新版本。带 lock 时 pnpm 会装出**双架构**原生模块（`@rollup/rollup-win32-arm64-msvc` + `-x64-msvc`、`@esbuild/win32-arm64` + `-x64`），比 npm 只装一套架构更健壮。
- 体积大户参考：`lucide-react`（7708 文件）、`caniuse-lite`（1682）、`@babel/helpers`（502）、`typescript`（264）。

## 11. 【Make 陈旧心跳记录 → 全局启动失败】[新增 2026-09-07]

- 现象：**所有项目**的「启动开发栈」都卡在第 7 步 `仍等待 Make 就绪… [无响应]`，等满 60 秒报 `Make 服务未在 60 秒内就绪（端口 53817）`。Vite 正常起来（第 6 步 ok），**反复点击无法自愈**。
- 根因：Make 异常退出（关机 / 强杀 / 休眠唤醒）后，在 `~/.axhub/make/.admin-server-info.json` 残留一条已死实例的记录。新 Make 启动时做单例校验会报
  `The recorded Axhub Make server could not be identified safely.` 并 **exit 1**。
  PS1 用 `Start-NodeBackground` 启动 Make 时**丢弃了它的输出**，所以日志里只能看到"无响应"，看不到真实报错。
- 触发时机：**电脑重启或休眠后**，只要 Make 没正常退出，下一次启动开发栈必然失败。这是会反复踩的坑，不是偶发。
- 快速判定：`netstat` 看 53817 **无监听** + 第 7 步 60 秒超时 → 直接检查 `~/.axhub/make/.admin-server-info.json` 是否残留（看里面 pid 是否还活着）。
- 手动复现真实报错（排查必用）：`node <项目>/node_modules/@axhub/make/bin/cli.mjs --no-open --port 53817`，前台跑就能看到上面那句英文报错；不要只看 launch 日志。
- 已实施的双保险：
  1. **自愈**（`launch-project.ps1` 第 3 步）：进入"端口空闲"分支时，若存在残留心跳记录，备份重命名为 `.stale-<时间戳>` 后再启动 Make。实测强杀 Make 后触发启动，18 秒自愈成功（此前需等 60 秒且必然失败）。
  2. **手动兜底**：工作台顶部新增「⟳ 重启 Make」按钮 → `POST /api/make/restart`，流程为 停止 53817 进程 → 清理残留心跳 → 重新启动 → 轮询 health 最多 30 秒。实测 ok，且重启后 `activeProjectId` 保持不变。
- 教训：PS1 里凡是用 `Start-NodeBackground` 起的后台进程，出错时输出全丢，排障成本极高。后续如再加后台启动，务必让它把 stdout/stderr 落到 `07-日志`。
